## 2. 재고 부족 이벤트 (`StockRunningLowEvent`) — catalog 소유

### 설계 판단 — 왜 order가 아니라 catalog가 발행하나
주문 때문에 재고가 준다고 해서 order가 발행 주체인 건 아니다. **재고는 catalog 소유**이고,
관리자 상품 수정 등 주문 외 경로로 줄어도 같은 알림이 나가야 한다.
→ 발행 주체를 catalog로 두면 order 도메인은 이 알림의 존재를 **전혀 모른다**.
부수효과로 `OrderService`는 한 줄도 안 바뀌었다(§5 검증 참고) — §9가 주장한 "OrderService 불변"의 더 강한 형태.

### 구성 (3층 규약 그대로)
| 파일 | 층 | 역할 |
|---|---|---|
| `domain/catalog/event/StockRunningLowEvent` | 이벤트 | `DomainEvent` implements. `(productId, productName, remainingStock, threshold)` |
| `domain/catalog/config/CatalogProperties` | 설정 | `catalog.low-stock-threshold`(기본 5). **0=품절도 포함** |
| `domain/notification/StockEventListener` | 어댑터 | `@Async` + `@TransactionalEventListener(AFTER_COMMIT)`, **위임만** |
| `domain/notification/StockAlertHandler` | 주체 | 실제 로직(로그 stub). 품절/부족 문구 분기 |

- 발행 지점: `ProductCommandService.decreaseStock` — 차감 성공 후 잔여재고가 임계치 **이하**면 발행.
- `AFTER_COMMIT`인 이유: 주문이 롤백되면 재고도 롤백되므로 "실제로 줄지 않은 재고" 오알림을 막는다.

### ⚠ 트랩 — 벌크 JPQL UPDATE는 1차 캐시를 갱신하지 않는다 (중요)
- `decreaseStock`은 `@Modifying @Query("update Product p set p.stock = p.stock - :qty …")` 벌크 UPDATE다.
  **영속성 컨텍스트에 올라와 있는 `Product` 엔티티를 갱신하지 않는다.**
- checkout은 `@Transactional`이라 `cartService.getCart` 단계에서 이미 `Product`가 1차 캐시에 올라와 있다.
  이 상태에서 `findById`로 잔여재고를 읽으면 **차감 전 값(stale)** 이 나와 오알림/미알림이 난다.
- **해결**: 엔티티 대신 **스칼라 프로젝션**으로 DB를 직접 읽는다.
  ```java
  @Query("select new com.glassvue.domain.catalog.repository.StockSnapshot(p.name, p.stock)"
       + " from Product p where p.id = :id")
  Optional<StockSnapshot> findStockSnapshot(@Param("id") UUID id);
  ```
  (`clearAutomatically = true`는 컨텍스트 전체를 날려 다른 엔티티까지 영향 → 채택 안 함.)
- **계열**: 7/16 §6의 *Oracle CHECK 제약 + ddl-auto=update* 트랩과 같은 뿌리 —
  **"ORM/도구가 알아서 해줄 것"이라는 가정이 어긋나는 지점**. 실측 없이는 안 잡힌다.

### 부수 변경 — `@ConfigurationPropertiesScan`
`CatalogProperties`를 등록하려면 도메인마다 `@EnableConfigurationProperties`용 `@Configuration`이 필요해진다.
→ 메인 클래스에 `@ConfigurationPropertiesScan` 한 줄로 대체(도메인별 프로퍼티 레코드 자동 등록).
기존 `JwtProperties`(SecurityConfig의 `@EnableConfigurationProperties`)와 충돌 없음 — 같은 빈 이름이라 멱등.

`OrderPlacedEvent`와 **대칭 구조**. 이번엔 새 이벤트라 `OrderService.cancel`에 publish 한 줄이 불가피하게 추가된다.

### 6-1. 🐞 `existsPurchase`가 `ORDERED`만 보던 버그 (`b576455`)

7/16에 주문 상태를 ORDERED→PAID→SHIPPED로 확장하면서 **같이 못 고친 흔적**.
`existsPurchase`는 `OrderService.hasPurchased` → `ReviewCommandService.create`의 리뷰 작성 자격
게이트(`REVIEW_NOT_PURCHASED`)에만 쓰이므로, **결제하고 배송까지 받은 고객이 리뷰를 못 쓰는** 상태였다.

- 수정: `status in (ORDERED, PAID, SHIPPED)` — **CANCELLED만 제외**.
- `<> CANCELLED`가 아니라 **명시적 열거**로 둔 이유: 나중에 추가될 상태(환불 등)가 자동으로
  "구매함"에 포함되지 않도록 **opt-in**으로 만들기 위함. 새 상태는 이 쿼리를 직접 고쳐야 한다.
- `OrderRepositoryIntegrationTest` 신설(6개) — 상태별 true/false + 타인·타상품 배제.
  기존 `OrderServiceTest.hasPurchased_delegates`는 **리포지토리 위임만** 검증해 이 버그를 못 잡았다.
  → **교훈**: "위임한다"만 검증하는 단위 테스트는 위임받은 쪽의 조건이 틀린 걸 절대 못 잡는다.
  쿼리 조건이 결과를 가르는 메서드는 통합 테스트로 막아야 한다.

> 발견 경위: 평균별점 작업 중 `OrderRepository`를 읽다 눈에 걸렸다. 요청받은 작업은 아니었지만

### 6-3. 상품 목록 평균별점 — 이벤트 기반 비정규화 (`87149c4`, **V4**)

**처음 계획(A안)을 버리고 B안으로 바꾼 작업.** 판단 근거를 남겨둔다.

| 안 | 방식 | 문제 |
|---|---|---|
| A | `ProductQueryService` → `ReviewQueryService` 직접 호출 | 기존 `review → catalog`와 합쳐져 **catalog ↔ review 순환** |
| B ✅ | review가 이벤트로 집계를 밀어넣고 catalog가 저장 | 의존은 `review → catalog` 한쪽뿐 |

A안은 스프링 빈 순환은 아니라 앱은 정상 기동한다(`ReviewQueryService` ≠ `ReviewCommandService`).
하지만 **도메인 레벨 순환**이 생겨, MSA 전환 시 두 서비스가 서로를 동기 호출하는 구조가 된다
— CLAUDE.md의 *"domain 하위를 폴더째 분리 가능해야 함"* 이 깨진다.

**핵심 설계 — 집계값을 이벤트에 실어 보낸다.**

```
[review] create/update/delete
   └─ statsByProduct로 재계산 → publish ReviewRatingChangedEvent(productId, avg, count)
              │  AFTER_COMMIT + @Async
              ▼
[catalog] ReviewEventListener(위임만) → RatingSyncHandler(진짜 주체)
   └─ product.avg_rating / review_count 벌크 UPDATE + products:list 캐시 evict
```

- `productId`만 보내면 구독자(catalog)가 평균을 구하려고 **review를 되물어야 해서 순환이 되살아난다.**
  리뷰는 review 소유이니 **집계도 review가 계산해 넘기고** catalog는 받아 쓰기만 한다.
- 집계 쿼리는 JPQL이라 Hibernate가 실행 직전 **자동 플러시** → 방금 save/delete한 변경이 반영된 값이 나온다.
- **캐시 무효화를 Handler에 둔 이유**: `products:list`는 catalog 소유 캐시고 응답에 별점이 들어가므로
  값이 바뀌면 catalog가 스스로 비워야 한다. review는 이 캐시의 존재를 모른다.
- `ReviewStats.roundedAverage()`로 반올림을 한곳에 모음 — 상품 목록과 리뷰 상세가 같은 값을 쓰도록.

**V4 마이그레이션에서 놓치기 쉬운 것 — 백필.**
컬럼만 추가하면 기존 상품이 전부 별점 0이 되고, **해당 상품에 리뷰가 새로 달릴 때까지 영영 0으로 남는다**
(이벤트는 "변경 시점"에만 오므로). 그래서 V4에 기존 리뷰 집계 `UPDATE`를 함께 넣었다.
적용 후 검증: `지바` 비정규화 4.5/2 = 실제 집계 4.5/2 일치.

> Oracle 타입 메모: `DOUBLE PRECISION`으로 선언하면 Oracle이 `FLOAT`으로 만들고 Hibernate `validate`를 통과한다.

**실측(dev :8081, P6SPY)** — 리뷰 작성→수정→삭제에 따라
`update product set avg_rating=4.0 → 2.0 → 0.0`이 **`event-*` 스레드에서 각자 트랜잭션으로 커밋**.
요청 스레드(`nio-8081-exec-*`)는 리뷰만 저장하고 즉시 응답. catalog가 review를 되묻는 쿼리는 **0회**.

### 6-4. 리뷰 목록 캐시 — **보류**(넣지 않기로 결정)

7/16 §7-2에 남아 있던 항목이지만, 지금 넣지 않는 게 맞다고 판단했다.

- 리뷰 목록은 `products:list`·`notices:list`와 **성격이 다르다**. 상품/공지 목록은 모든 방문자가
  같은 첫 페이지를 보지만, 리뷰 목록은 **상품별로 갈라져** 상품 수만큼 캐시 키가 생긴다.
  TTL 60초에 히트율은 낮고 Redis 메모리만 쓴다.
- 정작 비쌌던 "상품 목록에서 상품마다 평균별점 계산"은 **§6-3의 비정규화로 이미 없앴다** —
  캐시로 가리려던 문제 자체가 사라졌다.
- 넣으면 무효화 대상만 하나 더 는다(리뷰 CUD → 리뷰 캐시 evict + 별점 이벤트 → 상품 캐시 evict).

→ **P6SPY로 리뷰 목록이 실제 병목으로 측정되면** 그때 넣는다. "현 단계에 실효 없는 도구는
로드맵으로 미룬다"는 기존 판단(Sentry 보류)과 같은 기준.

### 6-5. 부수 — ARCHITECTURE에 쿼리 작성 기준 명문화 (`5ba922a`)

"고정 쿼리인데 왜 QueryDSL을 안 썼나"라는 질문이 나와서, 암묵적이던 컨벤션을 문서화했다.
판단 기준은 **조건이 런타임에 바뀌는가** 하나 — 동적이면 QueryDSL, 고정이면 JPQL `@Query`.
함께 기록한 것: JPQL 생성자 표현식의 **문자열 클래스 경로** 약점(DTO 개명 시 컴파일은 통과하고
런타임에 실패), 그리고 §2의 벌크 UPDATE 트랩과 `clearAutomatically`를 쓰지 않는 이유.
