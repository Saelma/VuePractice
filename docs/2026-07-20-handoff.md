## 2. 재고 부족 이벤트 (`StockRunningLowEvent`) — catalog 소유

### 설계 판단 — 왜 order가 아니라 catalog가 발행하나
주문 때문에 재고가 준다고 해서 order가 발행 주체인 건 아니다. **재고는 catalog 소유**이고,
관리자 상품 수정 등 주문 외 경로로 줄어도 같은 알림이 나가야 한다.
→ 발행 주체를 catalog로 두면 order 도메인은 이 알림의 존재를 **전혀 모른다**.
부수효과로 `OrderService`는 한 줄도 안 바뀌었다(§5 검증 참고) — §9가 주장한 "OrderService 불변"의 더 강한 형태.

### 구성 (3층 규약 그대로)
| 파일 | 층 | 역할 |
|---|---|---|
| `domain/catalog/event/StockRunningLowEvent` | 이벤트 | `DomainEvent` implements. `(productId, productName, remainingStock, threshold)` |
| `domain/catalog/config/CatalogProperties` | 설정 | `catalog.low-stock-threshold`(기본 5). **0=품절도 포함** |
| `domain/notification/StockEventListener` | 어댑터 | `@Async` + `@TransactionalEventListener(AFTER_COMMIT)`, **위임만** |
| `domain/notification/StockAlertHandler` | 주체 | 실제 로직(로그 stub). 품절/부족 문구 분기 |

- 발행 지점: `ProductCommandService.decreaseStock` — 차감 성공 후 잔여재고가 임계치 **이하**면 발행.
- `AFTER_COMMIT`인 이유: 주문이 롤백되면 재고도 롤백되므로 "실제로 줄지 않은 재고" 오알림을 막는다.

### ⚠ 트랩 — 벌크 JPQL UPDATE는 1차 캐시를 갱신하지 않는다 (중요)
- `decreaseStock`은 `@Modifying @Query("update Product p set p.stock = p.stock - :qty …")` 벌크 UPDATE다.
  **영속성 컨텍스트에 올라와 있는 `Product` 엔티티를 갱신하지 않는다.**
- checkout은 `@Transactional`이라 `cartService.getCart` 단계에서 이미 `Product`가 1차 캐시에 올라와 있다.
  이 상태에서 `findById`로 잔여재고를 읽으면 **차감 전 값(stale)** 이 나와 오알림/미알림이 난다.
- **해결**: 엔티티 대신 **스칼라 프로젝션**으로 DB를 직접 읽는다.
  ```java
  @Query("select new com.glassvue.domain.catalog.repository.StockSnapshot(p.name, p.stock)"
       + " from Product p where p.id = :id")
  Optional<StockSnapshot> findStockSnapshot(@Param("id") UUID id);
  ```
  (`clearAutomatically = true`는 컨텍스트 전체를 날려 다른 엔티티까지 영향 → 채택 안 함.)
- **계열**: 7/16 §6의 *Oracle CHECK 제약 + ddl-auto=update* 트랩과 같은 뿌리 —
  **"ORM/도구가 알아서 해줄 것"이라는 가정이 어긋나는 지점**. 실측 없이는 안 잡힌다.

### 부수 변경 — `@ConfigurationPropertiesScan`
`CatalogProperties`를 등록하려면 도메인마다 `@EnableConfigurationProperties`용 `@Configuration`이 필요해진다.
→ 메인 클래스에 `@ConfigurationPropertiesScan` 한 줄로 대체(도메인별 프로퍼티 레코드 자동 등록).
기존 `JwtProperties`(SecurityConfig의 `@EnableConfigurationProperties`)와 충돌 없음 — 같은 빈 이름이라 멱등.

## 3. 주문 취소 이벤트 (`OrderCancelledEvent`) — order 소유

`OrderPlacedEvent`와 **대칭 구조**. 이번엔 새 이벤트라 `OrderService.cancel`에 publish 한 줄이 불가피하게 추가된다.

- `domain/order/event/OrderCancelledEvent` — record + `from(Order)`
- `OrderEventListener.onOrderCancelled` — 어댑터, 위임만
- `OrderNotificationHandler.handle(OrderCancelledEvent)` — 오버로드

### 설계 판단 — 재고 복원은 이벤트에 담지 않는다
복원은 **취소 처리의 일부**(동기적으로 반드시 성공해야 함)지 후처리가 아니다.
알림처럼 best-effort(`@Async`, 앱 다운 시 유실)로 흘려보내면 안 되는 작업이라 `cancel()` 안에 그대로 둔다.

운영(:8080) 무중단을 위해 포트만 바꿔 dev 인스턴스로 확인. **공유 espdb라 검증 데이터는 생성 후 즉시 삭제**(`ZZ` 접두사).

### 재고 이벤트 — 3케이스
| 케이스 | 재고 | 결과 |

### fan-out + 취소 (한 흐름)
```
[nio-8081-exec-9] Order created: 019f7d1c-e0b4…
[event-1] StockAlertHandler        : [재고] 재고 부족(stub) — remaining=5 threshold=5
[event-2] OrderNotificationHandler : [알림] 주문 확인 발송(stub) …
[nio-8081-exec-1] Order cancelled: 019f7d1c-e0b4…
[event-2] OrderNotificationHandler : [알림] 주문 취소 안내 발송(stub) …
```
- **fan-out 실증**: 주문 1건에 Handler 2개가 **서로 다른 이벤트 풀 스레드**(`event-1`/`event-2`)에서 병렬 반응.
- **요청 스레드 분리**: 처리 스레드가 `nio-8081-exec-*` → `event-*`로 이동 = `@Async` 동작 확인.
- 취소 후 재고 6 복원 확인.
