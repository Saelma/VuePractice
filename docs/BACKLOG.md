# 기능 백로그 (이커머스)

> **이 문서가 답하는 질문: "무엇을 만들 것인가."**
> 설계·근거는 `ARCHITECTURE.md`, 일하는 방식은 `WORKING-AGREEMENTS.md`,
> 그날 한 일은 `YYYY-MM-DD-handoff.md`. 여기엔 **아직 없는 기능**만 적는다.
>
> **왜 따로 만들었나 (2026-07-23)**: 같은 갭 목록을 하루에 **두 번** 코드에서 다시 뽑았다.
> 재생성 비용이 반복해서 발생하면 문서로 만드는 게 맞다. 게다가 이 목록이 그날 핸드오프 안에
> 들어 있으면 **다음 날 문서가 생길 때 묻힌다** — WORKING-AGREEMENTS 가 존재하는 이유와 같은 문제다.

## 쓰는 법

- **핸드오프 `## 이월` 과 겹치지 않게 한다.** 이월은 *그날 작업에서 파생된 잔여*(수명 며칠),
  여기는 *제품 기능 후보*(수명 김)다. 이월에 제품 기능이 쌓이면 매일 복사돼 내려온다.
- 항목을 끝내면 **아래 「완료」로 옮기고 날짜·근거 문서를 남긴다.** 지우지 않는다 —
  "이건 왜 이렇게 돼 있지"를 나중에 되짚을 근거가 된다.
- **크기**는 어림값이다: 소=반나절 / 중=하루 / 대=며칠(도메인 신설·스키마 파급).
  ⚠ 어림할 때 **분해해 보고 적는다.** 2026-07-23 에 쿠폰을 "도메인 신설이니 대"로 유추했다가
  실제로는 한 시간대에 끝났다 — 핵심과 주변부(관리 화면 등)를 갈라서 적었어야 했다.

## B. 커머스 표준 기능

### B-5. 배송지 주소록 — 크기 중  ← **다음 추천**

현재 `member` 에 `ship_*` 5컬럼 = **기본 배송지 1개만**. 집/회사 구분이 안 된다.

- `member_address` 테이블 신설(별칭·기본배송지 플래그) + 주문서에서 선택.
- ⚠ **기존 데이터 이관이 필요하다** — `member.ship_*` 값을 새 테이블로 옮기고 컬럼을 정리해야 한다.
  지금까지의 마이그레이션은 대부분 순수 추가였는데 이건 다르다.

### B-6. 위시리스트(찜) — 크기 소~중

도메인 없음. 장바구니(Redis)와 구조가 비슷해 패턴을 재활용할 수 있다.
다만 장바구니와 달리 **영속이어야** 하므로(로그아웃해도 남아야 한다) Redis 가 아니라 테이블이 맞다.

## C. 규모가 커지면

### C-8. 상품 옵션(사이즈·색상) — 크기 대

**가장 큰 항목.** 지금 구조는 "상품 1 = 재고 1" 이라 옵션이 들어오면
`product`·`cart`·`order_item`·재고 차감/복원까지 **전부 파급**된다.
실제로 필요해지기 전에는 손대지 않는 게 맞다(ARCHITECTURE §1 "미리 만들지 않는다").

### C-9. 반품 · 교환 — 크기 대

`OrderStatus` 확장 + 환불 개념이 필요하다. **PG 없이는 반쪽**이라(돈을 돌려줄 수단이 없다)
PG 도입과 묶는 게 자연스럽다.

### C-10. 적립금 · 회원 등급 — 크기 중

`Member` 에 관련 필드 없음. 주문 완료 이벤트(`OrderPlacedEvent`)에 얹는 구조가 된다.

### C-11. 관리자 매출 통계 — 크기 중

관리자 API 가 **주문·이미지 둘뿐**이라 대시보드가 없다.
일/월 매출, 상품별 판매량 등. 집계 쿼리라 인덱스 확인이 함께 필요하다.

> "도메인 신설 = 크다"로 유추했을 뿐 분해해 보지 않았다. 실제로는 핵심(스키마·엔티티·적용
> 로직·주문 통합·주문서 UI)이 한 시간대였고, "대"로 보이게 한 것은 **관리자 관리 화면** 같은
> 주변부였다. → **크기를 적을 땐 무엇이 핵심이고 무엇이 주변부인지 갈라서 적는다.**
