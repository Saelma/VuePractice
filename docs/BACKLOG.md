- **핸드오프 `## 이월` 과 겹치지 않게 한다.** 이월은 *그날 작업에서 파생된 잔여*(수명 며칠),
  여기는 *제품 기능 후보*(수명 김)다. 이월에 제품 기능이 쌓이면 매일 복사돼 내려온다.
- 항목을 끝내면 **아래 「완료」로 옮기고 날짜·근거 문서를 남긴다.** 지우지 않는다 —
  "이건 왜 이렇게 돼 있지"를 나중에 되짚을 근거가 된다.
- **크기**는 어림값이다: 소=반나절 / 중=하루 / 대=며칠(도메인 신설·스키마 파급).
  ⚠ 어림할 때 **분해해 보고 적는다.** 2026-07-23 에 쿠폰을 "도메인 신설이니 대"로 유추했다가

  걸릴 수 있어 **매출부터** 한다 — 매출은 건수와 무관하게 *"지난달"* 을 지금도 못 묻는다.
- 크기 **중**: 백엔드 파라미터화(요약·일별·TOP 셋 다 기간을 받아야 한다) + 화면 + 프리셋 +
  경계·빈 구간 테스트. ⚠ **일별 추이의 「0인 날 채우기」가 기간 가변이 되면 다시 봐야 한다**
  (지금은 30 고정이라 `DAILY_DAYS` 로 채운다).

### B-27. 프로모션 **달력**(관리자 전용) — ✅ **완료 (2026-08-13)**

> **착수 조건이 G-8 로 채워졌다** — 그전까지 쿠폰이 전부 상시라 달력에 그려도 «가로줄 다섯 개»
> 였다. 아래 *"지금은 이르다"* 는 그때의 판단 그대로 남겨 둔다.
> ⚠ 실제로 그 「가로줄」이 재현됐고(상시 쿠폰의 사용 기간이 한 달을 덮었다), 사용자가 지적해
> **상시는 격자 밖 스트립으로** 뺐다 — 이 항목이 미뤄졌던 이유가 구현에서 그대로 나온 셈이다.


*"캘린더"* 라는 말이 맞는 자리다. **목록으로는 안 보이고 달력으로만 보이는 질문**이 하나 있다 —
*"이 날 무엇이 **동시에** 돌고 있나"*. 할인이 겹치면 마진이 겹쳐서 깎인다.

🔴 **고객용은 달력으로 만들지 않는다 — 배너다**(2026-08-12, 사용자 확정. 한 번 «두 장» 으로 적었다가
사용자가 되짚어 바꿨다). **G-8 로 옮겼다** — 여기는 **관리자 한 장**이다.
⚠ 이유는 그때 적어 둔 그대로다: 이벤트가 한 달에 한둘이면 **달력은 거의 빈칸**이고
*"다음 이벤트 D-3"* 한 줄이 더 잘 답한다. **달력이 이기는 조건(여러 개가 날짜에 흩어져 있을 때)은
관리자 쪽에서만 성립한다** — 관리자는 쿠폰·타임세일·발송을 **겹쳐서** 보기 때문이다.

- 재료는 이미 있다: `coupon.valid_from`·`valid_until`(실측 **5건, 지금 전부 유효**).
- 🔴 **그런데 지금은 이르다** — 쿠폰 5개가 **전부 상시**라 달력에 그려도 **가로줄 다섯 개**일 뿐이고,
  목록보다 나은 게 없다. **겹침이 정보가 되려면 기간이 갈려야** 한다.
- → **G-5(기간 할인·타임세일) 또는 G-8(이벤트 쿠폰)이 들어오는 시점**이 이 항목의 착수 조건이다
  (2026-08-12 사용자: *"기간 할인이나 타임세일 쪽에 도입될 것 같다, 쿠폰도 있을 테고"* — 맞다.
  **둘 중 하나만 들어와도 기간이 갈리기 시작한다**). 그때 달력 한 장에
  쿠폰·타임세일·(가능하면)마케팅 발송을 얹으면 *"다음 주에 뭐가 겹치나"* 를 한눈에 답한다.
- ⚠ **DevExtreme `Scheduler` 는 쓰지 않는다.** 그건 *사람이 시간을 예약하는* 도메인(상담·예약제)의
  컴포넌트다. 우리에게 필요한 건 **기간 막대를 월 격자에 얹는 것**이라 `Calendar` + 직접 그린 막대가 맞다.
- **크기 중**의 근거: 겹침 막대를 월 격자에 얹는 것 + 쿠폰·타임세일·발송을 **한 좌표계로 모으는 것**
  (셋의 기간 표현이 제각각이다). ⚠ **고객 배너(G-8)와 데이터는 같지만 DTO 는 가른다** — 관리자
  달력엔 마케팅 대상 수·할인 원가가 얹히고 **그게 고객에게 새면 안 된다**. 2026-08-06 에 고객용 문의
  DTO 를 관리자 화면에 재사용한 사고의 **반대 방향**이다.

> ⚠ **접은 후보 둘**(2026-08-12, 같은 조사에서 나왔고 **하지 않기로 했다** — 다시 꺼내지 말 것):
> - **마케팅 예약 발송**: 캘린더가 아니라 `DateBox` 하나면 되는 일이고, 🔴 **발송은 되돌릴 수 없다**
>   (DESIGN §7 이 그래서 확인 단계를 두게 했다). 예약은 *"눌렀는데 아직 안 나갔다"* 는 상태를 만들어
>   **취소 화면이 세트로** 따라온다 — 지금 얻는 것보다 늘어나는 위험이 크다.
> - **관리자 홈에 달력 위젯**: 지금 홈은 *처리 대기 → 재고 → 매출* 로 **답을 주는** 화면이다.
>   달력은 답이 아니라 **조회 도구**라 여기 놓으면 밀도만 떨어진다(DESIGN: 운영 화면은 밀도가 미덕).

### 선착순 한정 쿠폰 발급 (Redis) — 설계 메모

사용자가 이전 프로젝트에서 만들어 본 구조다. **지금은 넣지 않는다**(2026-07-23 결정).

**왜 지금이 아닌가**
1. **실효가 없다** — LAN 안에서 단독 사용이라 동시성 자체가 없다. 락 경합도 Redis 부하도
   측정할 수 없어 잘 만들었는지 확인할 방법이 없다(Sentry 를 보류한 것과 같은 판단).
2. **더 근본적으로, 지금 쿠폰 모델엔 「한정 수량」이 없다.** 현재는 관리자가 특정 회원에게
   지정 발급하는 구조라 **선착순 경쟁이 발생하지 않는다.** 이 설계를 얹으려면 먼저
   `coupon` 에 총량 + **자가 발급(claim) API** 가 있어야 한다 — "Redis 를 붙인다"가 아니라
   **기능을 새로 만드는** 일이다.

**설계 요약** (필요해지면 여기서 출발)

| 요소 | 역할 |
|---|---|
| 총량·사용량 카운터(Redis) | 발급 가능 판단. 같아지면 소진 |
| `user_coupon` **Set** | 중복 발급 차단 — `SISMEMBER` O(1) |
| **Lua 스크립트** | 한도 확인 + 중복 확인 + 증가를 **원자적으로** 처리(사이에 끼어들 틈 제거) |
| **소진 플래그** | 소진 뒤엔 카운터를 안 읽고 플래그만 보고 즉시 거절 |
| **Pub/Sub + TTL(60초)** | 발급이 멎으면 DB 동기화 트리거(debounce) |
| **Jitter** | 동기화가 한꺼번에 몰려 Redis 를 때리지 않게 분산 |
| **Write-back** | 이벤트 중엔 Redis 가 사실상 원장, DB 는 뒤따라 반영 |
| 재시도 + 보상 트랜잭션 | 동기화 실패 시 복구 |

- 이벤트는 지금 프로젝트도 JVM 내부(`ApplicationEventPublisher`)라 **MSA 단계에서 RabbitMQ 로
  전환하면 자연스럽게 맞물린다**(ARCHITECTURE 의 메시징 방침과 같은 방향).
- ⚠ 사용자가 "jitter 말고 분산 기법 하나를 더 썼는데 기억이 안 난다"고 했다. 후보:
  exponential backoff(jitter 와 거의 항상 짝) / coalescing·debounce / probabilistic early expiration.
  착수할 때 확인할 것.

### 부하 테스트 (k6) — 순서 메모

**도구는 k6 로 정했다**(2026-07-23). 스크립트가 JS 라 가볍고, 결과 지표(p95·RPS·에러율)를
그 자체로 뽑아 준다.

**선행 조건: 선착순 발급 기능.** 지금 쿠폰은 관리자가 특정 회원에게 지정 발급하는 구조라
**경쟁 자체가 없다** — 부하를 걸 대상이 없다.

#### 두 번에 나눠 한다 — 사이에 관측 스택이 들어간다

```
1. 선착순 발급 기능
2. k6 정합성 테스트     ← 관측 스택 불필요
3. 관측 스택
4. 같은 시나리오, 부하를 키워 다시   ← 이제 "어디가" 느린지 읽힌다
```

**왜 정합성이 먼저인가** — 선착순의 진짜 리스크는 성능이 아니라 **총량 초과 발급**이다.
쿠폰 100장에 1,000명이 몰렸을 때 **느린 건 참을 수 있지만 101장이 나가면 사고**다.
그리고 이건 **단위 테스트로 절대 안 잡힌다** — 순차 호출로는 재현되지 않고 실제 동시 요청이 필요하다.

**왜 2번엔 관측이 필요 없나** — 정합성 검증은 숫자만 세면 된다:
`k6 의 발급 성공 응답 수` vs `DB 의 실제 발급 건수`. 같으면 통과다.
여기서 대시보드를 봐도 얻을 게 없다. 오히려 **관측을 먼저 깔면 볼 게 없는 상태에서
대시보드부터 만들게 된다**(§ "미리 만들지 않는다").

**왜 4번엔 관측이 필요한가** — k6 는 **밖에서 본 증상**만 준다("p99 가 800ms").
그중 얼마가 Redis 대기인지, DB 커넥션 풀 고갈인지, JVM GC 인지는 **서버 안을 봐야** 갈린다.

⚠ **지나간 부하는 데이터가 안 남는다.** 그래서 3번을 깔고 나면 2번 시나리오를 **다시 돌려야** 한다
— 4번은 새 테스트가 아니라 **같은 시나리오를 관측이 켜진 상태에서 부하만 키워 재실행**하는 것이다.

#### 검증 목표

| 단계 | 보는 것 | 통과 기준 |
|---|---|---|
| 2 정합성 | 발급 성공 수 ↔ DB 실제 발급 수 | **총량 초과 0건** · 중복 발급 0건 |
| 4 성능 | p95/p99, RPS, 에러율 + 서버 내부 지표 | 병목 지점이 **식별될 것**(숫자 목표는 그때 정한다) |

⚠ **공유 espdb 에 쏘면 안 된다.** 부하 테스트는 격리된 DB·Redis 에서 한다
— 지금도 검증용 `esptest` 계정과 Redis 별도 db 를 쓰는 것과 같은 이유(운영 오염 방지).

### E-1. 로그인 무차별 대입 방어 — ✅ **완료 (2026-07-30)**

근거: `handoffs/2026-07-30-handoff.md` §9. `LoginAttemptGuard`(아이디 5회 / IP 20회 · 10분).

> ⚠ **여기 적힌 판단 하나를 뒤집었다**: *"차단 사실을 응답으로 드러내지 말 것 — 계정 존재를 알려주는 셈"*.
> 그 논리는 **존재하는 계정만 셀 때** 성립한다. 실제 구현은 **DB 조회 전에 입력된 아이디 그대로** 세므로
> 없는 아이디도 똑같이 잠기고, 그래서 429 가 존재 여부를 알려주지 않는다 → **숨기지 않고 알린다**
> (사용자 결정). 숨기면 진짜 사용자가 맞는 비밀번호를 넣고도 이유를 알 수 없다.
>
> 착수해서 새로 드러난 것 둘: ① `server.forward-headers-strategy` 가 없어 `getRemoteAddr()` 이 전부
> nginx(`127.0.0.1`)라 **IP 제한을 그냥 붙이면 전 사용자가 한 덩어리**가 된다 ② nginx 의
> `X-Forwarded-For` 는 클라이언트 값에 **덧붙이는** 방식이라 첫 값이 위조 가능 → **`X-Real-IP`** 를 쓴다.

<details><summary>원래 항목 (근거 보존)</summary>

⚠ **비밀번호를 무한정 시도할 수 있다.** `POST /api/auth/login` 에 시도 제한이 전혀 없다(실측).
비밀번호 최소 길이가 8자뿐이라 흔한 조합은 현실적으로 뚫린다.

- ⚠ **아이러니**: 오늘 만든 이메일 인증번호(B-14)엔 **5회 제한을 걸었는데**, 정작 **로그인엔 없다.**
  6자리 숫자보다 비밀번호가 더 중요한데 방어는 반대로 돼 있다.
- 최소안: Redis 카운터(`auth:login-fail:<loginId>`) — N회 실패 시 일정 시간 차단.
  **인증번호 저장소(`EmailVerificationCodeStore`)와 같은 구조**라 패턴이 이미 있다.
- ⚠ 설계 결정: **아이디 기준이냐 IP 기준이냐.** 아이디만 막으면 한 IP 가 여러 계정을 훑을 수 있고,
  IP 만 막으면 공유 IP 에서 선의의 사용자가 막힌다. 보통 **둘 다** 건다.
- ⚠ **차단 사실을 응답으로 드러내지 말 것** — "잠겼습니다"를 그대로 주면 **계정 존재를 알려주는 셈**이다
  (`AUTH-401` 열거 방지와 같은 판단).

</details>

### E-2. 정지·강등 시 access 토큰 즉시 무효화 — ✅ **완료 (2026-07-30)**

근거: `handoffs/2026-07-30-handoff.md` §4. 아래 「완료」 표에도 넣었다.

> ⚠ **범위가 2곳 → 5곳으로 늘었다.** 여기엔 정지·강등만 적었는데, 착수해 보니
> `refreshTokenStore.delete` 옆에 *"다른 세션 무효화"* 주석이 달린 자리가 **전부 같은 구멍**이었다 —
> 탈퇴·비밀번호 변경·비밀번호 재설정. **주석이 코드보다 앞서 있었다**(refresh 만 지워선 access 가 안 죽는다).
> 백로그를 쓸 때 "정지·강등" 이라는 *증상*으로 항목을 잡았기 때문에, 같은 *원인*을 가진 자리들이 안 보였다.

<details><summary>원래 항목 (근거 보존)</summary>

⚠ **정지·강등해도 최대 30분간 그대로 통한다.** `suspend()` 는 refresh 만 지우고
(`refreshTokenStore.delete`) **access 는 블랙리스트에 안 올린다**(실측). `changeRole` 은 **둘 다 안 한다.**

- 즉 **강등된 관리자가 30분간 관리자 권한을 계속 쓴다** — 역할이 JWT 클레임에 박혀 있기 때문이다.
- ⚠ 정지는 7/28 에 *"access 만료 전 30분 창"* 으로 **알고 넘어간 자리**이고, order 가드로 주문은 막았다.
  하지만 **역할 강등은 그때 함께 보지 않았다** — 이쪽이 더 위험하다.
- 해결에 필요한 것: 블랙리스트가 **jti 단위**라 회원의 모든 토큰을 한 번에 못 막는다.
  → `auth:revoked-before:<memberId>` 같은 **회원별 발급시각 컷오프**를 두고 필터에서 비교하는 방식이 맞다.
  (탈퇴는 `blacklistAccess` 로 자기 토큰 하나는 막지만 같은 한계가 있다.)

</details>

> ✅ 예상한 해법(`auth:revoked-before:<memberId>` 컷오프)이 그대로 맞았다. 착수해서 새로 알게 된 것은
> **경계 처리** 하나다 — `iat` 가 초 정밀도라 `<` 로 비교하면 **강등과 같은 초에 발급된 토큰이 살아남는다.**
> fail-closed(`iat <= cutoff`)로 갔고, 대가는 그 1초 안에 로그인한 사람이 한 번 더 로그인하는 것뿐이다.

### E-3. 비밀번호 정책 — ✅ **완료 (2026-07-30)**

근거: `handoffs/2026-07-30-handoff.md` §10. 10자 + 흔한 목록 + 아이디·닉네임 포함 금지.

> ⚠ **여기 적힌 "최소안: 길이 상향 **또는** 차단 목록" 은 둘 중 하나로는 부족했다.**
> 길이 10자만으로는 `password123`(11자)이 통과하고, 목록만으로는 `hong1234` 가 통과한다 —
> **셋(길이·목록·아이디 포함 금지)이 각각 다른 구멍을 막는다.** "또는" 이 아니라 "그리고" 였다.

<details><summary>원래 항목 (근거 보존)</summary>

지금 규칙은 **8자 이상**뿐이다(`@Size(min = 8)`). `password123` 같은 값이 통과한다 — 실제로
데모 계정들이 그렇다.

- 최소안: **길이 상향**(10~12자) 또는 **흔한 비밀번호 차단 목록**(상위 100개 정도).
- ⚠ **복잡도 규칙(대문자+특수문자 필수)은 권장하지 않는다** — 최신 지침(NIST 800-63B)은 그 방식이
  오히려 예측 가능한 패턴(`Password1!`)을 낳는다고 본다. **길이 + 차단 목록**이 낫다.
- ⚠ **기존 회원은 소급 적용할 수 없다** — 다음 변경 때부터다(B-13 의 "신규만 필수"와 같은 구조).

</details>

### F-1. 탈퇴 회원의 연관 데이터 — ✅ **완료 (2026-07-30)**

> ⚠ **이 항목의 목록이 틀렸다 — 7개로 적었는데 실제로는 12개였다.** 회원 id 를 들고 있는 엔티티를

<details><summary>원래 항목 (근거 보존)</summary>

⚠ 탈퇴 회원의 연관 데이터가 전부 남는다 — 크기 **중** · **우선순위 높음**

남는 것들 — 회원 id 로만 연결돼 있어 **주인 없는 행**이 된다:

- 방법 두 갈래: ①탈퇴 시 각 도메인이 정리하도록 **`MemberWithdrawnEvent` 발행**(도메인 경계 유지 —

- ⚠ **이미 쌓여 있다**(WA §2-5: 재발 방지와 기존 잔재 정리는 별개다). 실측(2026-07-29):

  | 테이블 | 고아 행 |
  |---|---|
  | `point_account` | **7** |
  | `member_address`·`notification`·`wishlist`·`point_history` | 0 |

  ```sql
  select count(*) from point_account a
   where not exists (select 1 from member m where m.id = a.member_id);
  ```

### F-8. 관리자 재고 편집에도 **재고 부족 알림**을 낸다 — ✅ **완료 (2026-08-14)** · 아래 「완료」

알림이 없어도 안다. 값이 있는 자리는 *"다른 관리자가 내린 것을 나도 안다"* 쪽인데, 관리자가 셋뿐이다.

⚠ **알림 자체가 쌓이는 문제는 F-2 와 얽힌다** — 전이 판정을 넣으면 F-2 의 압력도 줄어든다.

**남는 것과 사라지는 것이 이미 갈려 있다**(오늘 실측):

| 무엇 | 상품을 지우면 | 왜 |
|---|---|---|
| 주문 이력 | **멀쩡하다** | `order_item` 이 이름·가격 **스냅샷**을 갖는다 |
| 리뷰 | **남는다**(이름만 잃는다) | 느슨한 UUID 참조 · FK 없음 |
| 옵션·재고 이력 | **함께 사라진다** | FK ON DELETE CASCADE |
| 장바구니(Redis) | **조회할 때** 정리된다 | `CartService.getCart` 가 못 찾은 줄을 그 자리에서 지운다 |

- ✅ **방식 결정: `deleted_at` 컬럼**(2026-08-12, 사용자 확정). 아래 «최소안» 이 그대로 채택안이다 —

- **최소안**: 상태를 늘리지 말고 **`product.deleted_at` 한 컬럼**을 둔다(soft delete).
  삭제 = `deleted_at` 기록, 배치가 **N일(예: 7일) 지난 것만** 진짜 지운다.

  화면 하나가 지워진 상품을 계속 판다. → **판정을 리포지토리 한 곳**(`@Where` 또는 전용 메서드)에 두고,
  **테스트가 "삭제 대기 상품이 목록·검색·상세·장바구니에 안 나온다"를 갈래마다 못 박는다.**
  ⚠ 2026-08-11 §13 ⓪ 이 「손으로 적은 목록은 어긋난다」를 일곱 번 보여준 그 자리와 같은 성질이다.
- **장바구니는 배치가 훑을 필요가 없을 수 있다** — 위 표대로 조회 시 정리된다.
  ⚠ 다만 **장바구니를 안 여는 사람의 Redis 키는 남는다**(2026-08-11 실측: 운영 `cart:*` 96개가
  전부 주인 없음). 그건 이 항목이 아니라 **별도 문제**다 — 섞지 말 것.
- **되돌리기가 목적이므로 「복구」까지 있어야 한다** — 삭제 대기 목록 + 복구 버튼(관리자 화면).
  ⚠ 복구가 없으면 유예 기간은 *"7일 뒤에 후회한다"* 일 뿐이다.
- ⚠ **오늘 만든 「(지워진 상품)」 표기는 그대로 유효하다.** 유예가 생겨도 **배치가 진짜 지운 뒤**에는
  같은 상태가 되고, 그때까지는 이름이 살아 있다 — 즉 이 항목은 그 표기를 **없애는 게 아니라
  「그 상태에 도달하기 전에 되돌릴 시간」을 주는 것**이다.
- **크기 중**의 근거: 컬럼·마이그레이션 1 + 조회 갈래 정리(목록·검색·상세·장바구니·주문) +
  배치 1 + 관리자 화면(삭제 대기 목록·복구). 컬럼만 보면 소로 착각하기 쉬운데 **조회 갈래가 본체**다.

⚠ **할인에 기간 개념이 없다.** `product.list_price` 를 관리자가 손으로 넣고 손으로 되돌리는 방식이라,

  과거 주문 금액은 안 변한다. **그 토대가 이미 있어서** 이 기능이 얹힐 수 있다.
- ⚠ 캐시(`products:list`)와 얽힌다 — 할인 시작/종료 시점에 캐시가 낡는다. TTL 로 버틸지 evict 할지 결정 필요.
- ⚠ **B-27(프로모션 달력)의 착수 조건이 이 항목이다**(2026-08-12). 지금은 기간이 있는 것이 쿠폰뿐이고
  그 다섯이 전부 상시라 달력이 답할 질문이 없다 — **여기서 기간이 갈리기 시작하면** 겹침이 정보가 된다.

### G-8. **이벤트 쿠폰** (기간 중 「받기」를 누르면 받는다) — ✅ **완료 (2026-08-13)** · V49

> 아래는 착수 전에 적어 둔 근거·설계 논점이다. **결과는 「완료」 표에 있다** — 실제로 갈린 곳
> (플래그를 안 둔 이유 · 유니크가 기존 기능을 죽일 뻔한 것 · 배너가 「다음」을 말하는 자리)은 그쪽에 적었다.
>
> ⚠ **제목이 바뀌었다** — *"자동 발급"* 이 아니라 **「받기」 버튼**이다(2026-08-12 재결정).


**나온 자리**: 2026-08-12, 사용자 구상 — *"그 날 안에 접속하면 쿠폰 발급. 로그인해서 메인에 오면
이벤트 쿠폰 발급 API 를 부르고, 줄 쿠폰이 있으면 발급(중복 안 되게), 없으면 그냥 둔다.
처음엔 boolean 으로."*

✅ **그 설계가 이미 있는 패턴과 같다** — G-2(신규가입 쿠폰, 2026-07-31)가 그 모양이다:
`Coupon.welcome` **boolean** + 관리자 화면에서 지정 + 이벤트 3층(`WelcomeCouponListener` →
`WelcomeCouponHandler`) + *"지정 안 함 = 기능 꺼짐"*(경고가 아니라 기본 상태). **그대로 따른다.**

🔴 **그런데 그대로 따르면 터지는 자리가 하나 있다 — 중복 발급이다**(2026-08-12 실측):

- `CouponService.issue(couponId, memberId)` 에 **중복 가드가 없다.**
- `member_coupon` 에 **unique 제약도 없다**(마이그레이션 전체 조회 — 없음).
- **가입 쿠폰은 안 터졌다**: 회원가입 이벤트가 **1인 1회**라 두 번 불릴 일이 없었다.
- **이벤트 쿠폰은 접속마다 불린다** — 탭 두 개만 열어도 두 장이 나간다.

→ **막는 것을 두 층으로 둔다**: 서비스 가드(이미 가졌으면 조용히 통과) + **DB `unique(member_id, coupon_id)`**.
⚠ **앱 가드만으로는 동시 요청에 뚫린다** — 두 요청이 같은 순간 «없다» 를 읽는다. **DB 가 최종 방어**다.
🔴 ⚠ **유니크 인덱스를 넣기 전에 기존 중복을 먼저 센다**(WA §2-5). 2026-07-21 에 닉네임 UNIQUE(V6)를
넣는 순간 **운영 구 jar 가 500 을 냈다** — 같은 자리다. 세는 쿼리:
`select member_id, coupon_id, count(*) from member_coupon group by member_id, coupon_id having count(*) > 1;`

**결정 (2026-08-12, 사용자 확정)** — 셋 다 정해졌다. 착수할 때 다시 묻지 말 것:

| # | 정한 것 | 따라오는 것 |
|---|---|---|
| 1 | **동시에 유효한 이벤트 쿠폰은 하나** | ⚠ 아래 🔴 참조 — *"하나"* 가 **«행이 하나»** 라는 뜻이 아니다 |
| 2 | **출석 쿠폰이 아니다.** 달력이 *"이 날 새 쿠폰이 나온다"* 를 **예고**하고, 그 날 접속하면 **1매** | ✅ **크기가 안 커진다** — 이벤트마다 `Coupon` 행이 따로라 `unique(member_id, coupon_id)` 하나로 «이벤트당 1매» 가 저절로 된다. **발급 이력에 날짜를 둘 필요가 없다** |
| 3 | ~~트리거는 메인 진입 API~~ → **「받기」 버튼**(2026-08-12 재결정) | 🔴 **트리거 논쟁 자체가 사라진다** — 아래 참조 |

🔴 **결정 1 의 진짜 의미: 유니크 인덱스를 가입 쿠폰처럼 쓸 수 없다.**
가입 쿠폰은 `ux_coupon_welcome` 이 **`welcome=1` 인 행을 하나로** 막는다(V36). 이벤트 쿠폰에 같은 걸
걸면 **미래 이벤트를 미리 등록할 수 없다** — 그런데 **달력에 예고하려면 미래 행이 여러 개 있어야 한다**
(그게 결정 2 의 요점이다). → 막아야 하는 것은 «행 개수» 가 아니라 **«기간 겹침»** 이다.
⚠ **Oracle 유니크 인덱스로는 기간 겹침을 못 막는다** → **등록·수정 시 앱에서 검사**하고 거부한다
(겹치는 이벤트가 있으면 400). ⚠ 그러면 **DB 가 최종 방어가 아닌 유일한 자리**가 되므로,
«겹치는 두 이벤트를 동시에 등록» 을 **테스트로 못 박는다.**

🔴 **발급은 「받기」 버튼으로 한다 — 자동 발급이 아니다**(2026-08-12 재결정, 사용자 제안).
처음 구상은 *"그 날 접속하면 준다"*(메인 진입 시 자동)였는데, 배너에 **「받기」 버튼**을 두는 쪽으로 바꿨다.

**바뀌면서 사라지는 문제들** — 이게 이 결정의 값이다:

| 자동 발급이면 있던 문제 | 버튼이면 |
|---|---|
| 트리거를 **로그인 vs 메인** 중 골라야 했다 | **고를 필요가 없다** — 누를 때만 발급된다 |
| 로그인 API 에 넣으면 **refresh 가 14일**이라(`refresh-token-validity-ms: 1209600000`, 실측) 이벤트 날 접속해도 로그인 API 를 안 타 **못 받는다** | 무관해진다 |
| 메인은 트래픽 1위라 **매 진입마다** 발급 로직을 탄다 | 발급은 **누른 사람만** 탄다 |
| **받았는지도 모른다** — 배너를 못 보고 지나치면 인지가 안 남는다 | 누른 사람은 **자기가 받은 걸 안다** (실제 이커머스가 대개 «쿠폰 받기» 버튼인 이유) |

⚠ **대신 잃는 것 하나 — 안 누르면 못 받는다.** *"그 날 접속하면 준다"* 가 *"그 날 누르면 준다"* 가 된다.
그래도 이쪽을 고른 이유는 위 넷이 전부 사라지고, «모르는 채 받는 것» 보다 **«알고 받는 것»** 이
쿠폰의 목적(다시 오게 하는 것)에 맞기 때문이다.

**남는 조회는 「배너를 그릴까」 하나다** — 그건 여전히 싸게 끝나야 한다:

| 그 날 | 하는 일 |
|---|---|
| 이벤트 **없는 날**(대부분) | 「오늘·앞으로의 이벤트」를 **캐시**(하루 TTL)로 답한다 → **쿼리 0방** |
| 이벤트 **있는 날** | 「이미 받았나」 **1방**(버튼을 「받기/받음」 중 무엇으로 그릴지 정해야 한다) |

→ 캐시는 **이미 쓰는 도구다**(`products:list` 가 Redis 캐시 + `@CacheEvict`). 같은 방식으로 얹고,
관리자가 이벤트를 등록·수정하면 **그 캐시를 비운다**(상품 캐시가 하는 그대로).

**비로그인이 「받기」를 누르면** — 🔴 **누르기 전에 알게 한다:**

- **버튼 라벨을 「로그인하고 받기」로 바꾼다.** 누르고 나서 막히는 것보다 낫다
  (`confirm` 으로 물어도 이 프로젝트 관행에는 맞다 — `CartView`·`MyPageView` 가 쓴다 — 다만
  **누르기 전에 이미 알 수 있는 것을 굳이 물어보는 셈**이라 클릭만 한 번 는다).
- **로그인 후 제자리로 돌아오는 장치는 이미 있다**(실측): `/login?redirect=<경로>` 를 `LoginView` 가
  `route.query.redirect` 로 되돌린다. ⚠ **라우터 가드가 붙여 주는 건 «경로 이동» 일 때뿐**이라
  배너 버튼은 **직접 붙여야 한다**: `router.push({ path: '/login', query: { redirect: route.fullPath } })`.
- ⚠ **돌아온 뒤 자동으로 발급하지 않는다.** 돌아오면 배너가 「받기」로 서 있고 **한 번 더 누른다** —
  자동으로 주면 «내가 누른 적 없는데 받았다» 가 되어 위의 「알고 받는다」를 스스로 깬다.

**비로그인 배너 — 예고(D-3)도 함께 적는다**(2026-08-12, 사용자 확정.
앞서 «비로그인엔 예고를 적지 않는다» 로 적었던 것을 **뒤집는다**):

- 앞서 반대한 이유는 *"가입해서 혜택을 누려라"* 가 **즉시성을 암시**해서였다. **D-day 를 같이 적으면
  그 문제가 없다** — *"다음 이벤트 D-3 · 지금 가입하면 그때 받을 수 있어요"* 는 **사실 그대로**다.
- 🔴 **D-day 계산은 서버가 한다.** 클라이언트 시계·시간대를 믿으면 **어떤 사람에게만 D-1 이 D-2 로 보인다.**
  KST 경계를 서버가 만든다는 **B-26 의 원칙과 같은 자리**다 — 응답에 `daysUntil` 을 실어 보낸다.

🔴 **비어 있던 자리 — 「언제 받을 수 있나」와 「언제까지 쓸 수 있나」가 지금 같은 값이다**(2026-08-12 실측).

`Coupon` 의 기간 컬럼은 **`valid_from`·`valid_until` 하나뿐**이고, 그 값을 `redeem` 이
`isValidAt(now)` 로 **사용 가능 판정**에 쓴다(`CouponService:143` → `COUPON_EXPIRED`).
→ **이벤트 창을 그 값으로 쓰면 «8/15 하루 이벤트» 쿠폰이 그 날 자정에 만료된다** — 받자마자 쓸 수 없다.
⚠ 이 항목의 문장들(*"그 날 접속하면"*, *"D-3"*)은 전부 **발급 창**을 말하는데, 스키마에는 그 개념이 없다.

✅ **해법 확정 — 컬럼은 `issue_until` 하나만 더한다**(2026-08-12, 사용자 결정):

| 무엇 | 어느 컬럼 | 값 |
|---|---|---|
| 이벤트 날(**발급 시작 = 사용 시작**) | **`valid_from`**(기존) | 그 날 00:00 |
| **발급 마감** | 🔴 **`issue_until`**(신설, nullable) | 그 날 23:59 — *"그 날 접속한 사람만"* |
| 사용 마감 | **`valid_until`**(기존) | **한 달 뒤** |

🔴 **사용자 제안 «발급 시작을 이벤트 날과 같이 한다» 가 컬럼 하나를 지웠다.** 앞서 `issue_from`·
`issue_until` 둘을 더하려 했는데, 발급 시작과 사용 시작이 **항상 같은 값**이면 `issue_from` 은
`valid_from` 의 복사본일 뿐이다. → **마이그레이션이 셋에서 둘로 준다**(플래그·`issue_until`).
⚠ *"미리 받아 두고 다음 달부터 쓰세요"* 를 하고 싶어지면 그때 `issue_from` 을 더한다
(**null = `valid_from` 과 같다**로 읽으면 백필이 없다). **지금은 만들지 않는다.**

- ✅ **사용 기한은 「한 달」**(2026-08-12, 사용자). 🔴 **코드에 박지 않는다** — `valid_until` 은
  **이미 관리자가 입력하는 칸**이다(`CouponAdminView` 의 `<input type="date">`).
  → **화면이 «한 달 뒤» 를 기본값으로 채워 주고**, 다른 이벤트는 관리자가 고친다.
  **정책이 코드가 아니라 기본값에 있으면** 이벤트마다 다르게 갈 수 있고 컬럼도 안 는다.
- 🔴 **겹침 금지(결정 1)의 대상은 「발급 창 = `valid_from` ~ `issue_until`」** — 하루짜리다.
  사용 기간(`valid_until`, 한 달)은 **당연히 겹친다**. ⚠ **여기를 헷갈리면 등록이 통째로 막힌다** —
  8/15 쿠폰과 8/20 쿠폰의 사용 기간은 9월 중순까지 나란히 살아 있어야 정상이다.
- ⚠ **등록 시 검증**: `valid_until` 이 `issue_until` 보다 빠르면 **받자마자 만료된 쿠폰**이 나간다 → 거부.
- ⚠ **기존 쿠폰 5건은 `issue_until` 이 null** 이다 → **null = 이벤트 아님(상시)**. 백필이 필요 없다 —
  G-2 의 *"지정 안 함 = 기능 꺼짐"* 과 같은 방식이다.
- ⚠ **한 달이 지나면 안 쓴 쿠폰이 조용히 만료된다.** *"곧 만료됩니다"* 알림은 흔한 기능이지만
  **이 항목의 범위가 아니다** — 필요해지면 별도 후보로. (F-2 「알림이 무한정 쌓인다」와도 얽힌다.)

**「받기」의 모션** (2026-08-12, 사용자 요청 — *"딸깍하고 바로 «발급되었습니다» 말고, 그 사이에 애니메이션"*):

🔴 **이게 이 제품의 «처음 들어가는 의도적 모션»이다.** 지금 모션은 `transition-colors`,
카드 hover(`-translate-y-0.5`), 스켈레톤(`animate-pulse`) 뿐이다(실측) — 즉 **연출용 모션이 하나도 없다.**
그래서 이 항목은 «쿠폰 버튼 하나» 가 아니라 **모션의 기준을 세우는 자리**다. DESIGN 에 남길 것.

**벤치마크** — 절제된 것부터:

| # | 패턴 | 어디서 | 우리에게 |
|---|---|---|---|
| 1 | **버튼 자체가 상태를 바꾼다** — 「받기」→ 스피너 → **체크가 그려지며** → 「받음」(비활성) | 쿠팡·11번가·무신사의 «쿠폰 다운로드» | ✅ **1순위.** 무채색 원칙과 맞고 새 컴포넌트가 필요 없다 |
| 2 | **쿠폰이 「쿠폰함」으로 날아간다**(fly-to-target) | 장바구니 담기에서 흔한 패턴(쿠팡·아마존) | 은유가 이미 있다(장바구니). 다만 **헤더에 착지점이 필요**하고 모바일 좌표 계산이 붙는다 → **2단계** |
| 3 | **도장이 쿵 찍힌다**(스탬프) | 출석체크(토스·카카오) | 출석이 아니므로 은유가 안 맞는다 — **접는다** |
| 4 | **봉투가 열리며 쿠폰이 나온다**(가챠) | 이벤트 프로모션 일반 | 🔴 **과하다.** 무채색·절제 톤을 정면으로 깬다 — **접는다** |

✅ **토스식으로 간다**(2026-08-12, 사용자 확정). 레퍼런스 표에 **토스**가 이미 있고(DESIGN §2, 관리자 행)
마이크로 인터랙션(**누르는 순간 살짝 눌리고**, 끝나면 **조용히 확정되는**)이 우리 톤의 기준점이다.
→ 위 표의 **1번(버튼 자체가 상태를 바꾼다)**을 그 방식으로 만든다. 2번(fly-to-쿠폰함)은 2단계. → 구현하면
**DESIGN §2 에 행을 추가**하고 §6 에 모션 규칙을 적는다.

**지킬 것 다섯**:

1. 🔴 **애니메이션은 기다리는 시간을 «설명»하는 것이지 «만드는» 것이 아니다.** 서버가 80ms 에 답하는데
   연출이 800ms 면 사용자는 **720ms 를 기다린 것**이다. → 연출은 **응답을 기다리는 동안** 돌고,
   응답이 오면 완료로 **전이**한다. 다만 «기대감» 몫으로 **300~600ms** 는 정당하다(그 이상은 금지).
   ⚠ **같은 사람이 이벤트마다 반복해서 누른다** — 두 번째부터 길게 느껴진다.
2. ⚠ **실패 경로에도 모션이 있어야 한다.** 이미 받았거나 기간이 끝났으면 체크가 아니라 **되돌아오는**
   모션 + 이유 문구. 성공만 만들면 **실패가 «멈춘 것»처럼 보인다.**
3. 🔴 **연타를 막는다** — 모션이 도는 동안 버튼을 잠근다. 서버는 유니크 제약으로 막지만(위),
   **화면이 «발급되었습니다» 를 두 번 띄우면 그게 거짓말이다.**
4. ⚠ `prefers-reduced-motion: reduce` 면 **즉시 전환**한다(연출을 건너뛴다).
5. ⚠ **강조색은 CTA·상태에만**(DESIGN 무채색 원칙). 컨페티·색 폭죽은 이 톤에서 **튄다.**

- **응답은 boolean 하나로 시작한다**(사용자 말대로). *"발급됨/아님"* 만 있으면 화면이 토스트를 띄운다.
  ⚠ **말해 주지 않으면 안 준 것과 같다** — 쿠폰함을 열어 보는 사람만 알게 된다.
- ⚠ **메인은 트래픽이 가장 많은 화면**이다. 대부분의 호출은 *"줄 게 없다"* 로 끝나야 하고, 그 경로가
  **쿼리 두 방**(유효한 이벤트 쿠폰 · 이미 가졌나)이다. 지금 규모(쿠폰 **5** · 회원 **6**)에선 무시해도 된다 —
  **캐시는 나중에**(미리 만들지 않는다).
- **관리자 화면**: 쿠폰 화면에 「이벤트 쿠폰」 토글. **가입 쿠폰 토글이 이미 그 자리에 있다**(V36) — 그 옆이다.
- 🔴 **고객에게 알리는 화면은 이 기능의 «곁가지가 아니라 절반»이다.** 요점이 *"이 날 새 쿠폰이
  나온다"* 를 **미리 알리는 것**이라, 알림이 없으면 **그 날 우연히 들어온 사람만** 받는다.
  **예고가 곧 기능이다.**

  ✅ **고객용은 「배너」다 — 달력이 아니다**(2026-08-12, 사용자 확정. 한 번 «고객 달력» 으로 적었다가
  사용자가 되짚어 바꿨다). 이벤트가 한 달에 한둘이면 **달력은 거의 빈칸**이라 *"다음 이벤트 D-3"*

  누른 순간 로그인으로 튕기고, 돌아왔을 때 **이미 받은 상태**라 **화면이 두 번 말을 바꾼다.**

  → **새 배너를 만드는 게 아니라 그 스트립에 한 줄 더하는 일**이다. **크기 소.**
  ⚠ CTA 가 **「받기」가 아니라 「회원가입」**이라 위의 «말이 두 번 바뀐다» 에 걸리지 않는다 —
  **대상·문구·CTA 가 전부 다른 별개 배너**다.

  🔴 **다만 비로그인 줄에는 «예고» 를 적지 않는다.** *"곧 나온다"* 를 보고 가입해도 **그 날 다시 와야

  ⚠ 예고를 비로그인에게도 하려면 문구가 *"시작하면 알려드립니다"* 가 되고 **알림 발송이 세트로**
  따라온다(가입 시점에 «알림 예약» 이 필요하다) — **지금은 접는다.** 필요해지면 그때 별도 항목.

  **배너가 말하는 것 둘** — ⚠ 섞지 않는다:

  | 언제 | 문구 | 왜 나누나 |
  |---|---|---|
  | 오늘이 이벤트 날 | *"쿠폰이 발급되었습니다"* (+ 쿠폰함 링크) | **발급은 이미 끝났다** — 물어보는 게 아니라 알리는 것이다 |
  | 이벤트가 앞에 있음 | *"다음 이벤트 D-3"* | 예고다. **행동을 요구하지 않는다** |

  ⚠ **줄 게 없으면 배너를 그리지 않는다.** *"예정된 이벤트가 없습니다"* 는 자리만 먹는다
  (DESIGN: 빈 상태는 «무엇을 할 수 있나» 를 말할 때만 값이 있다).
  ⚠ **강조색은 CTA·상태에만**(DESIGN 무채색 원칙) — 이벤트 배너는 화려해지기 제일 쉬운 자리다.
- 🔴 **B-27(관리자 프로모션 달력)의 착수 조건이 이 항목으로도 채워진다** — 이벤트 쿠폰이 생기면 쿠폰의
  기간이 **갈리기 시작하고**(지금은 5개가 전부 상시), 그때 «이 날 뭐가 겹치나» 가 비로소 질문이 된다.
- 크기 **중**: 마이그레이션 2(플래그 · 유니크) + 서비스·API + 화면 토스트 + 관리자 토글 +
  **동시 요청 테스트**(중복이 진짜 막히는지 — 여기가 이 기능의 본체다).

### G-6. 등급 혜택 확장 — 크기 **소**

등급이 **적립률 하나만** 바꾼다(`MemberGrade(minPurchase, earnPercent)`). 실제 쇼핑몰의 등급은
보통 **할인·무료배송·전용 쿠폰**을 함께 준다.

- 가장 싼 확장: **등급별 무료배송 기준 인하**(VIP 는 1만원 이상 무료 등). `ShippingPolicy` 가
  이미 global 에 있어 회원 등급을 인자로 받게만 하면 된다.
- ⚠ **도메인 경계 주의** — `ShippingPolicy`(global)가 `MemberGrade`(point 도메인)를 알면 안 된다.
  **등급이 아니라 "적용할 기준 금액"을 넘겨받는** 형태여야 한다(호출자가 조회해서 넘긴다).

### G-7. 검색 보조 (최근·인기 검색어) — 크기 **소**

전역 검색은 있지만(B-8) **최근 검색어·인기 검색어·자동완성이 없다**(실측). 검색창이 비어 있으면
사용자는 **무엇을 칠지 스스로 떠올려야** 한다.

- 최근 검색어는 **localStorage 로 충분**하다(서버 불필요, 계정별 동기화는 과함).
- 인기 검색어는 **검색 로그가 필요**하다 → Redis 카운터(조회수와 같은 방식).
  ⚠ 단 지금 트래픽에선 **"인기"가 성립하지 않는다** — 최근 검색어만 먼저.
