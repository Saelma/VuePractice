## 쓰는 법

- **핸드오프 `## 이월` 과 겹치지 않게 한다.** 이월은 *그날 작업에서 파생된 잔여*(수명 며칠),
  여기는 *제품 기능 후보*(수명 김)다. 이월에 제품 기능이 쌓이면 매일 복사돼 내려온다.
- 항목을 끝내면 **아래 「완료」로 옮기고 날짜·근거 문서를 남긴다.** 지우지 않는다 —
  "이건 왜 이렇게 돼 있지"를 나중에 되짚을 근거가 된다.
- **크기**는 어림값이다: 소=반나절 / 중=하루 / 대=며칠(도메인 신설·스키마 파급).
  ⚠ 어림할 때 **분해해 보고 적는다.** 2026-07-23 에 쿠폰을 "도메인 신설이니 대"로 유추했다가
  실제로는 한 시간대에 끝났다 — 핵심과 주변부(관리 화면 등)를 갈라서 적었어야 했다.

> ⚠ **찾다가 "이미 있다"로 판명된 것도 적어 둔다** — 다음에 또 뽑을 때 같은 걸 다시 확인하지 않게:

#### B-15. 문의 답변 알림 — 크기 **소**

⚠ **문의에 답변이 달려도 작성자는 모른다.** 알림 타입은 `ORDER`·`STOCK`·`RESTOCK` 셋뿐이고
`InquiryCommandService.answer()` 는 이벤트를 발행하지 않는다(실측). 사용자가 **문의 화면에 다시
들어와 봐야** 답변을 안다 — 물어본 사람이 답을 못 보는 구조다.

- 인앱 알림(SSE)·벨·설정 토글이 **전부 이미 있다.** `INQUIRY` 타입 하나와 이벤트 발행 한 줄이면 붙는다.
- ⚠ **알림 스팸**은 걱정 없다 — 답변은 관리자가 수동으로 다는 것이라 폭주하지 않는다
  (그래서 D 의 「알림 실발송」 선행조건인 *"임계치 재알림 스팸 해결"* 과 무관하다).
- 같은 자리에 **리뷰 답글**도 있지만 그건 기능 자체가 없어 별건이다.

#### B-16. 관리자 대시보드(첫 화면) — 크기 **소~중**

⚠ **관리자로 로그인해도 갈 곳이 없다.** `/admin` 경로 자체가 없고(라우트는 `/admin/orders`,
`/admin/members` … 개별 화면뿐), 「관리 ▾」에서 하나를 골라 들어가야 한다.

- **데이터는 이미 다 있다**: `GET /api/admin/orders/counts`(상태별 주문 수)·`/api/admin/stats/sales`(매출).
  새 API 없이 **모아 보여주는 화면 하나**를 만드는 일이다.
- 보여줄 것: 오늘 주문·매출, **처리 대기**(결제완료=발송 대기, 반품요청), 재고 부족 상품 수.
- ⚠ 착수 시 정할 것: `/admin` 을 대시보드로 할지, 관리자 로그인 시 그리로 보낼지.

#### B-17. 주문 취소 사유 — 크기 **소**

⚠ **반품에는 사유가 있는데 취소에는 없다**(비대칭). `requestReturn(id, memberId, reason)` 인데
`cancel(id, memberId)` 는 사유를 안 받는다. 관리자 주문 목록에서 **왜 취소됐는지 알 방법이 없다.**

- `orders.cancel_reason` 컬럼 + 취소 화면의 사유 입력(선택지 + 직접 입력).
- 취소는 **고객도 관리자도** 한다 — 누가 취소했는지도 함께 남길지 착수 시 결정.

#### B-18. 리뷰·문의 관리(신고/숨김) — 크기 **중**

⚠ **부적절한 리뷰를 내릴 방법이 없다.** 관리자 API 전수를 뽑아 보니 리뷰·문의 쪽은
**문의 답변(`POST /api/inquiries/*/answer`) 하나뿐**이다. 작성자 본인만 지울 수 있으니
욕설·광고 리뷰가 올라오면 **관리자가 손댈 수 없다.**

- 최소안: 관리자 **숨김 처리**(삭제 아님 — 되돌릴 수 있어야 한다) + 관리 목록.
- 확장: 사용자 **신고** 접수 → 신고 많은 순 검토 큐.
- ⚠ 숨긴 리뷰는 `product.avg_rating` 집계에서 빠져야 한다 — `ReviewRatingChangedEvent` 재계산 경로를 탄다.

#### B-19. 재고 변경 이력 — 크기 **중**

⚠ **재고가 왜 그 숫자인지 되짚을 수 없다.** `product_variant.stock` 은 **현재값 하나**뿐이고,
주문·취소·반품·관리자 편집이 전부 같은 컬럼을 덮어쓴다. "어제 10개였는데 왜 3개지?" 에 답할 수 없다.

- `stock_history`(변동량·사유·행위자·시각) append-only. 적립금 이력(`point_history`)이 **원장** 역할을
  하는 것과 같은 구조다 — 그 선례를 그대로 따르면 된다.
- ⚠ **감사 로그(`admin_audit_log`)와 겹치지 않는다**: 저건 *관리자 조작*, 이건 *재고 변동 전체*
  (주문·취소·반품 포함). 관리자 편집만 남기려면 감사 대상 확대(위 「회원 관리 심화」)로 충분하다.

#### B-20. 배송 요청사항(메모) — 크기 **소**

⚠ **주문할 때 "부재 시 경비실에" 같은 요청을 남길 자리가 없다.** `OrderCreateRequest` 에 배송지
5필드(수령인·전화·우편번호·주소1·2)만 있고 메모 필드가 없다(실측). 실물 배송이 있는 커머스에서
거의 항상 있는 자리다.

- `orders.ship_memo` 컬럼 + 주문서 입력 + 주문상세·관리자 목록 표시.
- ⚠ **주문 스냅샷이다** — 배송지와 같은 성격이라, 나중에 주소록을 고쳐도 과거 주문의 메모는 그대로여야 한다.
- 자주 쓰는 문구를 선택지로 줄지(부재 시 문 앞/경비실/직접 수령) 착수 시 결정.

#### B-21. 가입 약관 동의 — 크기 **소~중**

⚠ **약관·개인정보 동의 절차가 아예 없다.** `SignupRequest` 는 `loginId`·`password`·`nickname`·`email`
넷뿐이고 가입 화면에도 체크박스가 없다(실측). **개인정보를 수집·저장하면서 동의를 받지 않는다** —
학습용이라도 이커머스 형태를 갖췄다면 빠지면 어색한 자리다.

- 최소안: 이용약관·개인정보 처리방침 **본문 페이지** + 가입 시 **필수 동의 체크** + 동의 시각 저장.
- ⚠ **동의 이력을 남길지**가 결정 포인트다. 컬럼 하나(`agreed_at`)로 끝낼 수도 있고, 약관 버전이
  바뀌면 재동의를 받아야 하니 `member_agreement`(약관종류·버전·동의시각) 테이블로 갈 수도 있다.
  → **버전 관리까지 갈 필요는 없어 보인다**(약관이 바뀔 일이 없는 연습 프로젝트). 최소안 권장.
- 마케팅 수신 동의(선택)는 알림 설정이 이미 있어 그쪽과 겹친다 — 넣는다면 그 화면과 합칠 것.

#### B-22. 리뷰 정렬·사진만 보기 — 크기 **소**

⚠ **리뷰가 쌓이면 볼 수가 없다.** `GET /products/{id}/reviews` 에 정렬·필터 옵션이 없어
**최신순 한 가지**뿐이다(실측). 상품 목록엔 「리뷰 많은순」을 오늘 넣었는데(§7-1),
정작 **리뷰 자체**는 고를 수가 없다.

- 정렬: 최신순 / 별점 높은순 / 낮은순. 필터: **사진 있는 리뷰만**(포토 리뷰는 이미 있다).
- 상품 목록 정렬과 같은 방식(화이트리스트)이라 패턴이 이미 있다.
- ⚠ **「도움돼요」는 별건**이다 — 그건 투표 테이블이 필요해 크기가 다르다(중). 지금 넣지 않는다.

#### B-23. 연관 상품 — 크기 **소**

⚠ **상품 상세에서 다른 상품으로 갈 길이 없다.** 보고 나면 뒤로 가기뿐이다(실측: `ProductDetailView`에
연관/추천 영역 없음).

- 최소안: **같은 카테고리 상품 4개**(현재 상품 제외, 인기순). 새 API 없이 기존 목록 API 를 조건만 달리해
  부르면 된다 — 홈이 이미 그렇게 쓴다(§B-8).
- ⚠ **"함께 구매한 상품"은 하지 않는다** — 주문 데이터가 수십 건이라 **추천이 성립하지 않는다**
  (선착순 쿠폰을 미룬 것과 같은 판단: 볼 게 없으면 만들어도 값이 없다).

### 선착순 한정 쿠폰 발급 (Redis) — 설계 메모

사용자가 이전 프로젝트에서 만들어 본 구조다. **지금은 넣지 않는다**(2026-07-23 결정).

**왜 지금이 아닌가**
1. **실효가 없다** — LAN 안에서 단독 사용이라 동시성 자체가 없다. 락 경합도 Redis 부하도
   측정할 수 없어 잘 만들었는지 확인할 방법이 없다(Sentry 를 보류한 것과 같은 판단).
2. **더 근본적으로, 지금 쿠폰 모델엔 「한정 수량」이 없다.** 현재는 관리자가 특정 회원에게
   지정 발급하는 구조라 **선착순 경쟁이 발생하지 않는다.** 이 설계를 얹으려면 먼저
   `coupon` 에 총량 + **자가 발급(claim) API** 가 있어야 한다 — "Redis 를 붙인다"가 아니라
   **기능을 새로 만드는** 일이다.

**설계 요약** (필요해지면 여기서 출발)

| 요소 | 역할 |
|---|---|
| 총량·사용량 카운터(Redis) | 발급 가능 판단. 같아지면 소진 |
| `user_coupon` **Set** | 중복 발급 차단 — `SISMEMBER` O(1) |
| **Lua 스크립트** | 한도 확인 + 중복 확인 + 증가를 **원자적으로** 처리(사이에 끼어들 틈 제거) |
| **소진 플래그** | 소진 뒤엔 카운터를 안 읽고 플래그만 보고 즉시 거절 |
| **Pub/Sub + TTL(60초)** | 발급이 멎으면 DB 동기화 트리거(debounce) |
| **Jitter** | 동기화가 한꺼번에 몰려 Redis 를 때리지 않게 분산 |
| **Write-back** | 이벤트 중엔 Redis 가 사실상 원장, DB 는 뒤따라 반영 |
| 재시도 + 보상 트랜잭션 | 동기화 실패 시 복구 |

- 이벤트는 지금 프로젝트도 JVM 내부(`ApplicationEventPublisher`)라 **MSA 단계에서 RabbitMQ 로
  전환하면 자연스럽게 맞물린다**(ARCHITECTURE 의 메시징 방침과 같은 방향).
- ⚠ 사용자가 "jitter 말고 분산 기법 하나를 더 썼는데 기억이 안 난다"고 했다. 후보:
  exponential backoff(jitter 와 거의 항상 짝) / coalescing·debounce / probabilistic early expiration.
  착수할 때 확인할 것.

### 부하 테스트 (k6) — 순서 메모

**도구는 k6 로 정했다**(2026-07-23). 스크립트가 JS 라 가볍고, 결과 지표(p95·RPS·에러율)를
그 자체로 뽑아 준다.

**선행 조건: 선착순 발급 기능.** 지금 쿠폰은 관리자가 특정 회원에게 지정 발급하는 구조라
**경쟁 자체가 없다** — 부하를 걸 대상이 없다.

#### 두 번에 나눠 한다 — 사이에 관측 스택이 들어간다

```
1. 선착순 발급 기능
2. k6 정합성 테스트     ← 관측 스택 불필요
3. 관측 스택
4. 같은 시나리오, 부하를 키워 다시   ← 이제 "어디가" 느린지 읽힌다
```

**왜 정합성이 먼저인가** — 선착순의 진짜 리스크는 성능이 아니라 **총량 초과 발급**이다.
쿠폰 100장에 1,000명이 몰렸을 때 **느린 건 참을 수 있지만 101장이 나가면 사고**다.
그리고 이건 **단위 테스트로 절대 안 잡힌다** — 순차 호출로는 재현되지 않고 실제 동시 요청이 필요하다.

**왜 2번엔 관측이 필요 없나** — 정합성 검증은 숫자만 세면 된다:
`k6 의 발급 성공 응답 수` vs `DB 의 실제 발급 건수`. 같으면 통과다.
여기서 대시보드를 봐도 얻을 게 없다. 오히려 **관측을 먼저 깔면 볼 게 없는 상태에서
대시보드부터 만들게 된다**(§ "미리 만들지 않는다").

**왜 4번엔 관측이 필요한가** — k6 는 **밖에서 본 증상**만 준다("p99 가 800ms").
그중 얼마가 Redis 대기인지, DB 커넥션 풀 고갈인지, JVM GC 인지는 **서버 안을 봐야** 갈린다.

⚠ **지나간 부하는 데이터가 안 남는다.** 그래서 3번을 깔고 나면 2번 시나리오를 **다시 돌려야** 한다
— 4번은 새 테스트가 아니라 **같은 시나리오를 관측이 켜진 상태에서 부하만 키워 재실행**하는 것이다.

#### 검증 목표

| 단계 | 보는 것 | 통과 기준 |
|---|---|---|
| 2 정합성 | 발급 성공 수 ↔ DB 실제 발급 수 | **총량 초과 0건** · 중복 발급 0건 |
| 4 성능 | p95/p99, RPS, 에러율 + 서버 내부 지표 | 병목 지점이 **식별될 것**(숫자 목표는 그때 정한다) |

⚠ **공유 espdb 에 쏘면 안 된다.** 부하 테스트는 격리된 DB·Redis 에서 한다
— 지금도 검증용 `esptest` 계정과 Redis 별도 db 를 쓰는 것과 같은 이유(운영 오염 방지).

- 최소안: Redis 카운터(`auth:login-fail:<loginId>`) — N회 실패 시 일정 시간 차단.
  **인증번호 저장소(`EmailVerificationCodeStore`)와 같은 구조**라 패턴이 이미 있다.
- ⚠ 설계 결정: **아이디 기준이냐 IP 기준이냐.** 아이디만 막으면 한 IP 가 여러 계정을 훑을 수 있고,

<details><summary>원래 항목 (근거 보존)</summary>

⚠ **정지·강등해도 최대 30분간 그대로 통한다.** `suspend()` 는 refresh 만 지우고

> ✅ 예상한 해법(`auth:revoked-before:<memberId>` 컷오프)이 그대로 맞았다. 착수해서 새로 알게 된 것은
> **경계 처리** 하나다 — `iat` 가 초 정밀도라 `<` 로 비교하면 **강등과 같은 초에 발급된 토큰이 살아남는다.**
> fail-closed(`iat <= cutoff`)로 갔고, 대가는 그 1초 안에 로그인한 사람이 한 번 더 로그인하는 것뿐이다.

- 오늘 홈에 혜택 스트립을 넣으면서 **쿠폰을 광고하지 못한 이유가 이것**이다(핸드오프 §7-2) —
  *"가입하면 쿠폰"* 이라고 쓸 수가 없었다. **문구가 아니라 기능이 없어서** 못 쓴 자리다.
- 최소안: 가입 시 **지정한 쿠폰을 자동 발급**(설정으로 쿠폰 id 하나). `MemberSignedUpEvent` 발행 →
  coupon 도메인이 구독(도메인 경계 — audit·restock 과 같은 3층 구조).
- ⚠ **D 의 「선착순 발급」과 다르다** — 저건 총량·경쟁이 있는 이벤트 쿠폰이고, 이건 **전원 지급**이라
  동시성 문제가 없다. 그래서 지금 할 수 있다.

### G-3. 일반 고객센터 문의 — 크기 **소~중**

⚠ **상품과 무관한 문의를 넣을 곳이 없다.** `Inquiry` 는 `productId` 를 필수로 갖는다(실측) —
*"배송이 안 와요"*, *"환불 계좌를 바꾸고 싶어요"* 같은 문의를 **할 데가 없다.**

- 방법 두 갈래: ①`inquiry.product_id` 를 **nullable** 로 열고 화면에 「일반 문의」 진입점 추가
  ②별도 `support_ticket` 도메인 신설.
  → **①이 맞다.** 관리자 답변·알림(B-15)·목록이 전부 재사용된다. ②는 같은 것을 두 번 만드는 것이다.
- ⚠ 열면 **상품 문의 목록 쿼리에 `product_id is not null` 조건이 필요**하다 — 안 넣으면 상품 상세에
  일반 문의가 섞여 나온다.

### G-4. 부분 취소 — 크기 **중**

⚠ **주문 전체만 취소된다.** `cancel(id, memberId)` 이 주문 단위라, **3개 중 1개만 취소**할 수 없다.
반품도 같다(주문 단위).

- 필요한 것: 품목별 취소 상태 + **금액 재계산**(쿠폰·적립금·배송비를 어떻게 나눌 것인가).
- ⚠ **여기가 진짜 어려운 부분이다** — 쿠폰이 "3만원 이상 5천원 할인"인데 1개를 빼서 3만원 미만이 되면
  **쿠폰이 무효가 되는가?** 배송비 무료 기준도 같은 문제다. 규칙을 먼저 정하지 않으면 금액이 어긋난다.
- 크기가 "중"인 건 **UI 가 아니라 이 정산 규칙 때문**이다.

### G-5. 기간 할인 (타임세일) — 크기 **중**

⚠ **할인에 기간 개념이 없다.** `product.list_price` 를 관리자가 손으로 넣고 손으로 되돌리는 방식이라,
*"이번 주말만 20%"* 를 하려면 **주말에 사람이 앉아 있어야 한다.**

- 최소안: `product_discount`(상품·할인율/액·시작·종료) + 조회 시 유효한 것 적용.
- ⚠ **주문 스냅샷은 이미 안전하다** — 주문에 정가·판매가를 복사해 두므로(B-7) 할인이 끝나도
  과거 주문 금액은 안 변한다. **그 토대가 이미 있어서** 이 기능이 얹힐 수 있다.
- ⚠ 캐시(`products:list`)와 얽힌다 — 할인 시작/종료 시점에 캐시가 낡는다. TTL 로 버틸지 evict 할지 결정 필요.

### G-6. 등급 혜택 확장 — 크기 **소**

등급이 **적립률 하나만** 바꾼다(`MemberGrade(minPurchase, earnPercent)`). 실제 쇼핑몰의 등급은
보통 **할인·무료배송·전용 쿠폰**을 함께 준다.

- 가장 싼 확장: **등급별 무료배송 기준 인하**(VIP 는 1만원 이상 무료 등). `ShippingPolicy` 가
  이미 global 에 있어 회원 등급을 인자로 받게만 하면 된다.
- ⚠ **도메인 경계 주의** — `ShippingPolicy`(global)가 `MemberGrade`(point 도메인)를 알면 안 된다.
  **등급이 아니라 "적용할 기준 금액"을 넘겨받는** 형태여야 한다(호출자가 조회해서 넘긴다).

### G-7. 검색 보조 (최근·인기 검색어) — 크기 **소**

전역 검색은 있지만(B-8) **최근 검색어·인기 검색어·자동완성이 없다**(실측). 검색창이 비어 있으면
사용자는 **무엇을 칠지 스스로 떠올려야** 한다.

- 최근 검색어는 **localStorage 로 충분**하다(서버 불필요, 계정별 동기화는 과함).
- 인기 검색어는 **검색 로그가 필요**하다 → Redis 카운터(조회수와 같은 방식).
  ⚠ 단 지금 트래픽에선 **"인기"가 성립하지 않는다** — 최근 검색어만 먼저.

### H-2. point 도메인 단위 테스트 부재 — ✅ **완료 (2026-07-31)**

근거: `handoffs/2026-07-31-handoff.md` §2. 단위 **53건**
(`MemberGradeTest` 21 · `PointAccountTest` 15 · `PointServiceTest` 17). 전체 **397 → 450**, `skipped 0`.

> ⚠ **어림은 맞았지만(크기 소) 항목 설명 두 곳이 틀렸다.**
> ① *"소스 16개"* → 실제 **17개**. ② 더 중요한 건 *"통합 하나로 덮여 있다"* 는 표현인데,
> `OrderServiceTest` 가 `PointService` 를 **`@Mock` 으로 통째 대체**해서 **덮인 게 아니라 아예 안 돌았다.**
> "테스트가 있다"와 "그 코드가 실행된다"는 다른 말이고, **파일 개수 세기로는 이 차이가 안 보인다**
> (H-5 JaCoCo 를 적어 둔 이유가 바로 이것 — 거친 지표의 한계가 실제로 드러났다).
>
> **새로 배운 것**: 통합의 `SUM(amount)==balance` 대조는 **부호 오류를 못 잡는다**.
> 사용을 양수로 기록해도 합계 검증만으로는 드러나지 않는다 — 이력의 **종류·부호·`balanceAfter`** 를
> 직접 보는 건 단위뿐이다. 승급 직후 요율(누적 반영 **후** 등급으로 적립)도 경계에서만 갈린다.
>
> **테스트가 진짜로 잡는지 확인한 방법**: 운영 코드를 **5가지로 일부러 망가뜨려** 돌렸다 —
> 등급 `>=`→`>`(6건 실패) · 승급 전 요율(1건) · `USE` 부호 제거(3건) · 환불 `Math.max` 제거(2건) ·
> 내림→반올림(7건). **전부 실패로 잡혔고** 원복 후 diff 0 을 확인했다.
> H-5 가 못 박은 *"단언 없는 테스트로도 커버리지는 오른다"* 에 대한 답이 이 절차다 —
> **커버리지 숫자가 아니라 "망가뜨리면 빨개지는가"로 검증한다.**

  (99,999 → 100,000)처럼 **경계에서 틀리기 쉬운 계산**이 통합 테스트 한 갈래로만 덮여 있다.

### H-3. 페이징 상한 — 크기 **소** · 지금은 **영향 없음**

`?size=5000` 요청이 **200 으로 통과**한다(실측). 스프링 기본 상한(2000)에 걸려 잘리지만,
**우리가 정한 값이 아니다.**

- 지금은 데이터가 수십 건이라 **아무 일도 안 일어난다** — 그래서 "지금은 정상"이다.
- 적어 두는 이유: 데이터가 늘면 **한 번의 요청으로 전체를 긁어갈 수 있는** 자리이고,
  그때는 이미 늦다. `spring.data.web.pageable.max-page-size` 한 줄이면 된다.
- ⚠ **관리자 화면의 DxDataGrid 원격 페이징이 큰 size 를 보내는지** 먼저 확인할 것 —
  상한을 낮췄다가 관리 화면이 깨지면 안 된다.

### H-4. N+1 · 인덱스 — 지금은 **정상**, 도구만 있음

- **N+1**: `default_batch_fetch_size: 100` 이 걸려 있고 목록은 비정규화 컬럼(`avg_rating`·`sold_count`·
  `review_count`)으로 조인을 피한다 — **설계로 이미 막아 뒀다.**
- **인덱스**: C-11 에 *"주문 수천 건이 되면 `(status, paid_at)` 복합 인덱스를 검토한다"* 는
  **임계치가 이미 적혀 있다.** 지금 25건 규모에선 `TABLE ACCESS FULL` 이 최적이다.
- **측정 도구**: P6SPY 가 dev 에 붙어 있어(2026-07-16) 실제 SQL·실행시간을 볼 수 있다.
- → **할 일 없음.** 임계치에 닿으면 그때 P6SPY 로 재고, 그 전엔 손대지 않는다(D 의 「리뷰 목록 캐시」와 같은 판단).

### H-5. JaCoCo (테스트 커버리지 측정) — 크기 **소** · 사용자 제안 2026-07-29

⚠ **"AI 가 코딩하니 커버리지 도구는 필요 없지 않나"** 라는 질문에서 나왔다. **판단은 반대**다.

사람이 쓰면 *"이건 테스트했고 저건 안 했다"* 는 감각을 머릿속에 갖고 다니는데,
**2026-07-29 하루에만 커밋이 63개**였다. 그 감각을 **아무도 들고 있지 않다.**
실제로 같은 날 H-1·H-2 를 찾은 방법이 **파일 개수 세기**였다 — 거친 지표다
(테스트 파일이 5개여도 커버리지가 20% 일 수 있다). **줄·분기 단위로 정확히 재는 것**이 필요하다.

- **도입 조건은 충족**: JaCoCo **0.8.14 가 Java 25 를 공식 지원**한다(확인 2026-07-29).
  Gradle 플러그인 한 줄, 외부 전송 없음, 리포트는 로컬 HTML.
- ARCHITECTURE §6 「학습 트랙」의 **"볼 게 있느냐"** 기준을 통과한다 — **테스트가 359개 있다.**
  Sentry 를 보류했던 것과 **정반대 상황**이다(그건 받을 곳이 없어 no-op 이었다).

⚠ **도입한다면 조건이 붙는다 — 이 항목의 핵심은 여기다:**

| 규칙 | 이유 |
|---|---|
| **리포트만, 게이트(최소 %) 없이** | 빌드를 막기 시작하면 **숫자 채우기가 목적**이 된다 |
| **"커버리지 올려줘"라고 시키지 않는다** | ⚠ AI 는 **단언 없는 테스트를 아주 빠르게 대량 생산**할 수 있다. 숫자는 오르고 안전은 안 오른다 |
| 쓰는 법은 **"이 분기가 안 덮였는데 진짜 위험한가"** | 목표 수치가 아니라 **H-1·H-2 를 정확히 재는 자**로 쓴다 |

> **커버리지는 정확성이 아니다.** 단언 없는 테스트로도 100% 가 나온다 —
> "이 줄이 실행됐다" 만 재지 "이게 맞다" 는 재지 못한다. 규약으로 못박고 시작할 것.

- 착수하면 **현재 커버리지 실측치**가 나오므로 H-1·H-2 의 크기 어림도 같이 정확해진다.
