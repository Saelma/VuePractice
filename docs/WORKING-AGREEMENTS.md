# 작업 합의 (Working Agreements)

> **이 문서는 날짜가 없다.** 날짜별 핸드오프(`docs/handoffs/YYYY-MM-DD-handoff.md`)는 "그날 무엇을
> 했나"를 적지만, 여기엔 **"어떻게 일하기로 했나"** 를 적는다. 핸드오프에 적힌 교훈은 다음 날 문서가
> 생기면 묻히기 때문에, 계속 지켜야 할 것은 전부 이리로 옮긴다.
>
> 항목마다 **왜 생겼는지(실제 사고)** 를 같이 적는다. 이유를 모르면 지키다가도 슬그머니 사라진다.
> 규칙이 늘면 줄이지 말고, 대신 **원인이 구조적으로 제거된 항목은 삭제**한다.

## 1. 작업 시작 전

### 1-1. 핸드오프는 최소 2일치 + ARCHITECTURE를 대조한다

최신 핸드오프 하나만 읽으면 **직전 문서에서 조용히 빠진 이월 항목**을 놓친다.

> **사고 (2026-07-20)**: 7/15 문서에 "재고 부족 알림"이 다음 할 일로 있었는데, 7/16 작업 때
> 주문 상태 확장만 하고 이 항목은 7/16 문서에서 사라졌다. 7/16만 보면 존재 자체를 알 수 없다.
> 같이 드러난 것: 7/15가 설계한 "이미지 그룹 재사용"이 product에만 연결돼 미증명 상태였고,
> 7/16이 만든 이벤트 3층 구조도 Handler가 stub 하나뿐이라 주장이 검증되지 않은 상태였다.

→ **§4의 「이월」 규약**이 이 문제의 구조적 해법이다. 대조는 그 보조 수단.

### 1-2. 스스로 뽑은 작업 목록은 한 번 뒤집어 본다

문서를 더 읽으면 우선순위가 바뀔 수 있다. 바뀌었으면 **"앞선 판단을 바꿉니다"라고 말하고** 바꾼다.

### 1-2-1. 짝이 있는 흐름은 **나란히 놓고 본다** — 백로그는 「없는 것」을 못 적는다 (2026-08-07)

`BACKLOG.md` 는 *"무엇을 만들 것인가"* 를 적는 문서다. 그래서 **이미 있는 기능 안의 구멍은
구조적으로 거기 없다** — 아무도 그걸 «만들 것» 으로 적지 않았기 때문이다.
그 구멍이 가장 잘 숨는 자리가 **짝이 있는 두 흐름 중 한쪽**이다.

> **사고 (2026-08-07)**: **주문을 취소하면 쓴 적립금이 사라지고 있었다.** 차감은 주문 시점에
> 끝나 있는데 `cancel()` 은 재고 복원과 알림만 했다. **반품 승인은 처음부터 환불하고 있었다.**
> 화면은 «취소됨» 으로 멀쩡하고 알림도 정상이라, 고객이 잔액을 보기 전까지 아무도 모른다.
> 발견 경위가 핵심이다 — 백로그에서 고른 게 아니라 **다음 후보를 코드에서 다시 뽑다가** 나왔다.

**같은 모양이 이미 세 번 있었다**: B-17(반품엔 사유가 있는데 취소엔 없다, 7/29 발견 → 8/04 수정) ·
E-1/E-2 비대칭(7/30) · 오늘. 앞의 둘은 **읽다가 눈에 띄어** 백로그 항목이 됐지만,
오늘 것은 **돈이 걸려 있었는데도** 아무 목록에도 없었다.

- [ ] **한쪽을 손댈 때 반대쪽을 열어 나란히 놓는다.** 짝의 예: 취소↔반품 · 등록↔삭제 ·
      구독↔해지 · 발행↔회수 · 숨김↔복구.
- [ ] 🔴 **«남기는 쪽 ↔ 보는 쪽» 도 짝이다** (2026-08-10). 값을 늘렸으면 **그 값을 표시·필터하는 쪽**을
      같이 연다 — enum↔라벨, 상태↔뱃지, 이벤트↔알림 문구.
      > **사고**: 감사 `AuditAction` 이 9개인데 프론트 라벨은 **3개**였다. `MEMBER_DELETE` 는
      > **11일간** 빠져 있었고 아무것도 안 터졌다 — 목록은 그려지고 화면도 멀쩡한데,
      > **필터에서 고를 수 없고** 날문자로 떴다. 감사를 «남긴다» 는 참인데 «볼 수 있다» 가 거짓이었다.
      ⚠ **이 짝은 조용해서 오래 간다.** 되돌리는 흐름(취소↔반품)은 돈이 어긋나 드러나지만,
      표시 쪽은 **어긋나도 아무 신호가 없다.** 그래서 여기는 규율이 아니라 **대조 테스트**로 막는다
      (§3 의 «드리프트 테스트» — 한쪽 파일을 읽어 키 집합을 단언한다).
- [ ] 🔴 **대조 테스트는 «지키는 코드와 다른 모양」이어야 한다** (2026-08-10).
      값을 **손으로 열거하는** 코드를 **손으로 열거하는** 테스트로 지키면, 값이 늘 때 **둘이 같이**
      어긋난다. 지키려면 **한쪽에서 목록을 읽어 와야** 한다(enum 파일·DB CHECK·`values()`).
      > **같은 날 양쪽 예가 다 나왔다.** ✅ 감사 라벨은 테스트가 `AuditAction.java` 를 **읽어서**
      > 대조하므로 enum 이 늘면 빨개진다. 🔴 리뷰 구매 인증은 코드가 3개 상태를 열거하고
      > 통합 테스트도 **같은 4개만** 세어, `DELIVERED` 가 늘었을 때 **아무도 안 빨개졌다**
      > (2026-07-16 의 같은 사고를 막으려고 만든 테스트였다 — 08-10 §16-2-1).
      ⚠ **«테스트가 있다» 는 근거가 아니다.** 무엇을 근거로 기대값을 만드는지를 본다 —
      기대값이 **사람 손**에서 나오면 그 테스트는 코드와 함께 낡는다.
- [ ] ⚠ **되돌리는 흐름끼리는 «무엇을 되돌리나» 를 항목으로 대조한다.** 이름이 비슷하다고
      같은 일을 하지 않는다 — 취소는 재고만 되돌렸고 반품은 재고·환불·적립·등급을 되돌렸다.
- [ ] 🔴 **목록이 맞아도 «양»이 틀릴 수 있다 — 읽는 값이 «원본»인지 «남은 것»인지도 대조한다**
      (2026-08-24). 위 네 줄이 지키라는 것은 전부 **«되돌릴 것들의 목록»** 이다. 목록이 다 맞아도
      **각 항목이 얼마를 되돌리는지**는 안 본다. 되돌리는 흐름에 «부분» 이 생기는 순간
      **«원본 = 남은 것» 이 깨지는데**, 그 등식은 코드 어디에도 안 적혀 있다 — 부분이 없던 시절엔
      구별할 이유가 없어서 **아무도 안 적었기 때문이다.**
      > **사고 (2026-08-24)**: 부분 취소(G-4)를 만든 뒤 **전체 취소가 적립금 2,000 을 다시 전액
      > 돌려줬다** — 이미 857+571 을 돌려준 주문에서. 재고도 2개 주문에 3개가 복원됐다.
      > `applyCancellation` 이 `getQuantity`·`getUsedPoint` 라는 **원본 스냅샷**을 읽었다.
      > 🔴 **§1-2-1 을 지켰는데도 났다** — 짝(`applyCancellation`↔`applyItemCancellation`)을 열어
      > 읽었고, 이 규약을 **코드 주석에 인용까지 했다**(`OrderService.java:394`). 그런데도 놓쳤다.
      > 🔴 **단위·통합 938개가 전부 초록인 채로** 운영에서 1,428원이 새어 나갔고, **브라우저 검증이**
      > 잡았다. ⚠ 원장 불변식(`SUM(point_history) == 잔액`)도 못 잡는다 — **잘못된 환불이 원장에
      > 성실히 기록됐다.** 불변식이 지키는 것은 «이력과 잔액이 맞는가» 지 «옳은 이력인가» 가 아니다.
      ⚠ **이 유형은 이것이 첫 번째다**(2026-08-25 에 「두 번」·「중복」·「원본」·「스냅샷을 읽」·
      「합이 안 맞」·「전량」 등 **여러 갈래로 다시 세어 0건** 확인). 한 번인데 올린 이유는
      **«규약을 지켰는데도 났다»** 하나다 — 그 하나가 «한 번은 조건, 두 번은 규약» 보다 무겁다고 봤다
      (2026-08-24 사용자 결정).
      🔴 **다음에 걸릴 자리는 이미 보인다 — 부분 반품**(G-4 결정 4 가 미룬 것). `approveReturn` 이
      읽는 값이 원본인지 남은 것인지가 **08-24 와 똑같은 모양**이다.
- [ ] ⚠ **안내 문구가 비어 있으면 기능을 의심한다.** 반품 폼은 *"적립금으로 환불됩니다"* 를
      말하고 있었고 취소 폼은 아무 말이 없었다. **신중해서가 아니라 실제로 안 하고 있었다.**

### 1-3. 리디자인·개선은 **현재 화면부터 읽고** 착수한다 (헛손질 방지)

이 프로젝트는 화면이 **이미 로드맵대로 상당부분 구현돼 있다**(DESIGN.md §9 로드맵이 앞서 이행됨).
2026-07-28 디자인 로드맵에서 상품 목록·상세·장바구니·주문서가 전부 "이미 카드/2단/우측요약"이라,
"표→카드" 같은 전면 재설계는 헛손질이었다(§12 교훈). **착수 전 그 화면 파일을 먼저 읽어** 무엇이 이미
돼 있는지 확인하고, "전면 재설계"가 아니라 **벤치마크 기준 폴리싱**으로 범위를 좁힌다. 사용자가 "이거
이상하지 않냐"고 물으면 감으로 고치지 말고 **현재 코드·동작을 먼저 확인**한다(필터 토글 데스크톱 버그 사례).

⚠ **문서의 「결론」이 맞아도 「이유」는 틀릴 수 있다 — 이유까지 실측한다** (2026-08-05).

> **사고**: 조건부 잔여가 *"고치려면 **재연결 정책과 토큰 갱신을 같이** 봐야 한다 — 한 줄 수정이
> 아니다"* 라고 적어 뒀다. **결론(작지 않다)은 맞았다.** 그런데 이유는 틀렸다 — 백오프도 401→갱신
> 로직도 **둘 다 이미 있었고**, 진짜 원인은 **알림 SSE 가 `request()` 를 안 거치고 생 `fetch` 를 써서
> 그 갱신 경로를 통째로 비켜간 것** 하나였다.
> ⚠ **결론만 보고 착수했으면 엉뚱한 곳(백오프·재시도 정책)을 고쳤을** 자리다 — 그리고 그건
> *"고쳤는데 증상이 그대로"* 로 끝난다(`TROUBLESHOOTING.md` §3-6 과 같은 모양).

→ 착수 전 실측은 *"이 문장이 맞나"* 가 아니라 **"이 문장이 대는 이유가 코드에 있나"** 를 본다.
→ 같은 날 이 함정이 **세 번** 나왔다(위 사례 · `stock_history` 행수 · `server.shutdown` 기본값).
   셋 다 **문서를 베껴 적는 순간** 생겼다.

## 2. 코드를 고칠 때

### 2-1. 엔티티를 고치면 마이그레이션이 세트로 따라온다

`ddl-auto: validate`라 **컬럼을 추가하고 마이그레이션을 안 쓰면 앱이 아예 안 뜬다.**

- **컬럼 추가 시 기존 데이터 백필이 필요한지 반드시 확인한다.**
  > **사고**: `product.avg_rating`을 추가할 때 백필을 안 넣었으면, 기존 상품은 전부 별점 0이 되고
  > **그 상품에 리뷰가 새로 달릴 때까지 영영 0으로 남는다**(갱신이 이벤트로만 일어나므로).
- 기존 행이 있으면 `NOT NULL`로 바로 못 만든다 → `nullable 추가 → 백필 → NOT NULL 확정` 3단계.
- **적용된 마이그레이션은 수정 금지**(체크섬). 되돌리려면 새 버전으로 보정한다.

### 2-2. 마이그레이션을 추가하면 빈 DB 적용까지 검증한다

기존 DB에서 성공하는 것과 **빈 DB에서 처음부터 깔리는 것은 다른 문제**다.

> **사고**: `V1__init.sql`이 없어서 빈 DB에서는 V2의 `CREATE INDEX`가 테이블 부재로 실패했다.
> 만들 때도, Hibernate 덤프를 그대로 쓰면 V3~V5가 추가하는 컬럼이 이미 들어 있어
> "이미 있는 컬럼을 ADD"로 실패한다 — V1은 **baseline 시점 스키마**여야 했다.

→ 검증 전용 계정 **`esptest`를 상시 유지**한다. 절차는 `glassvue-backend/src/main/resources/db/migration/README.md`.

### 2-2-1. Oracle `VARCHAR2(n)`은 **바이트**다 — 항상 `n CHAR`로 쓴다

이 DB의 `NLS_LENGTH_SEMANTICS`는 `BYTE`다. `VARCHAR2(50)`은 한글 약 16자밖에 못 담는다.

> **사고**(2026-07-21 발견): `V1__init.sql`은 전부 `VARCHAR2(n CHAR)`로 썼는데 **V5·V9가 `CHAR`를 빠뜨렸다.**
> 그래서 `member.nickname`은 50자인데 그걸 복사해 넣는 `orders.buyer_nickname`은 50**바이트**였다 —
> 닉네임이 한글 17자 이상인 회원은 **주문 자체가 ORA-12899로 실패**한다. 그런 회원이 아직 없어 안 터졌을 뿐이다.
> (V12에서 보정. 넓히는 방향이라 온라인으로 적용됐다.)

→ 마이그레이션에 `VARCHAR2`를 쓸 때는 예외 없이 `CHAR`를 붙인다.
→ **스냅샷 컬럼은 원본 컬럼과 길이·semantics가 같아야 한다.** 원본에서 통과한 값이 복사할 때 터진다.
→ 확인: `select column_name, char_used, char_length from user_tab_columns where table_name='X'`
(`char_used='B'`면 바이트 — 잘못된 것이다).

### 2-2-2. 🔴 새 컬럼의 `DEFAULT` 가 **기존 행에 대해 참인지** 본다 (2026-08-25)

§2-2 는 «빈 DB 에서 깔리나» 를, WA §2-4-2 는 «제약을 어기나» 를 본다. **둘 다 «뜻이 맞나» 는 안 본다.**
새 컬럼에 `DEFAULT 0`(또는 NULL)을 주면 기존 행이 전부 그 값을 갖게 되는데, 그게 **사실인 칸**과
**거짓말이 되는 칸**이 있다.

- **«얼마나 빠졌나» 류** — 0 이 <b>사실</b>이다. 그 기능이 없던 시절의 행이라 실제로 0 이다.
- 🔴 **«무엇을 요청했나 · 어떤 상태인가» 류** — 0/NULL 이 «없다» 인지 «모른다» 인지 **갈린다.**
  기존 행이 이미 «요청됨» 상태라면 0 은 **거짓**이다.

> **사고 (2026-08-25, V58 → V59)**: 부분 반품(G-10)이 `order_item.return_requested_quantity` 를
> `DEFAULT 0` 으로 넣었다. **이미 `RETURN_REQUESTED` 이던 주문**의 요청은 «주문 전체» 였는데
> (부분이라는 개념이 없던 시절이다) 새 코드가 그걸 **«아무 품목도 안 골랐다»** 로 읽어 승인이
> `ORDER-400RI` 로 거부됐다. 🔴 **고객은 요청해 놓고 영영 처리되지 않고, 관리자는 자기가 뭘 잘못
> 눌렀는지 알 수 없다.**
> ⚠ **V58 은 이 질문을 «하긴 했다»** — 누적 칸 셋(`returned_*`)에 대해 «0 은 모르는 값이 아니라
> 아는 값이다» 를 따져 적어 뒀다. **성격이 다른 넷째 칸에만 안 물었다.**
> ⚠ 🔴 **테스트로는 안 나온다.** 테스트가 만드는 행은 전부 **새 코드로** 만들어져서
> «마이그레이션 이전부터 그 상태이던 행» 이 **존재할 수 없다.** 전수 955 가 초록이었다.

**이 질문은 이미 두 번 «제대로» 물어졌다** — V55(G-9)가 «모르는 값은 NULL» 로 갔고(세일 흔적을
모르는 옛 주문에 «세일이 없었다» 고 말하지 않으려고), V57 이 «0 은 아는 값이다» 를 따졌다.
🔴 **2026-08-25 가 처음으로 «묻고서 틀린» 경우다.** 그래서 규약으로 올린다 — 물을 줄 몰라서가
아니라 **칸마다 다시 물어야 하는데 한 번 묻고 넘어가서** 났다.

- [ ] **컬럼마다 따로 묻는다.** 한 마이그레이션이 칸을 여럿 만들면 «이 마이그레이션의 기본값» 이
      아니라 **«이 칸의 기본값»** 을 각각 본다. 같은 스크립트 안에서도 답이 갈린다.
- [ ] **답이 «거짓» 이면 보정 UPDATE 를 같은 스크립트에 담는다.** 이미 적용된 뒤 알았으면
      **새 `V<n>`** 으로 낸다(적용된 스크립트는 수정 금지 — 체크섬).
- [ ] 🔴 **보정 조건은 «새 방식과 구분되는» 것이어야 한다.** 「값이 0 인 행」으로 잡으면
      **새 코드가 일부러 0 으로 둔 행까지** 덮는다. 위 사고에서는 «그 주문의 품목이 **전부** 0» 로
      좁혔다 — 하나라도 0 이 아니면 그건 새 방식으로 고른 요청이고 0 인 품목은 **일부러 뺀** 것이다.
      ⚠ 좁힌 조건은 대개 **다시 돌려도 안전하다**(두 번째엔 성립하지 않는다).
- [ ] ⚠ **배포 순서를 근거로 쓸 수 있다.** Flyway 는 **새 jar 가 뜰 때** 돌고 그때 구 jar 는 이미
      멈춰 있다 — 구 jar 가 만든 마지막 행까지 보정 스냅샷에 들어온다.
- [ ] 🔴 **확인은 실측이다.** 그 칸이 뜻을 갖는 상태의 행을 운영에서 뽑아 **눈으로 본다.**
      → 증상으로 만났을 때의 진단은 `TROUBLESHOOTING.md` §1(DB·마이그레이션)에 있다.

### 2-1-1. 컬럼을 **지우는** 변경은 한 마이그레이션에 담지 않는다 (expand / contract)

컬럼 추가는 구 jar 에 무해하지만 **컬럼 삭제는 구 jar 를 죽인다.** 통합 테스트를 돌리는 순간
Flyway 가 공유 espdb 에 적용하므로(§5), *배포하기 전에* 운영이 깨진다.

> **왜 (2026-07-24)**: 배송지 주소록(V18)에서 `member.ship_*` 5컬럼을 새 테이블로 옮겼다.
> 같은 마이그레이션에서 DROP 했다면 — 운영 구 jar 는 그 컬럼을 매핑 중이라 **재기동 불가**가 되고,
> `MemberResponse`·회원 조회는 그 즉시 `ORA-00904` 로 깨졌을 것이다.
> 7/21 의 닉네임 UNIQUE(V6) 사고와 같은 종류인데 **훨씬 파괴적**이다 — UNIQUE 는 신규 가입만 막았지만
> 컬럼 DROP 은 **이미 되던 조회를 통째로** 깬다.

→ 둘로 나눈다. **Vn: 추가 + 값 복사(구 jar 무영향) → 신 코드 배포 → Vn+1: 옛 것 DROP.**
→ 뒤쪽은 **이월이 아니라 백로그**에 둔다. "며칠 안에" 가 아니라 **"배포가 안정된 뒤"** 라는 조건부라
   수명이 다르다(이월에 두면 매일 복사돼 내려온다).

**그 사이의 이중 진실은 규율이 아니라 구조로 막는다.**

> *"신 코드는 옛 컬럼에 쓰지 않기로 하자"* 라고 **적어두고 끝내면 언젠가 누가 쓴다.**
> V18 에서는 **엔티티에서 매핑 자체를 걷어냈다** — 필드가 없으면 쓸 방법이 없다.
> `ddl-auto=validate` 는 **매핑되지 않은 여분 컬럼을 문제 삼지 않는다**(실측 확인).
> 부수효과로 **뒤쪽 마이그레이션은 코드 변경이 0** 이 된다 — 순수 DDL 한 줄.

### 2-3. 권한·소유 판단은 프론트와 백엔드 기준을 일치시킨다

> **사고**: 백엔드 `pay`/`cancel`은 `findByIdAndMemberId`로 **소유 기준**인데, 프론트는
> `v-if="!isAdmin"`으로 **역할 기준**이었다. 관리자가 직접 구매하면 자기 주문인데 버튼이 사라진다.

→ 프론트는 백엔드가 **실제로 쓰는 기준**을 그대로 따른다. 화면이 판단하려면 응답에
근거 필드가 있어야 한다(없어서 `OrderResponse.memberId`를 추가했다).

### 2-4. 새 관리자 엔드포인트엔 권한 테스트(401/403/200)를 반드시 붙인다

권한 규칙은 **서비스 단위 테스트로 절대 안 잡히고** 실제 요청을 보내야만 드러난다.

> **사고**: `POST /api/images`가 상품용으로 만들 때의 `hasRole("ADMIN")`에 묶여 있어,
> 포토 리뷰를 다 만들고 E2E를 돌리자 `AUTH-403`으로 통째로 막혔다.

→ 관리 API는 경로를 `/api/admin/**`로 모아 **한 줄로** 막는다(개별 매처를 잊을 수 없게).

#### 2-4-1. ⚠ 그 401이 **무엇을 증명하는지** 구분한다 (2026-08-07)

`anyRequest().permitAll()`이 기본이라 *"매처를 안 넣으면 열린다"*고 생각하기 쉬운데,
**경로마다 다르다.** 확인할 것은 하나다 — **컨트롤러가 소유자를 어디서 받나.**

| 컨트롤러가 | 매처를 빼면 | 예 |
|---|---|---|
| 경로·쿼리에서 받거나 서비스가 찾는다 | 🔴 **정말로 열린다** | 쿠폰·찜·적립금 |
| `@LoginUser AuthUser`(required=true)로 받는다 | **안 열린다** — 리졸버가 막는다 | `/api/inquiries/me` |

> **실측(2026-08-07, G-3)**: `/api/inquiries/me`의 권한 규칙을 **통째로 지우고** 테스트를 돌렸는데
> **전부 통과했다.** `LoginUserArgumentResolver`가 `UNAUTHENTICATED`를 던지고,
> `CustomAuthenticationEntryPoint`도 **같은 ErrorCode**를 쓴다 — 두 방어선이 **HTTP로 구분되지 않는다.**

→ **매처는 그래도 넣는다.** 다만 이유를 *"없으면 뚫린다"*로 적지 않는다. 진짜 이유는 둘이다:
① 인가는 **컨트롤러 앞**에서 끝나야 한다(앞에 필터가 붙는 순간 리졸버 방어의 전제가 깨진다),
② `@LoginUser`를 빼거나 `required=false`로 바꾸는 **한 줄 수정**이 그 경로를 조용히 공개로 만든다.

→ **테스트 주석에 무엇을 못 박는지 적는다.** 위 401은 «규칙이 있다»가 아니라
**«비로그인에게 남의 것이 안 나간다»**라는 결과다 — 어느 방어선이 잡든 참이어야 하는 것.
규칙 자체를 지키는 것은 테스트가 아니라 **코드 리뷰의 몫**이다.

### 2-4-2. DB 제약이 **앱에서 안 밟히면** SQL로 직접 넣어 본다 (2026-08-07)

앱이 먼저 잡는 방어(엔티티 생성자·서비스 가드)가 있으면, 그 아래 DB 제약은
**한 번도 실행되지 않는다.** 그래서 «걸어 뒀다»는 말만 남고 **진짜 도는지는 영영 모른다** —
오타가 있어도, 조건이 뒤집혀 있어도 테스트는 전부 초록이다.

→ 마이그레이션 검증(§2-2) 때 `esptest`에서 **직접 INSERT** 해 본다.
⚠ **거부만 확인하면 안 된다**(§3-3) — *"전부 막는 제약"*과 구분되지 않는다.
**어긋난 행이 거부되는 것 + 올바른 행이 들어가는 것**을 함께 보고 `rollback` 한다.

> 실측 예(2026-08-07 V42 `ck_inquiry_product_pair`): 어긋난 3종 `ORA-02290` 거부 ·
> 올바른 일반 문의 `ROWS_AFTER_INSERT=1` · `rollback` 후 0.

### 2-5. "재발 방지"와 "기존 잔재 정리"는 별개 작업이다

코드로 앞으로를 막아도 **이미 쌓인 건 그대로 남는다.**

> **사고**: 고아 이미지가 다시 안 생기게 고친 뒤에도 주인 없는 그룹 3개가 남아 있어
> 일회성 수동 정리가 필요했다. V4 백필도 같은 구조였다.

→ 재발 방지 코드를 넣을 때 **기존 데이터 상태를 반드시 같이 확인**한다.
안 그러면 "고쳤는데 왜 아직 남아 있지?"가 된다.

### 2-7. 직렬화기·캐시 포맷을 바꾸면 실측으로 호환을 확인한다

캐시(Redis)·직렬화 값은 **이미 쌓인 게 있다.** 직렬화 방식을 바꾸면 신 코드가 구 값을 못 읽어
**배포 직후 역직렬화 실패(500)** 가 날 수 있다.

> **사고 (2026-07-21)**: `[removal]` 경고를 없애려 캐시 직렬화기를 바꿨는데, 알고 보니 생성자가 아니라
> **클래스 전체가 deprecated**(Spring Data Redis가 Jackson2→3로 이동)라 "한 줄 교체"가 **메이저 마이그레이션**이었다.
> 게다가 Jackson3는 스칼라(UUID/Instant/enum)를 `["타입","값"]`로 안 감싸 **와이어 포맷이 바뀌었다** —
> 구·신 포맷이 상호 역직렬화 불가. 바이트/왕복 테스트를 돌리기 전엔 안 보였다.

- **"deprecated 정리"가 라이브러리 메이저 이전일 수 있다.** 교체 API가 같은 클래스의 다른 생성자인지,
  아예 **다른 클래스/패키지(다른 메이저)** 인지 먼저 확인한다. 후자면 스코프가 커지니 **알리고** 진행한다(§1-2).
- **포맷 호환은 실측한다.** 구·신 직렬화기의 출력을 **바이트 비교**하거나, 최소한 실제 값 타입으로
  **왕복(serialize→deserialize) 테스트**를 만든다. 테스트로 고정해 회귀를 막는다.
- **포맷이 바뀌면 배포 전략을 세운다** — 캐시 flush(키 삭제) 또는 캐시 이름에 버전. 핸드오프 배포 절에 적는다.
- **공유 Redis에서 신 포맷을 검증할 땐 격리한다** — 별도 DB 인덱스(`spring.data.redis.database`)로 띄워
  운영 키를 안 건드리게. 안 그러면 구 jar(운영)가 신 포맷 값을 읽고 500난다.

### 2-6. 되돌릴 수 없는 작업은 커밋 이후로 미룬다

파일 삭제·외부 전송처럼 롤백이 안 되는 일은 트랜잭션 안에서 하지 않는다.

> 트랜잭션 안에서 파일을 지우면 롤백 시 DB row는 살아나는데 파일은 사라져 **깨진 이미지**가 된다.
> 반대 방향 실패(파일만 남음)는 디스크만 낭비하므로 감수할 만하다.

→ `@TransactionalEventListener(AFTER_COMMIT)`로 미룬다.

### 2-8. **없으면 안 되는 자리에 `?.` 를 쓰지 않는다** — 옵셔널 체이닝은 실패를 삼킨다

`el?.scrollIntoView(...)` 는 *"요소가 없으면 넘어간다"* 는 뜻이다. **없으면 기능이 성립하지 않는
자리**에 쓰면 버그가 에러도 로그도 없이 사라진다.

> 실제 사고(2026-07-31, B-15): 알림 링크의 `#inquiries` 앵커가 안 먹었다. 원인은 `v-if="loading"`
> 뒤에 있는 섹션의 `ref` 가 아직 `null` 이었던 것인데, `?.` 때문에 **조용히 no-op** 이 되어
> 콘솔에 아무것도 안 남았다. 같은 자리의 `IntersectionObserver` 도 같은 이유로 **한 번도 관측한 적이
> 없었는데**(탭 밑줄이 스크롤을 안 따라감) 아무도 못 봤다 — 탭 *클릭*은 정상이라 증상이 반쪽만 보였다.

- **`v-if` 뒤의 `ref` 는 그 분기가 실제로 렌더된 뒤에만 존재한다.** 로딩 플래그를 `finally` 에서
  내리면 `await nextTick()` 을 지나도 화면은 스켈레톤이고 ref 는 전부 `null` 이다.
  → **플래그를 먼저 내리고 `nextTick` 을 기다린 뒤** DOM 을 만진다.
- 방어가 필요하면 **삼키지 말고 드러낸다**: `if (!el) { console.warn(...); return; }`.

### 2-9. 화면 위치(스크롤·앵커)는 **한 번 계산해서 끝내지 않는다**

아래 섹션으로 데려가는 코드는 **위쪽이 나중에 자라면** 엉뚱한 곳에 선다(목록·이미지가 따로 로딩되는
페이지가 전부 해당). 스크롤은 시작 시점의 위치로 가기 때문이다.

→ `ResizeObserver` 로 **레이아웃이 잠잠해질 때까지 다시 맞추고**, 짧은 시한(2초)과
**사용자 입력**(`wheel`·`touchstart`·`keydown`)에서 즉시 손을 뗀다(스크롤 하이재킹 방지).
화면을 벗어날 때 정리하는 것까지가 한 세트다.

### 2-10. **필드를 지우거나 뜻을 바꾸기 전에 그 이름을 저장소 전체에서 센다** (2026-08-19)

필드를 없애는 것만 위험한 게 아니다 — **같은 이름을 그대로 두고 뜻만 바꾸는 것이 더 위험하다.**

> **사고 직전 (2026-08-12 §14-2)**: 컨트롤러를 통째로 덮어써 API 둘이 사라졌다 —
> *"내가 고치는 화면만 보고 응답을 줄였다."*

→ **세는 것이 답을 준다.** 2026-08-19 에 두 번 실제로 값을 했다:

- **G-5**: `ProductResponse.price` 의 뜻을 «판매가» → «세일가» 로 바꾸려 할 때 프론트에서
  `product.price` 를 읽는 자리를 셌더니 **8곳 중 7곳이 고객가, 1곳만 관리자 입력칸**이었다.

  세일이 조용히 안 먹는다.** 위험을 흩는 대신 **한 곳에 모았다.**
  ⚠ 세지 않았으면 `ProductFormView` 가 세일가를 원가로 굳혀 **할인이 두 번 먹었다.**
- **B-27**: 달력 DTO 에서 `discountType`·`discountValue` 를 빼려 할 때 `couponDiscountText` 를 셌더니

→ 실무 규칙:
```bash
grep -rn "\.필드명\b" src/ --include=*.vue --include=*.js | grep -v "\.test\."   # 프론트
grep -rn "필드명\|getter명" src/main/java --include=*.java                          # 백엔드
```
→ **세고 나서 갈래를 나눈다**: «전부 같은 뜻인가» / «몇 곳만 다른가».
   🔴 **한 곳만 다르면 그 한 곳에 위험을 모으는 쪽이 낫다** — 여러 곳에 흩으면 «빠뜨린 한 곳» 이
   어디인지 나중에 알 수 없다.
→ ⚠ **이름이 뜻과 어긋난 채 살아 있을 수도 있다.** B-27 의 `event` 는 실제로는
   «격자에 그릴 것인가» 였다(→ `gridded`). **세다 보면 그런 것이 드러난다.**

### 2-11. **주석에는 «제약» 을 적고 «경위» 는 링크한다 — 실측 서사의 원본은 핸드오프 하나다** (2026-09-03)

CLAUDE.md 의 자리 나누기(*"같은 사실을 두 곳에 적으면 한쪽만 고쳐져 어긋난다. 원본은 핸드오프
하나뿐이다"*)는 **문서끼리의 규칙으로만 읽혀 왔다.** 코드 주석은 그 규칙 밖에 있었고, 그래서
핸드오프의 사고 서사가 주석으로 한 번 더 쓰였다.

> **실측 (2026-09-03)**: `glassvue-backend/src/main` 이 22,245줄 중 **주석 6,962줄(31%)** 이다.
> 일반적인 자바 프로젝트는 10~15% 다. ⚠ **그런데 문제는 밀도가 아니다** — 한 줄 `//` 는
> **682줄뿐**이고 나머지가 전부 javadoc(블록 889개 · 본문 5,374줄 · **블록당 평균 6줄**)이다.
> 즉 «코드를 그대로 옮겨 적은 소음» 이 아니라 **«경위를 옮겨 적은 서사»** 다.
>
> **사본이 실제로 갈렸다**: `OrderCancelledEvent` 가 자기 주석에 이렇게 적어 뒀다 —
> *"같은 이벤트의 `lines` 는 08-25 에 «남은 것» 으로 고쳤는데 **이 필드는 안 봤다**"*.
> 한 파일 안에서도 갈린 것이다.

→ **사본은 세면 보인다.** 실측값 하나가 몇 곳에 서술돼 있는지 세 본다:

```bash
grep -rhoE '2026[0-9]{4}-[0-9]{4}' glassvue-backend/src glassvue-frontend/src | sort -u | while read n; do
  printf "%s  코드 %d곳 / 핸드오프 %d곳\n" "$n" \
    "$(grep -rl "$n" glassvue-backend/src glassvue-frontend/src | wc -l)" \
    "$(grep -rl "$n" docs/handoffs/ | wc -l)"
done
```

2026-09-03 결과: 🔴 **`20260820-4733`(세일가 흔적이 안 남는다) 한 건이 6개 파일 7줄에 서술돼 있다** —
백엔드 `OrderItem`·`OrderServiceTest`·`V55` SQL · 프론트 `product.js`·`product.test.js`·
`OrderDetailView.vue`. `20260824-5296` 은 5개 파일. **한 사실을 일곱 번 적어 두면 일곱 번 고쳐야 한다.**
⚠ 위 명령은 **파일 수**를 센다(`grep -rl`) — 줄 수를 쓰려면 `-l` 을 뺀다(§4-3-1).

→ **가르는 기준은 «지우면 누가 코드를 잘못 고치나»** 다:

- **코드에 남긴다 — 제약**: 필드의 뜻과 단위(«이번 회차 금액이지 원금이 아니다»), 순서 의존,
  함께 넓혀야 할 CHECK 제약, 책임 경계(«여기서 자르지 않는다 — `AdminAuditLog` 가 한다»),
  고르지 **않은** 대안과 그 이유. → 이건 **다음 사람이 어길 수 있는 것**이라 옆에 있어야 한다.
- **핸드오프로 보낸다 — 경위**: 날짜별 사고 서사, 주문번호·금액 같은 실측 표본,
  «누가 무엇을 보고 어떻게 알았나». → 코드에는 **한 줄 링크**만:
  `(2026-08-24, handoffs/2026-08-24-handoff.md §11-2)`.

→ ⚠ **이미 하고 있는 일이다 — 핸드오프만 빠져 있었다.** 주석은 `WA §3`(23곳)·`BACKLOG G-6`(16곳)
처럼 **다른 문서는 절 번호로 참조한다.** 그런데 **`handoffs/` 를 가리키는 주석은 저장소 전체에
단 1줄**이었다(2026-09-03 실측). 참조하는 습관이 없는 게 아니라 **핸드오프만 인라인으로 옮겨
적고 있었다.**

→ 🔴 **지우기 전에 핸드오프에 그 사실이 실제로 있는지 확인한다.** 없으면 **먼저 핸드오프에 옮겨
적고** 나서 지운다 — 이 순서를 뒤집으면 규약이 정보를 없애는 도구가 된다.
`grep -rl "<실측값>" docs/handoffs/` 가 0이면 아직 지울 때가 아니다.

→ ⚠ **javadoc 블록은 붙을 선언 위에 하나만 둔다.** 둘 연달아 있으면 자바가 앞엣것을 조용히
버린다 — 컴파일도 경고도 통과하므로 **주석이 있는데 없는 상태**가 된다.
`scripts/check-orphan-javadoc.sh` (2026-09-03 에 7곳이 그랬다 · TROUBLESHOOTING 「빌드·테스트」).

→ ⚠ **정리는 «줄이기» 가 목표가 아니다.** 31% 라는 숫자를 낮추려고 제약까지 걷어내면

## 3. 검증 (E2E · 운영 데이터)

**공유 espdb를 dev·prod가 함께 쓴다.** 검증 데이터는 `ZZ` 접두사로 만들고 **즉시 삭제**한다.

- [ ] 스크립트가 죽어도 정리가 돌게 `trap`을 건다.
      > **사고**: 한글 쿼리스트링을 인코딩 없이 보내 스크립트가 중간에 죽었고, 정리 단계를 못 타

- [ ] **되돌릴 수 없는 조작(발송 처리)은 검증 스크립트에서 하지 않는다.**

      > 통과**했다. 규약을 **읽을 때**가 아니라 **테스트를 쓸 때** 안 떠오른 것이라, 새 규칙을 더하는
      > 대신 여기 사례를 붙인다 — 목록 API 를 만들면 **`totalElements` 단언 한 줄을 세트로** 넣는다.
      > (보강 테스트는 `size=1` 로 요청해 count 가 실제로 돌게 했고, 공유 DB 라 절대값 대신
      > **「쪼갠 합 == 전체」** 관계로 단언했다. 경위는 `handoffs/2026-08-06-handoff.md` §4-5.)

- [ ] **같은 조건을 쓰는 쿼리가 둘이면 둘 다 따로 검증한다**(2026-08-03, B-16).
      > **왜**: 재고 부족 API 는 `count`(전체 건수)와 `items`(상위 8줄)를 **다른 쿼리**로 뽑는데
      > 조건(`HIDDEN 제외` · `stock <= threshold`)은 같아야 한다. 갈리면 화면에 **"3건"이라 써 놓고
      > 목록엔 5줄이 뜬다** — 에러가 아니라 조용한 불일치라 아무도 못 본다.
      > **실측**: 한쪽에서만 `HIDDEN` 조건을 빼는 변형을 넣었더니 **서로 다른 테스트가 하나씩** 잡았다
      > (count 쪽 2건 · items 쪽 1건). 한쪽만 테스트했으면 다른 쪽 변형은 통과했다.
      → 목록 API 에 요약 숫자를 곁들일 때는 **숫자용 테스트와 목록용 테스트를 따로** 만든다.
      "같은 조건이니 하나면 된다"가 성립하지 않는 이유는 **조건이 코드에 두 번 적혀 있기 때문**이다.

- [ ] ⚠ **권한 테스트(401/403)는 "그 엔드포인트가 보호된다"를 증명하지 않는다**(2026-08-03, B-16).
      > **실측**: 컨트롤러 경로를 `/api/admin/products` → `/api/products` 로 옮기는 변형을 넣었더니
      > 11건 중 **10건이 실패했는데 `requiresAdmin` 만 통과**했다. `/api/admin/**` 매처는
      > **없는 경로에도** 401/403 을 내주기 때문이다(WA §5 가 배포 확인에서 경고한 것과 같은 원리 —
      > 그때는 "401 이 나니 엔드포인트가 있다"고 잘못 판단했다).
      → 즉 그 테스트가 재는 것은 **매처 계약**이지 엔드포인트가 아니다. 그래도 **계속 쓴다** —
      매처가 흔들리면(경로 오타·규칙 순서 변경) 거기서 잡히고, 엔드포인트 이탈은 **기능 테스트들이**
      잡는다. 두 테스트가 각각 다른 것을 지킨다는 걸 알고 쓰면 된다.
      ⚠ 다만 **권한 테스트만 있는 API 는 위험하다** — 그건 아무것도 증명하지 않을 수 있다.

- [ ] **"테스트 파일이 있다" 를 "그 코드가 돌고 있다" 로 읽지 않는다**(2026-07-31, H-2).
      > **왜**: `point` 를 언급하는 테스트 파일이 5개나 잡혔지만 적립 계산을 실제로 실행하는 건 **하나**였다.
      > `OrderServiceTest` 는 `PointService` 를 **`@Mock` 으로 통째 대체**해 한 줄도 실행하지 않는다.
      > 백로그가 *"통합 한 갈래로 덮여 있다"* 고 적은 자리는 사실 **덮인 게 아니라 안 돌던** 자리였다.
      → 커버 여부를 **파일 개수**로 어림하지 말고 `@Mock` 목록을 본다. 목으로 대체된 협력자는
      그 테스트에서 **검증 대상이 아니라 배경**이다.

- [ ] **브라우저 검증 절차를 안내할 때는 명령마다 「어디서 실행하는지」를 프롬프트로 표시한다**
      (2026-07-31, G-1 — **7/30 §12-2 와 같은 사고의 재발**).

      > 실행해 `Connection refused` 가 났다. `2222` 는 **호스트→VM 포워딩 포트**라 VM 안엔 존재하지 않는다.

- [ ] **HTTP 계약을 바꿨으면 `Order.create` 같은 코드 호출부만 찾지 말고 E2E의 요청도 고친다.**

### 3-1. 브라우저 검증에서 `ZZ`를 어디에 붙이나

자동화 테스트는 `@Transactional` 롤백으로 통째로 되돌아가지만, **브라우저 검증은 롤백이 없다.**
그래서 `ZZ`는 "나중에 손으로 지울 것"을 **이름으로 표시해 두는** 수단이다.

- [ ] **주문 검증은 실상품이 아니라 `ZZP-` 상품을 만들어서 한다.**
      실상품으로 주문하면 **그 상품의 재고가 실제로 깎인다.** `ZZP-` 상품은 검증 후 **삭제**할 수 있다
      (§3의 "상품은 삭제, 주문은 취소만"이 이 얘기다).
- [ ] **화면에서 자유 입력이 되는 필드에 `ZZ`를 남긴다** — 주문이라면 **수령인**(`ZZ수령인`)이 1순위다.
      정리 대상을 찾는 쿼리가 이걸로 걸린다:
      ```sql
      select * from orders where buyer_nickname like 'ZZ%' or ship_recipient like 'ZZ%';
      ```
      > **사고 (2026-07-22)**: 배송지 기능을 브라우저로 검증하며 **본인 계정 + 실상품(몽쉘)** 으로 주문했고
      > 수령인에 `123`을 넣었다. `ZZ`가 아무 데도 없어 위 쿼리에 **안 걸렸고**, `created_at >= trunc(sysdate)`로
      > 날짜를 뒤져서야 찾았다 — **하루만 지나면 그것도 안 통한다.** 실상품 재고도 3개 깎여 있었다.
- [ ] ⚠ **사용자가 직접 만든 검증 데이터에는 `ZZ` 규약이 안 걸린다** (2026-08-06).
      > **실측**: G-3 1단계를 사용자가 브라우저로 검증하며 **문의 1건**을 자기 계정·자기 문장으로
      > 만들었다. 기능은 그렇게 봐야 맞지만, `title like 'ZZ%'` 로 세면 **0건**이 나온다 —
      > 7/22 사고와 **같은 구멍**인데 이번엔 규약을 어긴 게 아니라 **규약이 닿지 않는 자리**다.
      → 검증을 **넘겨서 받았으면**, 그 자리에서 **무엇이 생겼는지 날짜·식별 문구까지** 핸드오프에
      적는다(세는 쿼리로는 다시 못 찾는다). 지울지는 사용자 결정이고, **묻지 않고 지우지 않는다.**
- [ ] **취소는 화면(정상 경로)으로 한다. DB를 직접 `UPDATE`하지 않는다.**
      > 재고 복원이 `OrderCancelledEvent` → 리스너로 일어난다. DB 상태만 바꾸면
      > **주문은 취소됐는데 재고는 안 돌아온다.** 조용히 어긋나 나중에 찾기 어렵다.
      > (2026-07-22 실측: 화면 취소 후 재고 97 → 100 복원, `cancelled_at`도 기록됨.)
- 애초에 `ZZ`가 안 맞는 항목도 있다 — "배송지 도입 **이전** 주문이 어떻게 보이나" 같은 확인은
      **과거 실주문**이 있어야 한다. 이런 건 만들지 말고 기존 데이터를 **읽기만** 한다.
- [ ] **잔재 점검은 "오늘 만든 것"이 아니라 `ZZ` **전수**로 한다.**
      > **사고 (2026-07-30 발견)**: 7/28 검증 때 만든 **ADMIN 계정**(`zz-<실명>`)이 그대로 남아 있었다.
      > 7/28·7/29 잔재 점검이 **그날 시나리오만** 되짚었기 때문에 **두 번 연속 지나갔다.**
      > 하루 단위로 보면 "오늘 것은 다 치웠다"가 매일 참이면서 **누적은 계속 는다.**
      → 하루를 닫을 때 **날짜 조건 없이** 전수로 본다(늘 같은 쿼리라 습관이 된다):
      ```sql
      select login_id, role, created_at from member where lower(login_id) like 'zz%';
      select count(*) from orders where lower(buyer_nickname) like 'zz%' or lower(ship_recipient) like 'zz%';
      select count(*) from inquiry where lower(title) like 'zz%';
      ```
      → ⚠ **대소문자를 가리지 않는 쪽으로 쓴다.** 위 계정 쿼리만 `lower()` 였고 주문 쿼리는 아니었다.
      > **실측 (2026-08-07)**: 사용자가 G-3 을 검증하며 문의 제목을 **`zz-제목`·`zz-답답하다`** 로 남겼다.
      > 규약을 지킨 것인데 `like 'ZZ%'` 로는 **0건**이다 — 규약을 지켜도 세는 쪽이 놓친다.
      > 접두사를 대문자로 쓰라고 사람에게 요구하는 것보다 **쿼리를 관대하게** 두는 편이 안전하다.
      → ⚠ **정상 경로로 못 치우는 것이 있으면 그 자체를 항목으로 남긴다** — 위 계정은 비밀번호를 모르면
      지울 방법이 아예 없었다(관리자 삭제 API 부재 → BACKLOG **B-24**). 잔재 점검이 **기능 갭을 드러내는** 자리다.

- [ ] **잔재를 셀 때 "만든 것"만 세지 말고 "고친 것"도 센다.** 검증 시나리오가 지나간 자리를 전부 되짚는다.
      > **사고 (2026-07-24 발견)**: 위 7/22 검증에서 주문은 화면으로 취소했고 재고도 복원해 "잔재 없음"으로
      > 닫았는데, **그 시나리오가 회원의 기본 배송지도 `123` 으로 덮어썼다.** 아무도 안 치웠고
      > **이틀 뒤 주소록 마이그레이션(V18)이 그걸 그대로 새 테이블로 옮겼다.**
      > 잔재 점검이 "주문·상품" 목록에만 묶여 있어서 회원 프로필은 시야에 없었다.
      → 검증 후 이렇게 묻는다: **이 시나리오가 INSERT 한 것은? UPDATE 한 것은?**
      두 번째 질문이 빠지면 조용히 남는다(취소·삭제로 되돌아가지 않는 자리들이다).

### 3-2. 커버리지(JaCoCo)를 어떻게 쓰나 — **자로만 쓴다** (2026-07-31, H-5)

`./gradlew test` 를 돌리면 리포트가 함께 갱신된다 → `build/reports/jacoco/test/html/index.html`.

- [ ] **게이트(최소 %)를 붙이지 않는다.** 빌드를 막기 시작하면 **숫자 채우기가 목적**이 된다.
      `jacocoTestCoverageVerification` 은 없는 게 아니라 **안 쓰는 것**이다(build.gradle 주석).
- [ ] **"커버리지 올려줘" 라고 시키지 않는다.** 단언 없는 테스트로도 100% 가 나온다 —
      커버리지는 *"이 줄이 실행됐다"* 만 재고 *"이게 맞다"* 는 재지 못한다.
      맞는지를 재는 건 **변형 주입**(위 §3)이다. 두 도구의 역할이 다르다:
      **JaCoCo = 어디를 안 봤나 / 변형 주입 = 본 것이 진짜 잡히나.**
      > 실증(2026-07-31, B-15): 가장 위험했던 버그(발행 조건을 상태 변경 **뒤**에서 읽은 것)는
      > **그 줄이 실행되긴 하므로 커버리지로는 절대 안 드러난다.** 변형 주입만 잡았다.
- [ ] 읽는 법은 **명령어(%)보다 분기(%)**, 그리고 **패키지가 아니라 클래스**로 내려가 본다.
      > 2026-07-31 첫 측정: 전체 명령어 87% / **분기 72%**. 그런데 `domain.notification` 은 26%·분기 0% 였고
      > 그 안에서 **리스너는 100%, 핸들러는 4%** 로 갈렸다 — 패키지 평균만 보면 이 갈림이 안 보인다.
- [ ] ⚠ **부분 실행으로 만든 리포트는 부분 커버리지다.** `--tests` 로 한 클래스만 돌리면 리포트도
      그 클래스 기준으로 덮어써진다. **판단은 `.env` 소싱 + 전체 실행**(§3 의 `skipped 0`)에서 나온 것만 쓴다.
- [ ] ⚠ **"안 덮였다" 는 그 코드를 열어 봐야 판정이 된다** — 숫자만 보고 결론을 적으면 틀린다
      (2026-07-31 하루에 **두 번** 걸렸다).
      > ① `InquiryQueryService` **0%** → *"비밀글 마스킹이 미검증"* 이라고 쓸 뻔했는데, 마스킹은
      > `InquiryResponse.from`(dto **100%**)에 있었다. ② H-8 항목에 *"`..` 경로 방어 미검증"* 이라고
      > 적었는데 **이미 삭제·백필 양쪽에 테스트가 있었다** — 분기 % 와 소스의 `if` 목록만 보고 적은 탓이다.
      → **"이 분기가 안 덮였나" 다음에 "그럼 누가 덮고 있나" 를 반드시 확인한다.** 백로그에 적기 전에.
- [ ] 생성 코드는 세지 않는다 — QueryDSL `Q*` 는 build.gradle 에서 제외, Lombok 생성 메서드는
      `lombok.config` 의 `addLombokGeneratedAnnotation` 으로 걸러진다. **엔티티 빌더·게터가 로직보다
      줄 수가 많아**, 안 걸러면 숫자가 우리가 쓴 코드와 무관해진다.

### 3-3. **「0」이라는 답에는 이유가 둘 있다 — 밟았는데 0인지, 안 밟아서 0인지** (2026-08-05)

*"에러 0건"* · *"목록이 비었다"* · *"이력이 0행"* 은 **고쳐졌다는 뜻도 되고 아무 일도 안 일어났다는
뜻도 된다.** 둘을 못 가르면 **아무것도 확인하지 않고 확인했다고 적게 된다.**

> **사고 (2026-08-05, 하루에 네 번)**:
> ① 전날 배포한 SSE 수정을 *"배포 후 `ERROR` 0건"* 으로 닫으려 했는데, 실은 **SSE 가 붙지도 않아**
>    끊길 일이 없었다 — **경로를 한 번도 안 밟은 채 나온 0** 이었다.
> ② 그걸 고쳐 실제로 끊고 다시 0 을 얻었는데, 이번엔 **끊김의 종류가 달라**(배포가 graceful
>    shutdown 을 깨뜨리고 있었다) 또 판정이 안 됐다.
> ③ 기대값에 *"`stock_history` 0행이라 볼 게 없다"* 고 적었는데 **실제로는 8행**이었다.
> ④ 배포 스크립트를 고친 뒤 `NoClassDefFoundError` **0** 을 얻었지만, *에러가 없다* 와
>    *종료가 제대로 돌았다* 는 다르다 — **양성 증거**(`Graceful shutdown complete` 등)를 같이 보고서야
>    판정이 됐고, **그 로그가 「graceful 은 꺼져 있다」는 내 단정까지 뒤집었다.**

→ **확인 수단을 정할 때 「0 이 나올 수 있는 경로가 몇 개인가」를 먼저 센다.** 둘 이상이면 그 0 은
   근거가 아니다. 갈라내는 방법은 둘 중 하나다:
   - **경로를 밟았다는 증거를 따로 만든다**(위 ①: nginx 에 연결 기록이 남았는가).
   - **양성 증거를 함께 본다**(위 ④: 없어야 할 것이 없는 것 + **있어야 할 것이 있는가**).
→ ⚠ **§4-3(실측을 적는다)의 그림자다.** `0` 은 실측값처럼 보여서 **가장 쉽게 근거로 둔갑한다.**

#### 3-3-4. 🔴 **「확인 못 했다」와 「확인할 수 없다」를 같은 말로 적지 않는다** (2026-09-02)

**§3-3 형제 넷째다.** 앞의 둘이 «0 이 무엇을 뜻하나» 였다면 이건 **«모른다» 가 무엇을 뜻하나** 다.

> **사고 (2026-09-02, §I-11-1)**: 적립금 잠금을 고치고 변형 셋을 넣었는데 **U2 만 안 잡혔다**
> (`PESSIMISTIC_WRITE` → `PESSIMISTIC_READ`). 이유를 보려고 **SQL 로깅을 켜려다 두 번 실패**했고
> (`--info`·환경변수 둘 다), *"Oracle 엔 공유 행 잠금이 없어 같은 SQL 일 것"* 이라는 **짐작을
> 근거로 적지 않기로** 하고 **«확인 안 함»** 으로 남겼다. ✅ **거기까지는 옳았다.**
>
> 🔴 **그런데 물어볼 곳을 틀리게 잡고 있었다.** 실행 SQL 을 **로그에서 «건져 올리려»** 했는데,
> **방언에 직접 물으면 한 줄이었다** — `Dialect#getReadLockString`. 둘 다 ` for update` 였다.
> **경합을 만들 필요도, 로깅을 켤 필요도 없었다.**

→ 🔴 **「확인 못 했다」를 적을 때는 «무엇을 시도했는지» 를 함께 적는다.** 그래야 다음 사람이
   *«그 방법으로 못 한 것»* 인지 *«원리적으로 못 하는 것»* 인지 가른다.
   ⚠ **안 적으면 그 줄이 «닫힌 문» 이 된다** — 아무도 다시 시도하지 않는다.
→ **«측정 대상» 과 «측정 지점» 을 갈라 생각한다.** 알고 싶은 것이 *«어떤 SQL 이 나가나»* 였는데
   측정 지점을 *«실행 로그»* 로만 잡았다. 같은 사실을 **더 이른 곳**(설정·방언·계약)에서
   물을 수 있으면 대개 그쪽이 싸고 결정적이다.
→ ⚠ **탐침을 테스트로 남긴다**(`LockModeSqlProbeTest`). 🔴 **그것이 지키는 것은 «두 모드가 같다»
   가 아니라 «그 사실을 우리가 알고 있다» 다** — 전제가 바뀌면(다른 DB·판올림) 빨개져서 알려 준다.

#### 3-3-3. 🔴 **검증 절차를 넘길 때는 «어떤 표본이어야 하는가» 를 함께 넘긴다** (2026-09-02)

**§3-3 의 형제이자 더 조용한 얼굴이다.** 그쪽은 «0 이 나올 경로가 둘» 이었는데, 이쪽은
**«기대값이 나올 경로가 둘»** 이다 — **고쳐서 나온 값**인지 **표본이 그 자리를 안 지나서 나온 값**인지.

> **사고 (2026-09-02, K-3)**: 배분 잔돈 보정을 배포하고 브라우저 검증을 넘겼다.
> 절차에 *«쿠폰+적립금이 상품합계를 전액 덮게 만들라»* 고 적었고, 사용자는 **그대로 밟았다.**
> 결과는 기대값과 일치했다 — 🔴 **그런데 고친 줄이 한 번도 안 돌았다.**
> 표본이 몽쉘 6,800 **× 5** 였는데 `6,800/34,000 = 1/5` 이고 쿠폰·적립금이 **둘 다 5의 배수**라
> **회차마다 딱 떨어져 버려질 소수부가 없었다.** 버그는 «버려진 소수부가 새는 것» 이라
> **샐 잔돈이 없으면 고치기 전 코드도 같은 값을 낸다**(시뮬레이션으로 대조해 확인).
> ⚠ **내 단위 테스트는 `10,000 × 3`(=1/3, 안 떨어짐)이었다 — 조건을 «알고» 있었다.**
> **절차에 안 적었을 뿐이다.** 밟는 사람은 3개를 담을 이유가 없었다.

→ **«무엇을 하라» 만 적지 말고 «그 표본이 왜 그 값이어야 하는가» 를 적는다.** 특히 고친 코드가
   **조건부로만 켜지는** 보정·가드·분기라면, **켜지는 조건을 절차의 첫 줄에 적는다.**
→ **판정 방법도 함께 준다** — 위 사고에서 판정은 «합계» 가 아니라 **«잔돈이 어느 회차에 붙느냐»**
   였다(합계는 고치기 전후가 같다). ⚠ **밟는 사람은 무엇을 봐야 하는지 모른다.**
→ 🔴 **되돌려서 확인이 여기에도 적용된다**: 절차를 주기 전에 *«이 표본을 고치기 전 코드로 돌리면
   결과가 다른가?»* 를 스스로 묻는다. **답이 «같다» 면 그 절차는 판정을 못 한다.**
→ ⚠ **검증이 «틀린» 것과 «판정을 못 하는» 것은 다르다.** 위 사고에서 사용자의 검증은 정확했고
   데이터도 성했다 — **틀린 것은 절차였다.** 결과를 되돌려 받았을 때 **밟은 사람을 의심하기 전에
   내가 넘긴 조건을 먼저 본다.**

#### 3-3-1. ⚠ **로그를 근거로 쓸 거면 그 자리에서 적는다 — 저널은 재부팅에 사라진다**

이 VM 의 `journalctl` 은 **휘발성**이라 `--list-boots` 에 **현재 부팅 하나만** 남는다.

> **사고 (2026-08-05)**: 전날 배포 확인에 쓴 *"`ERROR` 0건"* 을 다시 보려 했는데, 아침에 VM 이
> 재부팅돼 **어제 로그가 통째로 없었다.** *"어제는 0건이었다"* 조차 인용할 수 없게 됐다.

→ 로그로 판정했으면 **건수·시각·예외 이름을 핸드오프에 옮겨 적는다**(§4-3). 로그 자체는 증거로
   남지 않는다.
→ 대조군이 필요한 작업(배포 전후 비교 등)은 **같은 부팅 안에서** 끝낸다.

##### ⚠ 이 규약이 **이틀 만에 또 뚫렸다 — 경계가 「날짜」가 아니라 「부팅」이라서** (2026-08-10)

> **사고 (2026-08-07 → 08-10 에 발견)**: 취소 적립금 환불을 *"로그 전수 0건 — 아직 아무도 안 밟았다"*
> 로 판정했는데, DB 원장에는 **17:05:30 에 `주문 취소 환불 150`** 이 있었다(배포 4분 뒤).
> 사이에 **17:26 재부팅**이 있었고 조회는 **17:52** 였다. 「0건」은 밟지 않아서가 아니라 **지워져서**였다.
> ⚠ 재부팅 사실은 **같은 문서의 다른 절(§10 디스크 작업)에 적혀 있었다** — 대조되지 않았을 뿐이다.

**8/05 사고와 같은 원인인데 신호가 없었다**: 그때는 *"어제 로그를 오늘 다시 본다"* 라 **날짜가 달랐다.**
이번엔 **같은 날 오후 두 시간 안**이라 «오래된 로그» 라는 감각이 아예 서지 않았다.
**부팅 경계는 날짜 경계보다 촘촘하고, 우리가 스스로 만든다**(디스크·커널 작업, VM 조작).

- [ ] **로그로 「0」을 판정하기 전에 `uptime -s` 를 본다.** 판정 대상 시각이 그보다 앞이면 **그 0 은 무효다.**
      ⚠ *"오늘 것이니 남아 있겠지"* 가 안 통한다 — **오늘 재부팅했을 수 있다.**
- [ ] ⚠ **재부팅한 날은 그 사실을 「배포·검증 절」에도 적는다.** 인프라 절에만 적으면 위 사고가 그대로 난다.
- [ ] **돈·재고처럼 원장이 있는 경로는 로그가 아니라 원장(DB)으로 판정한다.** 저널은 사라지지만
      `point_history`·`stock_history` 는 남고, **금액·잔액·순서까지** 준다 — 로그 한 줄보다 강한 증거다.
      ⚠ 그러려면 원장 행이 **경로를 구분할 수 있어야** 한다: 취소 환불은 `reason` 이
      `"주문 취소 환불 …"`, 반품은 `"반품 환불 … (적립 … 회수)"` 라 **원장만 보고 갈린다.**
      («같은 정보를 두 번 적지 않는다» 로 `PointType.CANCEL` 을 안 만든 판단이 여기서 값을 했다.)

#### 3-3-2. **「안 남는 것이 정상」인 검증도 같은 규칙이다 — 「일어난 것」을 옆에 놓는다** (2026-08-20)

§3-3 은 **값이 0** 인 경우였다. 같은 함정이 **행이 아예 없는** 경우에도 그대로 있다 —
*"감사에 안 남는다"* · *"알림이 안 온다"* · *"두 번 눌러도 한 줄이다"* 는 **설계대로 안 남은 것**도 되고
**기록이 실패한 것**도 되고 **애초에 안 밟힌 것**도 된다. 셋 다 화면에는 «없음» 하나로 보인다.

→ **그 조작이 실제로 일어났다는 증거를 다른 원장에서 가져와 나란히 적는다.** 없으면 그건 확인이 아니라
   추측이다. ⚠ 「안 남았다」쪽만 적은 검증은 **읽는 사람이 뒤집을 수 없다** — 반대 증거가 문서에 없으니까.

> **실측 (2026-08-14 셋 · 2026-08-20 하나)**:
> ① 멱등(08-14 §7-2)은 **nginx 접근 로그**가 «요청이 두 번 왔다» 를,
> ② 재고 전이(§9-4)와 ③ 옵션 삭제(§9-5)는 **재고 이력**이 «두 번 저장했다 · 10 → 0 으로 지웠다» 를,
> ④ 재고를 감사에서 뺀 판단(08-20)은 **`stock_history` 의 `ADMIN_EDIT −5 → 5`** 가
>    «재고는 실제로 움직였다» 를 증언했다.
> 넷 다 그 증언이 없으면 **「가드가 일했다」와 「애초에 안 밟혔다」가 구분되지 않는다.**

🔴 **④ 는 여기서 한 걸음 더 갔다 — 대조가 «맞다» 를 확인해 준 것이 아니라 «부족하다» 를 드러냈다.**
원장에는 「변경 없음」 세 줄이 나란히 있었는데, 재고 이력을 옆에 놓고서야 **그중 하나만 실제로 재고가
움직인 저장**임이 보였다. 즉 **원장만으로는 셋이 구분되지 않았다.** 그래서 detail 을
「재고 바뀜(이력 참조)」로 갈라 적게 고쳤다 — ⚠ **값을 두 곳에 적은 것이 아니라
«어디를 보라» 를 적은 것**이다(같은 사실을 두 벌 두지 않는다는 규칙은 그대로다).

⚠ **§3-3 과 한 자리에 둔 이유**: 뿌리가 같다(«없음» 에는 이유가 여럿이다). 절을 따로 세우면
읽는 사람이 둘 중 어느 것을 봐야 하는지 흐려진다 — **지켜지지 않는 규약이 두 벌 되는 것**이
규약이 하나 모자란 것보다 나쁘다(2026-08-14 의 판단 그대로).

### 3-4. **관측 창은 09~18시 KST — 그 밖의 순간은 사람이 아니라 기계가 본다** (2026-08-21)

사용자가 화면 앞에 있는 시간은 **09~18시**다. 그 밖 시각에 «사람이 눈으로 보는» 항목을
검증 계획이나 이월에 넣지 않는다.

> **지시 (2026-08-20)**: *"00:00에 보는 건 이월에 끼지마, 그건 새벽이라 볼 수 없으니"*
> **지시 (2026-08-21)**: *"애초에 내가 09~18시 근무라 그 시간대에 못 봐요, 09~18시 사이에 하는 게 아닌 이상"*

⚠ **두 번째에 올렸고, 그때 범위가 넓어졌다.** 08-20 은 **새벽**만 짚었는데 08-21 것은
**18시 이후·09시 이전 전부**다. 🔴 08-20 이 *«한 번의 지시다 — 또 실리면 그때 올린다»* 로
조건을 걸어 뒀고 그 조건이 성립했다(§2-10 을 올릴 때와 같은 절차).

**왜 규약이어야 하나**: 넣어도 안 밟힌다. 그리고 안 밟힌 항목은 **다음 문서로 계속 물려받으며
«아직 못 봤다» 가 쌓인다** — 이월이 *"실제로 할 수 있는 일의 목록"* 이 아니게 된다.
🔴 **그게 이월이라는 장치를 무력화한다**(§4-1 이 이월을 둔 이유가 바로 그 목록의 신뢰다).

- [ ] **관측 시각을 고를 수 있는 검증은 09~18 안에 경계를 만들어** 밟는다.
- [ ] 전이 순간이 창 밖에만 오면 **두 갈래로 나눈다**:
      ①**결과만 확인**(«끝나 있는가») → **이월에 넣어도 된다**
      ②**순간 자체**를 봐야 하면 **기계로 본다**(낮에 폴링을 걸고 나중에 로그를 읽는다)
- [ ] ⚠ **낮으로 못 옮기는 것이 있다.** 세일(G-5/V52)은 `ProductDiscountRequest` 가 `LocalDate` 라
      경계가 **구조적으로 항상 00:00** 이다 — 기계 관측이 유일한 길이다.

#### 3-4-1. 🔴 **`@Scheduled` 회차는 «마지막 기동 시각»에서 센다 — 배포도 재부팅도 타이머를 리셋한다** (2026-08-21)

`fixedDelay` + `initialDelay` 스케줄러는 **cron 이 아니다.** «매시 12분» 같은 고정 시각이 없고,
**프로세스가 뜬 시각 + initialDelay** 가 1회차이며 그 뒤로 상대적으로 흐른다.

> **실측 (2026-08-21)**: 상품 영구 삭제 배치의 회차가 **하루에 세 번** 다시 잡혔다 —
> 08:26 기동(→08:31·09:31…) → **10:07 배포**(→10:12·11:12…) → **14:52 재부팅**(→14:57·15:57…).
> 관측 대상은 11:09 와 15:55 에 만료되는 상품 셋이었고, 회차가 밀릴 때마다 **«몇 시에 볼 것인가» 가
> 통째로 바뀌었다.**

- [ ] **관측 계획을 세울 때 회차를 계산한다**: `systemctl show <svc> -p ActiveEnterTimestamp`
      (또는 앱 로그의 `Started … in N seconds`) **+ `initialDelay`**.
- [ ] 🔴 **배포 시각이 다음 회차를 18시 밖으로 미는지 먼저 본다**(§3-4). 밀면 **배포를 관측 뒤로 미룬다.**
- [ ] ⚠ **«오늘 배포 안 했으니 그대로겠지» 가 틀릴 수 있다** — 재부팅도 같은 일을 한다.
      **`uptime -s` 가 오늘이면 회차는 거기서 다시 시작한 것이다.**

### 3-5. **기준값은 세션을 열 때 «다시 센다» — 적어 둔 마감값은 근거가 아니라 대조 대상이다** (2026-08-26)

검증은 «무엇이 몇 개였는가» 위에서만 판정된다. 그 값을 **문서에서 읽어 오면** 판정이 문서의
정확도에 걸린다 — 그리고 **그 문서는 틀린 적이 있다.**

- [ ] **세션을 시작할 때 기준값을 다시 센다.** 핸드오프에 적힌 「마감값」은 **출발점이 아니라
      대조 대상**이다 — 같으면 «안 움직였다» 가 실측으로 확인된 것이고, 다르면 **그 자체가 오늘의 정보**다.
- [ ] **검증이 값을 흔들면 그 자리에서 다시 센다.** 하루에 여러 번 검증하면 여러 번 센다.
- [ ] **마감에 한 번 더 센다** — 그게 다음 날의 대조 대상이 된다.

> **근거 ① (2026-08-20)**: 하루에 **네 번** 움직였다(`stock_history` 36 → 38 → 43 → 46 → 49).
> 그래서 *«마감값을 적어 두면 된다»* 가 아니라 *«그날 아침에 다시 센다»* 가 규칙인 것이다.
>
> **근거 ② (2026-08-24)**: 검증이 값을 흔들어, 그날 「조건부 잔여」에 적힌 숫자를 **근거로 쓰지 말라고**
> 문서에 따로 적어야 했다.
>
> **근거 ③ (2026-08-26)** — 🔴 **여기서 성격이 갈린다.** 앞의 둘은 «값이 움직였다» 인데,
> 이날은 **데이터가 하나도 안 움직였는데 문서가 틀렸다.** 전날 「마감값」이라 적힌 것이 실은
> **검증이 끝나기 전 값**이었다: 적립금 **172,908 → 실제 173,085** · 누적구매 **144,000 → 153,978** ·
> 전수 **955/287 → 실제 960/298**. DB 의 마지막 변경 시각이 **전날 17:37 에 멈춰 있어** 밤사이
> 변한 게 아니라는 것이 확인됐다. **즉 다시 세지 않았으면 «밤사이 뭔가 돌았나» 를 쫓을 뻔했다.**

⚠ **파생값도 같이 낡는다.** 이월에 적는 **예측값**(«삭제되면 N 이 될 것이다» 류)은 기준값에서
계산한 것이라, 기준값이 움직이면 **아무도 안 고치는 채로 틀린다** — 2026-08-26 에 `ZZ-123123`
CASCADE 예측이 `stock_history` **60** 시절 값(57)으로 남아 있었고, 그날 실측 기준(78)으로 다시
내야 했다(75). **마감에 셀 때 이월의 예측값도 함께 본다.**

**세는 것** — `product_variant` · `stock_history` · `product`(alive/trash) · `point_history` ·
`notification` · `orders` · 상품매출 · 검증에 쓸 계정의 적립금·누적구매·등급.
- ⚠ **이력은 `product_id` 로 센다** — 조인으로 세면 삭제 대기 상품의 이력이 0으로 보인다(2026-08-24).
- ⚠ **불변식을 같이 본다** — `SUM(point_history) == point_account.balance`. 값이 흔들린 날
  이것까지 보면 «움직인 것» 과 «깨진 것» 이 갈린다(2026-08-26 에 두 번 다 성립했다).

🔴 **이 규약이 이월을 대신하지는 않는다.** 값 자체는 그날 핸드오프에 남고, 여기 있는 것은
**«다시 센다» 는 절차**다 — 08-20·08-21·08-24·08-25 가 **나흘 연속 이월에 같은 문장을 다시 쓴** 뒤에야
규약이 됐다.

## 4. 핸드오프 작성 규약

> **위치**: 날짜별 핸드오프는 `docs/handoffs/YYYY-MM-DD-handoff.md` 에 둔다(2026-07-28 분리 —
> `docs/` 루트에 계속 쌓이면 BACKLOG·WORKING-AGREEMENTS 같은 상시 문서가 파묻힌다). `docs/` 루트에는
> 상시 문서(WORKING-AGREEMENTS·BACKLOG)만, 날짜 문서는 `handoffs/` 하위에.

### 4-0. 문서를 닫을 때는 **읽지 말고 센다** (2026-08-03)

핸드오프에는 **개수를 말하는 문장**이 여럿 있다 — 커밋 표, 조건부 잔여 「N건」, 「다음 기능 후보」,
「기능 검증 종결 기록」, 하루 총괄의 테스트 수. 이것들은 **하루 중에 계속 늘어나는데, 문장은 처음
쓴 상태로 남는다.**

> **사고 (2026-08-03, 하루에 세 번)**: ①커밋 표가 22건 중 **9건**만 ②그걸 고치는 커밋이
> **다른 워크트리**를 고쳐 표는 그대로 ③마감 후 *"7건 그대로"* 라 적힌 조건부 잔여가 실제로는 **8건**
> (그날 하나 추가했다). 같은 문서에서 「다음 기능 후보」엔 **그날 처리한 항목이 남아** 있었고,
> 「기능 검증 종결 기록」은 **7건 중 2건**만 적혀 있었다.
> ⚠ 세 번 다 **"문서 다 됐다"고 답한 뒤** 사용자가 되물어서 드러났다.
> ⚠ ③이 특히 비쌌다 — 다음 세션이 *"오늘 뭐가 끝났나"* 를 보는 자리라, **이미 한 일을 다시 후보로
> 집을** 뻔했다.

→ ✅ **구조적 해법: `scripts/check-handoff.sh`** (2026-08-03). 배포 스크립트가 시작할 때
**자동으로 돌린다** — `check-deploy-branch.sh`·`check-infra-drift.sh` 와 **같은 자리·같은 방식**
(막지 않고 경고만). 아래 다섯을 대조한다: ①커밋 표 ②손으로 쓴 개수 ③총괄 ↔ 종결 기록
④「## 이월」 존재 ⑤아직 「배포 대기」인 절.
> **왜 스크립트인가**: 이 항목을 규약으로 올린 **직후에 또 안 셌다.** `check-deploy-branch.sh` 가
> 나온 경위와 똑같다(규약을 적고도 **같은 날 재발**해서 스크립트가 됐다, §5).
> ⚠ 검증도 같은 방식으로 했다 — **문서를 일부러 어긋뜨려** 4종을 넣고 전부 잡히는지 봤다(§3 변형 주입).

→ 손으로 볼 때는 **기계로 대조한다**(읽으면 있는 것만 보이고 빠진 것은 안 보인다):

```bash
H=docs/handoffs/$(date +%F)-handoff.md
git log --since="$(date +%F) 00:00" --oneline | wc -l      # 실제 커밋
grep -c '^| `[0-9a-f]\{7\}` |' "$H"                        # 표 (차이는 마감 커밋뿐)
grep -c '^[0-9]\+\. ' <(sed -n '/조건부 잔여/,/^---/p' "$H")  # 잔여 항목 수 ↔ 「N건」 문장
```

→ **「다음 기능 후보」에서 그날 처리한 것을 지웠는지**, **「기능 검증 종결 기록」이 총괄 표와 같은
건수인지**를 눈이 아니라 **목록 대 목록**으로 맞춘다.

#### 4-0-1. 언제 닫나 — **배포할 때마다** (하루 끝에 몰지 않는다)

> **왜 배포인가**: ①되돌릴 수 없는 지점이라 **그때부터 그 항목의 기록이 확정**된다(그전엔 "대기"라
> 계속 움직인다) ②배포 직후엔 실측값(OpenAPI·번들 해시·health)이 손에 있어 **그 자리에서 안 적으면
> 나중에 다시 뽑아야 한다** ③브라우저 검증까지 붙어 **한 항목의 이야기가 완결**된다.

> **실증 (2026-08-03)**: 하루에 8건·24커밋·배포 4번이었다. **앞의 두 배포에서는 닫았고 그 절만
> 멀쩡했다.** 뒤의 두 번을 건너뛰자 거기서부터 집계가 벌어졌고, 마지막에 몰아서 닫으니
> **하루치 어긋남이 한꺼번에** 나왔다(§4-4 사고 셋이 전부 여기서 나왔다).

→ 배포 사이가 길어지면 **커밋 5개**를 보조 기준으로 쓴다.
   ⚠ 시간(2시간 등)이 아니라 **커밋 수**다 — 문서가 낡는 원인은 시간이 아니라 **변경 횟수**다.

#### 4-0-2. ⚠ **세어야 아는 숫자를 문장에 적지 않는다**

목록이 있는 자리에 *"7건 그대로 살아 있다"* 처럼 **개수를 손으로 적으면 반드시 어긋난다** —
항목은 하루 중에 늘어나는데 그 문장은 처음 쓴 상태로 남기 때문이다.

> **사고 (2026-08-03)**: 조건부 잔여를 **같은 문서 안에서 두 군데** *"7건"* 이라 적어 뒀는데
> 그날 8번을 추가해 **둘 다 틀렸다.** 하나는 사용자가 *"저건 뭐야 7건?"* 이라고 물어서 드러났다.

→ **목록이 곧 개수다.** 머리글엔 *"§3 참조"* 와 **무엇이 달라졌는지**만 쓴다
(*"오늘 8번이 늘었다"* 는 안전하다 — 그건 세는 게 아니라 **사건**이다).
→ 개수를 정말 보여야 하면 **손으로 쓰지 말고 세는 명령을 함께 남긴다**(위 §4-0 블록).

### 4-1. 마지막에 `## 이월` 절을 둔다 (필수)

**다음 문서로 반드시 옮겨야 할 미완 항목**을 적는다. 다음 날 문서는 이 절을 **그대로 물려받아**
시작한다. 처리했으면 그때 지운다.

- 이게 §1-1 사고의 **구조적 해법**이다. 대조는 사람 기억에 의존하지만, 이 절은 **빠뜨릴 수 없다.**
- 비었으면 "없음"이라고 명시한다 — 절 자체를 지우면 규약이 흐려진다.

### 4-2. 결론이 아니라 **판단 근거**를 적는다

"A안 대신 B안"만 적으면 나중에 왜 그랬는지 알 수 없어 되돌아간다.
버린 안과 **버린 이유**를 같이 남긴다.

### 4-3. 실측 수치를 적는다

"동작 확인"이 아니라 로그·건수·응답 코드를 적는다. 나중에 회귀를 판단할 기준이 된다.

#### 4-3-1. ⚠ 그 뒷면 — **명령 출력에 없는 값을 문장에 쓰지 않는다** (2026-08-03)

> **사고**: 하루를 닫는 요약에서 *"main 은 `1c5a45b` 에 있고"* 라고 적었는데 **그 해시를 출력한
> 명령이 없었다.** 실제 값은 달랐다. 문장이 *"main 은 ___ 에 있고"* 라는 **형태**를 하고 있었고,
> 그 빈칸이 해시 모양을 요구하자 종일 봐 온 것과 비슷한 7자리를 **만들어 채웠다.**
> 값을 몰라서 틀린 게 아니라 **문장 형태가 값을 요구해서 지어낸** 것이다.

**왜 특히 나쁜가**

- **틀린 값은 「모른다」보다 나쁘다** — V37 에서 동의 시각을 백필하지 않은 이유와 **같은 원리**다
  (*"NULL 은 정직하고, 지어낸 값은 근거로 쓰이는 순간 틀린 결정을 만든다"*). 그래 놓고 같은 날 어겼다.
- **검증 가능한 형태일수록 「실측한 것처럼」 보인다.** *"잘 됐습니다"* 는 읽는 사람이 걸러 읽지만
  `1c5a45b` 는 명령으로 얻은 값처럼 보인다 — §4-3(실측을 적는다)을 **거꾸로 무기 삼아** 신뢰를 얻는다.
- **되짚을 때 실제로 쓴다.** 해시는 `git show` 로 여는 값이고(§4-4 가 해시 열을 유지한 이유),
  틀리면 다음 사람이 *"그 커밋이 없는데?"* 로 시간을 쓴다.

**언제 나는가**: **마무리 요약 문장**에서 난다. 명령을 돌리며 확인하는 모드가 아니라
**정리해서 들려주는 모드**일 때. ⚠ 그리고 대개 **그 값이 문장에 필요하지도 않다** —
*"main 도 동기화됐습니다"* 로 충분했다. **정밀해 보이려고 넣은 값**이 가장 위험하다.

→ **출력에 없으면 한 번 더 돌리고, 안 돌릴 거면 그 값을 문장에서 뺀다.**
→ 특히 **해시·건수·시각·파일명·번들 이름** — "구체적으로 들리는" 값일수록 엄격하게.
   ⚠ §4-0 이 *문서의* 숫자를 세라는 것이라면, 이건 *말하는* 숫자의 출처를 대라는 것이다.

### 4-5. 커밋 메시지는 **실제로 담긴 변경**만 적는다

> **사고 (2026-07-30)**: 여러 파일을 한 스크립트로 고치다 **앵커 불일치로 중간에 실패**했는데,
> 커밋 메시지엔 실패한 부분("이월에 등록")까지 적어 뒀다. 파일 본문은 일부만 반영된 상태로 커밋·푸시됐다.
> **메시지가 실제보다 앞서 있으면**, 나중에 그 메시지를 믿고 문서 확인을 건너뛴다 — 커밋 로그는
> "무엇을 했다"의 기록이라 틀리면 다음 사람이 잘못된 전제로 출발한다.

→ 여러 파일을 스크립트로 고치면 **커밋 전에 결과를 확인**한다(`git diff --stat` 또는 대상 절 grep).
→ 이미 푸시된 뒤 발견하면 **되돌리지 말고 다음 커밋에서 채우고 경위를 남긴다**(히스토리 재작성보다 낫다).

### 4-4. "오늘의 커밋" 표는 문서를 닫은 **뒤에** 한 번 더 대조한다

이 표는 **자기 자신을 담은 커밋 이후를 구조적으로 못 적는다.** 문서를 닫는 커밋과 그 뒤에 붙는
후속 커밋이 조용히 빠진다 — 7/22에 실제로 두 줄이 빠져 있었다(마감 커밋 + 드리프트 경고 커밋).

- **작업을 끝낸 뒤** `git log --oneline --since="<오늘> 00:00"` 과 표를 맞춰 본다.
- ⚠ **눈으로 훑지 말고 개수를 센다**(2026-08-03).
      > **사고**: 하루에 22커밋이 났는데 **표엔 9건만** 있었다. 중간에 「마감 대조」를 **두 번이나**
      > 했는데도 그랬다 — 대조할 때마다 *"그 뒤 몇 개"* 만 이어 붙이다 보니, 붙이는 걸 한 번 건너뛴
      > 뒤로는 계속 어긋난 채 굴러갔다. 제목을 눈으로 보면 **빠진 것은 안 보인다**(있는 것만 보인다).
      ```bash
      git log --since="<오늘> 00:00" --oneline | wc -l          # 실제
      grep -c '^| `[0-9a-f]\{7\}` |' docs/handoffs/<오늘>-handoff.md   # 표
      ```
      → 하루를 닫을 때 **표를 통째로 다시 만든다**(이어 붙이지 않는다):
      `git log --reverse --since="<오늘> 00:00" --pretty='| \`%h\` | %s |'`
      → ⚠ **같은 날 두 번째 사고**: 그 재작성 스크립트가 **다른 워크트리에서 실행**돼(`cd` 가 앞
      명령에 남아 있었다) 커밋엔 *"전수 재작성"* 이라 적혔는데 **표는 그대로**였다.
      **고쳤다고 적기 전에 고쳐진 파일을 다시 센다** — §4-5(메시지는 실제로 담긴 변경만)와 한 세트다.
      ⚠ **워크트리가 둘이라 생기는 함정이다**: 문서·코드는 항상 **작업 워크트리**에서 고치고,
      `/home/ecstel/work`(main)는 **머지와 배포에만** 쓴다. 한 Bash 호출 안에서 `cd` 한 뒤
      스크립트를 이어 붙이지 않는다 — **절대 경로로 연다.**
- 형식은 `| 커밋 | 내용 |` **두 열, 짧은 해시 포함**(7/15·7/16·7/20·7/21 공통). 내용은
  커밋 제목을 그대로 쓴다 — 요약해 두면 `git log`와 대조가 안 돼 위 규칙이 작동하지 않는다.
- ⚠ 7/22에 "해시는 rebase에 낡는다"며 해시 열을 뺐는데 **근거가 틀렸다.** 그 말이 나온 7/21 문서의
  자리는 커밋 표가 아니라 *미푸시 diff*(`git log main..daily-status-review`) 절이었고, 그걸 표 전체로
  잘못 일반화했다. 7/21 표의 해시 11개는 지금도 전부 유효하다. **작업 브랜치를 rebase하지 않는 한
  낡지 않는다** — 해시가 있어야 `git show`로 바로 열 수 있다.

## 5. 배포

- [ ] **응답 계약이 바뀌면 백엔드·프론트를 함께 배포**한다(한쪽만 올리면 화면이 깨진다).
      순서는 **백엔드 먼저** — 스키마·데이터가 앞서 있어야 한다.
- [ ] 스키마 변경은 **통합 테스트를 돌리는 순간 Flyway가 공유 DB에 적용**된다.
      추가·nullable 변경은 구버전 jar에 영향이 없지만(실측 확인), 그 사실을 매번 확인한다.
- [ ] **순수 추가가 아닌 제약(UNIQUE·CHECK·NOT NULL)은 구 jar의 동작을 바꾼다** — 확인받고 적용한다.
      > **사고 (2026-07-21)**: 닉네임 UNIQUE(V6)를 통합 테스트가 공유 espdb에 적용하는 순간, 운영(구 jar)에서도
      > 중복 닉네임 가입이 막혀 500이 났다(구 jar는 이 제약을 409로 못 바꾼다). 기존 중복 0건이라 데이터는
      > 안 깨지고 되돌릴 수 있었지만, "추가·nullable은 안전"의 예외다. 적용 전 **기존 데이터 위반 여부(중복 등)를
      > 먼저 조회**하고(§2-5), 구 jar 동작 변화를 사용자에게 알린다.
- [ ] `sudo`가 필요한 명령은 **실행하지 않고 제안**한다(CLAUDE.md).
- [ ] **서버 설정(nginx·systemd)은 `infra/`가 원본이고 서버는 그 사본이다.** 서버에서 직접 고치지 않는다.
      > **왜 (2026-07-22)**: nginx 설정·systemd 유닛이 서버에만 있어 **저장소를 clone 해도 서버를 못 세웠다.**
      > 그 설정엔 사고로 얻은 지식이 들어 있다 — `index.html`만 `no-cache`, `location`에 `add_header`가
      > 있으면 **server 레벨 헤더가 통째로 무시**되는 규칙 등. 날아가면 다시 알아내야 한다.
      → 급해서 서버에서 먼저 고쳤으면 **그 자리에서 `infra/`에 반영**한다. 어긋난 사본은 없느니만 못하다.
      → 확인: `./scripts/check-infra-drift.sh` (읽기만 하므로 sudo 불필요). 반영 명령은 `infra/README.md`.
- [ ] 배포 후 운영에서 **실제 화면·API로** 확인한다. 접속 주소는 (2026-07-30 갱신):
      - **호스트 브라우저**: `https://localhost/` — VM 이 NAT 라 **호스트 포트포워딩(443)** 으로 들어간다.
        인증서 SAN 에 `DNS:localhost` 가 있어 이름 불일치 경고는 없다(self-signed 경고는 전과 같다).
        포워딩이 없으면 SSH 터널로도 된다: `ssh -L 8443:127.0.0.1:443 -p 2222 ecstel@127.0.0.1`
        → `https://localhost:8443/`.
      - **서버 안(이 VM)**: `https://127.0.0.1/` (SAN 에 `IP:127.0.0.1` 포함).
      - ⚠ **서버 IP(`192.168.50.14` 등)로 적어 두지 않는다** — 두 번 바뀌었다(§5 위 항목).
      > **사고 (2026-07-22)**: 서버 IP가 `.36` → `.14`로 바뀌었다(`enp0s3`가 DHCP `dynamic`이라
      > 재부팅하며 리스가 갈렸다). `.env`의 `DB_HOST`가 `.36`을 가리킨 채라 **DB 접속이 전부 타임아웃**,
      > 백엔드가 기동 실패로 무한 재시작하며 **운영이 통째로 내려가 있었다.**
      > 더 나쁜 건 증상이 **"통합 테스트 61건이 컨텍스트 로딩 실패"** 로 보였다는 것 —
      > 코드 문제로 착각하기 딱 좋다.
      → **테스트가 무더기로 컨텍스트 로딩에 실패하면 코드보다 인프라 접속을 먼저 의심한다.**
      실패 XML의 `Caused by` 최하단(근본 원인)까지 내려가면 `ORA-12170` 같은 접속 오류가 바로 보인다.
      → IP에 의존하는 설정(`.env`·인증서 SAN·nginx)은 **IP가 바뀌면 같이 틀어진다.** 한 곳만 고치고 끝내지 않는다.

      > **⚠ 같은 사고가 2026-07-30 에 재발했다** — 어댑터가 NAT 대역으로 바뀌며 `.14` → `10.0.2.15`.
      > 7/22 에 *"IP를 정적으로 고정했으므로 재발 없음"* 이라고 문서에 적어 뒀는데, **그 문장이 곧 대비였다.**
      > 규율(적어 두기)로 막던 것이라 어댑터 설정이 바뀌는 순간 아무 방어가 없었다.
      → **구조적 해법: 같은 호스트에 있는 것은 IP로 부르지 않는다.** `DB_HOST` 를 `127.0.0.1` 로 고정했다
      (2026-07-30). DB·Redis·Mailpit·백엔드가 전부 같은 VM 이라 **IP 를 거칠 이유가 애초에 없었다** —
      IP 가 있으면 "언젠가 바뀔 값"이 설정에 들어앉는다.
      → 남은 IP 의존은 **인증서 SAN** 뿐인데, 거기에도 `IP:127.0.0.1`·`DNS:localhost` 가 함께 들어 있어
      포트포워딩으로 `https://localhost/` 로 들어가면 경고가 없다. **재발급할 때는 IP 대신 DNS 로 잡는다.**

- [ ] **`systemctl is-active` 가 `active` 라고 답하는 것은 "기능이 정상" 의 증거가 아니다.**
      > **사고 (2026-07-30)**: DB 접속이 끊긴 상태에서도 백엔드 유닛은 `active` 였다 — 프로세스는 살아
      > 있는데 `/actuator/health` 는 `DOWN`(503) 이었다. `TROUBLESHOOTING.md` §3-1("지금 떠 있다는 건 자동기동 성공의 증거가
      > 아니다")의 다른 얼굴이다: 그건 *누가 손으로 올렸을 수 있다*, 이건 *떴지만 못 쓴다*.
      → 상태 확인은 **유닛이 아니라 기능으로** 한다: `curl -s http://127.0.0.1:8080/actuator/health`.
- [ ] **혼자 하는 동안 PR 은 안 연다. 대신 «머지 전 리뷰» 를 붙인다** (2026-09-02, 해 보고 정함).
      > **왜**: PR 의 핵심 가치는 «다른 사람의 눈» 인데 그게 없다. 남는 것은 diff 창인데,
      > 이 저장소엔 이미 그보다 촘촘한 관문이 있다(핸드오프 · 되돌려서 확인 · 전수 · 배포 관문 셋 ·
      > 불변식 11개 · 브라우저 검증). ⚠ **비용도 있다**: 브랜치를 상시로 쓰면 **07-23 사고의 조건**
      > (배포는 `main` 워크트리에서 빌드하는데 그게 뒤처짐)이 되살아나고, PR 본문에 설명을 쓰면
      > **서술이 두 곳**에 생긴다(CLAUDE.md 가 가장 강하게 막는 것).
      > → **`git push origin main` 으로 끝낸다.** 브랜치는 «실패하면 통째로 버릴» 위험한 변경에만.

      → 🔴 **다만 «리뷰» 는 값이 있다 — 그리고 그건 PR 이 아니라 브랜치만 있으면 된다.**
      `/code-review` 는 **로컬 diff 기준**이라 GitHub 도 `gh` 도 안 본다.
      ⚠ **2026-09-02 에 실제로 돌려 보고 정한 것이다** — 그날 «diff 읽기로는 못 잡는다» 고
      적으려던 참이었는데, 리뷰가 **여덟 자리를 짚었고 전부 타당했다**:
      픽스처가 **주문 DTO 의 칸 이름**을 써서 품목이 이름 없이 렌더되는데도 초록이던 것,
      단언값이 **화면에서 재구성 가능**해서 자기 주장을 반증 못 하던 것 셋
      (`totalQuantity 3 = 2+1` · `payAmount 23,000 = 20,000+3,000` · `amountUntilFree` 가
      품목 단가와 같음), 빠진 배선 셋.
      → 🔴 **«변형 주입» 과 «리뷰» 는 잡는 것이 다르다.** 변형은 *«이 규칙이 지켜지나»* 를 묻고,
      리뷰는 *«그 단언이 그 규칙을 실제로 반증할 수 있나»* 를 묻는다. **후자는 스스로 못 본다** —
      자기가 고른 값이 왜 그 값인지는 자기에겐 늘 자명하기 때문이다.
      → **테스트를 새로 만든 날은 머지 전에 `/code-review` 를 한 번 돌린다.**

- [ ] **배포 전에 `main`을 ff 머지한다. 배포 스크립트는 작업 브랜치가 아니라 `main` 워크트리에서 빌드한다.**
      ```
      deploy-backend.sh  → /home/ecstel/work/glassvue-backend
      deploy-frontend.sh → /home/ecstel/work/glassvue-frontend
      ```
      > **사고 (2026-07-23)**: 배송 추적(V13)을 작업 브랜치에 커밋·푸시하고 배포했더니 **옛 코드가 나갔다.**
      > `main`이 두 커밋 뒤처져 있었고, 스크립트는 그 워크트리에서 빌드하기 때문이다.
      > **더 나쁜 건 조용했다는 것** — 스크립트는 정상 종료하고 jar 파일 시각도 갱신돼서
      > 겉으로는 배포에 성공한 것처럼 보였다. 백·프론트 **둘 다** 그랬다.
      → 배포 순서: **작업 브랜치 push → `main` ff 머지·push → 배포 스크립트**.
      `git -C /home/ecstel/work log --oneline main..<브랜치>` 가 비어 있는지 먼저 본다.

      > **⚠ 같은 날 두 번 걸렸다.** 첫 사고 직후 이 규약을 적었는데도 **재발했다.**
      > 규약만으로는 안 걸러진다는 게 두 번째 사고로 증명됐다.
      → **구조적 해법**: `scripts/check-deploy-branch.sh` 를 배포 스크립트가 시작할 때 자동으로 돌린다.
      다른 로컬 브랜치에 안 넘어온 커밋이 있으면 **목록과 머지 명령까지** 찍어 준다.
      드리프트 검사와 같은 자리·같은 방식으로 **막지 않고 경고만** 한다.
      → 사람 쪽 해법: **배포를 요청하기 전에 머지를 먼저 끝낸다**(기억해야 할 단계를 줄인다).

- [ ] **확인 수단은 매번 "이 변경의 성질"에서 찾는다 — 한 가지 방법을 습관으로 쓰면 언젠가 틀린다.**
      > **왜 (2026-07-30)**: 하루에 네 가지를 썼다. **엔드포인트가 늘었으면** OpenAPI(`/v3/api-docs`)로
      > 보이지만(관리자 회원 삭제), **동작만 바뀌면 OpenAPI 가 구·신 jar 에서 똑같다** — 그때는
      > 행동으로 봐야 한다(옛 토큰이 401 이 되는지). **부수효과**가 증거가 되는 경우도 있고
      > (구 jar 가 만들지 않는 Redis 키), **거부 응답의 에러 코드**가 증거인 경우도 있다(비밀번호 정책 —
      > 게다가 거부되면 계정이 안 생겨 잔재도 없다).
      → 배포 전에 스스로 묻는다: **"구 jar 와 신 jar 가 다르게 답하는 지점이 어디인가?"**
      그 답이 확인 방법이다. 없으면 만들 것(로그·부수효과·행동) — 없는데 확인했다고 하면 7/23 사고다.

- [ ] **배포 확인은 "코드가 실제로 바뀌었다"는 증거로 한다 — 상태코드로 엔드포인트 존재를 가리지 마라.**
      > **사고 (2026-07-23)**: 신규 `POST /api/orders/{id}/deliver` 가 배포됐는지 보려고 미인증 요청을
      > 날려 **401이 나오니 "엔드포인트 있음"으로 판단**했다. 틀렸다 — `/api/orders/**` 는 인증이 필요해서
      > **없는 경로도 Security 필터에서 401**이 난다. 실제로는 구 jar였고, 그 판단이 사고를 한 번 가렸다.
      → 확실한 신호를 쓴다:
      ```bash
      curl -s http://127.0.0.1:8080/v3/api-docs | python3 -c "..."   # OpenAPI에 경로·requestBody가 있는지
      curl -sk https://127.0.0.1/ | grep -oE 'index\.[a-f0-9]+\.js'   # 배포된 번들 해시 ↔ 로컬 빌드
      ```
      OpenAPI는 **요청 스키마까지** 보여줘서 "계약이 바뀐 채로 배포됐는지"도 같이 확인된다.

- [ ] **프론트 배포 후 화면 확인은 하드 새로고침(Ctrl+Shift+R)으로 한다.**
      > **사고 (2026-07-21)**: 이미지 파생본 배포 후 썸네일이 여전히 원본(`.jpg`)으로 떠서 기능이 안 먹는 줄 알고
      > 한참 파헤쳤는데, 백엔드·API·배포된 번들은 전부 정상이었고 **브라우저가 옛 JS 번들을 캐시**하고 있었을 뿐이었다.
      > 하드 새로고침하니 `_t.webp`로 정상 표시.
      → "화면에 안 보인다"를 버그로 결론짓기 전에 **① API 응답 ② 배포된 번들 내용 ③ 하드 새로고침** 순으로 가른다.
      구조적 해법은 `index.html`만 `Cache-Control: no-cache`로 두는 것(해시된 정적 자산은 장기 캐시 유지).

## 6. 서비스가 부팅에 안 뜰 때 → **`docs/TROUBLESHOOTING.md` 로 옮겼다** (2026-08-05)

부팅 실패·SELinux·벤더 init 스크립트 진단은 *"어떻게 일하기로 했나"* 가 아니라
**"이 증상이면 어디를 의심하나"** 라, 이 문서의 성격과 맞지 않았다(88줄).

→ **`docs/TROUBLESHOOTING.md` §3** 에 그대로 있다. 이 문서에는 규약만 남긴다.
