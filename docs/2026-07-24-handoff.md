### 2-1. ⚠ 이 마이그레이션은 어제까지와 성격이 다르다 — 순수 추가가 아니다

V13~V17 은 **다섯 개 전부 순수 추가**였다(컬럼·테이블 ADD). B-5 는 다르다:
`member.ship_*` **기존 값을 새 테이블로 옮기고 원래 컬럼을 정리**해야 한다.

**위험**: `ddl-auto: validate` 이고 운영 jar 의 `Member` 엔티티가 `ship_*` 5개를 매핑한다.
통합 테스트를 돌리는 순간 Flyway 가 **공유 espdb 에 적용**되므로(WORKING-AGREEMENTS §5),
같은 마이그레이션에서 `ship_*` 를 `DROP` 하면 **구 jar 는 재기동이 불가능**해지고,
`MemberResponse`·`ShippingAddress` 조회는 그 즉시 `ORA-00904`(존재하지 않는 컬럼)로 깨진다.
7/21 의 닉네임 UNIQUE(V6) 사고와 같은 종류인데, **그때보다 훨씬 파괴적**이다 —
UNIQUE 는 신규 가입만 막았지만 컬럼 DROP 은 **기존 조회를 통째로** 깬다.

→ **expand / contract 2단계로 나눈다.**

```
V18 (오늘)  member_address 신설 + member.ship_* 값 복사   ← 순수 추가. 구 jar 무영향
            신 코드 배포 (읽기는 member_address 로)
V19 (나중)  member.ship_* DROP                            ← 신 코드가 운영에 완전히 올라간 뒤
```

`ship_*` 를 남겨두는 동안은 **두 곳에 같은 값이 있다**(이중 진실). 이건 감수한다 —
짧은 기간이고, 대안(한 번에 DROP)은 운영을 깨기 때문이다. 다만 **V18 이후 신 코드는
`member.ship_*` 에 쓰지 않는다** — 안 그러면 두 값이 갈라져 나중에 어느 쪽이 맞는지 알 수 없어진다.

⚠ `orders.ship_*` 는 **건드리지 않는다.** 그건 주문 시점 **스냅샷**이라 주소록과 무관하고,

## 3. 기능 추가 — 배송지 주소록 (V18)

백로그 **B-5**. `member.ship_*` 5컬럼 = 회원당 배송지 하나였던 걸(V11) 별칭 붙은 주소록으로 늘렸다.

### 3-1. ⚠ 착수 전에 발견한 것 — 이관 대상 1건이 7/22 검증 잔재였다

회원 4명 중 배송지가 있는 사람은 **1명**이었는데, 그 값이 이랬다.

```
수령인=123 · 우편번호=06134 · 주소=123123123 · 상세=123
```

WORKING-AGREEMENTS §3-1 에 기록된 **그 사고의 흔적**이다 — 7/22 에 배송지 기능을 브라우저로
검증하며 본인 계정 + 실상품으로 주문했고 수령인에 `123` 을 넣었다. 그때 **주문은 화면에서 취소했고
재고도 복원**했지만, 회원의 기본 배송지에 남은 이 값은 **아무도 안 치웠다.**

> §2-5 "재발 방지와 기존 잔재 정리는 별개" 의 또 다른 실례다. 그때는 "주문" 만 잔재로 봤고
> **그 검증이 회원 프로필도 건드렸다는 걸 놓쳤다.** 검증이 만든 것을 셀 때 주문·상품만 보지 말 것.

**마이그레이션은 이 판단을 하지 않는다.** "값이 있으면 옮긴다" 만 하고 잔재 정리는 별건으로 뒀다 —
빈 DB·미래 환경에서도 같은 스크립트가 돌아야 하고, 데이터를 골라내는 마이그레이션은 재현이 안 된다.
마침 **오늘 만든 화면으로 바로 지울 수 있다**(이월 참조).

### 3-2. ⚠ 첫 번째 "순수 추가가 아닌" 마이그레이션 — expand / contract 로 나눴다

V13~V17 은 **다섯 개 전부 컬럼·테이블 ADD** 였다. B-5 는 기존 값 이관 + 컬럼 정리가 붙는다.

한 번에 `member.ship_*` 를 DROP 하면 어떻게 되는지가 착수 전 유일한 위험이었다:

```
통합 테스트 실행 → Flyway 가 공유 espdb 에 적용 → 컬럼 사라짐
  → 운영 구 jar 는 그 컬럼을 매핑 중 → 재기동 불가 + 회원·주문 조회가 ORA-00904
```

7/21 의 **닉네임 UNIQUE(V6) 사고와 같은 종류인데 훨씬 파괴적**이다. UNIQUE 는 신규 가입만 막았지만
컬럼 DROP 은 **이미 되던 조회를 통째로** 깬다.

→ 사용자 결정으로 **둘로 나눴다**:

| | 내용 | 구 jar 영향 |
|---|---|---|
| **V18 (오늘)** | `member_address` 신설 + `member.ship_*` 값 복사 | **없음** (순수 추가) |
| **V19 (나중)** | `member.ship_*` DROP | 신 코드가 운영에 올라간 뒤에만 안전 |

뒤쪽은 이월이 아니라 **백로그 B-5-2** 에 뒀다 — 수명이 "며칠" 이 아니라 "배포가 안정된 뒤" 라는 조건부다.

> ⚠ **번호가 밀렸다.** 착수 시점엔 뒤쪽을 "V19" 로 불렀는데, 같은 날 오후에 위시리스트(§4)가
> **V19 를 가져갔다.** 그래서 `member.ship_*` DROP 은 **V20** 이 된다.
> 마이그레이션 번호는 **먼저 머지되는 쪽이 가져간다** — 계획 단계에서 번호를 예약해 두면
> 이렇게 어긋난다. 아래 본문에 남은 "V19" 표기는 그때의 판단 기록이라 그대로 두되,
> **앞으로를 가리키는 자리는 전부 V20 으로 고쳤다**(백로그·ARCHITECTURE 포함).

### 3-3. 이중 진실을 규율이 아니라 **구조**로 막았다

V18~V19 사이엔 같은 주소가 두 곳에 있다. 여기서 흔한 실패는 *"신 코드는 옛 컬럼에 쓰지 않기로 하자"*
라고 **적어두고 끝내는 것**이다. 그러면 언젠가 누가 쓴다.

→ **`Member` 엔티티에서 `ship_*` 매핑 5개를 아예 걷어냈다.** 필드가 없으면 쓸 방법이 없다.
`ddl-auto=validate` 는 **매핑되지 않은 여분 컬럼을 문제 삼지 않으므로**(실측: V18 적용 후 기동 통과)
DB 에 컬럼이 남아 있어도 아무 문제가 없다.

부수효과로 **V19 는 코드 변경이 0** 이 됐다 — 순수 DDL 한 줄이다.

### 3-4. 기본 배송지가 하나뿐임을 DB 가 보장한다

Oracle 에는 부분 유니크 인덱스(`WHERE is_default = 1`)가 없다. 함수 기반 유니크 인덱스로 같은 효과를 낸다:

```sql
CREATE UNIQUE INDEX uq_member_address_default
    ON member_address (CASE WHEN is_default = 1 THEN member_id END);
```

`is_default=0` 인 행은 색인값이 NULL 이라 유니크 대상에서 빠지고, 같은 회원의 두 번째 기본 배송지만
ORA-00001 로 거부된다. 주문번호 유니크(V15)를 "앱 채번이 어긋났을 때의 최종 방어선" 으로 둔 것과 같은 성격이다.

**그 대가로 순서 제약이 생겼다.** "옛 기본 해제" 와 "새 기본 지정" 이 **DB 에 도달하는 순서**가 중요한데,
JPA 더티 체킹은 **flush 순서를 보장하지 않는다** — 같은 엔티티 타입이라 뒤집힐 수 있다.

```java
addressRepository.findByMemberIdAndIsDefaultTrue(memberId)
        .ifPresent(MemberAddress::unsetDefault);
addressRepository.flush();          // ← 이 줄이 없으면 ORA-00001
address.markDefault();
```

삭제도 같은 문제다 — 기본 배송지를 지우고 다른 주소를 승계시킬 때 **DELETE 가 먼저 나가야** 한다.
안 그러면 기본이 두 행이 되는 순간이 생긴다.

> 이 `flush()` 들은 **지우기 쉬운 줄**이다("불필요해 보이는 flush"). 그래서 코드 주석과 여기 양쪽에 적었다.

### 3-5. FK 를 진짜로 걸었다 — `member_coupon` 과 다른 이유

`member_coupon.member_id` 는 주석에 **"FK 아님(느슨한 참조) — 도메인 경계"** 라고 적혀 있다.
`member_address` 는 반대로 **진짜 FK + `ON DELETE CASCADE`** 다. 모순이 아니다:

| | 방향 | 판단 |
|---|---|---|
| `member_coupon` → member | **도메인 간**(coupon → member) | FK 를 걸면 MSA 분리 때 걸림돌. 느슨한 UUID |
| `member_address` → member | **도메인 안**(member → member) | 쪼개도 member 와 **함께** 움직인다. FK 가 맞다 |

그리고 CASCADE 는 선택이 아니었다 — `MemberService.withdraw` 가 member row 를 지우므로,
CASCADE 가 없으면 **주소가 있는 회원은 탈퇴 자체가 FK 위반으로 실패**한다.

### 3-6. 백필 PK 를 `SYS_GUID()` 로 하지 않았다

CLAUDE.md 는 PK 를 **UUIDv7 · 앱에서 생성**으로 못박는데, 백필 행은 앱을 거치지 않는다.
`SYS_GUID()` 는 v7 이 아니고(시간순이 아니다), **한 번 들어가면 나중에 구분할 방법도 없다.**

→ SQL 에서 **v7 레이아웃을 그대로 조립**했다.

```
[48비트 unix ms = 12 hex] [버전 '7'] [rand_a 3 hex] [variant 'A'] [rand_b 15 hex] = 32 hex
```

RFC 9562 의 variant 는 상위 2비트가 `10` 이어야 해서 17번째 hex 는 8·9·A·B 중 하나여야 한다 → `'A'` 고정.
**실측**: 생성값 `019F9175E3107575A1348689147A35E0` — 13번째 hex 가 `7`, 앞 12 hex 를 되읽으면 현재 UTC 와 일치.

> ⚠ 이 플랫폼의 `SYS_GUID()` 는 **순차적**이라 난수부의 무작위성이 약하다(연속 호출이 1~2 hex 만 다르다).
> 필요한 건 **서로 다른 값**뿐이고 PK 유니크가 최종 방어선이라 그대로 뒀다 — 다만 이걸 **난수원으로
> 믿으면 안 된다**(토큰·비밀값 용도로는 부적합).

### 3-7. API 계약을 유지한 채 저장 위치만 옮겼다

`MemberResponse.ship*` 5개 필드는 **그대로 뒀다.** 프론트의 주문서 자동 채움과 `hasAddress` 판정이
이 필드를 보고 있어서, 형태까지 바꾸면 **저장 구조 이전과 화면 개편이 한꺼번에 얽힌다.**
값의 **출처만** `member.ship_*` → 주소록의 기본 항목으로 바꿨다.

같은 이유로 옛 경로 `PATCH /api/members/me/shipping-address` 도 살렸다 — 주문서의
"이 주소를 기본 배송지로 저장" 체크가 계속 쓴다. 서버가 그 요청을 **기본 항목 upsert** 로 처리해
주소가 두 벌로 갈라지지 않는다(통합 테스트로 고정했다).

> 덕분에 **주문 API(`POST /api/orders`)는 한 글자도 안 바뀌었다.** 주문서는 원래 배송지를
> 본문으로 받고 있었고, 주소록은 그 폼을 **채우는 방법**이 하나 늘어난 것뿐이다.

> 빈 DB 검증은 마이그레이션마다 **매번** 돌려야 하는 절차라 특히 그렇다.

같은 자리에서 **시퀀스 DROP 누락**도 고쳤다(§2-2 에서 예고한 워밍업). 7/23 V16 검증에서

오늘 실제로 시퀀스까지 지우고 돌려 **V15 가 깨끗이 재적용**되는 걸 확인했다.

## 4. 기능 추가 — 위시리스트(찜) (V19)

백로그 **B-6**. 주소록을 닫고 이어서 뽑았다. 장바구니와 구조가 거의 같아 **패턴을 그대로 재활용**했다
— 찜 행에는 상품 id 만 있고, 상품 정보는 catalog 공개 서비스에서 합성한다.

### 4-1. 같은 모양인데 저장소가 다르다 — 왜 Redis 가 아닌가

장바구니는 Redis(`CartStore`)인데 찜은 **테이블**이다. 백로그가 이미 그렇게 적어 뒀고 근거는 이렇다:

| | 장바구니 | 찜 |
|---|---|---|
| 수명 | "지금 사려는 것" — 세션이면 충분 | **로그아웃해도 남아야** 한다 |
| 잃으면 | 다시 담으면 된다 | **사용자가 모으던 것이 사라진다** |

Redis 에 두면 TTL·플러시·재시작에 **조용히** 날아가고, 사용자는 원인을 알 수 없이
"찜한 게 사라졌다"로만 겪는다. 되돌릴 방법도 없다.

### 4-2. ⚠ 핵심 판단 — 찜 여부를 상품 응답에 넣지 않았다

가장 편한 설계는 `ProductResponse` 에 `wishlisted` 불리언을 하나 얹는 것이다. **그러면 안 된다**:

```
wishlist → catalog   (찜 목록이 상품 정보를 읽는다. 이미 있다)
catalog  → wishlist  (상품 응답이 찜 여부를 알려면 필요. ← 이게 생기면 순환)
```

**2026-07-20 에 상품 목록 별점에서 겪은 것과 같은 문제**다. 그때는 `review → catalog` 가 이미 있어서
catalog 가 review 를 조회하면 순환이 되므로, **이벤트로 집계값을 밀어넣고 비정규화**해 풀었다.

그런데 **찜에는 그 해법이 안 통한다** — 별점은 상품마다 하나인 값이라 컬럼에 담을 수 있지만,
찜 여부는 **보는 사람마다 다르다.** 상품에 비정규화할 수 있는 값이 아니다.

→ **세 번째 방법을 썼다: 클라이언트 조인.**
`GET /api/wishlist/product-ids` 로 **내가 찜한 상품 id 집합**을 따로 주고, 화면이 상품 목록과 합친다.
서버는 도메인 경계를 지키고, 화면은 Set 하나만 들면 된다.

> 정리하면 도메인 순환을 피하는 수단이 이제 셋이다 — **이벤트**(별점) · **비정규화**(별점) ·
> **클라이언트 조인**(찜). 값이 *보는 사람마다 다르면* 앞의 둘은 쓸 수 없다.

### 4-3. 추가·해제를 둘 다 멱등으로

"이미 찜한 상품을 또 찜하면 409" 가 자연스러워 보이지만 그렇게 하지 않았다.

- 화면이 **토글**이라 사용자가 "중복 찜"을 **의도할 수 없다.**
- 그러니 중복 요청은 전부 **사고**다 — 더블클릭, 느린 네트워크에서의 재시도, 뒤로가기.
- 거기서 에러를 띄우면 사용자는 원인을 알 수 없고 **화면 상태만 어긋난다**(하트는 켜졌는데 에러창).
- 원하는 최종 상태("찜되어 있음")는 어느 쪽이든 같다.

해제도 대칭으로 멱등이다. "지워달라"의 목적은 **없는 상태**이고, 이미 그렇다면 할 일이 없는 것이지
오류가 아니다. 해제에서는 **상품 존재를 확인하지 않는다** — 확인하면 삭제된 상품을 찜 목록에서
**영영 못 뺀다.**

동시 요청으로 검사와 INSERT 사이가 벌어져도 DB 의 `UNIQUE(member_id, product_id)` 가 막는다.

### 4-4. 조회 인덱스를 일부러 안 만들었다

유일한 조회 경로가 "내 찜 목록"(`member_id = ?`)인데, 위 UNIQUE 제약이 만든 인덱스의
**선두 컬럼이 이미 `member_id`** 라 그 쿼리가 그대로 탄다. 같은 컬럼으로 인덱스를 하나 더 만들면
INSERT/DELETE 비용만 늘고 얻는 게 없다. **실측**: `user_indexes` 에 PK + UNIQUE 둘뿐이다.

### 4-5. 삭제된 상품을 조회에서 지우지 않는다

장바구니는 삭제된 상품을 만나면 **그 자리에서 지운다**(`cartStore.remove`). 찜은 **빼고 보여주기만** 한다.

> **왜 다른가**: `WishlistQueryService` 는 `@Transactional(readOnly = true)` 다. 조회가 데이터를 고치면
> "목록만 봤는데 뭔가 사라지는" 예측 불가능한 동작이 된다. 장바구니가 그렇게 하는 건 **결제 직전**이라
> 정합성이 더 중요한 자리이기 때문이고, 찜은 그럴 이유가 없다.
> 쌓이면 스위퍼를 두면 된다(이미지 고아 정리와 같은 방식) — 지금은 그럴 규모가 아니다.

### 4-6. 목록 값은 스냅샷이 아니라 **지금** 값이다

7/23~24 내내 "스냅샷" 을 일곱 번 적용했는데(닉네임·이미지·배송지·배송비·정가·쿠폰·주소록)
찜은 **정반대**다. 가격·재고·별점을 전부 조회 시점에 catalog 에서 읽는다.

이유가 명확하다 — 찜은 **"나중에 살까"** 하고 담아 두는 것이라, **값이 내렸는지 · 품절됐는지**를
봐야 쓸모가 있다. 찜한 시점의 가격을 박아 두면 오히려 **틀린 정보**가 된다.
(주문은 반대다 — "그때 얼마에 샀는지" 가 사실이어야 한다.)

→ 화면에도 그렇게 적었다: *"가격과 재고는 **지금** 값이에요."*

### 4-7. 화면 — 카드가 `<button>` 이라 하트를 안에 못 넣는다

상품 목록 카드는 **통째로 `<button>`** 이다(클릭하면 상세로). 하트를 그 안에 넣으면 **button 중첩**이라
유효하지 않은 HTML 이고 클릭 처리도 어긋난다.

→ 카드를 `relative` 래퍼로 감싸고 하트를 **절대배치**로 얹었다. 클릭이 카드로 새지 않게 `@click.stop`.

나머지 판단들:

- **낙관적 갱신** — 하트는 즉시 반응해야 하는 UI 라 화면을 먼저 바꾸고 서버에 보낸다. 실패하면 되돌린다.
  서버가 멱등이라 중복 클릭이 문제를 만들지 않는다(§4-3 이 여기서 값을 했다).
- **찜 id 집합은 스토어에 둔다**(`stores/wishlist.js`) — 목록·상세·찜 페이지가 같은 상태를 봐야 한다.
  화면마다 따로 들면 상세에서 찜을 풀고 뒤로 갔을 때 목록 하트가 여전히 채워져 있다.
- **로그아웃 시 비운다** — 안 비우면 같은 브라우저에서 다음 사람이 **남의 하트**를 본다.
- **비로그인도 하트를 본다.** 누르면 막지 않고 `redirect` 를 달아 **로그인으로 보낸다** — 찜은 로그인을
  유도하기 좋은 자리다.
- **품절이어도 찜은 된다.** 재입고를 기다리는 게 찜의 용도라 `available` 은 "지금 담을 수 있나"만 가른다
  (찜 목록의 「장바구니 담기」 버튼만 비활성).

## 5. `member.ship_*` 컬럼 DROP (V20) — expand / contract 의 **contract**

백로그 **B-5-2**. §3-2 에서 나눠 뒀던 뒤쪽을 **같은 날 안에** 처리했다.

### 5-1. 왜 며칠 안 기다리고 앞당겼나

백로그에는 조건을 *"V18 을 담은 jar 가 운영에서 정상 동작 중일 것. 되돌릴 일이 없다고 판단되면 그때"*
로 적어 뒀고, 막연히 며칠 뒤를 생각하고 있었다. 사용자가 **"다음 작업 전에 먼저 하는 게 낫지 않나"**
라고 제안해 다시 따져 봤고, **앞당기는 쪽이 맞았다.**

착수 전 실측으로 확인한 것:

| 확인 | 결과 |
|---|---|
| 운영 jar | V18·V19 를 담은 빌드(**10:20**)로 교체됨 · 브라우저 검증 통과 |
| `Member` 엔티티 | `ship_*` 필드 **없음**(주석만 남아 있다) |
| 코드 참조 | 네이티브 쿼리·JPQL 어디에도 **없음** |
| `Order.ship_recipient` | **다른 테이블**의 주문 스냅샷 — 무관 |

**결정적이었던 것은 "기다려서 얻는 게 뭔가" 였다.** 기다리는 목적은 롤백 여지를 남기는 것인데:

- 남아 있는 컬럼 값은 **이미 낡은 데이터**다. 주소록에서 고치거나 지워도 이쪽은 안 따라오므로,
  실제로 오늘 오전에 `123` 을 주소록에서 지웠을 때 **컬럼에는 그대로 남아 어긋나 있었다**(§3-13).
- 그리고 V18 이전 jar 로 되돌리면 **주소록이 통째로 사라진다.** 즉 **롤백 경로가 애초에 쓸 수 없다.**

→ 지키려던 안전장치가 **이미 작동하지 않는 상태**였다. 그러면 기다림은 비용만 남는다.

> ⚠ 그래도 **되돌릴 수 없는 작업을 앞당긴 것**이므로 근거를 여기 남긴다.
> 롤백 경로가 살아 있었다면 기다리는 게 맞았다.

### 5-2. 배포가 필요 없었다 — §3-3 의 부수효과

**코드 변경이 0**이다. jar 가 안 바뀌므로 배포할 것이 없고, 마이그레이션은 **통합 테스트가 돌 때
espdb 에 적용**된다. 오늘 하루 중 유일하게 배포 없이 끝난 스키마 변경이다.

이게 §3-3 에서 **엔티티 매핑을 미리 걷어낸 덕**이다. 그때 매핑을 남겨 뒀다면 오늘 V20 은
"엔티티 수정 + 테스트 수정 + 빌드 + 배포" 가 붙었을 것이다. **일을 앞으로 당겨 놓으면 뒤가 싸진다.**

### 5-3. 검증 (실측)

| 확인 | 결과 |
|---|---|
| V20 적용 | espdb **3.5초** · success |
| `member` 의 `SHIP%` 컬럼 | **0개** (5 → 0) |
| `orders` 의 `SHIP_%` 컬럼 | **9개 그대로** — 주문 스냅샷은 안 건드렸다 |

| 테스트 | **219개** · failures 0 · errors 0 · **skipped 0** (컬럼이 사라져도 아무 테스트가 안 깨졌다 = 참조가 정말 없었다는 증거) |
