## 2. 착수 전 결정 — 백로그가 「결정 필요」라 적은 자리는 실측으로 이미 답이 있었고, 없던 자리가 하나 나왔다

### 2-1. 🔴 돈은 통로가 하나다 — `ProductResponse`

배선을 읽었더니 장바구니(`CartService`)가 상품을 `ProductQueryService.findByIds` → `ProductResponse`
**로만** 읽고, 주문(`OrderService`)은 그 장바구니 줄을 복사한다. 배송비·쿠폰 최소금액도 전부
`cart.totalPrice()` 를 쓴다.

→ **유효 판매가를 한 자리에서 만들면 목록·상세·장바구니·주문·배송비·쿠폰이 전부 따라온다.**
여러 곳에 흩으면 **그 어긋남은 돈에서 난다**(08-10 B-25 가 같은 이야기).

### 2-2. ⚠ 캐시는 정할 것이 없었다

백로그가 *"TTL 로 버틸지 evict 할지 결정 필요"* 라 적어 둔 자리인데, `CacheConfig` 실측 **TTL 60초**다.
→ **TTL 로 버틴다.** 관리자 조작은 `@CacheEvict` 로 즉시 반영하고, **세일이 저절로 시작·종료하는 순간만**
최대 60초 늦다. evict 배선을 더 넣을 값어치가 없다.

### 2-3. 🔴 백로그에 없던 자리 — 정렬·가격필터가 `product.price` 컬럼을 본다

`ProductRepositoryImpl` 의 정렬 화이트리스트에 `price` 가 있고, `minPrice`/`maxPrice` 는
`@Cond(path="price")` 로 자동 처리돼 **컬럼을 그대로** 봤다. 세일가를 응답 조립에서만 얹었다면:

- 화면엔 8,000원인데 **「1만원 이하」 필터에 안 걸린다**
- **「가격 낮은 순」이 세일 전 순서**로 나온다

**08-13 §13-2 의 「화면에만 있었다」와 같은 종류**다. → **쿼리에서 계산한다**(사용자 결정).

### 2-4. 사용자와 확정한 셋

| 무엇 | 결정 | 안 고른 것과 그 대가 |
|---|---|---|
| 정렬·필터 | **쿼리에서 CASE 로 유효가 계산** | 「응답에서만」은 싸지만 화면과 조회가 어긋난다 / 「`sale_price` 컬럼 비정규화」는 갱신 배치가 필요하고 배치를 놓치면 **값이 거짓말을 한다** |
| 할인 방식 | **상품 단위 · 정률(%)** | 정액은 싸고 비싼 옵션에 같은 액수가 붙어 **체감 할인율이 제각각**이 된다 |
| 화면 표시 | **판매가 취소선 + 세일가**(정가는 숨김) | 정가 취소선은 할인폭이 커 보이지만 **정가 없는 상품은 세일인지가 안 보인다** |

### 2-5. 내가 정한 둘 (전례가 답을 갖고 있었다)

- **겹침** — G-8/V49 그대로. Oracle 유니크로 기간 겹침을 못 막아 **앱이 유일한 방어**라 테스트로 못 박고,
  조회는 `Optional` 이 아니라 **`List`** 로 받는다(뚫렸을 때 목록 전체가 500 나지 않게).
- **주문 스냅샷** — `price`=세일가 · `listPrice`=정가 둘만. B-7 토대가 이미 안전하다.

## 3. 🔴 착수 전 판단에 없던 덫 — 관리자 폼이 세일가를 원가로 굳힌다

`ProductResponse.price` 를 세일가로 바꾸기로 하고 프론트를 세었더니 `ProductFormView` 가
`form.price = p.price` 로 **응답의 판매가를 그대로 입력칸에 싣고 있었다.**

→ **세일 중에 상품을 수정하면 세일가가 원래 판매가로 저장되고**, 세일이 살아 있으면 **할인이 두 번 먹는다.**
컴파일도 테스트도 안 걸리고 화면은 멀쩡히 돈다.

### 3-1. 실측이 방향을 정했다 — **7 대 1**

08-13 §11-3(*"필드를 지우기 전에 그 이름을 저장소 전체에서 센다"*) 그대로 셌다.
`product.price` 를 읽는 자리 **8곳**:

| 성격 | 곳 | 수 |
|---|---|---|
| 고객에게 보이는 가격 | `ProductCard`·`ProductDetailView`(2)·`HomeView`·`WishlistView`·`CartView`·`recentlyViewed` | **7** |
| 관리자 입력칸 | `ProductFormView:40` | **1** |

→ **`price` = 세일가(청구액), `regularPrice` = 세일 전 판매가**, 폼만 `regularPrice` 를 읽는다.
🔴 **반대로 갔으면**(«`price` 는 원가, `salePrice` 를 새로 둔다») **7곳을 전부 `salePrice ?? price` 로
고쳐야 하고 한 곳만 빠져도 세일이 조용히 안 먹는다.** 위험을 여러 곳에 흩는 대신 **한 곳에 모은** 것이
이 선택이다.

⚠ 폼은 세일 중이라는 사실을 칸 아래에서 **말해 준다** — 안 그러면 관리자가 «내가 9,000 이라 적었는데
왜 7,200 으로 팔리지» 를 폼 어디에서도 확인 못 하고 **그 칸을 고쳐 맞추려 든다.**

## 4. 구현

- **V52** `product_discount`(상품·할인율 1~99·시작·종료). ⚠ **컬럼이 아니라 테이블인 이유 둘**:
  ①컬럼 한 벌이면 «지금 세일» 만 담겨 **다음 세일을 미리 등록할 수 없다** — 그게 이 기능의 목적이다
  ②덮어쓰면 끝난 세일이 흔적 없이 사라진다.
  🔴 **V48(`deleted_at`)이 컬럼으로 간 것과 갈리는 지점이 여기다** — 삭제 대기는 상품당 **하나뿐인 상태**고,
  할인은 **여러 개가 줄지어 서는 일정**이다.
- **적용 순서** `ROUND((price + priceDelta) × (100 - rate) / 100)` — 가격차를 **더한 뒤에** 할인율.
- **반올림** 정수 연산 `(x*(100-r)+50)/100` 으로 Oracle `ROUND(x,0)` 과 맞췄다.
  ⚠ SQL 과 Java 가 갈리면 **목록 가격과 장바구니 가격이 1원 어긋나고**, 그건 눈에 안 띄다가 결제에서 터진다.
- **정렬·필터** 상관 서브쿼리 + CASE. ⚠ **조인이 아니라 서브쿼리**인 이유: 조인하면 겹침이 뚫렸을 때
  **같은 상품이 목록에 두 줄로 조용히** 나온다 — 500 보다 나쁘다(아무 로그도 안 남는다).
- **관리자 API 는 `/api/admin/**` 아래** — 🔴 `SecurityConfig` 마지막 줄이 `.anyRequest().permitAll()`
  이라 `/api/products/**` 에 두고 매처를 한 줄 잊으면 **누구나 99% 세일을 걸 수 있다.**
  WA §2-4 가 관리 API 경로를 모아 두라고 한 이유가 정확히 이것이다.
  ⚠ B-25(관리자 주문 취소)는 반대로 갔는데, 그건 **형제 조작 넷이 이미 `/api/orders/...` 에 있었기** 때문이다.
  할인은 오늘 생긴 새 자원이라 그 논거가 없다.
- **날짜는 `LocalDate` 만 받고 경계는 서버가** 만든다(B-26 규약) · **종료일은 포함**.

### 4-1. 그 김에 이어 준 것 — 찜 목록

## 6. 🔴 전수에서 6건이 깨졌다 — 내 변경이 아니었고, **테스트의 잠복 결함이었다**

### 6-1. 원인 — **날짜가 지나야 드러나는 갈래**

- `ApiResponse` 에 **`@JsonInclude(NON_NULL)`** 이 붙어 있어 **열린 이벤트가 없으면 `data` 키가 통째로 빠진다.**
- 헬퍼 `openEventName` 은 *"없으면 만들고, 있으면 그걸 쓴다"* 고 적어 놓고
  `JsonPath.read(body, "$.data")` 로 읽는다 → **null 이 아니라 예외를 맞는다.**
  즉 **«없을 때를 위해» 쓴 갈래가 «없을 때» 터진다.**
- 실측: 열린 이벤트 **0건**(`5000` 08-13 마감 · `ZZ-이벤트쿠폰3` 08-14 마감, 둘 다 CLOSED).

🔴 **그동안 초록이었던 이유는 맞아서가 아니라 그 갈래를 안 밟아서다.** 08-13~14 에는 운영에 열린 이벤트가
늘 있어 **항상 첫 갈래로 흘렀고**, 오늘 둘의 발급 창이 다 지나자 처음으로 두 번째 갈래에 닿았다.
⚠ **코드를 아무리 봐도 안 보이는 종류다** — 달력이 넘어가야 드러난다.

### 6-2. 대응 — 08-14 §6-3 의 갈래로 「고친다」 쪽

*"테스트의 정의가 틀렸다 → 고친다 / 전제가 운영에 깨졌다 → 견디게 만든다"* 중 **전자**다.
헬퍼가 하겠다고 적은 일을 **실제로 못 하고 있었다.**
→ `bannerOrNull()` 로 모았다. ⚠ **같은 한 줄이 이 클래스에 네 곳 있었다** — 넷 다 «없으면 null 이겠지» 로
쓰였고 넷 다 같은 예외를 맞는다. 같은 사실이 네 곳에 흩어져 있으면 **한 곳만 고쳐진다.**

## 7. 🔴 내가 쓴 테스트가 간헐적으로 실패했다 — **원인을 확정하지 못했고, 그렇게 적는다**

`priceFilterUsesSalePrice` 가 **3~4회 중 1~2회** 실패했다(원상복구 상태에서도).
구조가 *«같은 조회를 세일 전후로 두 번 불러 비교»* 였고 그 사이에 `products:list` 캐시 쓰기와
`@CacheEvict` 가 끼어 있었다.

**가설 하나를 세워 실제로 밟았고 기각됐다**: *"`save()` 한 할인이 flush 되지 않아 상관 서브쿼리에
안 보인다"* → 테스트에 `em.flush()` 를 넣고 4회 돌렸더니 **여전히 2회 실패**했다.

→ **추측으로 원인을 적지 않는다.** 대신 **구조를 바꿔 그 의존을 없앴다**: 대조군을 「세일 없는 다른 상품」
으로 옮겨 **한 번의 조회로 둘을 함께** 증명한다. 이후 **5회 연속 통과.**

⚠ **대조군의 값어치는 오히려 커졌다** — 같은 순간·같은 쿼리에서 «걸리는 것» 과 «안 걸리는 것» 을
나란히 본다(WA §3-3).
🔴 **원인이 남아 있다는 사실 자체를 이월에 남긴다** — 캐시가 얽힌 다른 테스트에서 또 날 수 있다.

| **M1** | 곱 순서 뒤집기(할인 먼저, 가격차 나중) | 곱 순서 단언 |
| **M2** | 종료 경계를 배타 → 포함 | 경계 단위 테스트 |
| **M3** | 겹침 판정 `<,>` → `<=,>=` | 「맞닿는 것은 겹침이 아니다」 |
| **M4** | 정렬·필터에서 할인율 무시 | 가격 필터 · 가격 정렬 **둘** |
| **M5** | `NO_EXCLUDE` 를 `null` 로 | 겹침 거절 |

🔴 **M5 는 실측이 주석을 확인해 줬다** — 결과가 **200**(겹침이 통과됨)이었다. 즉 «NULL 비교는 UNKNOWN 이라

### 11-1. 밟은 것 — **표본을 만들어서 밟았다**

🔴 **`priceDelta ≠ 0` 인 옵션이 운영에 하나도 없어서**(실측 10개 전부 0) 검증용 상품을 새로 만들었다:
`ZZ-세일검증` · 판매가 **10,000** · 정가 비움 · 옵션 둘(「기본」 +0 / **「L」 +2,000**) · 재고 5씩.
⚠ **두 번째 옵션이 없으면 곱 순서를 뒤집어도 화면이 똑같다** — 08-14 §9-5 와 같은 이야기다.

| 스텝 | 무엇을 증명하나 | 결과 |
|---|---|---|
| 되읽기 문장 | 폼이 만들 것을 **금액까지** 말하나 | ✅ 「8월 19일부터 8월 19일까지 20% — 10,000원이 8,000원이 됩니다.」 |
| 🔴 **관리자 폼** | 판매가 칸이 **세일 전 값**인가 (§3 의 덫) | ✅ **10,000**(8,000 아님) + 「지금 20% 세일 중 — 고객에게는 8,000원」 |
| 고객 상세 | 판매가 취소선 + 세일가 + 종료일 | ✅ 10,000 취소선 · **8,000** · 20% · 「8월 19일까지」 |
| 🔴 **곱 순서** | 가격차를 더한 뒤 할인율인가 | ✅ 옵션 「L」 **9,600** = (10,000+2,000)×0.8 |
| 가격 필터 | 필터가 세일가를 보나 | ✅ 「9,000 이하」에 **나온다** |
| 🔴 **그 대조군** | 필터가 **실제로 거르고는 있나** | ✅ 「7,000 이하」에 **안 나온다**(8,000 > 7,000) |
| 정렬 | 「가격 낮은순」이 세일가 순인가 | ✅ |
| 장바구니 | 세일이 **청구로 이어지나** | ✅ 「기본」 8,000 · 「L」 9,600 |
| 겹침 | 앱이 유일한 방어 | ✅ 오늘~모레 30% → **「기간이 겹치는 할인이 이미 있습니다.」** |
| 🔴 **맞닿는 경계** | 연속 세일을 이어 붙일 수 있나 | ✅ **내일~모레는 통과**, 「예정」 배지 |

🔴 **「9,000 이하」와 「7,000 이하」를 나란히 밟은 것이 요점이다** — 앞엣것만 보면
«필터가 세일가를 본다» 와 «필터가 아예 안 걸린다» 가 **구분되지 않는다**(WA §3-3).

⚠ **자동 테스트로만 덮인 자리 없음.**

### 11-2. ⚠ 「정리했다」와 「남은 게 없다」는 다른 말이었다

사용자가 *"모두 진행하니까 잘 됐어"* 라고 했고 실제로 스텝은 다 통과했다. 그런데 **처분(7번)은
안 됐다** — 실측하니 상품이 살아 있고 할인 **2건**이 남아 있었다.

🔴 **나무랄 일이 아니라 적어 두면 되는 일이다**(08-14 §V51 검증 잔재와 같은 취급). 안 적으면
나중에 «이 세일 뭐지» 가 된다. ⚠ **그리고 물어보지 않고 «정리됐겠지» 로 문서를 닫았으면
조건부 잔여가 통째로 비어 있었을 것이다.**

⚠ 겹침 검증의 두 번째 할인이 30% 가 아니라 **20%** 로 등록됐다(할인율 칸을 그대로 두고 날짜만 바꾼 것).
**맞닿는 경계 통과를 증명하는 데는 할인율이 무관하므로 검증은 유효하다.**

### 11-3. 🔴 그래서 관측 기회가 하나 생겼다 — **08-20 00:00**

남은 할인 둘이 **경계를 맞대고 있다**:

| 할인 | 기간(KST) | 지금 |
|---|---|---|
| ① 20% | 08-19 00:00 ~ **08-20 00:00** | 진행 중 |
| ② 20% | **08-20 00:00** ~ 08-22 00:00 | 예정 |

→ **08-20 00:00 에 ①이 끝나고 ②가 곧바로 시작한다.** 그날 상품을 열어 보면:

- **「맞닿는 경계」가 실제로 이어지는가** — 세일가 8,000 이 **끊기지 않고** 유지되면 그렇다
  (한 순간이라도 10,000 이 보이면 경계에 틈이 있다는 뜻이다)

- ⚠ **캐시 60초 지연이 눈에 띄는지**(§2-2 에서 감수하기로 한 대가) — 실측으로 본 적이 아직 없다
