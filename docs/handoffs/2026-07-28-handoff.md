## 2. 구현

### 2-1. 단발성 토큰 — `PasswordResetTokenStore` (Redis, `RefreshTokenStore` 와 키 방향 반대)

- key=`auth:reset:<token>`, value=`memberId`, TTL 30분(`auth.password-reset.token-validity-ms`).
- ⚠ **토큰을 키로 둔다**(회원당 1개가 아니라 **토큰당 1개**). refresh 는 회원당 1개(회전)라 회원 id 가 키지만,
  재설정은 재발급이 이전 링크를 조용히 무효화하면 안 되고, 소비 때 토큰만으로 O(1) 삭제돼야 한다.
- `consume` = `getAndDelete`(GETDEL, 원자) → **단발성**. 동시에 두 번 소비돼도 값을 받는 쪽은 하나뿐이라 경합 안전.
- 토큰 문자열은 `UuidCreator.getTimeOrderedEpoch()`(BaseTimeEntity·restock 과 같은 생성기).

### 2-2. `AuthService` 두 메서드

- `requestPasswordReset(loginId): Optional<String>` — 회원 있으면 토큰 발급해 반환, **없으면 empty**.
  호출자(컨트롤러)는 이 둘을 구분해 사용자에게 드러내지 않는다(**열거 방지**).
- `confirmPasswordReset(token, newPassword)` — `consume` 으로 검증(없으면 `INVALID_RESET_TOKEN`) →
  `updatePassword(encode)` → `refreshTokenStore.delete(memberId)`(다른 세션 무효화, `MemberService.changePassword`
  와 동일 규칙: 비번 바뀌면 재로그인).

### 2-3. 엔드포인트 (둘 다 공개 — 기본 permitAll)

- `POST /api/auth/password-reset/request` `{loginId}` → 항상 200. `PasswordResetResponse{token}` 인데
  **`expose-token` 이 true 일 때만** 토큰을 싣는다(아니면 null). 컨트롤러가 노출을 게이트(서비스는 늘 발급).
- `POST /api/auth/password-reset/confirm` `{token, newPassword(@Size 8~64)}` → 200 / 400(`AUTH-400R`).
- SecurityConfig 변경 **불필요** — 기본이 `.anyRequest().permitAll()` 이라 `/api/auth/password-reset/**`
  는 자동 공개(로그인 전 접근이라 의도한 대로). 새 ErrorCode `INVALID_RESET_TOKEN("AUTH-400R", 400)`.

### 2-4. 설정 — 프로파일로 노출 격리

- `application.yml`(기본=운영): `auth.password-reset.expose-token: false`, `token-validity-ms: 1800000`.
- `application-dev.yml`: `expose-token: true` 오버라이드. `PasswordResetProperties`(@ConfigurationProperties,
  `@ConfigurationPropertiesScan` 으로 자동 등록 — JwtProperties 와 달리 SecurityConfig 명시 등록 불필요).

### 2-5. 프론트 — 요청/확정 두 화면 (공개 라우트)

- `views/ForgotPasswordView.vue`(`/forgot-password`): 아이디 입력 → 요청 → "링크 보냈습니다"(열거 방지 문구).
  **dev 는 응답 토큰이 있어** `/reset-password?token=…` 링크를 화면에 바로 띄운다(발송 대체). 운영은 token 이
  null 이라 그 블록이 안 뜬다.
- `views/ResetPasswordView.vue`(`/reset-password?token=`): 새 비번 2회 입력(8자·일치 검사) → confirm →
  "변경됨, 로그인하세요".
- `api/auth.js`: `requestPasswordReset`/`confirmPasswordReset`. `router/index.js`: 두 공개 라우트(`requiresAuth` 없음).
  `LoginView`: "비밀번호를 잊으셨나요?" 링크.

## 5. 부록 — `member.email` 선행 추가 (V29, B-11 착수 전)

B-11(관리자 회원 관리) 착수 전에 **컬럼만 미리** 심었다(사용자 결정). B-10 을 온전하게 만들 SMTP 발송이
붙을 때 보낼 주소가 있어야 하는데 `member` 에 email 이 없었다 — 그 자리를 지금 비워 둔다.

- **V29** `ALTER TABLE member ADD email VARCHAR2(255)` + `uk_member_email UNIQUE`. `Member.email` 필드
  (nullable) + `updateEmail`. **수집 폼·발송 로직은 넣지 않았다** — 그건 SMTP 작업(BACKLOG D)의 몫.
- **nullable 인 이유**: 기존 회원은 email 이 없어 NOT NULL 을 못 건다. 채우는 경로가 없어 지금은 전부 NULL.
- **UNIQUE 인 이유**: 계정 이메일은 loginId·nickname 처럼 식별자. Oracle 은 NULL 을 유니크 검사에서 빼므로
  전부 NULL 인 현재도 충돌 없다. 실제 수집 시작 때 검증(형식·중복)만 얹으면 된다.
- ⚠ **순수 추가 + nullable 이라 구 jar 무해** — 운영 구 jar 는 email 을 매핑 안 해도 `validate` 통과
  (member.ship_* 여분 컬럼의 반대 방향). 프론트는 무관(수집 폼 아직 없음).
- ⚠ **V29 는 이미 espdb 에 적용됐다** — 통합 테스트가 기동 시 espdb 에 마이그레이션을 적용하기 때문
  (`EMAIL VARCHAR2(255)` + `UK_MEMBER_EMAIL` 실측 확인). 그래서 **DB 는 이미 마이그레이션 상태**이고
  운영 구 jar 는 그대로 돌아간다. **백엔드 재배포는 급하지 않다** — email 을 쓰는 코드가 아직 없으니
  다음 배포(B-11/SMTP) 때 새 jar 이 자연히 매핑을 얹으면 된다. 지금 정합성만 맞추고 싶으면 백엔드만 재배포.
- **빈 DB(esptest) V1→V29 검증 통과** — `Successfully applied 29 migrations ... now at version v29` +
  `Started`(=`ddl-auto=validate` 통과, email 필드↔V29 컬럼 일치). 8083 검증 후 내림.

## 6. 관리자 회원 관리 (B-11) — 조회 전용

BACKLOG 마지막 표준 후보. 관리자 도구가 주문·매출에 쏠려 회원을 들여다볼 화면이 없었다. **조회 전용**으로
끝냈다(정지/역할변경은 쓰기라 파급이 달라 후속으로 미룸 — BACKLOG 원안과 사용자 결정 일치).

### 6-1. ⚠ 착수 전 발견 — facade 를 만들면 도메인 순환

회원 상세는 그 회원의 주문·반품·적립금·등급을 다 보여줘야 한다. 이걸 member 쪽 한 서비스가 order·point 를
불러 모으면(facade) 깔끔해 보이지만, **`OrderService` 가 이미 `member.Role` 을 import** 한다(order→member).
member 가 order 를 부르면 **member↔order 순환**이 되고 "domain 하위를 폴더째 분리"가 깨진다. 그래서:

- **각 도메인이 자기 admin 조회를 소유**하고, **상세 화면(프론트)이 조합**한다(위시리스트의 "클라이언트 조인"과 동일 수단).
  - member: `GET /api/admin/members`(목록·검색 loginId·nickname·email, 최신가입순) · `GET /api/admin/members/{id}`(기본상세)
  - order: `GET /api/admin/orders/by-member/{memberId}`(그 회원 주문 — `scopedTo(memberId)` 재사용, `status` 로 **반품만** 추림)
  - point: `GET /api/admin/points/{memberId}/account`·`/history`(`PointService.accountOf/historyOf`, myAccount/myHistory 재사용)
- 전부 `/api/admin/**` 아래라 SecurityConfig 한 줄로 ADMIN 보호(엔드포인트 추가돼도 권한 누락 불가).

### 6-2. 그 외 결정

- **탈퇴=하드삭제**(`MemberService.withdraw` → `delete`)라 목록은 **현존 회원만**. 탈퇴 회원 과거 주문은
  `order.buyer_nickname` 스냅샷으로 order 쪽에 남아 구매자를 안다.
- **반품 전용 도메인 없음** — 반품은 주문 상태(`RETURN_REQUESTED/RETURNED`)라 상세의 "주문·반품" 섹션에서
  상태 필터로 본다(별도 endpoint 불필요).
- **등급은 member 가 아니라 PointAccount** 소유(`totalPurchase` 로 계산) — point admin 으로 읽는다.
- 검색은 loginId·nickname·**email**(V29, 대개 null 이라 거의 안 걸리나 수집 시작 시 자연히 검색됨).
- 마이그레이션 **없음** — 새 테이블·컬럼 0(기존 member·order·point 조회만).

### 6-3. 프론트

- `views/MemberAdminView.vue`(`/admin/members`): DxDataGrid + CustomStore(원격 페이징) + 검색. 행 클릭 → 상세.
- `views/MemberDetailAdminView.vue`(`/admin/members/:id`): 기본정보·적립금카드(등급/잔액/누적/다음등급) +
  주문·반품 그리드(상태필터) + 적립금이력 그리드. 세 API(member·point·order)를 화면이 조합.
- `App.vue` 관리자 nav 에 "회원 관리" 추가, 라우터 2개(requiresAdmin).
- 표는 운영 화면이라 DataGrid 그대로(DESIGN.md §7), 셸만 토큰/공용 클래스.

### 6-5. ⚠ 라우터 가드 강화 — admin 경로 직접 접근은 무조건 `/products`

브라우저 검증 후 사용자 요청: "admin 쪽 직접 접근하면 products 로 보내버려". 기존 가드는 **비로그인**이
admin 경로에 오면 `/login` 으로 보내 관리 화면의 존재를 노출했다. 이제 admin 경로는 권한이 없으면
(비로그인 포함) **로그인 유도 없이 `/products`**.

동시에 **잠재 레이스도 고쳤다**: `loadMe()` 가 `App.vue` mount 이후라(비await), 관리자가 admin URL 을
**직접 열거나 새로고침**하면 초기 가드 시점에 `authState.user` 가 아직 null → 자기 화면인데 `/products` 로
튕겼다(클릭 네비게이션만 검증해 안 걸렸던 자리). 가드를 async 로 바꿔 **보호 경로 진입 시 토큰이 있으면
`authState.user` 를 먼저 로드**한 뒤 역할을 본다. `App.vue` 의 loadMe 는 `!authState.user` 일 때만 호출해 중복 `/me` 제거.

⚠ **catch-all 라우트 추가(후속)**: 위 가드는 **정의된** admin 라우트만 막는다. `/admin/member`(복수 `members`
오타)처럼 **매칭되는 라우트가 없으면 meta 도 없어** 가드가 관여 못 하고 빈 화면으로 "이동은 되는" 구멍이 있었다
(로그아웃 상태 실측). `{ path: '/:pathMatch(.*)*' }` catch-all 을 맨 끝에 두고, 미정의 경로 중 **`/admin/*` 는
`/products`**(관리 화면 존재 비노출), 그 외는 홈으로 redirect. ⚠ **프론트 전용 — 프론트 재배포 필요**(백엔드 무관).

## 7. 회원 정지 · 역할 변경 (B-11 후속) — 쓰기

B-11 조회 전용의 쓰기 후속. 관리자가 회원을 **정지/해제**하고 **역할(USER↔ADMIN)** 을 바꾼다.

### 7-1. 결정 (사용자 확정)

| 질문 | 결정 | 이유 |
|---|---|---|
| 정지 효과 | **전면 차단** | 로그인·토큰갱신(auth) + 주문(order) 다 막고 refresh 토큰 삭제. access 만료 전 30분 창의 주문까지 닫는다 |
| 관리자 보호 | **자기 자신만** | 자기 계정 강등·정지는 락아웃이라 금지(`CANNOT_MODIFY_SELF`). 다른 관리자는 허용 — 문제 관리자 강등 여지 |

### 7-2. 구현

- **저장**: `member.suspended`(V30, `NUMBER(1) DEFAULT 0 NOT NULL`). 상태가 이진이라 **boolean** — enum
  (VARCHAR2+CHECK)이면 값 추가 때 제약 교체가 따라오는데(orders.status 사고) 그 비용을 안 진다. BANNED/DORMANT
  가 필요해지면 그때 승격.
- **정지 지점(전면 차단)**:
  - auth: `AuthService.login`(비번 검증 **뒤** — 열거 방지) → `ACCOUNT_SUSPENDED`(AUTH-403S). `refresh` 도 동일.
  - order: `OrderService.checkout` 진입에서 `MemberService.isSuspended(memberId)`(member 공개 API) → 차단.
    order→member 는 이미 있던 방향(`member.Role` 참조)이라 순환 없음.
  - 정지 시 `MemberAdminCommandService` 가 `refreshTokenStore.delete` — 기존 세션은 access 만료(≤30분) 뒤 갱신 실패로 끊김.
- **자기 보호**: `MemberAdminCommandService.target()` 이 `actingAdminId==targetId` 면 `CANNOT_MODIFY_SELF`
  (MEMBER-400S), 조회조차 안 함. actingAdminId 는 `@LoginUser AuthUser` 에서.
- **엔드포인트**(조회와 같은 컨트롤러, `/api/admin/**` 보호): `POST .../{id}/suspend`·`/unsuspend`,
  `PATCH .../{id}/role`(body `{role}`). 응답은 갱신된 `AdminMemberResponse`(suspended 필드 추가).
- **감사**: SLF4J 로그만(누가 누구를 언제). 감사 테이블은 BACKLOG 후속.
- **프론트**: 상세 화면에 상태 뱃지 + 정지/해제·역할변경 버튼(`window.confirm`). **자기 계정이면 버튼 숨김**
  (`isSelf`, authState.user.id 대조). 목록에도 상태 컬럼. 정지 상태는 `badge-danger`.

## 8. 최상위 관리자 (SUPER_ADMIN) — 정지/역할 권한을 계층화

정지/역할 검증 후 사용자 요청: "최상위 관리자 권한이 필요, 김기현팀으로". 기존엔 **일반 관리자끼리 서로
정지·강등**할 수 있어(자기 자신만 보호) 위험했다. 최상위 계층을 두고 관리자 조작을 거기로 모은다.

### 8-1. 결정 (사용자 확정) — 엄격 분리

- 일반 ADMIN: **일반 회원(USER)만** 정지/해제. **역할 변경·관리자 정지는 SUPER_ADMIN 전용**.
- SUPER_ADMIN 계정: **아무도** 정지·강등 불가(자기 자신 포함).
- **김기현팀** 계정이 SUPER_ADMIN.

### 8-2. 구현

- **Role 에 SUPER_ADMIN 추가** + `Role.authorities()` — SUPER_ADMIN 은 `ROLE_ADMIN` 을 **포함**해
  기존 `/api/admin/**`(hasRole('ADMIN'))를 그대로 통과한다. `JwtAuthenticationFilter` 가 이 목록으로 authority 부여.
  SUPER_ADMIN 전용 판단은 **경로가 아니라 서비스 계층**(`MemberAdminCommandService`)에서.
- **가드**(`authorize`): 자기자신(`CANNOT_MODIFY_SELF`) → 대상이 SUPER면(`CANNOT_MODIFY_SUPER_ADMIN`)
  → (역할변경이거나 대상이 ADMIN인데) 행위자가 SUPER 아니면(`SUPER_ADMIN_ONLY`). 역할변경으로 SUPER 부여는
  금지(`CANNOT_GRANT_SUPER_ADMIN`) — 최상위는 API가 아니라 데이터로만. `actingRole` 은 JWT(AuthUser)에서.
- **V31**: `member.role` CHECK 를 `('USER','ADMIN','SUPER_ADMIN')` 로 교체. ⚠ 제약이 **시스템 이름**
  (SYS_C..., 환경마다 다름)이라 이름으로 못 지운다 → `search_condition_vc` 로 **찾아서** DROP 하는 PL/SQL 블록 후
  named `ck_member_role` 추가. 값을 넓히는 변경이라 구 jar 무해.
- **프론트**: `role==='ADMIN'` 비교가 곳곳(App nav·라우터 가드·상품/주문/공지/리뷰/문의 관리 버튼)에 흩어져 있어
  SUPER 가 관리 UI를 통째로 잃을 뻔했다 → `stores/auth` 에 `isAdminRole`/`isAdmin`(SUPER 포함) **공유 헬퍼**를 만들고
  전 지점 교체. 회원 상세는 뷰어·대상 계층에 따라 버튼 노출(일반 관리자는 관리자 대상 버튼 숨김, SUPER 대상은 아무 버튼 없음).

### 8-3. ⚠ 김기현팀 승격은 **배포 후** 별도 데이터 작업

**구 jar 는 SUPER_ADMIN 을 enum 으로 못 읽어**, DB에 SUPER_ADMIN 행이 있으면 그 회원 로딩이 깨진다.
그래서 순서가 정해져 있다: **① 신 백엔드 배포(SUPER_ADMIN enum 포함) → ② 김기현팀 승격 UPDATE**. 승격을
V31에 넣지 않은 이유가 이것 — 통합 테스트가 V31을 espdb에 적용하는 순간 김기현팀이 SUPER 가 되면 그때 떠 있는
구 jar가 김기현팀을 못 읽는다. 승격 SQL(배포 후):
```sql
UPDATE member SET role='SUPER_ADMIN' WHERE login_id='김기현팀';  -- 1행, 커밋
```
승격 후 김기현팀은 **재로그인**해야 토큰에 SUPER_ADMIN 이 실린다.

## 9. 관리자 감사 로그 — 조작 이력 (SUPER_ADMIN 조회)

「다음 기능 뭐할지 보여줘」 → 후보 제시 → 사용자가 **감사 로그**를 골랐다. 그때까지 관리자 조작(정지·해제·
역할변경)은 `MemberAdminCommandService` 의 SLF4J `log.info` 로만 흘러가 **조회할 수 없었다** — 누가 누구를
언제 바꿨는지 되짚을 방법이 없다. 이걸 append-only 테이블로 남기고 조회 화면을 붙였다.

### 9-1. ⚠ 착수 전 결정 (사용자 확정)

| 질문 | 결정 | 이유 |
|---|---|---|
| 감사 이력을 **누가 조회**하나 | **SUPER_ADMIN 전용** | "감시하는 자를 누가 감시하나" — 조작 당사자(ADMIN)가 자기 이력을 스스로 열람·판단하는 구조를 막는다. 감사 로그는 최상위만 보는 게 정석. |

### 9-2. 설계 — 왜 새 도메인 + 이벤트인가

- **새 도메인 `domain/audit`.** 감사는 회원만의 관심사가 아니다(주문 발송·반품 승인·상품 편집도 앞으로 남길
  수 있다). member 하위에 두면 그 종속이 굳는다 — 그래서 독립 도메인으로 뒀다.
- **member → audit 직접 호출 금지, 이벤트로만.** `MemberAdminCommandService` 는 성공 경로에서
  `AdminActionEvent` 를 **발행**만 하고, audit 이 `AdminAuditListener`(어댑터, 위임만)→`AdminAuditCommandService`
  (핸들러, 저장)의 **3층 컨벤션**으로 받는다(도메인 경계 · event-3layer).
- **같은 트랜잭션.** 기본 `@EventListener` 는 발행 시점에 동기로 실행돼 발행측 트랜잭션에 합류한다.
  그래서 **감사 저장이 실패하면 조작도 롤백**(감사 무결성)되고, 권한 거부 등으로 **조작이 롤백되면 감사도 안 남는다**.
  단위테스트로 발행/미발행을 못박았다(성공 시 이벤트 1건, `SUPER_ADMIN_ONLY` 거부 시 0건).
- **스냅샷.** actor_id/target_id 는 FK 없는 느슨한 UUID(도메인 경계). 대상이 나중에 탈퇴·개명·강등돼도
  이력이 깨지지 않게 그 시점의 **actor_name(관리자 닉네임)·target_login(대상 loginId)** 을 함께 박는다.
  이를 위해 조작 시그니처를 `(actingId, actingRole)` → **`AuthUser actor`**(id·role·nickname) 로 바꿨다.
- **조회 인가는 경로에서.** `/api/admin/audit/**` 를 `/api/admin/**`(ADMIN) **위에** `hasRole('SUPER_ADMIN')`
  로 얹어 좁은 규칙이 먼저 매칭되게 했다. 프론트도 `requiresSuperAdmin` 가드 + `isSuperAdmin` 링크(감사 이력 메뉴).
- **detail** — 역할변경만 전/후를 남긴다(`USER → ADMIN`). 정지·해제는 비운다.

### 9-3. 스키마 (V32 — 순수 추가)

`admin_audit_log`: `id RAW(16)` PK · `action VARCHAR2(20 CHAR)`(+named CHECK `ck_admin_audit_action`) ·
`actor_id RAW(16)`·`actor_name VARCHAR2(50 CHAR)` · `target_id RAW(16)`·`target_login VARCHAR2(50 CHAR)` ·
`detail VARCHAR2(1000 CHAR)` · `created_at/updated_at TIMESTAMP(9) WITH TIME ZONE`. 인덱스 `created_at DESC`
(목록 기본정렬)·`target_id`(대상별 조회). ⚠ 이름 컬럼은 전부 **CHAR semantics**(member 와 맞춤), 엔티티에도
**명시 length**(50/50/1000)를 줬다 — 안 주면 기본 255 라 `ddl-auto=validate` 가 char_length 로 걸러 부팅이 깨진다(V12 교훈).
