## 2. 곁가지 — **없는 경로가 500 이었다** (오늘 발견, 커밋 `8a8b56d`)

### 2-1. 어떻게 드러났나

위 §1-1 에서 *"로그 레벨을 잠깐 올릴 수 있나"* 하고 `/actuator/loggers/...` 를 찔러 본 것이 시작이다.
**500 이 돌아왔고 `ERROR "Unhandled exception"` 이 남았다.**

```
NoResourceFoundException: No static resource actuator/loggers/...
  → GlobalExceptionHandler#handleUnexpected → ERROR + 500
```

**이건 어제 §3-7(SSE)과 정확히 같은 계열이다** — 포괄 `Exception` 핸들러가 *받으면 안 되는 것*을 받아
①클라이언트 잘못을 서버 오류로 만들고 ②`ERROR 0건` 확인을 오염시킨다.
⚠ 즉 **9번을 판정하려던 수단 자체가 고장 나 있었다.** 그래서 9번보다 먼저 고쳤다.

### 2-2. 실측 — 구멍은 **두 종류**이고, 경로 모양에 따라 갈렸다

운영(:8080)에 직접 쏴서 전수로 봤다. 배포 전까지 오늘 `ERROR` 는 **8건**이고 **전부 이 확인이 만든
것**이다(11:28:16 최초 probe 1건 + 13:02:1x~13:02:45 전수 probe 7건 — 시각으로 대조했다).
**기존 오류는 0건**이다. 예외 종류로 가르면 `NoResourceFoundException` **5** ·
`HttpRequestMethodNotSupportedException` **2**(전수 probe 구간 기준).

| 요청 | 지금 | 나와야 할 것 | 예외 |
|---|---|---|---|
| `/api/zzz` · `/api/notices/zzz/deep/path` · `/` · `/actuator/loggers` | **500** | 404 | `NoResourceFoundException` (5건) |
| `DELETE /api/notices` · `PUT /api/products` | **500** | 405 | `HttpRequestMethodNotSupportedException` (2건) |
| `/api/products/nope-not-a-route` · `/api/notices/list-typo` | **400** ✅ | 400 | (`{id}` 패턴에 걸려 타입 변환 실패) |

🔴 **마지막 줄이 이 구멍이 오래 안 보인 이유다.** API 오타를 쳐 보면 대개 `{id}` 패턴에 걸려
**400 이 잘 나온다** — 500 이 되는 건 **어느 패턴에도 안 걸릴 때뿐**이라, 몇 번 찔러 보고
*"에러 처리 잘 되네"* 로 끝나기 쉬운 모양이었다.

### 2-3. 결정

| 물은 것 | 정한 것 | 근거 |
|---|---|---|
| 404 와 405 를 합칠까 | **가른다** | 답이 다르다 — 404 는 *"주소를 다시 봐라"*, 405 는 *"주소는 맞고 메서드가 틀렸다"*. 합치면 프론트가 원인을 못 좁힌다 |
| 에러 코드 | **`COMMON-404`·`COMMON-405` 신설** | 도메인별 404(`PRODUCT-404` 등)는 *"그 자원이 없다"* 이고 이건 *"그런 경로가 없다"* 라 **층이 다르다**. 도메인이 던지는 코드가 아니라 **스프링 예외를 옮겨 담는 자리**임을 enum 주석에 적어 뒀다 |
| 로그 레벨 | **`warn`** | 클라이언트 잘못이라 `ERROR` 는 아니지만(그게 이 수정의 목적), **프론트가 없는 경로를 부르고 있으면 알아야** 한다. 기존 `handleUnreadableBody`(400)와 같은 레벨 |
| `Allow` 헤더 | **준다** | HTTP 규약이고, *무엇이 되는지* 알려주는 게 405 의 값이다 |

**버린 안**: `ResponseEntityExceptionHandler` 를 상속해 스프링 기본 처리에 맡기는 것.
`NoResourceFoundException` 이 `ErrorResponse` 를 구현하고 있어 그 경로로도 404 가 나오지만,
**응답이 `ProblemDetail` 이 되어 우리 공통 래퍼 `ApiResponse` 와 형식이 갈린다**(CLAUDE.md 규칙).
전역 핸들러 하나를 바꾸면 **기존 400·500 응답 형식까지 전부 흔들리는** 크기라, 두 핸들러를 더하는
쪽이 훨씬 작다.

⚠ **정적 리소스 서빙과 충돌하지 않는지 확인했다** — 백엔드에 `resources/static` 이 **없고**,
nginx 가 프론트를 맡으며 `/api/` 와 `/actuator/health` 만 프록시한다(`infra/nginx/conf.d/glassvue.conf`).
SPA 딥링크는 nginx `try_files … /index.html` 이 처리하므로 **이 변경이 닿지 않는다.**

## 3. 조건부 잔여 9번 (SSE) — **경로는 밟았다. 판정은 §3-2 참조**

### 3-1. 증거 사슬 — 어제 없던 ①이 생겼다

배포 재시작을 **끊김 트리거로 썼다**(사용자가 로그인한 탭을 열어 둔 채로 배포).

| # | 무엇 | 실측 |
|---|---|---|
| ① **붙었다** | 배포 전 nginx 에 완료 기록 **0건** + 백엔드 8080 established 연결 **1개** | 13:37 시점 |
| ② **끊겼다** | nginx SSE **200** 이 기록됨(= 그 순간 응답이 끝났다) | **13:38:46** |
| ③ 재연결 시도 | 백엔드가 없던 순간 **502 5건** | 13:38:4x |
| ④ 두 번째 끊김 | **200** 한 건 더 — `SseEmitter` **30분 타임아웃**(`TIMEOUT_MS`) | **14:09:54** |
| ⑤ 판정 | `AsyncRequestNotUsableException` **0건** · `ERROR` **8**(= 오늘 probe 그대로, 증가 0) | |

어제는 ①이 없어 *"0 이 나올 이유가 두 개(고쳐졌다 / 안 밟았다)"* 였다. **오늘은 ①이 있다.**

### 3-2. ⚠ 그런데 이번 끊김은 **어제와 같은 종류가 아닐 수 있다**

재시작 로그를 보다 **배포 방식의 결함**이 드러났다(오늘 두 번째 곁가지):

```
WARN  Failed to stop bean 'webServerGracefulShutdown'
java.lang.NoClassDefFoundError: org/springframework/boot/web/server/GracefulShutdownCallback
```

**원인**: `deploy-backend.sh` 가 **구 프로세스가 살아 있는 채로 jar 를 덮어쓰고**(`cp -f`) 그다음
재시작한다. JVM 은 클래스를 **필요할 때 읽으므로**, 종료 경로에서만 쓰는 클래스는 **이미 바뀐 파일**
에서 찾게 되어 못 읽는다.

**따라서 graceful shutdown 이 실패했다** — 연결이 곱게 닫힌 게 아니라 **끊겨 나갔다.**
그러면 톰캣이 *"끊긴 클라이언트에 쓰려다 실패"* 하는 단계까지 못 갔을 수 있다.
즉 **`0건` 이 「핸들러가 잡았다」인지 「예외가 애초에 안 났다」인지 아직 못 가른다** —
어제와 **모양이 다른 0** 이지만, 여전히 두 해석이 남는다.

⚠ 양성 증거(핸들러 실행 로그)를 볼 방법이 없다 — 핸들러는 `debug` 인데 운영은 INFO 이고
actuator 로 레벨을 못 바꾼다(§1-1).

→ **남은 판정**: 어제 §3-7 이 명시한 **다른 경로**(*"브라우저가 페이지를 옮기면"*)로 한 번 더 끊는다.
그건 정상 종료 경로라 이번 결함과 무관하다. **8번 검증이 그 자리를 지나므로 함께 본다.**

### 3-3. 곁가지로 확정된 것 — 조건부 잔여 10번이 **재현됐다**

**14:09:57 부터 SSE 가 401 로 되돌아온다**(31초 간격). 그 직전 14:09:54 에 30분 타임아웃으로
스트림이 끝났는데, **access 토큰 유효시간도 30분**(`jwt.access-token-validity-ms=1800000`)이라
**둘이 같은 시각에 만료된다** — 재연결하려는 순간 토큰이 이미 죽어 있다.

⚠ 어제는 *"만료된 토큰을 든 탭이 재시도한다"* 까지만 적었는데, **두 수명이 같아서 반드시 겹친다**
는 것이 오늘 드러났다. 우연이 아니라 **구조**다(10번에 반영).

## 4. 브라우저 검증 — **8번·9번 둘 다 닫았다**

기대값을 먼저 뽑아 놓고 들어갔다(WA §3). ⚠ 그 과정에서 **내가 오늘 문서에 옮겨 적은 전제 하나가
틀린 것도 여기서 드러났다** — §이월 「다음 기능 후보」의 *"`stock_history` 아직 0행"* 은 어제 §2-9 를
그대로 베낀 것인데, 어제 §3-6 이 그 뒤에 늘려 **실제로는 8행**이었다(고쳤다).
*"어제 문서에 있으니 참"* 이 오늘도 한 번 깨졌다(WA §1-3).

### 4-1. 조건부 잔여 8번 (취소 폼 공백) — **종결**

대상은 **기존 `20260715-0002`**(2026-07-15 · 반팔티 × 1 · `ORDERED`). 새 주문을 만들지 않았다.

| 본 것 | 기대값 | 결과 |
|---|---|---|
| 취소 자체 | 된다 | ✅ `CANCELLED` · `cancelled_at` 14:22:15 |
| 🔴 **사유 저장 형태** | **`NULL`**(빈 문자열이면 실패) | ✅ **`NULL`** — 공백만 넣었는데 빈 문자열로 안 들어갔다 |
| 화면의 사유 줄 | 안 뜬다 | ✅ (사용자 확인) |
| 재고 복원 | 193 → **194** | ✅ **194** |
| `stock_history` | 8 → **9행**, `CANCEL +1` | ✅ **9행** · `CANCEL +1` · `actor_name` 비어 있음(주문 경로라 관리자가 아니다 — 설계대로) |

**이걸로 「그 사이의 Vue 폼 배선 한 칸」이 실측으로 덮였다.** 서버(공백→NULL)와 프론트(`'' → null`)는
각각 테스트가 덮고 있었지만, **둘을 잇는 폼이 실제로 그 값을 보내는지**는 화면으로만 확인된다 —
이 프로젝트에 컴포넌트 렌더링 테스트가 없어 **구조적으로 못 덮는 자리**였다(WA §3).

### 4-2. 조건부 잔여 9번 (SSE 수정) — **종결**

오늘 SSE 는 **세 가지 방식으로 끊겼고 세 번 다 예외가 0** 이다.

| # | 끊긴 방식 | 시각(200 기록) | 어제와 같은 경로인가 |
|---|---|---|---|

어제 §3-9 가 못 적은 이유는 *경로를 안 밟아서* 였고, 오늘은 밟았다.

### 4-3. 검증 잔재 — **INSERT 1 · UPDATE 2 · `ZZ` 신규 0**

WA §3-1 대로 *"INSERT 한 것은? **UPDATE 한 것은?**"* 을 둘 다 물었다(두 번째를 빼면 조용히 남는다).

| | |
|---|---|
| INSERT | `stock_history` **1행**(`CANCEL +1`) |
| UPDATE | 주문 `20260715-0002` **ORDERED → CANCELLED** · `반팔티/기본` 재고 **193 → 194** |

## 5. 곁가지 둘 — **배포가 구 프로세스 밑에서 jar 를 갈아치우던 것** (커밋 `3b6e020`)

### 5-1. 실측 — 깨지던 건 하나가 아니라 **셋**이었다

§3-2 에서 `webServerGracefulShutdown` 하나만 봤는데, 13:38 배포의 종료 구간을 전수로 세니
**`Failed to stop bean` 이 3건**이다(같은 boot 라 로그가 아직 살아 있어 직접 셀 수 있었다):

| 실패한 종료 단계 | 못 읽은 클래스 | 무슨 뜻인가 |
|---|---|---|
| `webServerGracefulShutdown` | `GracefulShutdownCallback` | 우아한 종료 콜백 |
| 🔴 **`webServerStartStop`** | `Catalina Lifecycle$SingleUse` (2회) | **톰캣 정지 자체** |
| 🔴 **`redisConnectionFactory`** | `LettuceFutureUtils` · netty `AbstractUnsafe$6` · `PromiseCombiner` | **Redis 커넥션 정리** |

즉 배포마다 **톰캣도 Redis 연결도 곱게 안 닫히고 프로세스 종료로 끊겨 나갔다.**
`NoClassDefFoundError` 총 **7건** · `Failed to stop bean` **3건** — 이게 대조군이다.

⚠ **`server.shutdown` 은 `application.yml` 에 없다.** 🔴 여기서 *"그러니 기본값 `immediate` 다"* 라고
**단정했는데 §5-3 의 실측이 뒤집었다** — 수정 후 종료 로그에 `Commencing graceful shutdown` 이
찍힌다. **Boot 4.1 은 graceful 이 기본**이다. *설정 파일에 없다* 는 관찰만 맞고 **결론이 틀렸다**
(문서에 있는 값을 안 보고 기본값을 추측한 것 — WA §1-3 과 같은 종류). 즉 이 고장은
*"우아한 종료를 켰는데 안 됐다"* 가 아니라 **켜든 안 켜든 종료 경로가 깨져 있던 것**이다.

### 5-2. 결정

| 물은 것 | 정한 것 | 근거 |
|---|---|---|
| 어떻게 고치나 | **`stop` → `cp` → `start`** | 구 프로세스가 **없는 동안** 파일이 바뀌므로 원인이 사라진다. 변경 3줄 |
| 버전 파일명 + 심볼릭 링크는? | **안 쓴다** | 정석이지만(구 inode 를 붙든다) jar 가 **95M** 인데 디스크가 **88%·3.2G 남음**이라 **누적 정리 로직이 따라붙는다**. 지금 규모엔 과하다 |
| `server.shutdown=graceful` 도 켤까 | **물음 자체가 성립하지 않았다** | 🔴 **이미 켜져 있다**(Boot 4.1 기본, §5-1 정정). 지금까지 안 돌았던 건 **꺼져서가 아니라 깨져서**다 |
| 다운타임 | **안 늘어난다** | `restart` 도 내렸다 올리던 것이고, 늘어난 건 **95M 복사 시간**뿐이다 |

⚠ **복사가 실패하면 서비스가 죽은 채로 남는다** — 먼저 내리기 때문에 생기는 새 위험이라,
`.bak` 로 되돌리고 기동하는 갈래를 함께 넣었다(안 넣으면 이 수정이 **더 나쁜 사고**를 만든다).

⚠ **프론트 배포는 같은 문제가 아니다**(확인했다) — `rm -rf $WEBROOT/* && cp -rf` 이지만
**붙들고 있는 프로세스가 없다**(nginx 는 요청마다 파일을 연다). 복사 중 잠깐 404 가 날 창은
있으나 성질이 다른 문제라 여기서 건드리지 않는다.

### 5-3. 검증 — **다음 배포에서 대조한다**

이 변경은 코드가 아니라 **절차**를 고친 것이라, 확인 수단도 절차의 흔적에서 찾는다
(WA §5: *"구 jar 와 신 jar 가 다르게 답하는 지점이 어디인가"*).

→ **기대값**: 다음 배포의 종료 구간에서 `NoClassDefFoundError` **0** · `Failed to stop bean` **0**
(대조군은 위 §5-1 의 **7 · 3**).

**결과 — 통과**(배포 15:04:56 정지 → 15:05:00 기동 · health `UP`).

| | 13:38 (대조군) | 15:04 (수정 후) |
|---|---|---|
| `NoClassDefFoundError` | **7** | **0** |
| `Failed to stop bean` | **3** | **0** |

⚠ **여기서도 「0 이라는 답에는 이유가 둘」을 밟지 않았다** — *에러가 없다* 와 *종료가 제대로 돌았다*
는 다르다. 그래서 **양성 증거**를 함께 봤고, 대조군에는 **한 줄도 없던** 것들이 나왔다:

```
15:04:57  GracefulShutdown : Commencing graceful shutdown. Waiting for active requests to complete
15:04:57  GracefulShutdown : Graceful shutdown complete
15:04:58  Closing JPA EntityManagerFactory for persistence unit 'default'
15:04:58  HikariPool-1 - Shutdown initiated...  → 15:04:59 Shutdown completed
```

🔴 **그리고 이 로그가 §5-1 의 내 단정을 뒤집었다**(위 정정) — graceful shutdown 은 **켜져 있었고**,
지금까지 안 돌던 이유는 **꺼져서가 아니라 깨져서**였다.

⚠ **부수효과 하나를 예고해 둔다**: 이제 종료가 실제로 *"활성 요청을 기다린다."* 이번엔 붙은 게 없어
1초에 끝났지만, **SSE 탭이 붙어 있으면 최대 30초까지 기다릴 수 있다**
(`spring.lifecycle.timeout-per-shutdown-phase` 기본 30s · 유닛의 `TimeoutStopSec=30`).
**전에는 그 단계가 깨져서 즉시 끊겼던 것**이라, 배포가 느려졌다고 느끼면 그게 원인이다 —
고장이 아니라 **되찾은 동작**이다.

## 6. 조건부 잔여 8번 — **만료 토큰이 SSE 를 영영 못 붙게 하던 것** (종결)

### 6-1. 착수 전 실측 — **원인이 적힌 것과 달랐다** (오늘 세 번째)

백로그·이월은 *"고치려면 **재연결 정책과 토큰 갱신을 같이** 봐야 한다 — 한 줄 수정이 아니다"* 라고
적어 뒀다. **결론(작지 않다)은 맞았지만 이유가 틀렸다** — 둘 다 **이미 있었다**:

| 있다고 생각 못 했던 것 | 실제 |
|---|---|
| 재연결 백오프 | **이미 있다** — 1초에서 2배씩, 상한 30초. ⚠ **관측된 「31초 간격」이 바로 이 상한**이었다 |
| 401 → 토큰 갱신 | **이미 있다** — `client.js` 의 `tryRefresh`, 동시 401 을 하나로 묶는 single-flight 까지 |

🔴 **진짜 원인**: 알림 SSE 는 `request()` 를 안 거치고 **생 `fetch`** 로 스트림을 연다
(`EventSource` 가 Authorization 헤더를 못 실어서 — 원래 주석에 그 이유가 적혀 있다).
그래서 **그 갱신 경로를 통째로 비켜갔다.** 스트림 쪽 주석은 이렇게 적고 있었다:

> *"토큰 만료로 401 이면 이 사이 REST 호출이 refresh 하고 다음 연결이 성공한다."*

**가만히 둔 탭에는 그 REST 호출이 없다.** 다른 요청에 기대는 설계가 그 조건에서만 성립했고,
조건이 깨진 자리가 정확히 *"열어 놓고 안 만지는 탭"* 이다.

⚠ **버린 안**: `SseEmitter` 타임아웃(30분)만 토큰 수명보다 짧게 줄이기. 겹침을 **미루기만** 한다 —
25분으로 줄이면 첫 재연결은 살지만 그다음(50분)엔 똑같이 만료된다. 갱신 없이는 안 풀린다.

### 6-2. 착수 시 결정 (사용자)

| 물은 것 | 정한 것 | 근거 |
|---|---|---|
| 갱신까지 실패하면 | **스트림만 멈춘다**(세션은 그대로) | REST 의 `request()` 는 refresh 실패 시 `clearSession()` 하지만 그건 **사용자가 방금 뭔가 눌렀을 때**의 이야기다. 이 루프는 조작 없이 30초마다 도는 배경 작업이라, 네트워크 일시 장애 한 번이 **가만히 있던 사용자를 튕겨낸다**. 대가: 새로고침 전까지 실시간 알림이 안 온다 |
| 갱신 함수를 새로 만들까 | **기존 `tryRefresh` 를 `refreshSession` 으로 공개** | single-flight 를 그대로 타므로 **REST 와 스트림이 동시에 401 이어도 재발급은 한 번만** 일어난다 |

### 6-3. 변형 주입 — **4건, 그중 하나가 운영 코드를 고치게 했다**

⚠ 넣기 전에 `git status --short` 가 비었는지 봤다(§3-8). 기준선 프론트 **133 · 실패 0**.

| # | 무엇을 망가뜨렸나 | 지킨다는 규칙 | 빨개진 것 |

| T1 | `refreshSession()` 호출 제거 | 스트림이 **스스로** 갱신한다 | **3** |
| T2 | 갱신 실패 갈래(`if (!ok)`) 제거 | 실패하면 **멈춘다** | **1** |
| T3 | `afterRefresh` 가드 제거 | 갱신 후에도 401 이면 **그만** | 🔴 **아래 참조** |
| T4 | 재연결에 플래그를 안 넘김(`openStream()`) | 가드가 **닿아야** 한다 | **1** |

⚠ **T1 은 3건을 한꺼번에 빨갛게 만들어 규칙이 안 갈렸다**(H-8 이 경고한 모양). 그래서 T2·T3·T4 로

🔴 **T3 이 오늘 가장 값어치 있었다 — 테스트가 빨개진 게 아니라 「워커가 메모리 부족으로 죽었다」.**
가드를 지우자 *즉시 재연결*이 **꽉 찬 무한 루프**가 됐다 — 원래 버그(30초마다 401)보다 **나쁜 상태**이고,

고 한 자리라, 테스트가 아니라 **운영 코드를 고쳤다**(커밋 `b85d496`):
**갱신 직후 재연결도 백오프 경로(1초)를 그대로 타게 모았다.** 가드가 깨져도 최악이 **초당 1회**로 묶인다.

### 6-4. 배포 · 브라우저 검증 — **통과**

(`localStorage.setItem('accessToken','broken')` 후 새로고침). *"기다려야만 보이는 버그"* 를
**만들어서 보는** 쪽으로 바꾼 것이 이 검증의 요점이다.

**오늘 네 번 나온 한 가지 — 「0 이라는 답에는 이유가 둘 있다」**

1. §1-1 어제의 `ERROR 0건` → 고쳐져서가 아니라 **경로를 안 밟아서** 0 이었다.
2. §3-1~§3-2 오늘의 0 → 밟긴 밟았는데 **끊김의 종류가 달라** 아직 못 닫았다(§4-2 ③으로 닫았다).
3. §4 기대값의 `stock_history` → *"0행이라 볼 게 없다"* 고 적었는데 **실제로 8행**이었다.
4. §5-3 배포 수정 후의 `NoClassDefFoundError 0` → *에러가 없다* 와 *종료가 돌았다* 는 다르다.
   **양성 증거**(`Graceful shutdown complete` 등)를 같이 보고서야 판정이 됐다 — 그리고 그 로그가
   §5-1 의 내 단정(*"graceful 은 꺼져 있다"*)까지 뒤집었다.

네 번 다 **숫자를 먼저 뽑아 놓고 봤기 때문에** 갈렸다.

**그리고 어제에 이어 또 — 「문서에 적힌 전제」가 코드와 달랐다 (오늘 세 번)**

1. §4 `stock_history` **0행** → 실제 **8행**(어제 문장을 그대로 베낀 것).
2. §5-1 *"`server.shutdown` 이 없으니 기본 `immediate`"* → **graceful 이 기본**이었다(§5-3 실측).
3. §6-1 *"재연결 정책과 토큰 갱신을 같이 봐야 한다"* → **둘 다 이미 있었다.**
   진짜 원인은 **스트림이 `request()` 를 안 지나간 것** 하나였다.

⚠ 3 은 **결론이 맞고 이유가 틀린** 경우다 — *"한 줄 수정이 아니다"* 는 맞았다.
그래서 **결론만 보고 착수했으면 엉뚱한 곳(백오프·정책)을 고쳤을** 자리다. 1·2 는 어제 WA 에 *"확인 수단은 이 변경의
성질에서 찾는다"* 로 적혀 있던 것이고, 3 은 **문서를 베껴 적는 순간** 생겼다.
