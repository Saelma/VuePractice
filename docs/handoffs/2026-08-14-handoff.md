## 2. 🔴 착수 전 결정 — 백로그가 «값만 늘리면 된다» 고 했지만 그렇지 않았다

BACKLOG 「감사 대상 확대」는 *"각 도메인이 `AdminActionEvent` 를 발행하고 `AuditAction` 값을
늘리면 된다"* 로 적혀 있었다. **배선을 읽으니 그 문장이 상품에는 안 맞았다.**

`admin_audit_log.target_id` 는 **NOT NULL 이고 뜻이 「대상 회원 id」**다. 지금까지 붙은 값들은
전부 그 기준을 통과했다 — `ORDER_CANCEL` 은 **주문자**, `REVIEW_HIDE`·`INQUIRY_HIDE` 는 **작성자**.
`AuditAction` 주석이 그 기준을 이렇게 못 박아 뒀다:

> *"갈리는 기준은 **도메인이 아니라 «대상에 회원이 있느냐»** 다."*

🔴 **상품이 그 기준을 처음으로 못 넘는 대상이다.** 상품에는 회원이 없고, 열은 비울 수도 없다.

**정한 것 (사용자와 확정, 2026-08-14)**

| 물음 | 답 | 안 고른 것과 이유 |
|---|---|---|
| `target_id` 에 무엇을 넣나 | **상품 id.** 열의 뜻을 «대상의 id — 무엇인지는 `action` 이 말한다» 로 넓힌다 | `target_type` 열 신설: 가장 정직하지만 **회원 아닌 대상이 아직 하나뿐**이다(미리 만들지 않는다). `target_id` nullable: «어느 상품인가» 를 id 로 못 걸게 된다 — 여기서의 null 은 V45 와 달리 «사실» 이 아니라 «안 넣은 것» 이다 |
| 어디까지 남기나 | **삭제 + 복구** | 삭제만: «지우고 바로 되살렸다» 를 못 읽어 원장으로서 반쪽이다. 등록·수정까지: 빈도가 높아 원장이 빠르게 커지고(F-2 와 같은 압력) «무엇이 바뀌었나» 를 `detail` 에 적는 방식을 따로 정해야 한다 |

⚠ **대가를 알고 골랐다.** 감사 화면의 검색은 `target_login` 부분일치뿐이라
(`AdminAuditLogRepository.search`) **상품 행은 「조작 종류」 필터로만 걸린다.**

## 3. 🔴 멱등이 원장을 두 줄로 만들 뻔했다

`Product.softDelete()` 는 **이미 대기 중이면 아무것도 안 한다**(그래야 유예가 안 되돌아간다).
`restore()` 도 복구 화면에서 두 번 눌러도 **200 이 정상**이다(«실패» 로 보이면 안 된다).

그래서 **«서비스 메서드가 호출됐다» 는 «조작이 일어났다» 와 다르다.** 호출 자리에서 그냥
이벤트를 발행하면 **복구 버튼을 두 번 누른 관리자가 원장에 두 줄을 남긴다.**

→ 두 엔티티 메서드가 **`boolean`(이번 호출로 실제로 바뀌었나)** 을 돌려주고, 서비스는 그때만
발행한다. ⚠ **멱등이 200 인 것은 그대로 두고 «기록만» 갈랐다** — 화면 동작을 바꾸면 F-7 의 판단을
뒤집는 것이 된다.

⚠ 이 모양은 새로 만든 것이 아니다. `MemberCoupon.restore()` 가 **이미 boolean** 이고,
그 이유도 같았다(2026-08-11 변형 주입 M9 — «아무것도 안 하게» 되는 것을 잡으려고).

## 4. 구현

| 자리 | 무엇 |
|---|---|
| `AuditAction` | `PRODUCT_DELETE` · `PRODUCT_RESTORE` |
| `V50` | CHECK 제약 확장 + `target_id` 열 주석 재작성(넷을 다 적었다: 회원·주문자·작성자·상품) |
| `Product` | `softDelete`/`restore` → **boolean** |
| `ProductCommandService` | 상태가 바뀐 경우에만 `AdminActionEvent` 발행. 상품명은 **`detail` 에 스냅샷** |
| `ProductControllerImpl` | `delete` 가 닉네임 대신 **`AuthUser`** 를 넘긴다(`actor_id` 가 NOT NULL) |
| `AdminProductControllerImpl` | `restore` 에 `@LoginUser` 추가(+ 인터페이스) |
| `audit.js` | 라벨·뱃지 2종 |
| `AuditLogAdminView` | 「대상 아이디」 빈칸 → `—` |

**왜 상품명을 `detail` 에 박나**: 상품은 **유예가 지나면 진짜로 사라진다.** id 만 남기면
«무엇을 지웠는지» 를 영영 못 읽는다 — **감사는 대상보다 오래 산다**(V45 가 `target_login` 스냅샷을
두는 이유와 같다).

**❌ 영구 삭제(purge)는 안 남긴다**: 부르는 것이 `ProductPurgeScheduler` 라 **행위자가 사람이 아니다.**
`actor_id` 는 NOT NULL 이고 배치를 가리킬 UUID 는 **지어낼 값**이다. 그 시점은 앱 로그에만 남는다.

**🔴 과거 삭제는 백필하지 않는다**: 출처가 없다 — `deleted_by_name` 은 «누가» 만 알고 «언제» 는
`deleted_at` 인데 **복구하면 둘 다 지워진다.** 원장은 오늘부터 시작한다(V44·V37 과 같은 판단).

### 6-1. 🔴 `AdminLowStockIntegrationTest` — 운영 데이터가 **테스트의 결함을 드러냈다**

*"count 가 DB 직접 집계와 일치한다 — 조건이 코드와 SQL 양쪽에서 같은지"* 라는 이름의 테스트다.
그 대조 SQL 에 **`deleted_at IS NULL` 이 없었다.** 서비스에는 있다(F-7, 08-12).

즉 **정의가 다른 채로 초록이었다.** 두 정의가 갈리는 행 — **「삭제 대기이면서 저재고」** — 이
운영에 없었기 때문이다. 어제 17:09 에 `ZZ-정가텟트`(재고 3)가 삭제 대기로 가면서 **그 행이 처음
생겼고**, 오늘 아침 전수에서 드러났다.

🔴 **이건 «테스트가 운영 데이터에 깨졌다» 가 아니다.** F-7 을 붙일 때 이 자리를 놓친 것이고,
운영 데이터는 **그걸 드러낸 것뿐**이다. → 대조 SQL 에 조건을 더했다(**고쳤다**).

### 6-2. ⚠ `EventCouponIntegrationTest` — 08-13 §9-4 가 예고한 **그 근본**이 터졌다

*"발급 창이 닫혀 있으면 그 쿠폰은 안 나간다"* 가 **단언에 닿지도 못하고** 실패했다 —
테스트가 만드는 «그저께~어제» 발급 창이 **어제 검증 쿠폰 `5000`(발급 창 08-13)과 겹쳐**
쿠폰 생성 자체가 거부됐다(겹침 금지는 앱이 지킨다).

→ 닫힌 창을 **한 해 전**으로 옮겼다. ⚠ **이건 «아마 없겠지» 가 아니다** — 이벤트 쿠폰 기능은
**2026-08-13 에 생겼으므로**(G-8, V49) 그 이전 발급 창을 가진 쿠폰은 **구조적으로 있을 수 없다.**

⚠ **근본은 그대로 남는다**(08-13 이월과 같은 문장): 공유 DB 라 «운영에 그 상태가 없다» 를 전제하는
단언은 언젠가 깨진다. **테스트 전용 스키마가 생기기 전까지는.**

### 6-3. 🔴 여기서 배운 것 — **두 실패는 대응이 다르다**

같은 «운영 데이터 때문에 빨개졌다» 로 보이지만:

- **테스트의 정의가 틀렸다** → **고친다**(6-1). 견디게 만들면 결함이 그대로 남는다.

⚠ 둘을 같은 손짓으로 처리하면 6-1 은 **영영 안 고쳐진다** — «또 운영 데이터네» 로 넘어간다.
