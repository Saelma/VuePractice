## 3. 감사 확대 4차 — 넷 중 **셋**을 붙였다 (V56)

08-20 §10 이 관리자 쓰기 엔드포인트를 전수로 뽑아 남긴 넷이 착수 목록이었다.

| 조작 | 처분 | 결과 |
|---|---|---|
| 카테고리 등록·삭제 | ✅ | `CATEGORY_CREATE`·`CATEGORY_DELETE` · 🔴 `target_type` 에 **`CATEGORY` 신설** |
| 공지 등록·수정·삭제 | ✅ | `NOTICE_CREATE`·`NOTICE_UPDATE`·`NOTICE_DELETE` · 🔴 **`NOTICE` 신설** |
| 문의 답변 | ✅ | `INQUIRY_ANSWER` · 대상은 **질문자**라 `target_type` 을 안 건드린다 |
| 이미지 파생 생성 | ❌ **안 붙인다** | 백로그 판단 그대로 — 운영 배치성 · 되돌릴 수 있다 · «누가» 를 물을 일이 없다 |

🔴 **넷을 다 붙이는 것이 목표가 아니었다.** 목록을 훑어 세는 것과 전부 처리하는 것은 다른 일이다.

### 3-1. 🔴 시험 결과 — **접을 수 있었는데 접지 않았다**

카테고리·공지는 `MEMBER`·`PRODUCT`·`COUPON` 어디에도 안 들어가는 **첫 대상**이다(그전 넷은 전부
기존 값으로 접혔다 — 할인→상품, 주문·리뷰·문의→회원). **접는 길이 둘 다 있었다:**

- **카테고리 → `PRODUCT`** (상품을 담는 그릇이니까)
  ❌ 접으면 `target_id` 는 카테고리 id 인데 종류는 «상품» 이라, 「대상 종류=상품」으로 훑을 때
  **상품 이력 사이에 상품 아닌 행이 섞인다.** 그 필터의 존재 이유가 «회원 아닌 행을 갈라 보는 것»
  인데 **접는 순간 그 쓸모를 스스로 무너뜨린다.**
- **공지 → `MEMBER`** (공지에도 `author_id` 가 있다)
  ❌ 리뷰·문의가 «대상=작성자» 로 통한 이유는 **고객이 쓴 것을 관리자가 조치**해서다.
  공지는 **관리자가 쓰고 관리자가 고친다** → actor 와 target 이 거의 늘 같은 사람이라
  **원장 한 줄이 아무것도 안 가른다.**

→ 🔴 **«대상은 id 를 물어볼 값어치가 있는 쪽»(V43·V53) 규칙 자체는 그대로 통했다.** 이번엔 그 답이
기존 셋 **밖**에 있었을 뿐이고, **틀을 고칠 일은 없었다. 그것이 시험의 결과다.**

### 3-2. 공지는 **어제 기능 하나가 닫히면서 비로소 뜻을 갖게 된 값**이다

E-4(2026-08-20) 전에는 공지를 **고객도 쓸 수 있었다.** 원장은 «관리자가 무엇을 했나» 라,
그 상태로는 `NOTICE_CREATE` 를 남길 자리가 **없었다** — 「관리자 조작」이 아니었으니까.

⚠ 08-20 이월이 이 선행 관계를 *«공지의 선행 조건(E-4)은 오늘 풀렸다»* 로 명시해 뒀다.
🔴 **그 한 줄이 없었으면 오늘 «공지는 왜 지금까지 빠져 있었지» 를 다시 추론해야 했다.**

### 3-3. detail 규칙 — V53 을 그대로 따랐고, 한 군데만 더 접었다

`PRODUCT_UPDATE` 의 규칙(바뀐 것만 «전→후» · 긴 필드는 «바뀜» 만 · 변경 없어도 줄은 남긴다)을
공지 수정에 그대로 적용했다. 🔴 **본문(`content`)은 «바뀜» 만 적는다** — 공지 본문은 상품 설명보다
길어서 전/후를 다 실으면 `detail`(1000자)을 **확실히** 넘긴다. **잘린 원장은 틀린 원장이다.**

**삭제는 둘 다 «지우기 전에» 읽는다.** 🔴 **카테고리·공지에는 soft delete 가 없다**(F-7 은 상품에만
있다) — 행이 진짜로 사라지므로 **detail 이 유일하게 남는 흔적**이다.

**문의 답변의 detail 에 «첫 답변 / 답변 수정» 을 적는다.** 🔴 되돌릴 수 없는 것은 답변이 아니라
**알림**이고(B-15 는 첫 답변에만 보낸다), **그 한 마디가 «알림이 나갔나» 의 답**이다.
⚠ 그래서 등록·수정을 **두 값으로 안 갈랐다** — 갈라도 얻는 것이 detail 에 이미 있다.

### 3-4. ⚠ 백필은 안 했다 — 여기서는 **지어내는 것이 된다**

V53 은 `target_type` 을 **백필했다**(action 을 보면 결정되므로 «계산» 이다). 오늘은 다르다 —
없는 것이 **«누가·언제»** 이고 그건 아무 데도 없다:

- 카테고리: `created_at` 만 있고 **행위자 컬럼이 없다.** 삭제된 것은 행 자체가 없다.
- 공지: `author`·`author_id` 는 **등록자**만 안다 — 수정·삭제는 «누가 언제» 를 안 남겼다.
- 답변: `answered_at` 은 있어도 **답변자를 모른다.** ⚠ V51 이 주문 넷에서 만난 그 모양이다 —
  **«언제는 남고 누가는 안 남았다».**

→ 원장은 오늘부터 시작한다(V44·V50·V51 과 같은 판단).

### 3-5. 🔴 새 `target_type` 두 값은 **통합 테스트에서만 밟힌다**

`AuditActionTargetTypeTest` 는 **DB 를 안 띄운다** — enum 끼리만 대조하므로
`CHECK (target_type IN (...))` 를 **한 번도 실행하지 않는다.** V56 이 그 제약을 안 넓혔다면
그 테스트는 **초록인 채로** 운영에서 터졌을 것이다(Oracle enum CHECK 트랩).

→ `ContentAuditIntegrationTest` 를 새로 만들었다. ⚠ **단언을 조회로 해야 한다** —
그래야 Hibernate auto-flush 가 INSERT 를 DB 까지 밀어 제약이 실제로 실행된다.
«이벤트가 발행됐다» 만 세면 롤백까지 **INSERT 가 DB 에 안 닿는다**(백로그가 못 박아 둔 함정).

### 3-6. 곁가지 — 어제 놓친 Swagger 한 줄

`NoticeController.create` 의 요약이 **«공지 등록 (로그인 필요, 작성자=로그인 유저)»** 인 채였다.
E-4 로 관리자 전용이 된 것이 **어제**인데 문서 문자열이 안 따라왔다. 바로잡았다.
⚠ WA §1-2-1(«남기는 쪽 ↔ 보는 쪽» 도 짝이다)의 **아주 작은 판본**이다 — 권한을 좁혔으면
그 권한을 **설명하는 쪽**도 같이 열어야 했다.

**갈린 것들:**

- 🔴 **답변 둘이 갈렸다** — `· 답변 수정`(알림 없음) / `· 첫 답변`(알림 나감). 행위자도 다르다:

## 6. 🔴 14:46 강제 재부팅 — 한 사건이 넷으로 보였다

세션이 11:15 에 끊겼고 14:50 에 돌아오니 **증상이 넷**이었다. 넷 다 **같은 원인**이었다 —
`uptime -s` 가 **`2026-08-21 14:46:50`** 이었다.

| 보인 것 | 실제 |
|---|---|
| 폴링·세션이 11:15 에 끊김 | 재부팅 |
| `git status` 가 `index file smaller than expected` | 재부팅이 git 쓰기를 잘랐다 |
| `systemctl show … ActiveEnterTimestamp=` 가 **빈 값** | 서비스가 아직 `activating` 이었다 |
| 백엔드 `deactivating (stop-sigterm) · Result: timeout` | 🔴 **기동에 성공했는데 9초 늦어서 죽었다** |

⚠ **진단·복구 절차는 `TROUBLESHOOTING.md` §3-7·§3-8 로 옮겼다.** 여기엔 경위와 실측만 남긴다.

### 6-1. 시간을 쓴 순서가 틀렸다

디스크(52% · 23G 여유) → inode(2%) → 메모리 → OOM 로그를 **먼저** 팠고 **넷 다 정상**이었다.
`uptime -s` 는 **다섯 번째**로 봤는데, **그 한 줄이 넷을 한꺼번에 설명했다.**

🔴 **교훈**: 여러 증상이 **같은 시각에** 나타나면 **공통 원인을 먼저 찾는다.** 증상마다 따로
파고들면 «각각 다른 고장» 이라는 그림이 그려지고, 그 그림이 틀렸다는 걸 늦게 안다.
⚠ WA §3-3-1 이 이미 이웃한 규율을 적어 뒀다 — *«로그가 0건이면 판정 전에 `uptime -s`»*.
**같은 명령이 여기서도 답이었는데 「로그가 0건일 때」로만 좁게 적혀 있었다.**

### 6-2. 백엔드 — 기동 129.298초 vs `TimeoutStartSec=120`

| 회차 | 소요 | 결과 |
|---|---|---|
| 1차 (14:48:57~) | **129.298초** | 🔴 systemd 가 120초에 SIGTERM → `Failed to start` |
| 2차 (14:51:23~, `Restart=on-failure`) | **57.352초** | ✅ `active` (14:52:30) |

**앱은 두 번 다 정상적으로 떴다.** 1차가 느린 이유는 같은 VM 의 Oracle 이 함께 뜨기 때문이고,
2차는 캐시가 더워져 절반 이하다. ⚠ **즉 재부팅마다 «한 번 실패하고 두 번째에 사는» 패턴**이라
**혼자 나아서 원인을 안 찾게 된다.** 오늘 처음으로 그 자리를 봤다.

🔴 **제안(sudo 라 적용은 사용자)**: `TimeoutStartSec=120` → **`300`**.
⚠ `ExecStartPost` 헬스체크는 **그대로 둔다** — 그게 «active = 요청 처리 준비 완료» 를 만드는
장치다(유닛 주석이 그 이유를 적어 뒀다). 늘려야 하는 건 **기다려 주는 시간**뿐이다.

### 6-3. git — 손상은 **마지막에 쓰인 것**에 몰렸다

| 무엇 | 상태 |
|---|---|
| `.git/index` | **0바이트** |
| `.git/refs/heads/main` | **0바이트** |
| loose object | 🔴 **5개가 0바이트** / 성한 것 **1053개** |
| `.git/logs/HEAD`(reflog) · packed-refs · pack 파일 | ✅ 무사 |

🔴 **`git push` 는 성공했는데 로컬만 날아간 상태였다.** 11:16:18 에 만든 핸드오프 커밋
(`027847d`)이 **GitHub 에는 있고** 로컬에는 **0바이트 object** 로만 있었다 —
그래서 `git ls-remote` 가 로컬 HEAD(`73d20f6`)보다 **한 커밋 앞선** 값을 답했다.

✅ **복구 완료**: 0바이트 object 5개 삭제 → 깨진 loose ref 삭제 후 `update-ref` → `git reset` 으로
인덱스 재생성 → `git fetch` 로 5개 복원 → `origin/main` 으로 ff.
**`git fsck` 깨끗 · 작업 트리 무손실**(핸드오프 파일이 커밋본과 `sha256` 까지 같은 것을 확인하고 ff 했다).

⚠ **잃은 것이 없는 이유가 «운이 좋아서» 가 아니다** — 커밋을 **작게 자주 하고 바로 push** 해서
크래시 시점에 «로컬에만 있는 것» 이 **한 커밋뿐**이었고, 그 한 커밋도 원격에 있었다.
