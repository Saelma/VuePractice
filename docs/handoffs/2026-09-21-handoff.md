## 2. 조건부 잔여 **36개 판정** — 3주간 안 바뀐 절을 목록 대 목록으로 텄다

### 2-1. 왜 이걸 골랐나

BACKLOG §B 의 「다음 후보를 어떻게 고르나」 순서 2번(*"이월이 비면 새 감사 축을 뽑는다"*)에 따른 것이고,
**M 축이 «다음 축을 못 낳았다» 며 «원장 세기가 아닌 다른 각도» 를 요구한 자리**에 들어간다.

착수 근거는 실측이다: `§조건부 잔여` 의 내용이 마지막으로 **실제로 갱신된 날은 2026-08-27** 이고,
그 뒤 08-28 → 09-01 → 09-02 → 09-07 → 09-10 → 09-17 → 09-18 이 **전부 «그대로 물려받는다» 한 줄**이었다.

*"항목이 «적힌 시점에 이미» 거짓일 수 있다"* 가 가장 두껍게 쌓일 조건이다.

⚠ **목록의 실제 범위를 먼저 복원했다.** 08-27 판은 08-26/25/24 를 **이미 전부 재기술**하고 있어

| §4-1 | 이월은 다음 문서가 **목록 대 목록으로 처분**한다 | ✗ 🔴 **조건부 잔여엔 이 규약이 없다** |

🔴 **§1-3-1 이 오늘 일곱 중 몇을 걸렀을까 — 0 이다.** 아무도 그 항목들을 집지 않았기 때문이다.
§1-3·§1-3-1 은 *«집을 때 확인해라»* 이고, 이 병은 *«아무도 안 집으면 영원히 판정 안 된다»* 다.
**다른 기전**이고, 이월에만 있는 처분 규약이 조건부 잔여엔 없는 것이 구조적 원인이다.

### 3-2. 그런데 **규약이 답이 아니다** — 이 문서의 선례 둘이 그렇게 말한다

- §4-0: *"이 항목을 **규약으로 올린 직후에 또 안 셌다**"* → `check-handoff.sh` 가 됐다.
- §5: `check-deploy-branch.sh` 도 *"규약을 적고도 **같은 날 재발**해서"* 스크립트가 됐다.

그리고 오늘 것은 **기계가 실물과 대조할 수 있다.** → **규약 신설 ✗ · 스크립트 ✓.**

### 3-3. 🔴 곁다리 — **WA §4-0 자체가 낡아 있었다**

§4-0 은 *"아래 **다섯**을 대조한다"* 고 적고 ①~⑤ 를 나열하는데, `check-handoff.sh` 는 **일곱**을 본다
(⑥ 마감값 블록 중복 2026-09-07 · ⑦ 마감값 ↔ 지금 DB 2026-09-10). **검사를 더할 때마다 그 줄을 안 고쳤다.**

⚠ 🔴 **그리고 이건 바로 아래 §4-0-2 를 자기 절에서 어긴 것**이다 —
*"목록이 있는 자리에 개수를 손으로 적으면 반드시 어긋난다"* 고 적어 놓고 그 위에서 「다섯」이라 적었다.
→ **개수를 빼고 목록만 두고**(사용자 결정), 세려면 `grep -c '^# --- ' scripts/check-handoff.sh` 로 센다고 남겼다(실측 **7**).

### 3-4. 만든 것 — `scripts/check-stale-residue.sh`

§조건부 잔여가 지목한 **«고유명»이 지금도 실물과 맞는가**를 본다. WA §3-6 이 요구하는 셋을 갖췄다:

| §3-6 | 이 도구에서 |
|---|---|
| **무엇을 세나** | 주문번호 · `ZZ-` 표본 이름 · 파일 · 식별자 · CSS 토큰. ⚠ 서술형 주장(「캐시 60초 미실측」·「화면이 유일한 방어」)은 **안 센다** — 기계가 못 가른다 |
| **어디서 세나** | 🔴 **전부 실물** — 주문번호는 **DB**, 표본 이름은 `product`·`coupon`·`member`, 파일은 파일시스템, 식별자는 코드 트리. **문서끼리 대조하지 않는다**(같이 늙는다) |
| **다 셌는가** | 🔴 고유명이 0개면 «어긋남 없음»이 아니라 **«판정 불가»(2)**. 그리고 **본 개수를 늘 찍는다** — `본 것: 주문번호 17 · 표본이름(ZZ) 2 · …` |

### 3-5. 🔴 **첫 판은 «과거 거짓» 을 하나도 못 잡았다** — 왜 놓쳤는지가 설계 전부다

08-27 문서에 돌리니 **50개를 대조하고 «어긋남 없다»** 를 냈다. §2 에서 손으로 찾은 넷이 **전부 눈 밖**이었다.
🔴 **이게 §3-6 이 말한 «덜 세서 성립해 보이는» 그 답이다.** 넷을 고쳐서 지금 판이 됐다:

| 왜 놓쳤나 | 고친 것 |
|---|---|
| 🔴 **로케일**. `ko_KR.UTF-8` 에서 GNU sed 4.8 의 `s/….*$//` 가 **한글·이모지 섞인 긴 문자열에서 조용히 안 바뀐다**(같은 입력이 **828바이트** / `LC_ALL=C` **18바이트**). 창 자르기가 통째로 안 먹어 **옆 주문의 상태**를 집었다 | 본문 스캔을 전부 `LC_ALL=C`(`SCAN()`)로 고정. **TROUBLESHOOTING 색인에 넣었다** |
| 주장이 번호 **앞**에 올 수 있다 — 「**미결제** 주문 둘(`4185`·`4186`)」 | «제 뒤» 를 먼저, 없으면 «제 앞». 둘 다 **이웃 번호와 `·`** 에서 끊는다 |
| 표본 이름이 주문번호가 아니다 — `ZZ-123123` 은 **상품**이다 | 백틱 안의 `ZZ-…` 를 따로 뽑아 `product`·`coupon`·`member` 에서 찾는다 |
| 주장이 **«그 파일 안에서»** 다 — 「`SignupView` 의 `border-ink-200`」. 저장소 전체로 grep 하면 `index.css` 에 토큰 정의가 있어 **늘 참**이 된다 | 항목이 화면 이름과 토큰을 함께 말하면 **그 파일 안에서** 찾는다 |
| 인용(`>`) 줄의 **정정 기록**이 현재 주장으로 읽혔다 | `>` 줄은 «과거 경위» 라 **뺀다** — 안 빼면 **고친 사실 자체가 어긋남으로 다시 잡힌다** |
| 「미결제」를 `paid_at IS NULL` 로만 보면 **취소된 채 미결제인 주문**이 통과한다(4185·4186 이 5주간 그랬다) | 미결제 주장인데 상태가 `CANCELLED`·`RETURNED` 면 **「표본이 죽었다」** 로 지목 |

⚠ 🔴 **처음엔 로케일 문제를 «한 줄에 주문이 여럿이라» 로 진단했다** — 증상은 맞고 **원인이 틀렸다.**
WA §1-3 의 *"결론이 맞아도 이유는 틀릴 수 있다"* 를 그 자리에서 다시 밟았다.
가른 것은 **바이트 수 한 줄**이었다(`LC_ALL=C` 와 그냥 돌린 것의 `wc -c` 비교).

### 3-6. 검증 (WA §3 변형 주입) — §4-0 이 `check-handoff.sh` 에 한 것과 같은 방식

변형 **6종**(상태 거짓 · 없는 주문 · 없는 표본 이름 · 없는 파일 · 화면 한정 토큰 · 없는 식별자)을
넣어 **6종 모두 한 번씩** 잡히는 것을 봤다(중복 지목 없음). 절을 비우거나 제목을 바꾸면 **2로** 끝난다.

🔴 **회귀 — 이게 이 도구의 값이다**:

```

2026-08-27 (썩은 판)          → exit 1   그 화면에 없음: SignupView.vue 의 border-ink-200

```

**손으로 찾은 넷 중 셋을 기계가 잡는다.** ⚠ 못 잡는 하나는 `20260826-6187` 인데,
08-27 문서가 **상태를 아예 안 적었기 때문**이다 — 주장이 없으면 대조할 것도 없다. **도구의 한계이고, 알고 둔다.**

### 3-8. ✅ 곁가지 — **결정이 바뀌었는데 안 따라온 문장 셋을 고쳤다** (사용자 확인 뒤)

🔴 **오늘 판정한 것과 같은 병**이다 — 09-18 에 *"호스트로 안 가져간다, **다시 묻지 않는다**"* 로 정했는데
**세 곳이 여전히 `scp` 를 권하고 있었다.** 그중 하나는 **말만 하는 게 아니라 매번 찍고 있었다**:

| 자리 | 무엇이라 말했나 | 어떻게 고쳤나 |
|---|---|---|
| `scripts/backup-db.sh` **출력** | 백업이 끝날 때마다 🔴 *"VM 밖으로 가져가야 백업이다 — 호스트(PowerShell)에서: `PS> scp …`"* 를 **찍었다** | **뺐다.** 매번 권하면 **결정이 안 선 것처럼 보인다** |
| `scripts/backup-db.sh` 머리말 · `scripts/deploy-backend.sh` 주석 | *"끝에 찍는 `scp` 로 호스트에 가져가야 백업이 된다"* | **결정 + 대가**로 바꿨다 — 🔴 *"VM 자체를 잃으면 백업도 함께 잃는다"* |
| `infra/README.md` | *"VM 안의 백업은 백업이 아니다 — **호스트로 가져가야 한다**"* | **원칙은 남기고** 뒤를 바꿨다 — *"그럼에도 안 가져가기로 했다 · **대가를 아는 채로 고른 것이다**"* |

⚠ **원칙을 지우지 않았다.** 「VM 안의 백업은 백업이 아니다」는 **여전히 참**이고, 결정은 그 사실을
**모르고 한 게 아니라 알고 한 것**이다 — 그래서 나란히 적는다(WA §4-2: 버린 안과 **버린 이유**를 같이 남긴다).
⚠ 되돌릴 방법은 머리말 주석에 **명령 한 줄로** 남겼다(권하지는 않는다).

## 4. ✅ 배송완료 리뷰 — **6주 만에 밟았다** (08-11 「막힌 것 셋」 ① **종결**)

### 4-1. 왜 지금인가

08-10 §16-2 가 찾고 08-11 이 고친 뒤 **전수 + 변형 주입 M1·M2·M7 까지 통과**시켰는데,
브라우저 검증만 *"🔴 **밟을 대상 없음**"* 으로 닫혔다(08-11 §7-3: 「대상 자체가 0」).
**그 뒤 6주 동안 아무도 다시 세지 않았다.** 오늘 세니 **하나 생겼다.**

### 4-2. 착수 전 판정 (WA §1-3-1) — 코드가 주장대로 있나

| 주장 | 실측 |
|---|---|
| 「판정을 상태를 만드는 사람 눈앞으로 옮겼다」 | ✅ `OrderStatus.isPurchaseProven()` 의 `switch` 에 **`default` 가 없다** — 값을 추가하면 컴파일이 깨진다 |
| 「`DELIVERED` 가 구매 증명에 들어갔다」 | ✅ `case ORDERED, PAID, SHIPPED, DELIVERED -> true` |
| 「`RETURN_REQUESTED`·`RETURNED` 제외는 제품 판단」 | ✅ `case CANCELLED, RETURN_REQUESTED, RETURNED -> false`(2026-08-11 사용자 결정) |
| 리포지토리가 그 한 곳에서 받나 | ✅ `OrderRepository.existsPurchase()` → `OrderStatus.purchaseProven()` |

### 4-3. 🔴 **판정이 갈리는 표본이다** (WA §3-3-3) — 이게 이 검증의 값이다

`김기현팀` 의 **반팔티 주문은 아홉 건인데, `DELIVERED` 는 `20260825-5633` 하나뿐**이다:

```
20260715-0002 CANCELLED   20260724-0247 RETURNED    20260824-5295 CANCELLED
20260716-0007 CANCELLED   20260810-2649 RETURNED    20260824-5296 CANCELLED
20260825-5633 DELIVERED   20260825-5484 RETURNED    20260824-5297 CANCELLED
```

🔴 **나머지 여덟은 전부 `isPurchaseProven() == false` 다.** 그러니
**고침 전 코드였으면 아홉 건 모두가 「구매 증명 안 됨」이라 거절된다.** 통과하면 그건 `DELIVERED` 덕이고,
**그게 08-10 에 고친 바로 그 자리다.** ⚠ 이런 표본이 하나뿐이라 6주가 걸렸다.

### 4-4. 거절도 함께 밟는다 (WA §2-4-2)

통과만 보면 «가드가 아예 없어도» 같은 그림이 나온다. 그래서 **거절 표본**을 같이 넘긴다 —
**`게이밍 마우스`** 는 `김기현팀` 이 **한 번도 안 샀다**(주문 0건).
⚠ 「취소·반품으로만 산 상품」 중 리뷰 미작성인 것은 **없었다** — 그래서 거절 표본은 «산 적 없음» 갈래로 골랐다.

### 4-5. 브라우저 검증 — ✅ **셋 다 기대대로**(사용자: *"너가 말한대로 a b c 결과 다 잘 떴어"*)

로그인: **`김기현팀`**. 리뷰 폼은 **상품 상세 아래 「상품 리뷰」 절**에 있다(로그인해야 보인다).

| # | 어디 | 무엇을 | 기대 |
|---|---|---|---|
| A | `https://localhost/products/019f647b-d1e6-7aed-9de3-0d46da6dbbae` (**반팔티**) | 별점(기본 5) 두고 「내용」에 아무 글 → **「리뷰 등록」** | 🔴 **성공** — 폼이 비워지고 아래 리뷰 목록에 새 리뷰가 뜬다. 별점 요약 개수가 **1 → 2** |
| B | `https://localhost/products/019f647b-d1b8-76e7-a444-047452245056` (**게이밍 마우스**) | 같은 방식으로 「리뷰 등록」 | 🔴 **거절** — 버튼 위 빨간 줄에 **「구매한 상품만 리뷰할 수 있습니다.」**(`REVIEW-403P`, 서버 메시지 그대로) |

⚠ **되돌릴 수 있다** — 리뷰는 본인이 지울 수 있다(`DELETE /reviews/{id}`, 화면에도 있다).
지우면 «리뷰 미작성» 조합이 **다시 살아난다** — 표본이 영구히 사라지는 일은 아니다.

### 4-6. 검증 뒤 재계수 (WA §3-5) — **리뷰 하나만 움직였다**

```
review 3 → 4   (김기현팀 × 반팔티 · 별점 5 · 14:07 KST)
member 10 · orders 87 · notification 146 · admin_audit_log 104(최장 64) ·

```

- 🔴 **B·C(거절 둘)는 아무 값도 안 남겼다.** 그게 **가드가 진짜로 막았다는 증거**다 —
  «막혔다고 화면이 말한다» 와 «정말 안 들어갔다» 는 다른 주장이고, 여기서는 둘 다 확인됐다.
- ⚠ **`admin_audit_log` 가 안 늘었다**(104 그대로) — 맞다. 고객이 쓴 리뷰는 **관리자 조작이 아니라** 원장 대상이 아니다.
  ⚠ 되짚어야 할 일이 생기면 **원장이 아니라 `review.created_at`** 이 근거다.

### 4-7. 무엇이 종결됐나

08-11 §7 이 *"**못 밟음** — ① 배송완료 리뷰 — 대상 자체가 0"* 으로 닫은 자리가 **6주 만에 닫혔다.**
🔴 **남은 「막힌 것」은 둘이다** — 탈퇴 회원 관리자 조작 · 탈퇴 시 장바구니 정리.
오늘 실측으로 **둘 다 여전히 막혀 있다**:

| 막힌 것 | 왜 아직 못 밟나 (2026-09-21 실측) |
|---|---|
| **탈퇴 회원 관리자 조작** | 탈퇴 회원은 **한 명 있다**(`20260728-0478` 의 구매자). 그런데 갈래 셋이 전부 대상 0 — 주문은 `DELIVERED` 하나뿐이라 **관리자 취소가 안 걸리고**(`ORDERED`·`PAID` 필요), **리뷰 0 · 문의 0** 이라 숨김도 못 밟는다 |
| **탈퇴 시 장바구니 정리** | 실제 탈퇴가 있어야 한다(되돌릴 수 없다). ⚠ **장바구니는 테이블이 없다**(Redis) — DB 로는 못 본다. 코드는 `CartMemberWithdrawnListener` 에 있다 |

→ 🔴 **이 둘은 «조건이 오면 밟는다» 가 아니라 «누가 탈퇴해야 온다» 다.** 오늘 ① 처럼 **세어 보면 열려 있을 수 있으니**,
다음에 이 줄을 집는 사람은 **세는 것부터** 한다 — 6주 동안 아무도 안 셌다.

## 5. ✅ §I-11 「크기 극소」 묶음 — 셋 다 했다 · **배포·브라우저 검증 끝**

### 6-2. 착수 전 판정 (WA §1-3-1) — **고쳐진 기능인가, 열린 버그인가**

🔴 **고쳐진 기능이고, 검증만 안 된 것**이다:

| 주장 | 실측 |
|---|---|
| 「탈퇴 회원 관리자 조작이 404 로 막힌다」 | ⚠ **과거형이다.** `MemberService.loginIdOf` 가 **2026-08-10 에 정정**돼 예외 대신 `null` 을 준다 |
| 원장에 «없다» 를 지어내지 않는다 | ✅ `target_login` 에 `null` 이 그대로 들어간다 — 닉네임이나 「(탈퇴)」를 넣지 않는다는 결정 |
| 리뷰 숨김·주문 취소가 그 자리를 탄다 | ✅ `ReviewCommandService:129` · `OrderService:532` 둘 다 `memberService.loginIdOf(...)` |
| 탈퇴 시 장바구니가 정리된다 | ✅ `CartMemberWithdrawnListener` → `cartService.clear()`. 키는 **Redis `cart:{memberId}`** |
| 탈퇴가 무엇을 지우나 | 토큰 → 배송지 → **이벤트**(적립금·찜·쿠폰·알림·재입고·문의·장바구니) → 회원 행. **주문과 리뷰는 남는다**(F-1) |

🔴 **판정이 갈리는 지점이 둘**이다: ①조작이 **404 가 아니라 성공**해야 하고 ②원장의 `target_login` 이
**NULL** 이어야 한다. ⚠ ②가 없으면 «성공했다» 만으로는 **닉네임을 지어 넣은 구현과 구별이 안 된다.**

### 6-3. 🔴 **기존 계정을 안 쓴다** — 그리고 `ZZP-` 상품을 만든다

- 탈퇴는 **하드 삭제**다(`purge`). 기존 계정을 쓰면 되돌릴 수 없다 → **새로 가입해서 쓴다**
  (`member` 10 → 11 → 탈퇴 후 **10 으로 복귀**). 여분 계정 넷(`김기현팀5/6/7`·`일반회원팀`)은 **안 건드린다.**
- 🔴 **`ZZP-탈퇴검증` 상품을 만들어서 주문한다** — WA §3-1: *"실상품으로 주문하면 그 상품의 재고가 실제로 깎인다."*
  ⚠ **오늘 §5-6 의 C 에서 이 규약을 어겼다** — 지바·반팔티 실상품을 써서 재고가 **989→987 · 197→196** 으로 깎였다.
  🔴 **되돌리려면 그 주문의 반품을 승인해야 하는데, 그러면 §I-11 증거물이 사라진다**(이월 #27) — **결정이 필요한 자리**로 남긴다.
- 자유 입력 칸에 `ZZ` 를 남긴다 — 수령인 **`ZZ수령인`**, 계정 **`zz-탈퇴검증`**(WA §3-1 의 정리 쿼리가 이걸로 건다).

### 6-4. 넘긴 스텝과 기대값 — ✅ **전부 통과**(사용자: *"브라우저 테스트 모두 성공적으로 통과했어용"*)

**준비 (김기현팀)** — `/products/new` 에 `ZZP-탈퇴검증`(가격 1,000 · 옵션 「기본」 재고 5).

**만들기 (새 계정 `zz-탈퇴검증`)** — 가입 → `ZZP-탈퇴검증` 1개 주문(수령인 `ZZ수령인`) →
주문 상세에서 **「결제하기」까지만** 🔴(발송하면 `isCancellable` 이 `ORDERED`·`PAID` 뿐이라 관리자 취소가 막힌다) →
그 상품에 **리뷰 작성**(`PAID` 면 구매 인증을 통과한다) → **장바구니에 아무거나 담아 둔 채** → `/settings` 에서 **탈퇴**.

**검증 (김기현팀)** — `/admin/orders`(⚠ **「전체」 탭 먼저** — 이월 #6) 에서 **대행 취소**(사유 필수) ·
`/admin/reviews` 에서 그 리뷰 **숨김**. → 🔴 **둘 다 성공해야 한다. 고치기 전이었으면 404 다.**

### 6-5. 🔴 실측 — **말이 아니라 원장과 Redis 로 갈랐다**

**판정 ① 조작이 실제로 먹었다**

```
20260921-9476  CANCELLED  cancelled_by_name=김기현팀  사유=3123123   ← 대행 경로를 탔다
review '456456'  hidden=1                                            ← 숨김이 먹었다
```

**🔴 판정 ② `target_login` 이 NULL — 그리고 같은 원장에 «대조군» 이 나란히 있다**

```
06:38:36  ORDER_SHIP     target_login=김기현팀     ← 살아 있는 회원 (대조군)
06:38:38  ORDER_DELIVER  target_login=김기현팀     ← 살아 있는 회원 (대조군)
06:57:16  ORDER_CANCEL   target_login=<<NULL>>    ← 🔴 탈퇴 회원
06:57:23  REVIEW_HIDE    target_login=<<NULL>>    ← 🔴 탈퇴 회원
```

⚠ **이 대조가 이 검증의 값이다.** «NULL 이 나왔다» 만으로는 «원래 아무것도 안 넣는 구현» 과 구별이 안 되는데,
**같은 표 안에서 있는 회원은 채워지고 없는 회원만 비었다.** 지어낸 값(닉네임·「(탈퇴)」)도 없다.

**판정 ③ 장바구니가 정리됐다**

```
cart:01a0c2beed7477fb9de67b36af51b3f1              → EXISTS 0
cart:01a0c2be-ed74-77fb-9de6-7b36af51b3f1          → EXISTS 0   (하이픈 형식도 확인)
남은 cart:* 키 1개 = 019fb670-… → **김기현팀3**(주인이 있다)
```

⚠ 🔴 **08-11 에 «`cart:*` 96개가 전부 주인 없는 것» 이었던 상태가 정리됐음**도 함께 보였다 —
지금 남은 키는 **하나이고 주인이 있다.**

**판정 ④ 탈퇴가 하드 삭제다** — `member` **11 → 10** · `zz%` 계정 **0**. ⚠ 주문과 리뷰는 남았다(F-1 설계).

### 6-6. 🔴 **새로 나온 것 — 탈퇴 회원에게 알림이 «새로» 생긴다**

취소 직후 알림이 하나 생겼는데 **받는 사람이 탈퇴 회원**이다:

```
06:57:16  <<탈퇴>>  ORDER  20260921-9476 · 1000원 주문이 취소되었습니다.
```

🔴 **아무도 영원히 못 읽는 알림이다.** F-1 은 «탈퇴하면 지운다» 인데 **탈퇴 «뒤» 에 생기는 것은 아무도 안 막는다** —
`purge` 가 지나간 뒤에 관리자 조작이 새 행을 만든다. 보관 정리가 **180일 뒤**(안 읽음) 지우긴 한다.

#### 🔴 그리고 **불변식이 이걸 잡았다** — 오늘 처음으로 `1` 이 됐다

```
scripts/check-money-invariants.sh → 종료코드 1
  🔴 coupon 고아 notification   위반 1     (나머지 19 는 전부 0)
```

⑬ 은 `notification` 에 **회원이 없는 행**을 센다. 🔴 **6주 동안 0 이었던 이유는 «고쳐져 있어서» 가 아니라
«아무도 그 조작을 안 밟아서» 였다** — §4·§5 에서 본 것과 **글자 그대로 같은 모양**이다.

🔴 **그런데 이름이 원인을 단정하고 있었다**: 주석이 *"⑫⑬ **탈퇴 리스너가 남긴 것**이 없다"* 라고 적혀 있다.
오늘 나온 1건은 **리스너가 남긴 게 아니라 탈퇴 «뒤» 에 새로 생긴 것**이다 — **같은 증상, 다른 원인**이고
**고치는 자리가 다르다**(리스너 ↔ 생성 시점 검사). 그대로 두면 다음 사람이 **리스너를 판다.**
→ **스크립트 주석을 고쳐 원인 둘을 갈라 적었다**(WA §1-3 을 그 줄에 붙였다).

⚠ **그래서 오늘 마감값의 «불변식 20 성립» 은 더 이상 참이 아니다** — **19 성립 · ⑬ 위반 1**.

⚠ **다만 «탈퇴 시 정리» 를 더하는 것은 답이 아니다** — 기존 방어 둘이 **모두 «탈퇴 시점» 을 본다**:

(알림 생성 자리에서 «회원이 있나» 를 볼 것인가, 이벤트 발행 자리에서 볼 것인가).

## 7. ✅ `ZZP-탈퇴검증` 삭제 — 그리고 그것이 **두 항목을 되살렸다**

WA §3-1(*"`ZZP-` 상품은 검증 후 삭제할 수 있다"*)대로 화면(정상 경로)으로 지웠다.
**삭제 대기 0 → 1** · 영구 삭제 예정 **2026-09-28 07:06**(유예 7일, F-7/V48).

### 7-1. 🔴 `deleted_at` 오프셋 — **6주 만에 원인 후보가 하나로 좁혀졌다**

⚠ **먼저 내 오독을 적는다**: `created_at` 을 전수로 재고 «전부 `+00:00` 이니 섞임은 거짓» 이라고
말할 뻔했다. 🔴 **08-19 의 관찰은 `deleted_at` 이었다 — 다른 칸이다.** 원문을 다시 열어 갈랐다:

> **08-19 §1-1 원문**: *"`deleted_at` 의 오프셋이 행마다 섞여 있다. **08-12 행은 `+09:00`,
> 08-14 행들은 `+00:00`** 으로 저장돼 있다."*

즉 **읽는 쪽이 아니라 저장이 실제로 갈렸고**, 경계가 **08-12 ↔ 08-14** 다.

**실측 (2026-09-21)**:

| 무엇 | 값 |
|---|---|
| 서버 로컬 | **KST(+09:00)** (`timedatectl`) |
| 앱 JVM | `-Duser.timezone` **없다**(`infra/systemd` · 프로세스 인자 모두) |
| 🔴 앱이 오늘 쓴 `deleted_at` | **`2026-09-21 07:06:31 +00:00`** (= 16:06 KST) |
| 🔴 `sqlplus` 세션 | `sessiontimezone = **+09:00**` · `dbtimezone = +00:00` |
| 컬럼 타입 | `TIMESTAMP(9) WITH TIME ZONE` (V48 부터 줄곧 — **타입이 바뀐 적은 없다**) |
| 타임존 설정 | `application*.yml` 에 `time_zone` 류 **한 줄도 없다** |

🔴 **그래서 구조적으로 갈린다**: 엔티티가 `Instant` 라 **앱은 타임존 없이 UTC(`+00:00`)로 바인딩**하고,
**`sqlplus` 로 직접 넣으면 세션 타임존(`+09:00`)이 박힌다.** **입력 경로가 둘이면 오프셋이 둘이다.**

⚠ **그날 실제로 SQL 을 썼다는 증거는 없다** — 그 행(08-12 삭제분)은 **이미 영구 삭제**돼 표본이 없다.
그래서 **«원인 확정» 이 아니라 «후보를 하나로 좁혔다»** 로 적는다(추측으로 단정하지 않는다).
→ **조건부 잔여의 그 항목을 그렇게 고쳐 적었다.** 🔴 **지금 남은 표본은 오늘 것 하나뿐이고 `+00:00` 이다** —
다음에 SQL 로 시각을 넣을 일이 생기면 **그때가 이 가설을 가를 자리**다.

### 7-2. 🆕 M-4·O-7 의 운영 경로 — 대상이 생겼다 (이월 #5)

이월 #5 가 *"다음 영구 삭제 때 DB 로 본다 — 삭제 대기 상품 0개"* 로 기다리던 자리에
**2026-09-28 07:06** 에 영구 삭제가 예정된 상품이 하나 생겼다.
⚠ **그날 전에는 못 본다** — 유예가 7일이고 sweep 은 1시간 주기다.
