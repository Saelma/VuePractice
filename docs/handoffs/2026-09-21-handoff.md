### 2-1. 왜 이걸 골랐나

| **다 셌는가** | 🔴 고유명이 0개면 «어긋남 없음»이 아니라 **«판정 불가»(2)**. 그리고 **본 개수를 늘 찍는다** — `본 것: 주문번호 17 · 표본이름(ZZ) 2 · …` |

### 3-5. 🔴 **첫 판은 «과거 거짓» 을 하나도 못 잡았다** — 왜 놓쳤는지가 설계 전부다

08-27 문서에 돌리니 **50개를 대조하고 «어긋남 없다»** 를 냈다. §2 에서 손으로 찾은 넷이 **전부 눈 밖**이었다.
🔴 **이게 §3-6 이 말한 «덜 세서 성립해 보이는» 그 답이다.** 넷을 고쳐서 지금 판이 됐다:

| 왜 놓쳤나 | 고친 것 |
|---|---|
| 🔴 **로케일**. `ko_KR.UTF-8` 에서 GNU sed 4.8 의 `s/….*$//` 가 **한글·이모지 섞인 긴 문자열에서 조용히 안 바뀐다**(같은 입력이 **828바이트** / `LC_ALL=C` **18바이트**). 창 자르기가 통째로 안 먹어 **옆 주문의 상태**를 집었다 | 본문 스캔을 전부 `LC_ALL=C`(`SCAN()`)로 고정. **TROUBLESHOOTING 색인에 넣었다** |
| 주장이 번호 **앞**에 올 수 있다 — 「**미결제** 주문 둘(`4185`·`4186`)」 | «제 뒤» 를 먼저, 없으면 «제 앞». 둘 다 **이웃 번호와 `·`** 에서 끊는다 |
| 표본 이름이 주문번호가 아니다 — `ZZ-123123` 은 **상품**이다 | 백틱 안의 `ZZ-…` 를 따로 뽑아 `product`·`coupon`·`member` 에서 찾는다 |
| 주장이 **«그 파일 안에서»** 다 — 「`SignupView` 의 `border-ink-200`」. 저장소 전체로 grep 하면 `index.css` 에 토큰 정의가 있어 **늘 참**이 된다 | 항목이 화면 이름과 토큰을 함께 말하면 **그 파일 안에서** 찾는다 |
| 인용(`>`) 줄의 **정정 기록**이 현재 주장으로 읽혔다 | `>` 줄은 «과거 경위» 라 **뺀다** — 안 빼면 **고친 사실 자체가 어긋남으로 다시 잡힌다** |
| 「미결제」를 `paid_at IS NULL` 로만 보면 **취소된 채 미결제인 주문**이 통과한다(4185·4186 이 5주간 그랬다) | 미결제 주장인데 상태가 `CANCELLED`·`RETURNED` 면 **「표본이 죽었다」** 로 지목 |

⚠ 🔴 **처음엔 로케일 문제를 «한 줄에 주문이 여럿이라» 로 진단했다** — 증상은 맞고 **원인이 틀렸다.**
WA §1-3 의 *"결론이 맞아도 이유는 틀릴 수 있다"* 를 그 자리에서 다시 밟았다.
가른 것은 **바이트 수 한 줄**이었다(`LC_ALL=C` 와 그냥 돌린 것의 `wc -c` 비교).

### 3-6. 검증 (WA §3 변형 주입) — §4-0 이 `check-handoff.sh` 에 한 것과 같은 방식
