## 4. G-6 HTTP 통합 테스트 **5건** — 화면에서 읽은 값을 그대로 단언값으로 박았다

`PointFlowIntegrationTest` 에 붙였다. **새 클래스를 안 만든 이유**: 그 파일이 이미 «등급» 의 집이고
(적립률·승급·강등), 회원·상품·로그인·장바구니 헬퍼가 다 있다. 새 클래스를 세우면 **픽스처 사본이 하나
더 생긴다.** 클래스 주석의 «여기서만 드러나는 것» 에 네 번째 항목을 더했다.

| 테스트 | 단언 |
|---|---|
| `silverLowersFreeShippingThreshold` | SILVER → `freeShippingThreshold` **24,000** · 25,000 장바구니 **fee 0 · 남은 금액 0** |
| `silverRemainingUsesSameThresholdAsFee` | SILVER 20,000 → fee **3,000** · 남은 금액 **4,000** |
| `bronzeKeepsDefaultThreshold` | 대조군 — BRONZE 같은 25,000 → **3,000** · **5,000** |
| `noAccountFallsBackToBronzeWithoutCreatingOne` | 계정 없이도 열리고 🔴 **계정이 안 생긴다** |
| `gradeShippingFeeIsSnapshotOnOrder` | SILVER 로 주문(fee 0) → **강등해도 그 주문은 0 그대로** |

✅ **픽스처는 예고대로 두 줄이었다** — `findByMemberId` → `addPurchase(200_000)` → `saveAndFlush`.
⚠ 50,000짜리 기존 상품으로는 **25,000 장바구니를 만들 수 없어** 5,000원짜리를 하나 더 세웠다
(무료배송 경계를 1,000원 단위로 짚어야 한다).
⚠ **장바구니는 Redis 라 롤백이 안 닿는다** → `@AfterEach` 에서 `cartService.clear()`
(`CouponOrderIntegrationTest` 선례). 이 다섯은 결제까지 안 가서 스스로 안 비워진다.

**결과**: `PointFlowIntegrationTest` **18건**(기존 13 + 새 5) 전부 초록 ·

(픽스처가 `@Transactional` 로 롤백되고, 장바구니는 `@AfterEach` 가 치운다).

### 4-1. 🔴 되돌려서 확인 — **셋이 잡혔고, 셋 다 의도한 자리였다**

새 테스트가 «있다» 는 것과 «잡는다» 는 것은 다르다(WA §3). 변형 둘을 운영 코드에 넣고 돌렸다:

| 변형 | 잡은 테스트 | 나온 값 |
|---|---|---|
| ① `CartService` 가 `amountUntilFree` **만** 기본 기준(30,000)으로 부른다 | `silverRemainingUsesSameThresholdAsFee` | 4,000 기대 → **10,000** |
| ① 같은 변형 | `silverLowersFreeShippingThreshold` | 0 기대 → **5,000** |
| ② `gradeOf` 가 계정을 **만들어 저장**한다 | `noAccountFallsBackToBronzeWithoutCreatingOne` | 빈 Optional 기대 → **계정 있음** |

🔴 **①이 두 테스트를 한꺼번에 빨갛게 만든 것이 이 절의 값이다.** 그 변형이 만드는 화면은
**«배송비 무료» 라고 적어 놓고 «5,000원 더 담으면 무료배송» 이라고 말하는 화면**이다 —
한 응답 안에서 두 값이 서로 어긋나는 모양이고, **단위 테스트로는 못 보는 자리**다
(둘 다 각자는 «맞는 값» 을 돌려준다).
⚠ **대조군(BRONZE)과 스냅샷 테스트는 ① 아래서도 초록이었다** — BRONZE 는 등급 기준이 기본 기준과
같아서다. **변형이 정확히 «등급이 개입하는 자리» 만 무너뜨렸다**는 뜻이라, 이 셋이 우연히
빨개진 게 아니라는 증거이기도 하다.

✅ 변형을 되돌리고 운영 코드에 `MUTANT` 흔적이 **0** 임을 확인한 뒤 전수를 다시 돌렸다.
