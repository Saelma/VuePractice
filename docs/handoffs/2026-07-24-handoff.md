### 2-1. ⚠ 이 마이그레이션은 어제까지와 성격이 다르다 — 순수 추가가 아니다

V13~V17 은 **다섯 개 전부 순수 추가**였다(컬럼·테이블 ADD). B-5 는 다르다:
`member.ship_*` **기존 값을 새 테이블로 옮기고 원래 컬럼을 정리**해야 한다.

**위험**: `ddl-auto: validate` 이고 운영 jar 의 `Member` 엔티티가 `ship_*` 5개를 매핑한다.
통합 테스트를 돌리는 순간 Flyway 가 **공유 espdb 에 적용**되므로(WORKING-AGREEMENTS §5),
같은 마이그레이션에서 `ship_*` 를 `DROP` 하면 **구 jar 는 재기동이 불가능**해지고,
`MemberResponse`·`ShippingAddress` 조회는 그 즉시 `ORA-00904`(존재하지 않는 컬럼)로 깨진다.
7/21 의 닉네임 UNIQUE(V6) 사고와 같은 종류인데, **그때보다 훨씬 파괴적**이다 —
UNIQUE 는 신규 가입만 막았지만 컬럼 DROP 은 **기존 조회를 통째로** 깬다.

→ **expand / contract 2단계로 나눈다.**

```
V18 (오늘)  member_address 신설 + member.ship_* 값 복사   ← 순수 추가. 구 jar 무영향
            신 코드 배포 (읽기는 member_address 로)
V19 (나중)  member.ship_* DROP                            ← 신 코드가 운영에 완전히 올라간 뒤
```

`ship_*` 를 남겨두는 동안은 **두 곳에 같은 값이 있다**(이중 진실). 이건 감수한다 —
짧은 기간이고, 대안(한 번에 DROP)은 운영을 깨기 때문이다. 다만 **V18 이후 신 코드는
`member.ship_*` 에 쓰지 않는다** — 안 그러면 두 값이 갈라져 나중에 어느 쪽이 맞는지 알 수 없어진다.

⚠ `orders.ship_*` 는 **건드리지 않는다.** 그건 주문 시점 **스냅샷**이라 주소록과 무관하고,
주소록을 고쳐도 과거 주문의 배송지는 그대로여야 한다(7/23 까지 여섯 번 적용한 스냅샷 원칙).

## 3. 기능 추가 — 배송지 주소록 (V18)

백로그 **B-5**. `member.ship_*` 5컬럼 = 회원당 배송지 하나였던 걸(V11) 별칭 붙은 주소록으로 늘렸다.

### 3-1. ⚠ 착수 전에 발견한 것 — 이관 대상 1건이 7/22 검증 잔재였다

회원 4명 중 배송지가 있는 사람은 **1명**이었는데, 그 값이 이랬다.

```
수령인=123 · 우편번호=06134 · 주소=123123123 · 상세=123
```

WORKING-AGREEMENTS §3-1 에 기록된 **그 사고의 흔적**이다 — 7/22 에 배송지 기능을 브라우저로
검증하며 본인 계정 + 실상품으로 주문했고 수령인에 `123` 을 넣었다. 그때 **주문은 화면에서 취소했고
재고도 복원**했지만, 회원의 기본 배송지에 남은 이 값은 **아무도 안 치웠다.**

> §2-5 "재발 방지와 기존 잔재 정리는 별개" 의 또 다른 실례다. 그때는 "주문" 만 잔재로 봤고
> **그 검증이 회원 프로필도 건드렸다는 걸 놓쳤다.** 검증이 만든 것을 셀 때 주문·상품만 보지 말 것.

**마이그레이션은 이 판단을 하지 않는다.** "값이 있으면 옮긴다" 만 하고 잔재 정리는 별건으로 뒀다 —
빈 DB·미래 환경에서도 같은 스크립트가 돌아야 하고, 데이터를 골라내는 마이그레이션은 재현이 안 된다.
마침 **오늘 만든 화면으로 바로 지울 수 있다**(이월 참조).

### 3-2. ⚠ 첫 번째 "순수 추가가 아닌" 마이그레이션 — expand / contract 로 나눴다

V13~V17 은 **다섯 개 전부 컬럼·테이블 ADD** 였다. B-5 는 기존 값 이관 + 컬럼 정리가 붙는다.

한 번에 `member.ship_*` 를 DROP 하면 어떻게 되는지가 착수 전 유일한 위험이었다:

```
통합 테스트 실행 → Flyway 가 공유 espdb 에 적용 → 컬럼 사라짐
  → 운영 구 jar 는 그 컬럼을 매핑 중 → 재기동 불가 + 회원·주문 조회가 ORA-00904
```

7/21 의 **닉네임 UNIQUE(V6) 사고와 같은 종류인데 훨씬 파괴적**이다. UNIQUE 는 신규 가입만 막았지만
컬럼 DROP 은 **이미 되던 조회를 통째로** 깬다.

→ 사용자 결정으로 **둘로 나눴다**:

| | 내용 | 구 jar 영향 |
|---|---|---|
| **V18 (오늘)** | `member_address` 신설 + `member.ship_*` 값 복사 | **없음** (순수 추가) |
| **V19 (나중)** | `member.ship_*` DROP | 신 코드가 운영에 올라간 뒤에만 안전 |

뒤쪽은 이월이 아니라 **백로그 B-5-2** 에 뒀다 — 수명이 "며칠" 이 아니라 "배포가 안정된 뒤" 라는 조건부다.

> ⚠ **번호가 밀렸다.** 착수 시점엔 뒤쪽을 "V19" 로 불렀는데, 같은 날 오후에 위시리스트(§4)가
> **V19 를 가져갔다.** 그래서 `member.ship_*` DROP 은 **V20** 이 된다.
> 마이그레이션 번호는 **먼저 머지되는 쪽이 가져간다** — 계획 단계에서 번호를 예약해 두면
> 이렇게 어긋난다. 아래 본문에 남은 "V19" 표기는 그때의 판단 기록이라 그대로 두되,
> **앞으로를 가리키는 자리는 전부 V20 으로 고쳤다**(백로그·ARCHITECTURE 포함).

### 3-3. 이중 진실을 규율이 아니라 **구조**로 막았다

V18~V19 사이엔 같은 주소가 두 곳에 있다. 여기서 흔한 실패는 *"신 코드는 옛 컬럼에 쓰지 않기로 하자"*
라고 **적어두고 끝내는 것**이다. 그러면 언젠가 누가 쓴다.

→ **`Member` 엔티티에서 `ship_*` 매핑 5개를 아예 걷어냈다.** 필드가 없으면 쓸 방법이 없다.
`ddl-auto=validate` 는 **매핑되지 않은 여분 컬럼을 문제 삼지 않으므로**(실측: V18 적용 후 기동 통과)
DB 에 컬럼이 남아 있어도 아무 문제가 없다.

부수효과로 **V19 는 코드 변경이 0** 이 됐다 — 순수 DDL 한 줄이다.

### 3-4. 기본 배송지가 하나뿐임을 DB 가 보장한다

Oracle 에는 부분 유니크 인덱스(`WHERE is_default = 1`)가 없다. 함수 기반 유니크 인덱스로 같은 효과를 낸다:

```sql
CREATE UNIQUE INDEX uq_member_address_default
    ON member_address (CASE WHEN is_default = 1 THEN member_id END);
```

`is_default=0` 인 행은 색인값이 NULL 이라 유니크 대상에서 빠지고, 같은 회원의 두 번째 기본 배송지만
ORA-00001 로 거부된다. 주문번호 유니크(V15)를 "앱 채번이 어긋났을 때의 최종 방어선" 으로 둔 것과 같은 성격이다.

**그 대가로 순서 제약이 생겼다.** "옛 기본 해제" 와 "새 기본 지정" 이 **DB 에 도달하는 순서**가 중요한데,
JPA 더티 체킹은 **flush 순서를 보장하지 않는다** — 같은 엔티티 타입이라 뒤집힐 수 있다.

```java
addressRepository.findByMemberIdAndIsDefaultTrue(memberId)
        .ifPresent(MemberAddress::unsetDefault);
addressRepository.flush();          // ← 이 줄이 없으면 ORA-00001
address.markDefault();
```

삭제도 같은 문제다 — 기본 배송지를 지우고 다른 주소를 승계시킬 때 **DELETE 가 먼저 나가야** 한다.
안 그러면 기본이 두 행이 되는 순간이 생긴다.

> 이 `flush()` 들은 **지우기 쉬운 줄**이다("불필요해 보이는 flush"). 그래서 코드 주석과 여기 양쪽에 적었다.

### 3-5. FK 를 진짜로 걸었다 — `member_coupon` 과 다른 이유

`member_coupon.member_id` 는 주석에 **"FK 아님(느슨한 참조) — 도메인 경계"** 라고 적혀 있다.
`member_address` 는 반대로 **진짜 FK + `ON DELETE CASCADE`** 다. 모순이 아니다:

| | 방향 | 판단 |
|---|---|---|
| `member_coupon` → member | **도메인 간**(coupon → member) | FK 를 걸면 MSA 분리 때 걸림돌. 느슨한 UUID |
| `member_address` → member | **도메인 안**(member → member) | 쪼개도 member 와 **함께** 움직인다. FK 가 맞다 |

그리고 CASCADE 는 선택이 아니었다 — `MemberService.withdraw` 가 member row 를 지우므로,
CASCADE 가 없으면 **주소가 있는 회원은 탈퇴 자체가 FK 위반으로 실패**한다.

### 3-6. 백필 PK 를 `SYS_GUID()` 로 하지 않았다

CLAUDE.md 는 PK 를 **UUIDv7 · 앱에서 생성**으로 못박는데, 백필 행은 앱을 거치지 않는다.
`SYS_GUID()` 는 v7 이 아니고(시간순이 아니다), **한 번 들어가면 나중에 구분할 방법도 없다.**

→ SQL 에서 **v7 레이아웃을 그대로 조립**했다.

```
[48비트 unix ms = 12 hex] [버전 '7'] [rand_a 3 hex] [variant 'A'] [rand_b 15 hex] = 32 hex
```

RFC 9562 의 variant 는 상위 2비트가 `10` 이어야 해서 17번째 hex 는 8·9·A·B 중 하나여야 한다 → `'A'` 고정.
**실측**: 생성값 `019F9175E3107575A1348689147A35E0` — 13번째 hex 가 `7`, 앞 12 hex 를 되읽으면 현재 UTC 와 일치.

> ⚠ 이 플랫폼의 `SYS_GUID()` 는 **순차적**이라 난수부의 무작위성이 약하다(연속 호출이 1~2 hex 만 다르다).
> 필요한 건 **서로 다른 값**뿐이고 PK 유니크가 최종 방어선이라 그대로 뒀다 — 다만 이걸 **난수원으로
> 믿으면 안 된다**(토큰·비밀값 용도로는 부적합).

### 3-7. API 계약을 유지한 채 저장 위치만 옮겼다

`MemberResponse.ship*` 5개 필드는 **그대로 뒀다.** 프론트의 주문서 자동 채움과 `hasAddress` 판정이
이 필드를 보고 있어서, 형태까지 바꾸면 **저장 구조 이전과 화면 개편이 한꺼번에 얽힌다.**
값의 **출처만** `member.ship_*` → 주소록의 기본 항목으로 바꿨다.

같은 이유로 옛 경로 `PATCH /api/members/me/shipping-address` 도 살렸다 — 주문서의
"이 주소를 기본 배송지로 저장" 체크가 계속 쓴다. 서버가 그 요청을 **기본 항목 upsert** 로 처리해
주소가 두 벌로 갈라지지 않는다(통합 테스트로 고정했다).

> 덕분에 **주문 API(`POST /api/orders`)는 한 글자도 안 바뀌었다.** 주문서는 원래 배송지를
> 본문으로 받고 있었고, 주소록은 그 폼을 **채우는 방법**이 하나 늘어난 것뿐이다.

### 3-11. 곁가지 — esptest 비우기에 `sudo` 가 필요 없었다

`migration/README` 의 절차는 `sudo -iu oracle` + `sysdba` + `dba_tables` 였다. 그런데
**자기 스키마의 객체를 DROP 하는 데는 DBA 권한이 필요 없다** — `esptest` 로 직접 접속해
`user_tables`·`user_sequences` 를 돌면 끝이다. 오늘 그렇게 했다.

> **왜 고쳤나**: `sudo` 가 낀 절차는 **사람 손을 기다리게** 만들고, 기다리게 만드는 검증은 건너뛰게 된다.
> 빈 DB 검증은 마이그레이션마다 **매번** 돌려야 하는 절차라 특히 그렇다.

같은 자리에서 **시퀀스 DROP 누락**도 고쳤다(§2-2 에서 예고한 워밍업). 7/23 V16 검증에서
`seq_order_no` 가 살아남아 `CREATE SEQUENCE` 가 ORA-00955 로 실패했는데 README 에 반영이 안 돼 있었다.
오늘 실제로 시퀀스까지 지우고 돌려 **V15 가 깨끗이 재적용**되는 걸 확인했다.

## 4. 기능 추가 — 위시리스트(찜) (V19)

백로그 **B-6**. 주소록을 닫고 이어서 뽑았다. 장바구니와 구조가 거의 같아 **패턴을 그대로 재활용**했다
— 찜 행에는 상품 id 만 있고, 상품 정보는 catalog 공개 서비스에서 합성한다.

### 4-1. 같은 모양인데 저장소가 다르다 — 왜 Redis 가 아닌가

장바구니는 Redis(`CartStore`)인데 찜은 **테이블**이다. 백로그가 이미 그렇게 적어 뒀고 근거는 이렇다:

| | 장바구니 | 찜 |
|---|---|---|
| 수명 | "지금 사려는 것" — 세션이면 충분 | **로그아웃해도 남아야** 한다 |
| 잃으면 | 다시 담으면 된다 | **사용자가 모으던 것이 사라진다** |

Redis 에 두면 TTL·플러시·재시작에 **조용히** 날아가고, 사용자는 원인을 알 수 없이
"찜한 게 사라졌다"로만 겪는다. 되돌릴 방법도 없다.

### 4-2. ⚠ 핵심 판단 — 찜 여부를 상품 응답에 넣지 않았다

가장 편한 설계는 `ProductResponse` 에 `wishlisted` 불리언을 하나 얹는 것이다. **그러면 안 된다**:

```
wishlist → catalog   (찜 목록이 상품 정보를 읽는다. 이미 있다)
catalog  → wishlist  (상품 응답이 찜 여부를 알려면 필요. ← 이게 생기면 순환)
```

**2026-07-20 에 상품 목록 별점에서 겪은 것과 같은 문제**다. 그때는 `review → catalog` 가 이미 있어서
catalog 가 review 를 조회하면 순환이 되므로, **이벤트로 집계값을 밀어넣고 비정규화**해 풀었다.

그런데 **찜에는 그 해법이 안 통한다** — 별점은 상품마다 하나인 값이라 컬럼에 담을 수 있지만,
찜 여부는 **보는 사람마다 다르다.** 상품에 비정규화할 수 있는 값이 아니다.

→ **세 번째 방법을 썼다: 클라이언트 조인.**
`GET /api/wishlist/product-ids` 로 **내가 찜한 상품 id 집합**을 따로 주고, 화면이 상품 목록과 합친다.
서버는 도메인 경계를 지키고, 화면은 Set 하나만 들면 된다.

> 정리하면 도메인 순환을 피하는 수단이 이제 셋이다 — **이벤트**(별점) · **비정규화**(별점) ·
> **클라이언트 조인**(찜). 값이 *보는 사람마다 다르면* 앞의 둘은 쓸 수 없다.

### 4-3. 추가·해제를 둘 다 멱등으로

"이미 찜한 상품을 또 찜하면 409" 가 자연스러워 보이지만 그렇게 하지 않았다.

- 화면이 **토글**이라 사용자가 "중복 찜"을 **의도할 수 없다.**
- 그러니 중복 요청은 전부 **사고**다 — 더블클릭, 느린 네트워크에서의 재시도, 뒤로가기.
- 거기서 에러를 띄우면 사용자는 원인을 알 수 없고 **화면 상태만 어긋난다**(하트는 켜졌는데 에러창).
- 원하는 최종 상태("찜되어 있음")는 어느 쪽이든 같다.

해제도 대칭으로 멱등이다. "지워달라"의 목적은 **없는 상태**이고, 이미 그렇다면 할 일이 없는 것이지
오류가 아니다. 해제에서는 **상품 존재를 확인하지 않는다** — 확인하면 삭제된 상품을 찜 목록에서
**영영 못 뺀다.**

동시 요청으로 검사와 INSERT 사이가 벌어져도 DB 의 `UNIQUE(member_id, product_id)` 가 막는다.

### 4-4. 조회 인덱스를 일부러 안 만들었다

유일한 조회 경로가 "내 찜 목록"(`member_id = ?`)인데, 위 UNIQUE 제약이 만든 인덱스의
**선두 컬럼이 이미 `member_id`** 라 그 쿼리가 그대로 탄다. 같은 컬럼으로 인덱스를 하나 더 만들면
INSERT/DELETE 비용만 늘고 얻는 게 없다. **실측**: `user_indexes` 에 PK + UNIQUE 둘뿐이다.

### 4-5. 삭제된 상품을 조회에서 지우지 않는다

장바구니는 삭제된 상품을 만나면 **그 자리에서 지운다**(`cartStore.remove`). 찜은 **빼고 보여주기만** 한다.

> **왜 다른가**: `WishlistQueryService` 는 `@Transactional(readOnly = true)` 다. 조회가 데이터를 고치면
> "목록만 봤는데 뭔가 사라지는" 예측 불가능한 동작이 된다. 장바구니가 그렇게 하는 건 **결제 직전**이라
> 정합성이 더 중요한 자리이기 때문이고, 찜은 그럴 이유가 없다.
> 쌓이면 스위퍼를 두면 된다(이미지 고아 정리와 같은 방식) — 지금은 그럴 규모가 아니다.

### 4-6. 목록 값은 스냅샷이 아니라 **지금** 값이다

7/23~24 내내 "스냅샷" 을 일곱 번 적용했는데(닉네임·이미지·배송지·배송비·정가·쿠폰·주소록)
찜은 **정반대**다. 가격·재고·별점을 전부 조회 시점에 catalog 에서 읽는다.

이유가 명확하다 — 찜은 **"나중에 살까"** 하고 담아 두는 것이라, **값이 내렸는지 · 품절됐는지**를
봐야 쓸모가 있다. 찜한 시점의 가격을 박아 두면 오히려 **틀린 정보**가 된다.
(주문은 반대다 — "그때 얼마에 샀는지" 가 사실이어야 한다.)

→ 화면에도 그렇게 적었다: *"가격과 재고는 **지금** 값이에요."*

### 4-7. 화면 — 카드가 `<button>` 이라 하트를 안에 못 넣는다

상품 목록 카드는 **통째로 `<button>`** 이다(클릭하면 상세로). 하트를 그 안에 넣으면 **button 중첩**이라
유효하지 않은 HTML 이고 클릭 처리도 어긋난다.

→ 카드를 `relative` 래퍼로 감싸고 하트를 **절대배치**로 얹었다. 클릭이 카드로 새지 않게 `@click.stop`.

나머지 판단들:

- **낙관적 갱신** — 하트는 즉시 반응해야 하는 UI 라 화면을 먼저 바꾸고 서버에 보낸다. 실패하면 되돌린다.
  서버가 멱등이라 중복 클릭이 문제를 만들지 않는다(§4-3 이 여기서 값을 했다).
- **찜 id 집합은 스토어에 둔다**(`stores/wishlist.js`) — 목록·상세·찜 페이지가 같은 상태를 봐야 한다.
  화면마다 따로 들면 상세에서 찜을 풀고 뒤로 갔을 때 목록 하트가 여전히 채워져 있다.
- **로그아웃 시 비운다** — 안 비우면 같은 브라우저에서 다음 사람이 **남의 하트**를 본다.
- **비로그인도 하트를 본다.** 누르면 막지 않고 `redirect` 를 달아 **로그인으로 보낸다** — 찜은 로그인을
  유도하기 좋은 자리다.
- **품절이어도 찜은 된다.** 재입고를 기다리는 게 찜의 용도라 `available` 은 "지금 담을 수 있나"만 가른다
  (찜 목록의 「장바구니 담기」 버튼만 비활성).

## 5. `member.ship_*` 컬럼 DROP (V20) — expand / contract 의 **contract**

백로그 **B-5-2**. §3-2 에서 나눠 뒀던 뒤쪽을 **같은 날 안에** 처리했다.

### 5-1. 왜 며칠 안 기다리고 앞당겼나

백로그에는 조건을 *"V18 을 담은 jar 가 운영에서 정상 동작 중일 것. 되돌릴 일이 없다고 판단되면 그때"*
로 적어 뒀고, 막연히 며칠 뒤를 생각하고 있었다. 사용자가 **"다음 작업 전에 먼저 하는 게 낫지 않나"**
라고 제안해 다시 따져 봤고, **앞당기는 쪽이 맞았다.**

착수 전 실측으로 확인한 것:

| 확인 | 결과 |
|---|---|
| 운영 jar | V18·V19 를 담은 빌드(**10:20**)로 교체됨 · 브라우저 검증 통과 |
| `Member` 엔티티 | `ship_*` 필드 **없음**(주석만 남아 있다) |
| 코드 참조 | 네이티브 쿼리·JPQL 어디에도 **없음** |
| `Order.ship_recipient` | **다른 테이블**의 주문 스냅샷 — 무관 |

**결정적이었던 것은 "기다려서 얻는 게 뭔가" 였다.** 기다리는 목적은 롤백 여지를 남기는 것인데:

- 남아 있는 컬럼 값은 **이미 낡은 데이터**다. 주소록에서 고치거나 지워도 이쪽은 안 따라오므로,
  실제로 오늘 오전에 `123` 을 주소록에서 지웠을 때 **컬럼에는 그대로 남아 어긋나 있었다**(§3-13).
- 그리고 V18 이전 jar 로 되돌리면 **주소록이 통째로 사라진다.** 즉 **롤백 경로가 애초에 쓸 수 없다.**

→ 지키려던 안전장치가 **이미 작동하지 않는 상태**였다. 그러면 기다림은 비용만 남는다.

> ⚠ 그래도 **되돌릴 수 없는 작업을 앞당긴 것**이므로 근거를 여기 남긴다.
> 롤백 경로가 살아 있었다면 기다리는 게 맞았다.

### 5-2. 배포가 필요 없었다 — §3-3 의 부수효과

**코드 변경이 0**이다. jar 가 안 바뀌므로 배포할 것이 없고, 마이그레이션은 **통합 테스트가 돌 때
espdb 에 적용**된다. 오늘 하루 중 유일하게 배포 없이 끝난 스키마 변경이다.

이게 §3-3 에서 **엔티티 매핑을 미리 걷어낸 덕**이다. 그때 매핑을 남겨 뒀다면 오늘 V20 은
"엔티티 수정 + 테스트 수정 + 빌드 + 배포" 가 붙었을 것이다. **일을 앞으로 당겨 놓으면 뒤가 싸진다.**

### 5-3. 검증 (실측)

| 확인 | 결과 |
|---|---|
| V20 적용 | espdb **3.5초** · success |
| `member` 의 `SHIP%` 컬럼 | **0개** (5 → 0) |
| `orders` 의 `SHIP_%` 컬럼 | **9개 그대로** — 주문 스냅샷은 안 건드렸다 |
| 주소록 데이터 | **1건 무사** |
| 테스트 | **219개** · failures 0 · errors 0 · **skipped 0** (컬럼이 사라져도 아무 테스트가 안 깨졌다 = 참조가 정말 없었다는 증거) |
| 운영 | health `UP` · `/api/products` 200 · `https:200` — **재배포 없이 그대로** |

> **빈 DB(esptest) 검증 통과**: V1→V20 순차 적용(**20개, 4.9초**) + `validate` 통과(기동 66초).
> V11 이 만들고 V12 가 semantics 를 고친 컬럼을 V20 이 지우는 순서가 정상 동작한다 —
> 적용된 마이그레이션을 고치는 게 아니라 **뒤에서 지우는 게 맞다**(§2-1).

## 6. 기능 추가 — 관리자 매출 통계 (C-11, 마이그레이션 없음)

백로그 **C-11**. B 묶음을 다 비운 뒤 C 에서 뽑았다. 관리자 API 가 주문·이미지뿐이라 대시보드가 없었다.

### 6-1. 이 기능의 전부는 "무엇을 매출로 보는가" 다

코드는 쿼리 셋인데, **판단이 셋** 붙는다. 착수 전에 실제 데이터를 보고 정했다.

| | 결정 | 왜 |
|---|---|---|
| **시각** | `created_at` ❌ → **`paid_at`** | 주문한 시점은 **영영 결제 안 될 수도** 있다. 매출은 돈이 들어온 시점 |
| **상태** | `<> CANCELLED` ❌ → **`PAID·SHIPPED·DELIVERED` 명시적 열거** | 부정 조건으로 쓰면 나중에 추가되는 상태(환불·교환)가 **자동으로 매출에 섞인다**(`existsPurchase` 와 같은 판단) |
| **일자** | UTC ❌ → **KST** | `paid_at` 은 UTC 저장이라 그냥 자르면 **한국시간 00~09시 결제가 전날**로 찍힌다 |

> ⚠ **`paid_at` 유무로 거르면 안 된다.** 이게 제일 빠지기 쉬운 함정인데, 착수 전 실측에서 바로 드러났다 —
> `paid_at` 이 있는 주문이 **7건**인데 매출 대상은 **6건**이었다. 나머지 1건은 **결제 후 취소**라
> `paid_at` 이 남아 있지만 환불이다. 시각으로만 거르면 이게 매출에 섞인다.
> 통합테스트에 이 케이스를 따로 고정했다.

일자 그룹핑에는 **JPQL 에 타임존 변환이 없어** 네이티브 쿼리를 썼다. V15 주문번호에서 똑같이 걸렸던 자리다.

### 6-2. 상품매출과 배송비를 합치지 않는다 (사용자 결정)

배송비는 **그대로 택배비로 나가는 돈**이라 상품매출에 섞으면 "장사가 잘되고 있나"를 읽을 수 없다.
그래서 서버가 `itemSales`(상품합계−쿠폰할인)와 `shippingSales` 를 **따로** 준다. 둘을 더한 값이
필요하면 `payAmount` 를 본다.

**상품별 판매액은 쿠폰 할인 전**이다. 쿠폰은 **주문 단위**로 붙어서 어느 상품이 얼마를 깎았는지
나눌 근거가 없다 — 안분하면 그럴듯하지만 **지어낸 숫자**가 된다.
그래서 상품별 합계와 요약의 상품매출은 **일부러 다르고**, 화면에도 그 이유를 적었다.

### 6-3. ⚠ 조용히 0을 돌려주던 버그 — 하마터면 테스트가 통과할 뻔했다

집계는 항상 한 행이라 `Object[] summarize(...)` 로 선언했다. 그런데:

```
SQL 직접 실행 : 6건 / 60,000원
API 응답      : 0건 / 0원
```

Spring Data 가 네이티브 쿼리에서 **"한 행의 여러 컬럼"과 "여러 행"을 구분하지 못해** 조용히 빈 값을
돌려주고 있었다. 예외도 로그도 없다.

> **더 나쁜 건 테스트가 이걸 못 잡을 뻔했다는 것**이다. "결제 전후 매출 증분"을 비교했는데
> 값이 항상 0이면 **0 − 0 = 0** 으로 **통과**한다. 실제로 3건 중 2건이 그렇게 vacuous 하게 통과했고,
> 절대값을 쓰는 다른 테스트가 실패해서야 드러났다.
>
> → **증분(델타)만 확인하는 테스트는 "둘 다 0"을 통과시킨다.** 최소 하나는 **절대값**을 봐야 한다.

**구조적 해법**: `List<Object[]>` 로 받고 첫 행을 꺼낸다. 그리고 **API 응답이 DB 직접 집계와
일치하는지 대조하는 테스트를 상시로** 넣었다 — 서비스가 쓰는 정의를 SQL 로 다시 써서 비교하므로,
둘이 갈라지면 그 자리에서 잡힌다.

### 6-4. 인덱스 — 백로그가 요구한 확인은 "안 넣는 것"으로 끝났다

백로그에 *"집계 쿼리라 인덱스 확인이 함께 필요하다"* 고 적혀 있었다. 실행계획을 봤다:

```
TABLE ACCESS FULL | ORDERS | Rows 1     (전체 25행)
```

**25행에는 full scan 이 최적**이고, 인덱스를 만들면 조회는 안 빨라지면서 INSERT/DELETE 비용만 는다.
→ **넣지 않았다.** 다시 볼 임계치를 백로그에 남겼다 — **주문 수천 건**이 되면 `(status, paid_at)` 검토.

> "확인이 필요하다"를 **"추가가 필요하다"로 읽지 않았다.** 실효 없는 도구를 넣지 않는 것과 같은 판단이다
> (Sentry 보류 · 선착순 쿠폰 보류).

### 6-5. 마이그레이션이 없는 첫 기능이다

`orders`·`order_item` 만으로 다 나왔다. 7/23~24 에 스냅샷(구매자 닉네임·상품명·가격·배송비·쿠폰)을
꼬박꼬박 남겨 둔 것이 여기서 값을 했다.

특히 **`order_item.product_name` 덕에 상품별 집계가 catalog 를 조회하지 않는다** — 도메인 의존이 안 생긴다.
상품명이 바뀌면 같은 상품이 두 이름으로 갈리므로 `product_id` 로 묶고 **가장 최근 결제 건의 이름**을
쓴다(`KEEP DENSE_RANK LAST`).

### 6-8. 배포 · 브라우저 검증 — 통과, 그리고 **차트 hover 가 안 보이던 버그**

배포 확인(OpenAPI 43 → **44**, `/api/admin/stats/sales` · 번들 `index.15e8601a.js` · 미인증 **401**)
후 브라우저 검증에서 화면 값이 DB 와 맞는 것까지 확인했다(전체 60,000원 / 6건, 이번 달 30,000원 / 3건).

**그런데 사용자가 "hover 하면 얼만지 보여줬으면" 이라고 했다.** 이미 넣어 둔 기능이라 곧 버그였다.

```html
<div class="overflow-x-auto">      <!-- 차트 스크롤 컨테이너 -->
  ...
    <span class="absolute -top-6 ...">  <!-- 막대 위 = 컨테이너 바깥 -->
```

**한 축이 `visible` 이 아니면 다른 축도 `auto` 가 된다**(CSS overflow 규칙). `overflow-x-auto` 만 걸었는데
세로도 잘리는 상자가 되어, 막대 위로 띄운 툴팁이 **통째로 안 보였다.**

→ **위치만 고치지 않고 방식을 바꿨다.** 막대 30칸이면 한 칸이 20px 남짓이라 툴팁을 막대에 붙이면
**양끝 칸에서 가로로도 잘린다** — 세로 클리핑을 고쳐도 같은 문제가 반복된다.
값을 **차트 헤더 고정 자리**에 표시하도록 바꿨다. 잘릴 일이 없고 좁은 화면에서도 읽힌다.

곁들여 나온 두 가지:

- **hover 대상을 막대가 아니라 칸 전체로.** 매출 0인 날은 막대 높이가 0이라 막대에만 걸면
  **커서를 올릴 수가 없다.** 낮은 막대도 조준이 어렵다. 터치용으로 `click` 도 같이 받는다.
- **선택 강조를 불투명도로.** 처음엔 `brand-700` 을 쓰려 했는데 이 팔레트에선 그게 **hover 용 더 밝은 색**이라
  (`index.css` 주석: *"검정 버튼은 밝아지는 쪽이 자연스럽다"*) 선택된 막대가 오히려 **흐려진다.**
  평소 70% → 선택 100% 로 갈랐다. **팔레트 이름의 숫자가 항상 "진하기"를 뜻하지는 않는다.**

재배포 후 사용자 확인 완료(번들 **`index.7ad5e8d8.js`** 일치). 매출 없는 빈 칸에도 커서가 먹는다.

> **검증 잔재 0건**: 오늘 생긴 주문 0 · `ZZP` 상품 0 · `ZZ` 주문 0.
> 매출 통계는 **읽기만 하는 기능**이라 검증이 데이터를 만들지 않는다.

## 7. 기능 추가 — 적립금 · 회원 등급 (V21)

백로그 **C-10**. 오늘 다섯 번째 기능이다. `member` 에 관련 필드가 없어 point 도메인을 신설했다.

### 7-1. 적립 시점을 배송완료로 — 회수 로직을 **구조로** 없앴다

착수 전 유일한 큰 결정이었다(사용자 선택). 주문 취소는 `ORDERED`·`PAID` 에서만 되고 `SHIPPED` 이후는
불가하다. 그래서 **`DELIVERED` 에서 적립하면 되돌릴 일이 원천적으로 없다** — 회수 로직도, 회수하다
잔액이 음수가 되는 경우도 다룰 필요가 없다. 실제 커머스의 "구매확정 후 적립" 과 같은 자리다.

> 오늘 V18(§3-3)에서 배운 **"규율이 아니라 구조로 막는다"** 를 그대로 적용한 셈이다.
> "결제 시 적립하고 취소되면 회수하기" 는 규율이고, "되돌릴 수 없는 상태에서만 적립" 은 구조다.

### 7-2. ⚠ 적립을 이벤트로 빼지 않았다 — 유실되면 고객 돈이 사라진다

이벤트 3층 구조가 이미 있으니 배송완료 이벤트에 적립을 얹는 게 자연스러워 보였다. **그러면 안 된다.**

이 프로젝트의 리스너는 `@Async @TransactionalEventListener(AFTER_COMMIT)` 이라 **인프로세스
best-effort** 다 — 유실될 수 있다. 알림이 유실되면 메일 한 통을 놓치지만, **적립이 유실되면
고객의 돈이 사라진다.** 되돌릴 방법도, 유실됐다는 걸 알 방법도 없다.

→ 적립은 `OrderService.deliver()` 안에서 **동기**로 끝내고(같은 트랜잭션, 롤백되면 함께 롤백),
`OrderDeliveredEvent` 는 **결과를 알리는** 용도로만 발행한다.

> 같은 판단이 이미 있었다 — **재고 복원**은 취소 처리의 일부(동기 성공 필수)라 이벤트로 빼지 않았다
> (ARCHITECTURE). 적립금도 같은 쪽이다. 유실 금지를 이벤트로 보장하려면 아웃박스/RabbitMQ 가 필요하고
> 그건 MSA 단계다.

### 7-3. 이력이 원장, 잔액은 캐시

`point_history` 가 원장이고 `point_account.balance` 는 그 합이다. **잔액만 두면 "왜 이 숫자지" 를
따질 수 없는데, 돈에 준하는 값에서 그건 위험하다.** 잔액을 바꾸는 모든 경로가 이력을 함께 남기도록
한 메서드에 묶어, "잔액만 고치고 이력을 빠뜨리는" 코드를 쓸 수 없게 했다.

통합테스트가 매번 `SUM(amount) == balance` 로 대조한다. `amount` 는 **부호 있는 값**이라
(적립 +, 사용 −) 합계를 그냥 SUM 으로 낼 수 있다. 배포 후 운영에서도 실측했다 — 어긋난 계정 0.

### 7-4. 적립 기준액 · 승급 즉시 적용

- **기준액 = 상품합계 − 쿠폰할인 − 사용 적립금.** 배송비는 운임이라 빼고, **적립금으로 낸 부분을
  빼는 이유는 포인트가 포인트를 낳지 않게** 하기 위해서다.
- **적립률은 누적 반영 후 등급으로 계산한다.** 이번 주문으로 승급했으면 그 혜택을 바로 준다 —
  "이번 주문 때문에 올랐는데 적립은 옛 등급" 은 고객에게 설명이 안 된다.
- 금액 계산 순서: **상품합계 → 쿠폰 → 적립금 → 배송비**. 배송비는 여전히 **할인 전** 상품합계 기준이라
  쿠폰·적립금을 써도 안 바뀐다(§13-2 무료배송 판단과 일관).

### 7-5. ⚠ 통합테스트가 설계 결함을 잡았다 — 적립이 주문을 막았다

`OrderFlowIntegrationTest` 가 배송완료 단계에서 404 로 깨졌다. 목 누락이 아니라 **진짜 문제**였다:

> **적립금 계정이 없는 회원의 주문을 배송완료 처리하면 `POINT-404` 로 주문 흐름이 통째로 막혔다.**

계정은 가입 시 만들고 기존 회원은 V21 이 백필하지만, 그 둘을 안 거친 회원이 있을 수 있다
(리포지토리로 직접 만든 테스트 회원 등). **적립은 주문의 부가 결과지 전제 조건이 아니다.**
→ 쓰기 경로(`use`·`earnOnDelivery`)에서는 계정을 **그 자리에서 연다**(읽기 경로는 여전히 저장 안 함).

이건 **테스트가 없었으면 운영에서 터졌을** 종류다 — 계정 없는 회원이 첫 배송완료를 맞는 순간
배송완료 자체가 실패했을 것이다.

### 7-6. 화면

- **마이페이지**: 적립금·등급 카드(잔액·등급·다음 등급까지 남은 금액·최근 이력). 다음 등급까지의
  금액은 **서버가 계산**해 준다 — 화면이 등급 임계값을 몰라도 된다(쿠폰 `discountPreview` 와 같은 판단).
- **주문서**: 적립금 사용 입력(잔액·상한 표시, "전액" 버튼, 결제금액 즉시 반영). 상한은 서버와 같은
  규칙으로 화면이 먼저 막는다.
- **주문 상세**: 사용 적립금(−) · 적립된 금액 표시. **적립 예정 금액은 배송완료 전엔 안 보여준다** —
  예정을 미리 띄우면 취소·반품에서 약속이 어긋난다.

### 7-8. 배포 · 브라우저 검증 — 전 흐름 통과 (사용자 확인)

배포 확인(OpenAPI 44 → **46**, `/api/points/me`·`/me/history` · `OrderCreateRequest.usePoint` ·
`OrderResponse.usedPoint/earnedPoint` · 미인증 **401**) 후 사용자가 **적립→승급→사용까지 전 흐름**을 돌렸다.
DB 이력이 그 자체로 증거다:

```
배송완료 3건 → +800 · +80 · +2,240 (누적 100,000 넘으며 BRONZE→SILVER 승급)
주문 0167    → 3,120 사용, 그 주문 배송완료 시 +97 적립
```

> **§7-4 가 실제로 확인됐다**: 0167 은 8,000원인데 3,120 포인트를 써서 실제 낸 돈이 4,880원이고,
> 적립이 8,000의 2%(160)가 아니라 **4,880의 2%(97)** 로 붙었다 — 포인트가 포인트를 낳지 않았다.
> 잔액도 이력 합과 정확히 일치(정합성 쿼리 0행).

### 7-9. 곁가지 — 송장번호 빈 값 경고가 안 보이던 버그

사용자가 발견했다: 발송 처리에서 송장번호를 비우고 눌러도 빨간 경고가 안 뜬다.

**검증은 돌고 있었다** — `error.value = '송장번호를 입력해 주세요.'`. 문제는 그 `error` 가
페이지 **맨 위** `alert-error` 에 뜨는데, 발송 패널은 상태 탭 **아래**라 스크롤한 상태에서
누르면 경고가 **화면 밖 맨 위**에 떴다. 그래서 아무 일도 안 일어난 것처럼 보였다.

→ 발송 패널 전용 `shipError` 를 두고 **입력칸 바로 아래**에 표시한다. 프론트만 바뀌어 재배포.

> **교훈**: 폼 검증 메시지는 **그 폼 옆**에 띄운다. 페이지 전역 에러 영역은 폼이 스크롤 밖으로
> 나가는 순간 안 보인다. "검증이 없다" 가 아니라 "검증 결과가 안 보인다" 였다.

## 8. 기능 추가 — 상품 옵션 (V22·V23, 오늘 가장 큰 작업)

백로그 **C-8**. "상품 1 = 재고 1" 을 **"상품 1 = 옵션 N, 재고는 옵션마다"** 로 바꿨다.
재고를 다루는 자리가 전부 파급된다 — 오늘 유일하게 여러 도메인(catalog·cart·order)을 관통한 작업이다.

### 8-1. ⚠ "미리 만들지 않는다" 를 의식적으로 어겼다

착수 전에 사용자와 길게 상의했다. **지금 파는 상품(과자 등)엔 옵션이 없다** — ARCHITECTURE §1 은
"요구 없이 만들면 틀린다" 고 옵션 같은 걸 경계한다. 처음엔 C-9(반품)를 권했다(오늘 만든 적립금으로
PG 없이 환불이 되므로 자연스러운 다음 단계였다).

**사용자가 "C-8로 크게 가자" 고 결정했다** — 학습 목적으로 재고 구조 대공사를 실제로 겪어 보려는 것.
원칙의 예외를 의식적으로 선택한 경우라 백로그에 근거를 남겼다.

### 8-2. 설계 결정 — 단일 옵션 목록 + 가격차 (사용자 확정)

| 결정 | 대안 | 왜 |
|---|---|---|
| **단일 옵션 목록** | 구조화된 축(사이즈×색상) | "검정 / M" 을 한 줄로 평판화(SKU 방식). 조합 폭발 없이 대공사를 겪는다 |
| **가격차 허용** | 옵션 가격 동일 | 실제 판매가 = 기본가 + delta. "L +2000" 같은 실제 케이스 |
| **모든 상품이 옵션 ≥1** | 옵션 없는 상품은 product.stock 유지 | 재고가 **항상 옵션에** 있어 갈라 처리할 필요가 없다(구조로 막기, V18 방식) |

### 8-3. 파급 범위 — 재고가 내려가니 전부 따라온다

```
product.stock  →  product_variant.stock          (재고의 집)
cart Redis field: productId → variantId           (담는 단위)
order_item: +variant_id +variant_name             (주문 스냅샷 + 복원 대상)
decreaseStock(productId) → decreaseStock(variantId)  (차감/복원)
ProductResponse.stock → variants[] + totalStock + soldOut
```

화면도 전부: 상품 상세 **옵션 선택 UI**(2개 이상일 때), 관리자 등록/수정 **옵션 편집기**(추가·삭제·재고·가격차),
장바구니·주문상세 **옵션명**, 상품 목록 **품절 배지**(전 옵션 품절 시).

### 8-4. 단일 옵션 상품에 "기본" 노이즈를 안 남긴다

과자처럼 옵션이 하나뿐이면 "기본" 이라는 옵션명이 장바구니·주문에 뜨면 지저분하다.
→ **화면은 옵션이 2개 이상일 때만 선택 UI** 를 보여주고, 서버는 order_item·cart 에 **단일 옵션이면
`variant_name`/`optionName` 을 null 로** 스냅샷한다. 그래서 과자 주문은 옵션 도입 전과 화면이 똑같다.

### 8-5. ⚠ 통합테스트가 잡은 두 가지 (테스트 없었으면 배포 사고)

**① `product.stock` NOT NULL + 기본값 없음 → 신 코드 INSERT 가 ORA-01400.**
V18(주소록)에서 `ship_*` 는 **nullable** 이라 매핑만 걷어내도 됐다. 그런데 `product.stock` 은
**NOT NULL(기본값 없음)** 이라, 매핑을 걷어낸 신 코드가 상품을 INSERT 하며 stock 을 생략하면
**NULL 삽입 불가**로 깨진다. → **V23 으로 `DEFAULT 0`**. 신 jar 는 0 이 채워지고(죽은 컬럼) 구 jar 는 무영향.

> 교훈: **expand/contract 로 컬럼을 죽일 때, NOT NULL 컬럼은 nullable 컬럼과 다르다.**
> 매핑만 걷어내면 되는 게 아니라 DEFAULT 를 줘야 한다. V18 이 nullable 이라 이 함정을 못 봤다.

**② 적용된 V22 의 주석을 고쳐서 FlywayValidateException(체크섬).**
V22 가 espdb 에 적용된 뒤 주석 한 줄("DROP 은 V23")을 고쳤더니 체크섬이 어긋나 앱이 안 떴다.
**"적용된 마이그레이션은 수정 금지"(§2-1)** 를 내가 어겼다. 원복해서 해결.
(그래서 V22 주석은 "DROP 은 V23" 이라 적혀 있지만 V23 은 실제로 stock 기본값 마이그레이션이다 —
컬럼 DROP 은 더 뒤 버전이다. 적용된 파일이라 못 고친다.)

### 8-6. 옛 주문 취소 시 재고 복원

order_item.variant_id 가 **취소 시 복원 대상**이다. 옛 주문(옵션 이전)은 V22 가 각 상품의 기본 옵션으로
백필했다 — 안 하면 "어느 옵션에 복원하지?" 에 답이 없다. **삭제된 상품**의 옛 order_item 은 백필 대상 옵션이
없어 variant_id 가 null 로 남고(실측: 33건 중 10건), 그 취소는 복원을 조용히 건너뛴다(복원할 옵션이 없다).

## 9. 기능 추가 — 반품 · 적립금 환불 (V24)

백로그 **C-9**. 사용자가 "더 하자" 며 이어서 골랐다. **어제까지 "PG 없이는 반쪽"** 이던 게
오늘 오후 적립금(§7)을 만든 덕에 **온전해졌다** — 기능 순서가 값을 한 자리다.

### 9-1. PG 없이 환불 — 적립금이 수단이 됐다

돈을 돌려줄 PG 가 없다. 대신 **결제금액을 적립금으로 환불**한다. 실제 커머스의 "적립금 환불" 과 같고,
오늘 만든 point 도메인이 그대로 환불 창구가 된다. 상태 흐름:

```
DELIVERED → RETURN_REQUESTED → RETURNED   (관리자 승인)
RETURN_REQUESTED → DELIVERED              (거절, 원상복귀)
```

### 9-2. ⚠ 핵심 — 포인트 파밍 구멍을 막았다

반품이 적립금을 건드리므로, **적립을 회수하지 않으면 무한 파밍**이 된다:

> 50,000원 사서 배송완료 → 500 적립. 반품 → 50,000 환불받고 **500 적립도 그대로 챙긴다.**
> 이걸 반복하면 상품을 안 사고도 적립금이 무한정 늘어난다.

→ **환불 = 상품합계 − 쿠폰** 을 주면서, 그 주문의 **배송완료 적립(earned_point)을 회수**한다.
한 번의 **순변동**으로 처리한다:

```
순변동 = 환불액(상품합계−쿠폰) − 적립회수(earned_point)
```

환불액이 적립보다 **항상 크므로**(적립은 그 몇 %) 순변동 ≥ 0 — 잔액이 음수가 될 일이 없고,
**적립분은 순이득으로 남지 않는다.** 통합테스트가 정확히 이걸 고정한다:
*"사서 적립받고 반품해도 잔액은 환불액과 같다(적립 500이 위로 안 쌓임 — 파밍이면 50,500)."*

### 9-3. 등급도 되돌린다 — "샀다 반품하면 등급만 남는" 것 방지

배송완료 때 누적 구매확정액에 더했으니, 반품하면 **빼고 등급을 재산정**한다(강등 가능).
안 그러면 큰 걸 사서 등급 올리고 반품해 등급만 남기는 우회로가 생긴다.
**환불·적립회수·등급 재산정·재고 복원이 한 트랜잭션** — 함께 커밋되거나 함께 롤백된다.

### 9-4. 무엇을 환불하고 무엇을 안 하나

| | |
|---|---|
| **환불** | 상품합계 − 쿠폰할인 (사용했던 적립금 + 현금분을 한꺼번에 적립금으로) |
| **환불 안 함** | 배송비 — 운임은 이미 소진됐다(실제 커머스와 같다) |
| **회수** | 배송완료 적립 · 누적 구매확정액(등급) |
| **복원** | 옵션 재고(취소와 동일 — 옵션 단위, C-8 위) |

### 9-5. 상태 가드 · 권한

- 배송완료(DELIVERED)만 반품 **요청** 가능, 요청(RETURN_REQUESTED)만 **승인/거절** 가능 — 상태 전이가
  꼬이지 않게 엔티티 메서드가 가드한다(각 단계 통합테스트로 고정).
- 요청은 **본인 주문만**(findByIdAndMemberId), 승인/거절은 **관리자만** — `/api/orders/*/return-approve`·
  `/return-reject` 를 SecurityConfig 매처로 막는다(ship·deliver 와 같은 방식, §2-4 규약).

### 9-6. 마이그레이션 (V24)

`orders` 에 `return_reason`·`return_requested_at`·`returned_at`(전부 nullable, 기존 주문은 NULL 이 사실).
**CHECK 두 개를 갱신** — `ck_orders_status` 에 RETURN_REQUESTED·RETURNED, `ck_point_history_type` 에 REFUND.
둘 다 **이름이 붙어 있어**(V13·V21) DROP/ADD 두 줄이면 된다 — 자동 생성 이름을 PL/SQL 로 찾던 옛 방식이 필요 없다.
"CHECK 에 처음부터 이름을 붙인다" 규칙이 오늘 두 번째로 값을 했다.

### 9-8. 배포 · 브라우저 검증 — 통과 (사용자 확인)

배포 후 사용자가 주문→배송완료→반품 요청→관리자 승인→환불 확인까지 관통했다.
"환불이 제대로 됐나" 를 함께 확인했는데, DB 이력이 규칙 그대로였다:

```
주문 20260724-0245: 8,000원 · 배송완료 적립 160(SILVER 2%)
반품 환불 = 8,000(상품합계−쿠폰) − 160(적립 회수) = 순 +7,840
point_history: REFUND +7,840 "반품 환불 8000 (적립 160 회수)"
```

> **사용자가 헷갈린 지점**: "8,000 반품인데 왜 잔액은 7,840만?" → **의도한 동작**이다.
> 8,000은 다 돌려줬고, 배송완료 때 준 적립 160을 회수했기 때문에 순증가가 7,840이다.
> 160을 안 뺐다면 "공짜 적립 160" — 그게 막으려던 파밍이다(§9-2). "산 값은 온전히 환불, 보상은 무효".

> **검증 잔재 정리 종결**: 오늘 주문 11건 전부 종결(취소 5·배송완료 5·반품 1) — 미완 0.
> `ZZP` 상품은 화면에서 삭제(옵션도 FK CASCADE 로 함께 삭제, 고아 옵션 0 실측).
> **잔액==이력합 정합성** 어긋난 계정 0(반품 환불 포함).

### 10-1. ⚠ 인기(판매량)순 — avgRating 비정규화(V4)를 그대로 답습했다

「인기순」의 진짜 문제는 **판매량이 order 소유 사실인데 정렬은 catalog 목록에서 일어난다**는 것이다.
catalog 가 order 를 직접 조회하면 order→catalog(이미 존재) + catalog→order = **순환**이 생겨 MSA 분리가 막힌다.

이 코드베이스는 **똑같은 문제를 이미 풀어 뒀다** — 리뷰 별점(avgRating, V4)이다. review 가 이벤트를 밀어넣고
catalog 가 받아 `product.avg_rating` 에 **비정규화**한다(catalog 는 review 를 조회 안 함 = 순환 없음).
판매량도 문자 그대로 같은 방식으로 풀었다:

- **V25** — `product.sold_count NUMBER DEFAULT 0 NOT NULL` + 백필(취소·반품 아닌 주문의 수량 합).
- **이벤트** — 주문됨(`OrderPlacedEvent`) **+**, 취소(`OrderCancelledEvent`) **−**, 반품승인(**신설** `OrderReturnedEvent`) **−**.
  세 이벤트에 상품별 수량(`List<SoldLine>`)을 실었다. `SoldLine.from(order)` 가 **상품 단위로 합산**한다
  (같은 상품의 여러 옵션을 함께 사면 한 줄로 합쳐져야 인기순이 맞다).
- **구독** — catalog `SalesEventListener`→`SalesSyncHandler`(별점 리스너/핸들러와 같은 3층 규약).
  `products:list` 캐시도 여기서 evict(별점과 동일).
- **정렬** — `SORTABLE` 에 `soldCount` 한 줄 추가 → 인기순 = `GET /api/products?sort=soldCount,desc`.
  **새 엔드포인트 없음** — 기존 검색·정렬·캐시를 그대로 재사용한다.

집계 정의는 매출통계(§6)와 미묘하게 다르다: **매출은 PAID 부터**(돈이 들어온 것)지만, 인기는 **주문(ORDERED)부터** 센다
(수요 신호라 결제 전 주문도 인기에 반영). `@Async` best-effort라 근사값이지만 — 인기 랭킹이라 별점과 같이 허용 오차다.
`addSoldCount` 는 CASE 로 **0 밑으로 안 내려가게** 막았다(이벤트 유실·중복 시 음수 방지, 잔액 CHECK 와 같은 방어선).

## 11. 기능 추가 — 인앱 알림 시스템 (V26, SSE) — ⚠ 배포 전

> B-9 재입고 알림을 논의하다 **알림 시스템 자체가 없다**는 걸 확인하고(핸들러가 전부 로그 stub) 먼저 지었다.
> 사용자가 **자체 개발(FCM 아님) + SSE 즉시 푸시 + 알림 끄기 설정**으로 스코프를 정했다.

### 11-1. 왜 FCM 이 아니라 자체 SSE 인가

FCM/웹푸시는 **탭이 닫혀도** 보내려는 것(모바일 백그라운드) — 외부 서비스(Firebase)·서비스워커·VAPID 가 필요해
"외부 의존 없음/LAN" 원칙과 정면 충돌한다. 우리가 원하는 건 **사이트를 보는 동안** 뜨는 인앱 알림(벨+토스트)이고,
그건 **서버가 열린 페이지에 알려주기만** 하면 된다 → 자체 SSE 가 정답이다(WebSocket 은 양방향이라 과함).

### 11-2. 구조 — stub 을 진짜로

`notification` 도메인의 핸들러 4개가 전부 **로그 stub** 이었다(주문·재고 이벤트는 이미 날아오고 있었다).
그 재료 위에 저장+표시를 얹었다:
- **V26**: `notification`(회원·타입·제목·내용·link·is_read) + `member_notification_pref`(타입별 on/off, opt-out).
- **생성**: `NotificationCommandService.create()` 가 유일한 입구. **stub 핸들러가 이걸 호출** →
  주문 이벤트(생성·배송·취소)→**구매자** 알림, 재고부족→**관리자 전원**(`MemberService.adminIds()` 신설, member 공개 API).
  ⚠ 설정에서 그 타입을 껐으면 **만들지 않는다**(opt-out, 행 없으면 켜짐).
- **알림함 API**: 목록(페이징)·안읽음수·읽음·**모두 읽음**·설정 조회/변경. `NotificationType`(ORDER·STOCK) = 설정 단위.

### 11-3. SSE — 인증이 관건이었다

- 서버: `NotificationStream`(회원별 `SseEmitter` 레지스트리) — 생성 시 push, `@Scheduled(15s)` 하트비트로
  유휴 연결 유지, onCompletion/timeout/error 정리. 페이로드가 알림 전체라 클라는 **재조회 없이** 목록·토스트에 넣는다.
- ⚠ **인증**: 브라우저 기본 `EventSource` 는 Authorization 헤더를 못 실어 우리 JWT(로컬스토리지)와 안 맞는다.
  그래서 프론트가 **fetch + ReadableStream** 으로 직접 열고 Bearer 를 실었다(토큰 URL 노출 회피). 재연결은 백오프로 직접.
- ⚠ **nginx**: `/api/notifications/stream` 은 **`proxy_buffering off` + 긴 `proxy_read_timeout`** 이 필요하다
  (기본 버퍼링이면 이벤트가 뭉쳐 즉시 안 나간다). sudo 라 사용자가 적용한다(아래 이월에 conf 블록).
  안 해도 알림은 DB 에 남아 **벨/뱃지는 새로고침·재접속 때 보인다** — 토스트(즉시성)만 안 뜬다(우아한 열화).

### 11-4. 프론트

- `stores/notifications.js` — 상태(items·unread) + SSE(fetch 스트림·재연결) + 낙관적 읽음. 로그인 시 연결, 로그아웃 시 끊고 비움.
- `NotificationBell`(헤더, 뱃지+드롭다운) · `NotificationToaster`(오른쪽 위 슬라이드, 5초 자동) ·
  `/notifications` 전체 페이지 · `NotificationSettings`(마이페이지 타입별 토글).

### 11-5. 검증

- 백엔드: 단위 5(생성 pref 체크·SSE push·읽음 소유권·설정 upsert·기본값 채움). 전체 컴파일·테스트 **BUILD SUCCESSFUL**.
- 프론트: 스토어 테스트 4(낙관적 읽음·모두읽음·disconnect) 추가 → **98 통과**, `pnpm build` 성공.

### 11-6. ⚠ 배포 직후 사고 — 감사 컬럼 타임존 (V27)

배포·nginx·토스트까지 갔는데 **알림 조회가 500** 났다. 원인: **V26 이 `created_at`/`updated_at` 을 plain
`TIMESTAMP(6)`** 로 만들었다 — 기존 모든 테이블·`BaseTimeEntity`(Instant)는 **`TIMESTAMP(9) WITH TIME ZONE`** 인데.
plain TIMESTAMP 를 Instant 로 **읽을 때** `ORA-18716("시간대에 없습니다")` 가 난다. **`ddl-auto=validate` 가 TZ 유무를
안 잡아** 앱은 정상 기동하고, 읽기에서만 터져 배포 후에야 드러났다(라이브 DB `user_tab_columns` 로 확인).
- **고침 V27**: `TRUNCATE`(검증분 폐기) 후 `ALTER … MODIFY (… TIMESTAMP(9) WITH TIME ZONE)`. V26 은 적용됨(체크섬)이라 수정 금지.
- **교훈 → 메모리·규약**: 새 테이블 감사 컬럼은 **반드시 `TIMESTAMP(9) WITH TIME ZONE`**. validate 를 믿지 말 것.

### 11-7. ⚠ 재배포 후 또 나온 두 가지 (SSE 인가 · 설정 경합)

V27 재배포 뒤 로그에서 두 개 더 나왔다:
- **SSE async 인가** (`Access Denied` + "response already committed"): `SseEmitter` 는 스트리밍 후 **ASYNC 디스패치**로
  마무리되는데, 무상태(JWT)라 그 디스패치엔 SecurityContext 가 없어 `AuthorizationFilter` 가 거부한다.
  → **`SecurityConfig` 에 `.dispatcherTypeMatchers(DispatcherType.ASYNC, DispatcherType.ERROR).permitAll()`**(스프링 공식 해법).
- **설정 토글 유니크 위반** (`ORA-00001` `UQ_MEMBER_NOTIF_PREF`): `changeSetting` 이 find→insert 라, 같은 (member,type)
  **빠른 연속 토글**이 둘 다 "없음"으로 읽고 각자 INSERT → 충돌. → **UPDATE 먼저, 0행이면 INSERT** 로 바꿔 재토글은
  순수 UPDATE(경합 없음). 화면도 **요청 중 토글 잠금**(더블클릭 방지)으로 최초 동시삽입까지 막는다.
- **⚠ 재배포 필요**: 이 둘 반영에 백엔드+프론트 다시 배포. (마이그레이션 없음 — V27 이 마지막.)
