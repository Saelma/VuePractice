## 3. 구현 (커밋 `2326109`)

두 건 다 **고치는 것 자체는 한 줄**이었다. 문제는 **같은 모양이 다시 생기는 것**이라, 거기에 시간을 썼다.

### 3-1. ① 판정을 **상태를 만드는 사람의 눈앞**으로 옮겼다

리포지토리 주석에는 이미 *"새 상태는 여기 직접 추가하도록 opt-in 으로 둔다"* 라고 **의도가 적혀 있었다.**
그런데 **두 번 다 안 지켜졌다**(2026-07-20 에 한 번, 2026-07-23 V13 에 또). 의도가 틀린 게 아니라
**그 약속을 지킬 계기가 열거 쪽에 없었다** — 상태를 추가하는 사람은 `OrderStatus.java` 만 연다.

→ 판정을 `OrderStatus.isPurchaseProven()` 으로 옮기고 **`default` 없는 switch** 로 썼다:

```java
return switch (this) {
    case ORDERED, PAID, SHIPPED, DELIVERED -> true;
    case CANCELLED, RETURN_REQUESTED, RETURNED -> false;
};
```

값을 추가하면 *"the switch expression does not cover all possible input values"* 로 **컴파일이 깨진다**(§4 M7 실측).
**규율로 두 번 못 지킨 것을 컴파일러에 넘겼다.**

⚠ 리포지토리는 `existsPurchaseIn(…, Set<OrderStatus>)` + 기본 메서드 `existsPurchase(…)` 로 나눴다 —
**「구매함」의 기준을 호출부가 고르지 못하게** 한다(고를 수 있으면 두 번째 기준이 생긴다).

### 3-2. ② 판정 함수 하나로 모았다 — **WA 를 새로 쓰지 않았다**

08-10 §16-3-1 이 못 박은 대로다: *"필요한 건 규약이 아니라 함수다"*(WA §2-3 이 이미 그 규약인데
2026-07-28 ~ 08-11 동안 어긋나 있었다).

- `Role.isAdmin()` — 판정의 원본. 프론트 `isAdminRole`(`stores/auth.js:15`)의 짝.
- `AuthUser.isAdmin()` — principal 쪽 짝. `role` 이 null 이어도 안 터진다.
- `Role.adminRoles()` — **쿼리로 물어야 할 때**의 같은 경계.

| 자리 | 전 | 후 |
|---|---|---|
| `OrderService:203` | `user.role() == Role.ADMIN` | `user.isAdmin()` |
| `ReviewCommandService:133` · `NoticeCommandService:63` · `InquiryCommandService:111` | 〃 | 〃 |
| `InquiryResponse:41` | `viewer.role() == Role.ADMIN` | `viewer.isAdmin()` |
| `MemberService:52` | `findIdsByRole(Role.ADMIN)` | `findIdsByRoleIn(Role.adminRoles())` |

⚠ **`MemberAdminCommandService:130` 은 그대로 뒀다.** `target.getRole() == Role.ADMIN` 은
«대상이 ADMIN 이면 SUPER 만 건드린다» 라 **의도대로**다(이월의 「일괄 치환 금지」).

⚠ 여섯째 자리는 비교가 아니라 **쿼리**라 리포지토리까지 갔다. `findIdsByRole`(단수)를 남겨 두면
호출부가 또 역할을 하나만 고를 수 있어 **메서드째 목록형으로 바꿨다.**

### 3-3. 🔴 ①의 테스트도 **같이 어긋나 있었다** — 그래서 모양을 바꿨다

`OrderRepositoryIntegrationTest` 는 **2026-07-16 사고를 막으려고 만든 것인데**, 상태 4개를 손으로 적은
메서드 4개였다 — **막으려던 코드와 정확히 같은 모양**이라 `DELIVERED` 가 생겼을 때 **나란히** 안 자랐다.

→ 상태를 테스트에 적지 않는다. `@EnumSource(OrderStatus.class)` 가 통째로 돌고, 기대값은
`isPurchaseProven()` 에서 받는다. 상태 만드는 법도 **`default` 없는 switch** 라 값이 늘면 같이 깨진다.

⚠ **그런데 전수 테스트만으로는 부족하다.** 「쿼리가 정책과 일치한다」만 보므로 **둘이 같이 틀리면 통과한다** —
§4 의 M1 이 그 실증이다. 그래서 «정책 자체» 를 보는 테스트(`policy_hasBothSides`)를 따로 뒀고,
**M1 을 잡은 것은 그쪽**이었다.

### 3-4. ②는 **자리마다의 테스트로는 못 막는다** — 소스를 훑는다

사고는 «어느 서비스가 틀렸다» 가 아니라 **«같은 판단이 여섯 군데에 복사돼 있었다»** 였다.
각 서비스 테스트를 아무리 잘 써도 **일곱 번째가 새로 생기는 것**은 못 잡는다.

→ `AdminRoleBoundaryTest` 가 `src/main` 을 훑어 **행위자 쪽 `== Role.ADMIN`** 을 찾는다.
actor 와 target 을 가르는 것은 **접근자 이름**이다: `AuthUser.role()` ↔ `Member.getRole()`.
그래서 «의도대로인 자리» 를 오탐 없이 비껴간다(§4 M5 로 확인).

⚠ 이 테스트에 **「0건」 방어**를 넣었다(WA §3-3). 작업 디렉터리가 달라 한 파일도 못 읽으면
**아무것도 검사하지 않고 초록**이 되므로, 훑은 파일 수도 함께 못 박는다.

사용자가 *"브라우저 테스트하니까 잘 된 것 같아"* 라고 했을 때 **무엇이 확인됐는지 갈랐다**:

| | 흔적 | 내가 판정할 수 있나 |
|---|---|---|
| 주문 상세 조회 · 문의 마스킹 | **로그도 DB 도 안 남는다**(조회라 `log.info` 가 없다) | ❌ — 물어봐야 안다 |
| 리뷰 작성 | `Review created` 로그 + `review` 행 | ✅ — **오늘 0건** |
| 관리자 삭제·숨김 | 감사 이력 | ✅ — **오늘 0건** |

→ **자국이 남는 둘이 0이라 «전부 잘 됐다» 가 성립하지 않았다.** 물어보니 실제로 읽기 셋만 봤던 것이다.
⚠ 08-07 §9-2 가 **로그 0건을 통과로 적은** 사고였다. 이번엔 반대로 **0건을 근거로 되물었다.**

### 7-3. 🔴 ① 은 **운영에서 밟을 표본이 하나도 없다** — 이월의 「3조합」은 틀린 안내였다

§1-1 에서 «막힌 3조합» 을 세어 이월에 브라우저 스텝으로 적었는데, **조합만 세고 그게 실제로
리뷰를 쓸 수 있는 자리인지는 안 봤다.** 사용자가 *"반팔티는 산 적 있는디, 몽쉘들은 삭제된 상품인디"*
라고 되물어 드러났다:

| 조합 | 왜 못 밟나 |
|---|---|
| ZZP-전설의 몽쉘 · ZZP-야생의 몽쉘 | **상품행이 없다**(삭제됨) → `ProductQueryService.ensureExists` 에서 막힌다 |
| 반팔티 | 상품은 `SELLING` 이지만 **김기현팀이 07-24 07:25 에 이미 리뷰를 썼다** → `DUPLICATE_REVIEW` |

⚠ **리뷰를 이미 썼다는 것이 곧 그때는 안 막혔다는 뜻이다** — 07-24 07:23 주문 → 07:25 리뷰라
`SHIPPED` 이전에 썼다. 즉 **막히는 창(배송완료 이후)에 들어가기 전에 쓴 것**이고,
§16-2 가 *"손으로 눌러 보는 검증에서는 통과한다"* 고 한 그 성질이 **실제 데이터로 확인된 셈**이다.

→ **밟지 않기로 했다**(2026-08-11, 사용자 결정). 대상을 만들려면 새 주문을 **발송**까지 보내야 하는데
발송은 되돌릴 수 없고(WA §3) 검증 잔재도 남는다. 기존 리뷰를 지우는 것도 진짜 데이터를 지우는 일이다.
**코드·테스트로는 닫혔으므로**(전수 테스트 + 변형 M1·M2·M7) **「고쳤는데 밟을 대상이 없다」로 남긴다.**

⚠ 오늘 이 모양이 **셋**이다: ①(리뷰) · 재고 알림 · 08-10 §13-2(탈퇴 회원 관리자 조작).
**세 번째가 되면 성질을 봐야 한다** → §7-4.

### 7-4. ⚠ 「밟을 대상이 없다」가 쌓이는 이유

셋 다 **정상 흐름의 끝자락**이다 — 배송완료 후, 재고가 임계 아래로, 탈퇴 후. 운영 데이터가
그 상태로 자연히 가려면 시간이 걸리고, **일부러 만들면 되돌릴 수 없다.**
⚠ 이건 «검증을 게을리했다» 가 아니라 **이 프로젝트의 검증이 닿지 않는 영역**이라는 뜻이다.
지금은 통합 테스트가 그 자리를 대신하고 있고(실제 Oracle 대상), 그게 유일한 근거다.
→ 규약으로 올릴 만한 것이 있는지는 **표본이 더 쌓인 뒤에** 본다(문서 한 줄로 규약을 신설하지 않는다).

10. **관리자가 대신 취소한 주문이 생겼다**(2026-08-10, B-25 검증 — 8/10 §9-1).
    `20260727-0291` · `20260727-0258`(둘 다 `김기현팀`) · `20260724-0250`(**`김기현팀2`**).
    ⚠ **7번과 성격이 같다** — 주문이므로 매출에 얽히고 `ZZ` 가 붙어 세는 쿼리에 잡힌다. **다시 들추지 말 것.**
    ⚠ 따로 적는 이유: 이 셋은 **`cancel_reason` 에 검증용 문구**(*"그냥 하고싶어씀"*·*"123213"* 등)가
    남았고 **`cancelled_by_name` 이 채워진 첫 행들**이다. 나중에 «관리자 취소가 실제로 어떻게
    남는가» 를 볼 표본이 필요하면 여기다.
