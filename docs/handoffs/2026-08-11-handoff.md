### 1-1. 🔴 이월의 「8건」은 **단위가 섞여 있었다**

이월은 *"운영에서 (회원,상품) **8조합**이 실제로 막혀 있다"* 라고 적혀 있었다. 세어 보니 **아니다**:

```sql
select count(*) from (
  select distinct o.member_id, oi.product_id from orders o join order_item oi on oi.order_id=o.id
  where o.status='DELIVERED'
  minus
  select distinct o.member_id, oi.product_id from orders o join order_item oi on oi.order_id=o.id
  where o.status in ('ORDERED','PAID','SHIPPED'));
```

| | 이월 | 실측(2026-08-11) |
|---|---|---|
| 막힌 것 | 「(회원,상품) 8조합」 | **주문행 8 · 조합 5** — 8 은 조합이 아니라 **행** 수였다 |
| 그중 회원행이 있는 것 | — | **3조합**(전부 `김기현팀`) |
| 회원행이 **없는** 것 | — | **2조합** — `20260728-0478`, §13-2 의 그 탈퇴 회원 |

⚠ **탈퇴 회원은 애초에 리뷰를 못 쓴다.** 그러니 *"지금 고객 8명이 리뷰를 못 쓰는 상태"* 는
정확히는 **한 계정의 3조합**이다. 고칠 이유는 그대로지만 **미루는 비용은 이월이 적은 것보다 작았다.**

> 🔴 **그런데 이 「3조합」도 브라우저 스텝으로는 못 쓴다 — §7-3 에서 다시 갈렸다.**
> 여기서 센 것은 **조합**이고, 「밟을 수 있는 자리」는 *상품이 아직 있는가* · *이미 리뷰를 썼는가* 까지

> 5로 고치면서 «이제 정확하다» 고 여겼는데, 세는 **대상**이 틀린 것은 그대로였다.

> ⚠ 어디서 갈렸나: 08-10 §16-2 는 막힌 것을 **주문번호로 열거**했고(`-0167`/`-0166`/… 처럼 같은 상품이

## 3. 구현 (커밋 `2326109`)

두 건 다 **고치는 것 자체는 한 줄**이었다. 문제는 **같은 모양이 다시 생기는 것**이라, 거기에 시간을 썼다.

### 3-1. ① 판정을 **상태를 만드는 사람의 눈앞**으로 옮겼다

리포지토리 주석에는 이미 *"새 상태는 여기 직접 추가하도록 opt-in 으로 둔다"* 라고 **의도가 적혀 있었다.**
그런데 **두 번 다 안 지켜졌다**(2026-07-20 에 한 번, 2026-07-23 V13 에 또). 의도가 틀린 게 아니라
**그 약속을 지킬 계기가 열거 쪽에 없었다** — 상태를 추가하는 사람은 `OrderStatus.java` 만 연다.

→ 판정을 `OrderStatus.isPurchaseProven()` 으로 옮기고 **`default` 없는 switch** 로 썼다:

```java
return switch (this) {
    case ORDERED, PAID, SHIPPED, DELIVERED -> true;
    case CANCELLED, RETURN_REQUESTED, RETURNED -> false;
};
```

값을 추가하면 *"the switch expression does not cover all possible input values"* 로 **컴파일이 깨진다**(§4 M7 실측).
**규율로 두 번 못 지킨 것을 컴파일러에 넘겼다.**

⚠ 리포지토리는 `existsPurchaseIn(…, Set<OrderStatus>)` + 기본 메서드 `existsPurchase(…)` 로 나눴다 —
**「구매함」의 기준을 호출부가 고르지 못하게** 한다(고를 수 있으면 두 번째 기준이 생긴다).

### 3-2. ② 판정 함수 하나로 모았다 — **WA 를 새로 쓰지 않았다**

08-10 §16-3-1 이 못 박은 대로다: *"필요한 건 규약이 아니라 함수다"*(WA §2-3 이 이미 그 규약인데
2026-07-28 ~ 08-11 동안 어긋나 있었다).

- `Role.isAdmin()` — 판정의 원본. 프론트 `isAdminRole`(`stores/auth.js:15`)의 짝.
- `AuthUser.isAdmin()` — principal 쪽 짝. `role` 이 null 이어도 안 터진다.
- `Role.adminRoles()` — **쿼리로 물어야 할 때**의 같은 경계.

| 자리 | 전 | 후 |
|---|---|---|
| `OrderService:203` | `user.role() == Role.ADMIN` | `user.isAdmin()` |
| `ReviewCommandService:133` · `NoticeCommandService:63` · `InquiryCommandService:111` | 〃 | 〃 |
| `InquiryResponse:41` | `viewer.role() == Role.ADMIN` | `viewer.isAdmin()` |
| `MemberService:52` | `findIdsByRole(Role.ADMIN)` | `findIdsByRoleIn(Role.adminRoles())` |

⚠ **`MemberAdminCommandService:130` 은 그대로 뒀다.** `target.getRole() == Role.ADMIN` 은
«대상이 ADMIN 이면 SUPER 만 건드린다» 라 **의도대로**다(이월의 「일괄 치환 금지」).

⚠ 여섯째 자리는 비교가 아니라 **쿼리**라 리포지토리까지 갔다. `findIdsByRole`(단수)를 남겨 두면
호출부가 또 역할을 하나만 고를 수 있어 **메서드째 목록형으로 바꿨다.**

### 3-3. 🔴 ①의 테스트도 **같이 어긋나 있었다** — 그래서 모양을 바꿨다

`OrderRepositoryIntegrationTest` 는 **2026-07-16 사고를 막으려고 만든 것인데**, 상태 4개를 손으로 적은
메서드 4개였다 — **막으려던 코드와 정확히 같은 모양**이라 `DELIVERED` 가 생겼을 때 **나란히** 안 자랐다.

→ 상태를 테스트에 적지 않는다. `@EnumSource(OrderStatus.class)` 가 통째로 돌고, 기대값은
`isPurchaseProven()` 에서 받는다. 상태 만드는 법도 **`default` 없는 switch** 라 값이 늘면 같이 깨진다.

⚠ **그런데 전수 테스트만으로는 부족하다.** 「쿼리가 정책과 일치한다」만 보므로 **둘이 같이 틀리면 통과한다** —
§4 의 M1 이 그 실증이다. 그래서 «정책 자체» 를 보는 테스트(`policy_hasBothSides`)를 따로 뒀고,
**M1 을 잡은 것은 그쪽**이었다.

### 3-4. ②는 **자리마다의 테스트로는 못 막는다** — 소스를 훑는다

사고는 «어느 서비스가 틀렸다» 가 아니라 **«같은 판단이 여섯 군데에 복사돼 있었다»** 였다.
각 서비스 테스트를 아무리 잘 써도 **일곱 번째가 새로 생기는 것**은 못 잡는다.

→ `AdminRoleBoundaryTest` 가 `src/main` 을 훑어 **행위자 쪽 `== Role.ADMIN`** 을 찾는다.
actor 와 target 을 가르는 것은 **접근자 이름**이다: `AuthUser.role()` ↔ `Member.getRole()`.
그래서 «의도대로인 자리» 를 오탐 없이 비껴간다(§4 M5 로 확인).

⚠ 이 테스트에 **「0건」 방어**를 넣었다(WA §3-3). 작업 디렉터리가 달라 한 파일도 못 읽으면
**아무것도 검사하지 않고 초록**이 되므로, 훑은 파일 수도 함께 못 박는다.

### 4-1. 🔴 M3a — **감시 테스트가 되돌린 버그를 통과시켰다** (커밋 `4ce7cbb`)

## 7. 브라우저 검증 — ② **종결** · ① **밟을 대상이 없다**

### 7-1. ② 는 닫혔다 (사용자 브라우저)

| 확인 | 결과 |
|---|---|
| SUPER_ADMIN 으로 **남의** 주문 상세 | 열렸다 (고치기 전 404) |
| 비밀 문의가 SUPER 에게 **안 가려진다** | 확인됨 (`InquiryResponse:41`) |
| 관리자 화면 전반 | 회귀 없음 |

⚠ 남의 리뷰·공지·문의 **삭제**는 안 밟았다 — 감사 이력 오늘 **0건**이 그 증거다.
같은 판정 함수를 타므로 위 셋과 갈릴 이유는 없지만, **밟은 것과 안 밟은 것을 섞어 적지 않는다.**

### 7-2. 🔴 «잘 된 것 같다» 를 그대로 적지 않았다 — **읽기 동작은 자국을 안 남긴다**

사용자가 *"브라우저 테스트하니까 잘 된 것 같아"* 라고 했을 때 **무엇이 확인됐는지 갈랐다**:

| | 흔적 | 내가 판정할 수 있나 |
|---|---|---|
| 주문 상세 조회 · 문의 마스킹 | **로그도 DB 도 안 남는다**(조회라 `log.info` 가 없다) | ❌ — 물어봐야 안다 |
| 리뷰 작성 | `Review created` 로그 + `review` 행 | ✅ — **오늘 0건** |
| 관리자 삭제·숨김 | 감사 이력 | ✅ — **오늘 0건** |

→ **자국이 남는 둘이 0이라 «전부 잘 됐다» 가 성립하지 않았다.** 물어보니 실제로 읽기 셋만 봤던 것이다.
⚠ 08-07 §9-2 가 **로그 0건을 통과로 적은** 사고였다. 이번엔 반대로 **0건을 근거로 되물었다.**

### 7-3. 🔴 ① 은 **운영에서 밟을 표본이 하나도 없다** — 이월의 「3조합」은 틀린 안내였다

§1-1 에서 «막힌 3조합» 을 세어 이월에 브라우저 스텝으로 적었는데, **조합만 세고 그게 실제로
리뷰를 쓸 수 있는 자리인지는 안 봤다.** 사용자가 *"반팔티는 산 적 있는디, 몽쉘들은 삭제된 상품인디"*
라고 되물어 드러났다:

| 조합 | 왜 못 밟나 |
|---|---|
| ZZP-전설의 몽쉘 · ZZP-야생의 몽쉘 | **상품행이 없다**(삭제됨) → `ProductQueryService.ensureExists` 에서 막힌다 |
| 반팔티 | 상품은 `SELLING` 이지만 **김기현팀이 07-24 07:25 에 이미 리뷰를 썼다** → `DUPLICATE_REVIEW` |

⚠ **리뷰를 이미 썼다는 것이 곧 그때는 안 막혔다는 뜻이다** — 07-24 07:23 주문 → 07:25 리뷰라
`SHIPPED` 이전에 썼다. 즉 **막히는 창(배송완료 이후)에 들어가기 전에 쓴 것**이고,
§16-2 가 *"손으로 눌러 보는 검증에서는 통과한다"* 고 한 그 성질이 **실제 데이터로 확인된 셈**이다.

→ **밟지 않기로 했다**(2026-08-11, 사용자 결정). 대상을 만들려면 새 주문을 **발송**까지 보내야 하는데
발송은 되돌릴 수 없고(WA §3) 검증 잔재도 남는다. 기존 리뷰를 지우는 것도 진짜 데이터를 지우는 일이다.
**코드·테스트로는 닫혔으므로**(전수 테스트 + 변형 M1·M2·M7) **「고쳤는데 밟을 대상이 없다」로 남긴다.**

⚠ 오늘 이 모양이 **넷**이 됐다: ①(리뷰) · 재고 알림 · 08-10 §13-2(탈퇴 회원 관리자 조작) ·
⑤(탈퇴 시 장바구니, §11-5). **세 번째가 되면 성질을 봐야 한다** → §7-4.

### 7-4. ⚠ 「밟을 대상이 없다」가 쌓이는 이유 (⚠ 하루 끝에 **넷**이 됐다)

| 항목 | 기다리는 조건 | 왜 못 만드나 |
|---|---|---|
| ①(배송완료 리뷰) | 배송완료 + 미작성 + 상품 생존 | 발송이 **되돌릴 수 없다**(WA §3) |
| 재고 알림(§3-2 여섯째) | 재고가 임계 아래로 | 운영 재고를 일부러 못 낮춘다 |
| 08-10 §13-2(탈퇴 회원 관리자 조작) | 탈퇴 회원의 `ORDERED`·`PAID` 주문 | 탈퇴가 **되돌릴 수 없다**(WA §2-6) |
| ⑤(탈퇴 시 장바구니, §11-5) | 실제 탈퇴 | 〃 |

넷 다 **정상 흐름의 끝자락**이다 — 배송완료 후, 재고 소진, 탈퇴 후. 운영 데이터가 그 상태로
자연히 가려면 시간이 걸리고, **일부러 만들면 되돌릴 수 없다.**
⚠ 이건 «검증을 게을리했다» 가 아니라 **이 프로젝트의 검증이 닿지 않는 영역**이라는 뜻이다.
지금은 통합 테스트가 그 자리를 대신하고 있고(실제 Oracle·Redis 대상), 그게 유일한 근거다.

⚠ **아래 둘은 같은 조건(실제 탈퇴)을 기다린다** — 08-10 §13-2 와 ⑤. **그때 함께 밟을 것.**
그러면 «되돌릴 수 없는 조작 한 번» 으로 **두 항목이 닫힌다.**
→ 규약으로 올릴 만한 것이 있는지는 **표본이 더 쌓인 뒤에** 본다(문서 한 줄로 규약을 신설하지 않는다).
⚠ 다만 **묶어서 밟는다** 는 것 자체는 오늘 얻은 것이라 이월에 적었다 — 조건이 같은 항목끼리
모아 두지 않으면, 탈퇴가 일어났을 때 **한쪽만 확인하고 지나간다.**

## 8. Fable 감사 3번 — **취소해도 쿠폰이 안 돌아왔다** (커밋 대기)

08-10 §16-4 가 «의심됨» 으로만 적어 둔 여섯 건 중 3번. 오늘 §1-1·§7-3 에서 두 번이나 **세는 대상이
틀렸던** 뒤라, 에이전트 확신도를 옮기지 않고 **코드와 DB 를 직접 봤다.**

### 8-1. 확인 — 「의심됨」이 아니라 **확실**이다. 다만 모양이 다르다

`applyCancellation` 이 취소 뒤에 따라오는 일을 모아 둔 자리인데:

```java
increaseStock(...)                 // 재고 ✅
pointService.refundCancelledOrder(...)  // 적립금 ✅ (2026-08-07 에 추가)
publishEvent(OrderCancelledEvent)  // 알림 ✅
                                   // 쿠폰 ❌ — 줄이 없다
```

`approveReturn`(반품 승인)도 같다. 그리고 **`CouponService` 에 되돌리는 메서드가 아예 없었다** —
`MemberCoupon.use()` 는 있고 `restore()` 가 없다. 즉 «호출을 빠뜨렸다» 가 아니라
**「되돌린다」 는 개념이 만들어진 적이 없다.**

### 8-2. 🔴 예상 밖 — **고치려 해도 어느 쿠폰이었는지 몰랐다**

`orders` 의 쿠폰 컬럼은 **`COUPON_NAME`·`COUPON_DISCOUNT` 둘뿐**이다(실측: `user_tab_columns`).
적립금은 `used_point` 라는 **금액만으로** 되돌려지지만 — 얼마를 돌려줄지가 곧 답이다 —
쿠폰은 **어느 장인지**를 알아야 그 행의 `used_at` 을 지운다. 같은 회원이 같은 쿠폰을 여러 장 받을 수
있어(`CouponService.issue` 가 허용) **이름으로는 못 찾는다.**

⚠ 08-10 §16-4 는 *"8/07 에 적립금을 고칠 때 쿠폰은 표에 행조차 없었다"* 고 적었는데, 실제로는
**행이 있었어도 그날 못 고쳤을** 자리다 — 마이그레이션이 먼저 필요했다. → V46.

### 8-3. 운영 피해 실측 — **아직 0건**

| | 실측(2026-08-11) |
|---|---|
| 쿠폰을 쓴 주문 | **1건** — `20260728-0478` · DELIVERED · 「테스트 5000원」 · 5,000원 |
| 그중 취소·반품된 것 | **0건** ← 아직 아무도 안 밟았다 |
| 남은 `member_coupon` | 2장, 둘 다 `김기현팀2`, **둘 다 미사용** |

⚠ *"쿠폰 쓴 주문이 1건인데 `member_coupon` 에 사용 표시가 0장"* 은 **버그가 아니다** —
그 주문의 주인이 **탈퇴**해서 `deleteAllForMember`(F-1)가 발급분을 지웠다.
그 탈퇴 회원이 §7-3 의 `20260728-0478` 과 **같은 사람**이다.

→ 그래서 **백필하지 않는다.** 되돌릴 대상 자체가 없고, 짐작으로 채우면 **엉뚱한 사람의 쿠폰이
되살아난다**(V37 이 동의 시각을 백필하지 않은 것과 같은 판단).

### 8-4. 고친 방식 — 되돌릴 것들을 **한 줄에 모았다**

- **V46**: `orders.member_coupon_id RAW(16)` nullable. FK 없음 — 탈퇴하면 발급쿠폰이 통째로
  지워지는데(F-1) FK 가 있으면 **주문이 그 삭제를 막는다**(과거 주문을 남기는 결정과 정면 충돌).
- **`MemberCoupon.restore()`** — 이미 미사용이면 `false` 를 준다(호출부가 «실제로 되돌렸나» 를 알아야
  로그가 일어나지 않은 일을 적지 않는다). ⚠ **유효기간은 보지 않는다** — 만료됐다고 안 돌려주면
  고객은 **쓴 적도 없는 쿠폰을 잃는다.** 만료 판정은 다음 `redeem` 이 한다.
- **`CouponService.restore(id)`** — `null` 을 받아 준다(호출부가 «쿠폰 썼나» 로 갈라지지 않게).
  ⚠ 없는 쿠폰에 **예외를 던지지 않는다.** 취소 트랜잭션 안이라 던지면 **취소 자체가 롤백**돼
  «쿠폰이 안 돌아온» 게 아니라 **«취소가 안 되는»** 상태가 된다 — 더 나쁘다. 대신 `log.warn`.
- **`applyCancellation` · `approveReturn` 양쪽에** 붙였다. 한쪽만 넣으면 그게 다음 비대칭의 시작이다.

### 8-5. ⚠ 이 자리는 **두 번 연속** 걸렸다 — 그래서 테스트를 한 곳에 모았다

2026-08-07 에 취소가 **적립금**을 안 돌려주고 있었고, 그걸 고친 뒤에도 **쿠폰**이 같은 이유로 빠져 있었다.
원인은 매번 같다 — **되돌릴 것들이 한 줄로 모여 있지 않으면 새로 생긴 것이 조용히 누락된다.**

→ `cancel_restoresEverything` 이 **재고·적립금·쿠폰·알림을 함께** 못 박는다. 갈라 두면
«쿠폰 테스트가 없어서 쿠폰이 빠졌다» 가 그대로 반복된다. **다음에 되돌릴 것이 생기면 여기에 줄이 는다.**

⚠ **반품 승인은 서비스 테스트가 아예 없었다**(`approveReturn` 을 부르는 테스트가 0개였다).
2026-08-07 사고가 «반품만 고쳐진» 비대칭이었는데 **정작 반품 쪽엔 지켜 줄 것이 없었다** —
`approveReturn_restoresEverything` 을 새로 세웠다.

⚠ 대조군도 뒀다: `cancel_noCoupon_stillSamePath`. 없으면 «항상 restore 를 부른다» 로 고쳐도 통과한다.

### 8-6. 🔴 그런데 그 테스트들로는 **「돌아왔다」를 못 봤다** — 변형 M9 가 드러냈다

`MemberCoupon.restore()` 가 **아무것도 안 하게** 바꿨는데 **전체가 초록이었다.**
위 테스트들은 `CouponService` 가 **목**이라 «restore 를 불렀다» 까지만 본다 —
**되돌아왔는지는 모른다.** 7/31 H-2 의 «`@Mock` 착시» 와 정확히 같은 자리고,
실제로 `restore` 를 직접 검증하는 테스트는 **0개**였다.

→ `CouponOrderIntegrationTest`(실제 Oracle + MockMvc)에 붙였다:

| 테스트 | 무엇을 못 박나 |
|---|---|
| `cancelRestoresCoupon` | 취소 후 **같은 쿠폰으로 다시 주문된다** |
| `cancelWithoutCoupon_doesNotTouchOtherCoupons` | 살아 있는 주문이 쥔 쿠폰을 **무관한 취소가 풀지 않는다** |

⚠ `used_at` 을 직접 읽지 않는다 — **«다시 쓸 수 있다» 가 곧 고객이 얻는 것**이기 때문이다.
컬럼이 비어도 다른 가드에 걸려 못 쓰면 소용없다. 대조군은 기존 `sameCouponCannotBeUsedTwice` 다
(취소를 **안 하면** 두 번째는 409).

⚠ **그 대조군도 처음엔 약했다.** 미사용 쿠폰만 두고 개수를 세면 «아무거나 되살린다» 로 고쳐도
개수가 그대로라 초록이다(변형 M10). **실제로 쓴 쿠폰이 살아 있는 상태**로 바꿔서야 잡혔다 —
대조군은 «반대 경우가 있다» 가 아니라 **«그 차이가 보인다»** 여야 한다.

## 11. Fable 감사 6번 — **탈퇴해도 장바구니가 남았다** (커밋 `b2c2278`)

### 11-1. 확인 — 「의심됨」이 맞았고, **왜 빠졌는지**가 더 중요하다

탈퇴 정리 리스너가 일곱이다: 적립금·찜·쿠폰·알림·재입고·문의 + 배송지(직접). **`cart` 만 없다.**

⚠ **나머지 일곱은 전부 DB 테이블인데 장바구니만 Redis 다**(`cart:{memberId}`, `CartStore`).
F-1 을 만들 때 「지울 **테이블**」을 세었지 「지울 **저장소**」를 세지 않았다.
오늘 §1-1(조합↔행)·§7-3(조합↔밟을 자리)과 **같은 종류**다 — **목록의 단위가 틀리면 항목이 빠진다.**

### 11-2. 실측

| | 값 |
|---|---|
| 운영 db0 `cart:*` | **96개** |
| 그중 **회원이 없는 것** | **96개 (전부)** |
| 회원이 있는 것 | **0개** |
| TTL 분포 | 9일 1 · 11일 18 · 12일 4 · 14일 4 · 15일 24 · 16일 41 · 17일 4 |

⚠ **TTL 30일이 결국 지우므로 영구 누수는 아니다.** 그래도 고치는 이유는 F-1 의 성격이
«언젠가 사라진다» 가 아니라 **«탈퇴하면 지운다»** 이기 때문이다 — 최대 30일간
«그 사람이 무엇을 담아 뒀는지» 가 서버에 남는 것은 다른 도메인 처리와 어긋난다.

⚠ 회원이 6명인데 키가 96개인 것은 대부분 과거 검증·테스트가 만든 것으로 보인다.
**테스트는 db1 로 격리돼 있다**(`build.gradle` 의 `spring.data.redis.database=1`, 2026-07-29 조회수 사고의 결론).

### 11-3. 고친 방식

`CartMemberWithdrawnListener` — 다른 일곱과 **같은 3층·같은 `@EventListener`**.

⚠ **Redis 삭제는 롤백되지 않는다.** 회원 삭제가 뒤에서 실패하면 장바구니만 지워진 채 남는다.
그래도 이쪽을 택했다: 반대(회원은 지워졌는데 장바구니가 남는 것)가 **개인정보가 남는** 쪽이고,
장바구니는 **다시 담으면 되는** 값이다. `RefreshTokenStore`·`TokenRevocationStore` 정리가
이미 같은 판단이다(`MemberService.purge` 의 첫 두 줄).

### 11-4. 🔴 테스트의 「모든 자리」가 거짓말이었다

`MemberPurgeIntegrationTest.seedEverything` 주석은 *"회원 id 를 들고 있는 **모든** 자리에 한 행씩
심는다(코드에서 전수로 뽑은 목록)"* 였는데 **장바구니가 없었다.** 오늘 네 번째로 만난
«손으로 적은 목록» 이다.

→ `assertNoRedisResidue`: 목록을 적는 대신 **회원 id 가 든 Redis 키를 훑는다.**
예외는 `auth:revoked-before:{memberId}` **하나뿐**이고 그건 `purge` 가 **일부러 써 넣는** 값이다(E-2 —
회원 행이 사라져도 남의 기기의 access 토큰은 만료까지 통하므로 컷오프가 남아야 한다).
⚠ **«예외가 실제로 있는지» 도 함께 단언**했다 — 안 그러면 필터가 아무것도 안 거른 채 초록일 수 있다.

⚠ **`@AfterEach` 정리도 넣었다.** `@Transactional` 은 DB 만 롤백하고 **Redis 는 남는다**(WA §3) —
하필 이 파일이 «남는 것» 을 고치는 자리라, 스스로 치우지 않으면 앞뒤가 안 맞는다.

**변형 M21**(리스너를 통째로 제거 = 원래 상태 재현) → 탈퇴·강제삭제 **2건**이 잡음.

## 12. Fable 감사 8번 — **매출과 판매량의 시점이 달랐다** · 7번 낡은 주석 (커밋 `9e24e51`)

### 12-1. 확인 — 「확인 필요」였고, **지금 발생 중이었다**

### 12-2. 🔴 오늘 아침과 **같은 모양**이었다

`REVENUE_STATUSES` 주석에 이렇게 적혀 있었다:

> *"새 상태는 여기 직접 넣도록 opt-in 으로 둔다(`existsPurchase` 와 같은 판단)."*

**같은 판단이 맞았고, 같은 방식으로 어긋났다** — `existsPurchase` 는 `DELIVERED` 를 놓쳤고(§3-1)
여기는 `RETURN_REQUESTED` 를 놓쳤다. **주석으로 적은 opt-in 은 두 자리에서 다 안 지켜졌다.**

→ 판정을 `OrderStatus.isRevenue()` 로 옮겼다(**`default` 없는 switch**).
⚠ **`isPurchaseProven` 과 합치지 않았다** — 실제로 갈리는 자리가 둘이다:
`ORDERED`(샀지만 결제 전 → 매출 아님) · `RETURNED`(받아 봤지만 환불 → 매출 아님).
그 차이를 테스트로 못 박아 **누가 합치면 빨개지게** 했다(변형 M23 으로 확인).

### 12-3. ⚠ 정의의 복사본이 **셋**이었다 — 셋째는 테스트였다

① 서비스 상수 ② 리포지토리 주석 ③ **크로스체크 테스트의 native SQL**(`IN ('PAID','SHIPPED','DELIVERED')`).

`RETURN_REQUESTED` 를 넣자 ③만 옛 정의로 남아 **`15 ≠ 16`** 으로 깨졌다.
⚠ 그 테스트 이름이 *"API 응답이 DB 직접 집계와 일치한다 — 정의가 코드와 SQL 양쪽에서 같은지"* 다 —
**「코드와 SQL 이 같은지」를 본다면서 정작 자기가 또 하나의 코드**였던 셈이다.
→ 셋 다 `isRevenue()` 를 가리키게 바꿨다. 테스트가 지키는 것은 «어느 상태인가» 가 아니라
**«같은 상태 집합으로 JPQL 과 native SQL 이 같은 답을 내는가»** 이고, 그게 원래 의도였다.
