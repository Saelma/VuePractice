## 4. access 토큰 즉시 무효화 (E-2) — **완료** (배포 대기)

정지·강등이 **최대 30분간 효과가 없던** 구멍. 역할이 JWT 클레임에 박혀 있어 강등해도 옛 토큰의
`role` 은 ADMIN 이다.

### 4-1. ⚠ 착수 전 실측이 백로그보다 나빴다

| | 백로그가 적은 것 | 실측 |
|---|---|---|
| `suspend` | refresh 만 지운다 | 맞다 |
| `changeRole` | "둘 다 안 한다" | 맞다 — **refresh 삭제조차 없다** |
| 범위 | 정지·강등 2곳 | **5곳**(+탈퇴·비밀번호 변경·비밀번호 재설정) |

**범위를 넓힌 근거**: `refreshTokenStore.delete` 옆에 *"다른 세션 무효화"* 주석이 달린 자리가 전부
같은 구멍이었다 — **주석이 코드보다 앞서 있었다**(refresh 만 지워선 access 가 안 죽는다).
백로그가 놓친 이유는 항목을 **증상**("정지·강등이 안 먹는다")으로 잡았기 때문이다. 같은 **원인**을
가진 자리는 그 이름으로는 안 보인다.

### 4-2. 왜 블랙리스트가 아니라 컷오프인가

`TokenBlacklist` 는 **jti 단위**다. 회원이 여러 기기에 로그인해 있으면 **서버는 그 jti 들을 모른다** —
그래서 "이 회원의 토큰 전부"를 막을 방법이 없다. 토큰을 모으는 대신 **시각 하나**를 남긴다:
`TokenRevocationStore`(Redis `auth:revoked-before:<memberId>`) + `JwtAuthenticationFilter` 의 `iat` 비교.

- **TTL 은 access 유효기간만큼만** — 그 뒤엔 컷오프 이전 토큰이 전부 자연 만료되므로 컷오프가 남을
  이유가 없다(블랙리스트가 "남은 만료시간만큼만" 올리는 것과 같은 판단 → 키 무한증가 없음).
  실측: 남은 컷오프 키 10개 전부 TTL 있음(1,614~1,671초), **영구 키 0**.
- **경계는 fail-closed**(`iat <= cutoff`): `iat` 는 **초 정밀도**라 `<` 로 비교하면 **강등과 같은 초에
  발급된 토큰이 살아남는다.** 대가는 그 1초 안에 로그인한 사람이 한 번 더 로그인하는 것뿐이다.
- **`iat` 가 없는 토큰도 무효로 본다** — 우리 `JwtProvider` 는 항상 넣으므로, 없다는 것은 판정 불가라는 뜻이다.
- ⚠ **역할변경은 refresh 를 지우지 않는다.** 지우면 로그아웃되는데, 재발급하면 **새 역할**이 박히므로
  그게 정상 경로다. 정지는 반대다 — **재발급 자체를 막아야** 하므로 refresh 도 지운다. 둘의 목적이 다르다.

### 4-3. 프론트 짝 — 화면이 거짓말하는 것을 함께 막았다

백엔드만 고치면 강등 후에도 `localStorage` 의 `user.role` 이 ADMIN 이라 **관리 메뉴가 계속 보이고
라우터 가드도 통과**한 뒤 API 에서 403 이 난다(WA §2-3: 프론트는 백엔드가 실제로 쓰는 기준을 따른다).

→ `doRefresh` 성공 직후 `/api/auth/me` 를 다시 읽어 `setUser` 한다. **역할이 달라질 수 있는 시점은
재발급뿐**이므로 훅 자리가 정확히 거기다. 실패는 무시한다(토큰은 이미 유효 — 다음 재발급에서 맞춰진다).

- ⚠ **기존 프론트 테스트의 기대값이 바뀐다**(fetch 호출 3회 → 4회). 계약이 실제로 바뀐 것이라 함께 고쳤다.

### 4-4. ⚠ 함께 생기는 변화 — 비밀번호를 바꾸면 **현재 기기도** 로그아웃된다

컷오프는 **시각 기준**이라 "이 토큰만 살려두기"가 안 된다. 그래서 비밀번호 변경·재설정 시
**요청을 보낸 기기의 토큰도 함께 죽는다.**

- **그대로 두기로 판단한 이유**: 비밀번호를 바꾸는 이유가 보통 *"남이 쓰고 있다"* 이므로
  **전부 끊는 쪽이 안전한 기본값**이다. 프론트 동작도 일관된다 — 401 → refresh(이미 삭제됨) 실패 →
  `clearSession()` → 로그인 화면.
- 현재 기기를 유지하려면 **변경 응답에 새 토큰을 실어 주는** 방식이 필요하다(응답 계약 변경).
  요구가 생기면 그때. 지금은 재로그인 한 번이 대가다.

> 아니고, **테스트만 같은 초에 몰린다.** 버그를 가리는 sleep 이 아니라 실제 시간 간격의 재현이다.

## 5. 배포

### 5-1. H-1(§3) — 배포 대상 아님

테스트 파일 하나뿐이고 프로덕션 코드·스키마·프론트가 무변경이다. 운영 jar 에 들어갈 것이 없다.

### 5-2. E-2(§4) — **배포 대기** (백·프론트 함께)

- **백엔드·프론트 둘 다 바뀌었다.** 응답 계약은 안 바뀌었지만 **동작 계약이 바뀐다**(옛 토큰이 죽는다).
  순서는 WA §5 기본대로 **백엔드 먼저 → 곧바로 프론트**.
  - 백엔드만 올라간 창: 강등·정지된 사용자의 토큰이 죽고, 구 프론트는 refresh 후 `user.role` 을
    갱신하지 않아 **관리 메뉴가 남는다**(지금과 같은 상태 — 더 나빠지지 않는다).
  - 프론트만 올라간 창: `/api/auth/me` 재조회가 추가되지만 컷오프가 없어 **아무 일도 안 일어난다**.
  → 어느 쪽도 파괴적이지 않지만, **백엔드 먼저**가 "새 동작을 프론트가 뒤따르는" 순서라 맞다.
- ⚠ **배포 전에 운영 백엔드를 먼저 살려야 한다**(§2-3) — 지금 DB 를 못 잡아 `DOWN` 이다.
  재기동으로 `UP` 을 확인한 뒤 배포 순서를 밟는다.
- ⚠ **배포 확인은 상태코드가 아니라 코드 증거로**(WA §5): `/v3/api-docs` 로는 이번 변경이 안 드러난다
  (엔드포인트가 안 늘었다) → **행동으로 확인**한다. 브라우저 절차는 아래.
- 마이그레이션 없음(Redis) → DB 선행 작업 없음. 롤백 시 남는 것은 컷오프 키뿐이고 TTL 로 사라진다.

### 5-3. 브라우저 검증 절차 (사용자 — 배포 후)

메모리 규약대로 API E2E 대신 화면 스텝으로 적는다.

1. **강등**: 최상위 관리자로 로그인 → 다른 브라우저(또는 시크릿 창)에서 **일반 관리자**로 로그인해
   「관리 ▾」에 들어가 둔다 → 최상위 창에서 그 관리자를 **USER 로 강등** →
   관리자 창에서 아무 화면이나 이동 → **관리 메뉴가 사라지고** 관리 화면 접근이 막혀야 한다
   (전에는 최대 30분간 그대로 통했다).
2. **정지**: 일반 회원으로 로그인해 둔 창 → 관리자가 그 회원을 **정지** → 회원 창에서 아무 요청 →
   **로그인 화면으로 밀려나야** 한다 → **해제** 후 다시 로그인되면 정상.
3. **비밀번호 변경**: 두 창에 같은 계정으로 로그인 → 한 창에서 비밀번호 변경 →
   **양쪽 다** 로그인 화면으로(§4-4 의 의도된 동작).
4. ⚠ 검증 계정은 `ZZ` 로 만들고 끝나면 탈퇴시킨다(WA §3-1). 실계정으로 하면 **역할·비밀번호가 실제로 바뀐다.**
