### 3-2. ⚠ "롤백되면 감사도 안 남는다" 를 실제로 어떻게 재는가

이 주장이 이 도메인 설계의 핵심(같은 트랜잭션 합류)인데, **테스트 자신의 트랜잭션 안에서는 볼 수 없다**
— 끝에 통째로 롤백되므로 무엇을 단언해도 같은 결과가 나온다.

→ `TransactionTemplate` 으로 **REQUIRES_NEW 독립 트랜잭션**을 열고 그 안에서 정지시킨 뒤 예외를 던졌다.
감사 저장이 `REQUIRES_NEW` 였다면 조작이 롤백돼도 **감사 행은 커밋된 채 살아남는다** — 그게 이 테스트가
잡으려는 경우다. 롤백되므로 공유 DB 에 잔재도 없다.

- ⚠ **롤백 전에 "행이 1건 생겼다"를 먼저 단언했다.** 이게 없으면 마지막 `isEmpty()` 가
  **아무 일도 안 일어나서** 통과하는 경우와 구분되지 않는다(빈손 통과 방지).

## 4. access 토큰 즉시 무효화 (E-2) — **완료** (배포 대기)

정지·강등이 **최대 30분간 효과가 없던** 구멍. 역할이 JWT 클레임에 박혀 있어 강등해도 옛 토큰의
`role` 은 ADMIN 이다.

### 4-1. ⚠ 착수 전 실측이 백로그보다 나빴다

| | 백로그가 적은 것 | 실측 |
|---|---|---|
| `suspend` | refresh 만 지운다 | 맞다 |
| `changeRole` | "둘 다 안 한다" | 맞다 — **refresh 삭제조차 없다** |
| 범위 | 정지·강등 2곳 | **5곳**(+탈퇴·비밀번호 변경·비밀번호 재설정) |

**범위를 넓힌 근거**: `refreshTokenStore.delete` 옆에 *"다른 세션 무효화"* 주석이 달린 자리가 전부
같은 구멍이었다 — **주석이 코드보다 앞서 있었다**(refresh 만 지워선 access 가 안 죽는다).
백로그가 놓친 이유는 항목을 **증상**("정지·강등이 안 먹는다")으로 잡았기 때문이다. 같은 **원인**을
가진 자리는 그 이름으로는 안 보인다.

### 4-2. 왜 블랙리스트가 아니라 컷오프인가

`TokenBlacklist` 는 **jti 단위**다. 회원이 여러 기기에 로그인해 있으면 **서버는 그 jti 들을 모른다** —
그래서 "이 회원의 토큰 전부"를 막을 방법이 없다. 토큰을 모으는 대신 **시각 하나**를 남긴다:
`TokenRevocationStore`(Redis `auth:revoked-before:<memberId>`) + `JwtAuthenticationFilter` 의 `iat` 비교.

- **TTL 은 access 유효기간만큼만** — 그 뒤엔 컷오프 이전 토큰이 전부 자연 만료되므로 컷오프가 남을
  이유가 없다(블랙리스트가 "남은 만료시간만큼만" 올리는 것과 같은 판단 → 키 무한증가 없음).
  실측: 남은 컷오프 키 10개 전부 TTL 있음(1,614~1,671초), **영구 키 0**.
- **경계는 fail-closed**(`iat <= cutoff`): `iat` 는 **초 정밀도**라 `<` 로 비교하면 **강등과 같은 초에
  발급된 토큰이 살아남는다.** 대가는 그 1초 안에 로그인한 사람이 한 번 더 로그인하는 것뿐이다.
- **`iat` 가 없는 토큰도 무효로 본다** — 우리 `JwtProvider` 는 항상 넣으므로, 없다는 것은 판정 불가라는 뜻이다.
- ⚠ **역할변경은 refresh 를 지우지 않는다.** 지우면 로그아웃되는데, 재발급하면 **새 역할**이 박히므로
  그게 정상 경로다. 정지는 반대다 — **재발급 자체를 막아야** 하므로 refresh 도 지운다. 둘의 목적이 다르다.

### 4-3. 프론트 짝 — 화면이 거짓말하는 것을 함께 막았다

백엔드만 고치면 강등 후에도 `localStorage` 의 `user.role` 이 ADMIN 이라 **관리 메뉴가 계속 보이고
라우터 가드도 통과**한 뒤 API 에서 403 이 난다(WA §2-3: 프론트는 백엔드가 실제로 쓰는 기준을 따른다).

→ `doRefresh` 성공 직후 `/api/auth/me` 를 다시 읽어 `setUser` 한다. **역할이 달라질 수 있는 시점은
재발급뿐**이므로 훅 자리가 정확히 거기다. 실패는 무시한다(토큰은 이미 유효 — 다음 재발급에서 맞춰진다).

- ⚠ **기존 프론트 테스트의 기대값이 바뀐다**(fetch 호출 3회 → 4회). 계약이 실제로 바뀐 것이라 함께 고쳤다.

### 4-4. ⚠ 함께 생기는 변화 — 비밀번호를 바꾸면 **현재 기기도** 로그아웃된다

컷오프는 **시각 기준**이라 "이 토큰만 살려두기"가 안 된다. 그래서 비밀번호 변경·재설정 시
**요청을 보낸 기기의 토큰도 함께 죽는다.**

- **그대로 두기로 판단한 이유**: 비밀번호를 바꾸는 이유가 보통 *"남이 쓰고 있다"* 이므로
  **전부 끊는 쪽이 안전한 기본값**이다. 프론트 동작도 일관된다 — 401 → refresh(이미 삭제됨) 실패 →
  `clearSession()` → 로그인 화면.
- 현재 기기를 유지하려면 **변경 응답에 새 토큰을 실어 주는** 방식이 필요하다(응답 계약 변경).
  요구가 생기면 그때. 지금은 재로그인 한 번이 대가다.

### 5-2. E-2(§4) — **배포 대기** (백·프론트 함께)

- **백엔드·프론트 둘 다 바뀌었다.** 응답 계약은 안 바뀌었지만 **동작 계약이 바뀐다**(옛 토큰이 죽는다).
  순서는 WA §5 기본대로 **백엔드 먼저 → 곧바로 프론트**.
  - 백엔드만 올라간 창: 강등·정지된 사용자의 토큰이 죽고, 구 프론트는 refresh 후 `user.role` 을
    갱신하지 않아 **관리 메뉴가 남는다**(지금과 같은 상태 — 더 나빠지지 않는다).
  - 프론트만 올라간 창: `/api/auth/me` 재조회가 추가되지만 컷오프가 없어 **아무 일도 안 일어난다**.
  → 어느 쪽도 파괴적이지 않지만, **백엔드 먼저**가 "새 동작을 프론트가 뒤따르는" 순서라 맞다.
- ⚠ **배포 전에 운영 백엔드를 먼저 살려야 한다**(§2-3) — 지금 DB 를 못 잡아 `DOWN` 이다.

- ⚠ **배포 확인은 상태코드가 아니라 코드 증거로**(WA §5): `/v3/api-docs` 로는 이번 변경이 안 드러난다

3. **비밀번호 변경**: 두 창에 같은 계정으로 로그인 → 한 창에서 비밀번호 변경 →
   **양쪽 다** 로그인 화면으로(§4-4 의 의도된 동작).
4. ⚠ 검증 계정은 `ZZ` 로 만들고 끝나면 탈퇴시킨다(WA §3-1). 실계정으로 하면 **역할·비밀번호가 실제로 바뀐다.**

**두 가지가 함께 드러났다.**

1. **점검 방식의 구멍** — 7/28·7/29 는 *"그날 시나리오"* 만 되짚었고, 이 계정은 **두 번 연속 지나갔다.**
   하루 단위로는 "오늘 것은 다 치웠다"가 매일 참인데 **누적은 계속 늘어난다.**
   → **WA §3-1 에 규약 추가**: 하루를 닫을 때 `like 'zz%'` **전수**로 본다(날짜 조건 없이).
2. **정상 경로로 치울 수 없다** — 탈퇴는 본인 전용이고 **관리자 삭제 API 가 없다.** 비밀번호를 모르면

> ⚠ **문서에 실제 login_id 를 적지 않았다** — 실명 기반 ID + ADMIN 이라는 조합이라, 7/29 §10-3 에서
> 계정명을 일반화한 것과 같은 이유다(공개 대비). 실제 값은 위 쿼리로 바로 나온다.

## 7. 탈퇴 연관 데이터 정리(F-1) + 관리자 강제 삭제(B-24, V35) — **완료** (배포 대기)

§6-2 에서 **한 묶음으로 하기로** 판단한 그것. 같은 날 안에 둘 다 끝냈다.

### 7-1. ⚠ 착수하니 백로그 목록이 틀렸다 — 7개가 아니라 12개

F-1 은 남는 테이블을 7개로 적어 뒀는데, **회원 id 를 들고 있는 엔티티를 코드에서 전수로 뽑으니 12개**였다.

| | 대상 | 비고 |
|---|---|---|
| **지운다** | 배송지 · 찜 · 적립금(계정+이력) · 보유쿠폰 · 알림 · **알림설정** · 재입고구독 · **문의** | `notification_pref` 는 **백로그 목록에 없었다** |
| **남긴다** | 주문 · **리뷰** · **공지** | 이 셋은 판단이 필요한데 **목록에 아예 없었다** |

→ **감으로 쓴 목록은 착수할 때 다시 뽑는다.** 백로그의 목록은 출발점이고 명세가 아니다
(B-4 쿠폰의 "크기 어림" 교훈과 같은 종류 — 분해해 보지 않으면 틀린다).

**핵심 발견**: 리뷰·문의·공지 모두 **작성 시점 닉네임을 스냅샷**으로 들고 있다(`review.author`·
`notice.author` — `orders.buyer_nickname` 과 같은 패턴). 그래서 **남기는 게 기술적으로 가능**했고,
이건 기술 문제가 아니라 **정책 판단**이었다.

- **사용자 결정: 리뷰 남김 / 문의 삭제.** 리뷰는 다른 고객의 구매 판단 근거이자 `avg_rating`·
  `review_count` 집계의 근거다. 문의는 본인↔관리자 대화에 가깝고 **비밀글 필드까지 있어** 내용에
  주문번호·연락처 같은 것이 들어갈 수 있다.
- 공지는 **관리자가 쓴 콘텐츠**라 자명하게 남긴다(작성자 계정이 사라져도 글은 남아야 한다).

### 7-2. 설계 — 왜 이벤트인가

member 가 남의 테이블을 직접 지울 수는 없다(도메인 경계). 그래서 `MemberWithdrawnEvent` 를 발행하고
**각 도메인이 자기 것만 지운다** — audit·restock 이 쓰는 3층(Event · Listener는 위임만 · Handler가 주체) 그대로.

- **같은 트랜잭션**(기본 `@EventListener`)이라 정리가 실패하면 **회원 삭제도 롤백**된다.
  "회원은 없는데 데이터는 남은" 어긋남이 구조적으로 안 생긴다(감사 로그와 같은 판단).
- **진입점은 둘, 삭제는 한 곳**: 본인 탈퇴와 관리자 강제 삭제가 `MemberService.purge` 를 공유한다.
  따로 뒀다면 *"관리자로 지운 회원만 데이터가 남는다"* 같은 어긋남을 언제든 만들 수 있었다.
- 순서에 이유가 있다: **토큰 무효화(E-2) → 배송지 삭제 → 이벤트 발행 → 회원 행 삭제.**
  이벤트를 행 삭제 **전에** 발행하는 건, 리스너가 회원을 다시 읽어야 할 일이 생기면 그때는 이미 없어서다.
- ⚠ **문의는 벌크 DELETE 를 쓰지 않았다.** 문의마다 첨부 이미지 그룹을 해제해야 하는데(단건 삭제 경로가
  지키는 규칙) 벌크는 그 경로를 건너뛰어 **고아 이미지**를 남긴다 — 2026-07-20 에 손으로 3건 치운 그 문제다.

### 7-3. ⚠ 겪은 사고 — 같은 클래스명 6개가 컨텍스트를 죽였다

리스너를 6개 도메인에 `MemberEventListener` 라는 **같은 이름**으로 만들자 앱이 아예 안 떴다:
`ConflictingBeanDefinitionException: bean name 'memberEventListener' … conflicts with existing`.

- **패키지가 달라도 스프링 기본 빈 이름은 단순 클래스명**이다. 도메인별로 접두사를 붙여 해결
  (`PointMemberWithdrawnListener` …). 기존 `OrderEventListener`·`StockEventListener` 가 우연히
  안 겹쳤을 뿐이라, 앞으로 도메인마다 같은 역할의 리스너를 만들 때 계속 만날 자리다.
- ⚠ 증상이 **테스트 5건 전부 컨텍스트 로딩 실패**로 나타났다 — §2 의 IP 사고와 같은 모양이다.
  그때는 인프라였고 이번엔 코드였다. **`Caused by` 최하단까지 내려가야** 갈린다(둘 다 그렇게 찾았다).

### 7-4. B-24 — 되돌릴 수 없어 권한을 한 칸 좁혔다

`DELETE /api/admin/members/{id}` — **SUPER_ADMIN 전용**. 대상이 일반 USER 여도 일반 ADMIN 은 못 지운다
(역할변경과 같은 급으로 봤다 — 되돌릴 수 없기 때문이다). 자기 자신·SUPER 대상은 기존 `authorize` 가 막는다.

- **감사 발행이 삭제보다 먼저**다 — `publish` 가 `target_login` 스냅샷을 읽는데, 지운 뒤에는 그 값이 없다.
- **V35**: `AuditAction.MEMBER_DELETE` 를 더했으니 CHECK 제약도 넓혀야 한다(Oracle enum CHECK 트랩).
  ⚠ **V32 가 제약에 이름을 붙여 둬서 두 줄로 끝났다** — V31 의 role 은 시스템 이름이라 `search_condition_vc`
  를 조회해 동적으로 DROP 해야 했다. **제약에 이름을 주는 습관이 여기서 값을 했다.**
  넓히는 방향이라 구 jar 에 무영향(구 jar 는 새 값을 만들지 않는다).
- **화면**: 회원 상세에 SUPER 전용 「회원 삭제」 + **2단 확인**. ⚠ 문구에 **지워지는 것과 남는 것을 그대로
  적었다** — 관리자가 "주문 기록도 날아가나?"를 눌러 보고 알게 하면 안 된다(안 날아간다).

## 9. 로그인 무차별 대입 방어 (E-1) — **완료** (배포 대기)

§8 이후 사용자가 이어서 지시한 항목. 이월의 「다음 후보」 1순위로 적어 둔 그것이다.

### 9-1. ⚠ 착수하며 찾은 함정 둘 (코드를 먼저 읽어서 걸렀다)

| 함정 | 실측 |
|---|---|
| **IP 제한이 정반대로 동작한다** | `server.forward-headers-strategy` 가 **설정돼 있지 않다**(기본 `NONE`) → `getRemoteAddr()` 이 모든 요청에서 nginx 주소(`127.0.0.1`). 그대로 "IP당 20회" 를 걸면 **한 사람이 20번 틀리는 순간 전 사용자가 잠긴다** |
| **`X-Forwarded-For` 는 위조된다** | nginx 설정이 `$proxy_add_x_forwarded_for` = **클라이언트가 보낸 값에 덧붙이기**라 첫 값을 공격자가 심을 수 있다. `X-Real-IP $remote_addr` 는 nginx 가 **항상 덮어쓴다** → 그쪽을 쓴다 |

→ `ClientIpResolver`(X-Real-IP → remoteAddr 폴백)를 따로 뒀다. **기능 하나를 위해 전역 설정
(`forward-headers-strategy`)을 켜지 않은 이유**: 그건 `isSecure()`·리다이렉트 URL 생성 등 앱 전체의
동작을 바꾼다. 지금 필요한 건 "이 요청의 클라이언트 IP" 하나라서 국소적으로 해결했다.

### 9-2. ⚠ 백로그의 판단 하나를 뒤집었다 (사용자 확인)

백로그 E-1 은 *"차단 사실을 응답으로 드러내지 말 것 — 계정 존재를 알려주는 셈"* 이라고 적어 뒀다.
**그 논리는 존재하는 계정만 셀 때 성립한다.**

- 실제 구현은 **DB 조회 전에, 입력된 아이디 그대로** 센다 → **없는 아이디도 똑같이 잠긴다** →
  429 가 존재 여부를 알려주지 않는다(응답이 대칭이다).
- 숨기는 쪽의 대가가 크다: 진짜 사용자가 **맞는 비밀번호를 넣고도 401** 만 보게 되어 이유를 알 수 없다.
- → **알린다**(429 `AUTH-429`, "잠시 후 다시 시도해 주세요"). 사용자 결정(2026-07-30).

### 9-3. 설계 — 왜 둘을 세고, 무엇을 리셋하나

| 결정 | 이유 |
|---|---|
| **아이디 5회 + IP 20회** 둘 다 | 아이디만 막으면 **한 IP 가 여러 계정을 훑는다**(계정마다 5회씩). IP 만 막으면 **공유 IP(가정·사무실)에서 선의의 사용자가 함께 막힌다.** |
| 임계값 5 / 20 · 10분 | 인증번호(B-14)와 같은 값이라 일관된다. 사람의 오타는 보통 3회 이하 → 5회는 여유. 무차별 대입은 시간당 ~30회로 성립하지 않는다. IP 20 은 공유 IP 여지 |
| **성공은 아이디 카운터만 리셋** | IP 까지 지우면 **계정 하나를 가진 공격자가 자기 계정으로 로그인해 IP 예산을 리셋**하고 훑기를 계속할 수 있다 |
| TTL 은 **첫 실패에만** | 매 시도마다 연장하면 공격자가 계속 두드려 **선의의 사용자를 영구히 잠글 수 있다.** 대가는 아이디당 시간당 ~30회 허용 |
| 성공 처리는 **정지 검사 뒤** | 정지 계정은 비밀번호가 맞아도 로그인이 아니다 — 앞에 두면 정지된 계정으로 시도 예산을 무한히 새로 얻는다 |
| **대소문자 정규화** | 안 하면 `Hong`/`hong` 이 다른 카운터가 되어 대소문자만 바꿔 우회한다. 조회는 대소문자를 구분하지만 **방어는 더 넓게** 잡는다(B-13 이메일 정규화와 같은 판단) |

### 9-4. ⚠ 테스트가 서로를 잠글 수 있는 자리 — 격리로 풀었다

MockMvc 는 헤더가 없으면 클라이언트 IP 가 전부 `127.0.0.1` 이다. E-1 테스트는 **일부러 임계값을 넘기므로**
그 버킷을 쓰면 **같은 실행의 다른 테스트가 429 로 깨진다**(의도적 로그인 실패를 쓰는 테스트가 이미 2건 있다).

→ E-1 테스트는 **자기 IP**(`203.0.113.x`·`198.51.100.x`, 문서용 대역)를 보낸다. 정리가 아니라 **격리**다
(7/29 Redis 조회수 사고와 같은 판단). **WA §3 에 규약으로 올렸다** — 앞으로 실패 로그인을 쓰는 테스트가
늘면 어느 날 뒤쪽 테스트가 429 로 깨지고, 원인이 자기 테스트에 없어 찾기 어렵다.

|---|---|
| 백엔드 컴파일 | 통과 |

> 그게 아니면 카운트만 하고 차단은 안 하는 상태(있으나 없으나인 방어)와 구분되지 않는다.

## 10. 비밀번호 정책 (E-3) — **완료** (배포 대기)

E-1 의 짝. **시도 제한은 속도를 늦추고, 정책은 애초에 맞히기 어렵게 한다** — 하나만 하면 반쪽이다.

### 10-1. 무엇을 넣고 무엇을 넣지 않았나

| | 결정 | 이유 |
|---|---|---|
| 길이 | **10자**(기존 8자) | 8자는 흔한 조합이 현실적으로 뚫린다. ⚠ **길이만으로는 `password123`(11자)이 통과한다** — 그래서 목록이 필요하다 |
| 흔한 목록 | `resources/security/common-passwords.txt` 약 100개, **소문자 정확 일치** | 부분 문자열 검사는 오탐이 늘고 사용자가 이유를 알기 어렵다. 완전할 필요도 없다 — 온라인 추측은 E-1 이 아이디당 시간당 ~30회로 막는다 |
| 아이디·닉네임 포함 금지 | **양방향** | 목록만 있으면 `hong1234` 가 통과하는데, 그게 자기 아이디면 **공격자가 제일 먼저 추측하는 통**이다. 목록에 담을 수 없는 종류라 규칙으로 막는다 |
| 복잡도 규칙(대문자·특수문자) | **안 넣음** | NIST 800-63B 는 그 방식이 오히려 **예측 가능한 패턴**(`Password1!`)을 낳는다고 본다 — 사람은 규칙을 만족시키는 가장 짧은 길을 택한다 |

- ⚠ **2자 이하 닉네임은 포함 검사에서 제외**한다. 닉네임이 "하" 라면 '하' 가 든 모든 비밀번호가
  거부되는데, 그건 정책이 아니라 **고장**이다(테스트로 고정).
- ⚠ **목록을 못 읽으면 기동을 실패시킨다.** 조용히 길이 검사만 남으면 **보안 기능이 있는 척하는 상태**가
  되어 더 나쁘다(E-2 의 fail-closed 와 같은 판단).

### 10-2. 검증 위치 — DTO 가 아니라 서비스

길이는 DTO(`@Size`)에 남기고(빠른 실패), **나머지는 서비스**에서 본다. 아이디·닉네임 포함 여부는
**다른 필드를 함께 봐야** 판정되고, 비밀번호 변경 흐름에는 **요청 본문에 아이디가 아예 없다**(회원을 조회해야 안다).

**세 경로 전부에 걸었다** — 가입 · 비밀번호 변경 · 재설정 확정. 규칙이 맞아도 **한 문에서 부르는 것을
잊으면 그 문으로 약한 값이 들어온다**(H-1 의 "리스너 이후가 검증된 적 없던" 것과 같은 종류의 실패다).
그래서 통합 테스트가 **배선**을 따로 본다.

순서에도 이유를 뒀다:

- **비밀번호 변경**: 정책 검사는 **현재 비밀번호 확인 뒤**. 앞에 두면 남이 아무 값이나 넣어 보며
  "이 값은 정책에 걸린다/안 걸린다" 를 알아낼 수 있다(공짜로 피할 수 있는 누출).
- **재설정 확정**: 정책 검사는 **토큰 소비 뒤**. 앞에 두면 약한 값을 넣어 본 사람이 토큰을 잃지 않고
  재시도할 수 있는데, 그건 편의 대신 **링크의 단발성**을 깨는 것이다. 다시 요청하면 된다(테스트로 고정).

### 10-3. ⚠ 데모 계정 결정과 충돌하지 않는다

7/29 §10-4 에서 *"앱 테스트 계정 비밀번호(`password123`)는 그대로 둔다"* 고 결정했다. 이 정책은
**소급 적용되지 않으므로** 그 결정과 부딪히지 않는다 — 저장된 것은 해시라 위반 여부를 알 수도 없고,
**로그인은 정책을 검사하지 않는다.** 다만 **그 값으로 비밀번호를 새로 정할 수는 없다.**

→ 그래서 테스트 픽스처도 **두 갈래로 갈렸다**: **API 로 계정을 만드는 것**(가입·변경·재설정)은 정책을
통과하는 값으로 바꿨고, **리포지토리로 직접 저장하는 것**은 `password123` 을 그대로 뒀다
(그게 곧 "기존 회원" 을 재현하는 자리라, 오히려 바꾸면 소급 적용 없음을 검증할 수 없다).

### 조건부 잔여 (급하지 않음 — 조건이 생기면 그때)

1. **`/tmp` WebP 잔재** — tmpfiles.d 10일 규칙으로 자동 삭제. 당길 거면 `rm -f /tmp/cwebp*binary /tmp/dwebp*binary`.
2. **운영자ID 계정 검증 적립 영구 잔존**(SILVER·누적 204,880·잔액 97P) — 취소 불가가 설계라 그대로. 데모 때 감안.
3. **공유기 DHCP 예약**(MAC `08:00:27:df:8e:fd`) — ⚠ **전제가 사라졌다**(2026-07-30): 어댑터가 NAT 라
   공유기에서 받는 IP 자체가 없다. **브리지로 되돌리면 되살아나는 항목**이라 지우지 않고 남긴다 —
   그때는 예약 + 인증서 SAN 을 함께 봐야 한다.
4. **인증서 SAN** — `IP:192.168.50.14` 는 죽은 값이다. `IP:127.0.0.1`·`DNS:localhost` 가 함께 있어
   `https://localhost:8443/`(포워딩)로는 경고가 없다 → **당장 할 일 없음.** 재발급할 일이 생기면
   **IP 대신 DNS 로** 잡는다(근거: ARCHITECTURE HTTPS 행 · infra/README 인증서 절).
5. **8fter 의 미학(색·여백·타이포)** — 페이지 구조만 문서화됐고 시각 톤은 안 적었다. 사용자가 "무엇이
   좋았는지" 한 줄 주면 DESIGN.md §2 를 보강한다.
6. **디자인 더 갈 여지**(B-12 잔여) — 회원 상세 레이아웃 카드화, 상태 뱃지 pill 강화.
