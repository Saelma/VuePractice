## 2. 착수 전 실측

> WA §1-3: 문서의 **결론이 맞아도 이유는 틀릴 수 있다.**
> 그래서 BACKLOG·8/06 문서의 문장을 옮겨 적지 않고 **코드에서 다시 뽑았다.**

### 2-1. 어제 문서가 적은 것이 맞는가

| 확인한 것 | 실측 | 출처 |
|---|---|---|
| `product_id` 가 정말 NOT NULL 인가 | **맞다** — DDL `RAW(16) NOT NULL`, 엔티티 `nullable=false, updatable=false` | `V1__init.sql:143`, `Inquiry.java:30` |
| `inquiry_type` 이 이미 있나 | **없다.** DDL 컬럼은 11개(`id`·`product_id`·`author_id`·`author`·`title`·`content`·`secret`·`status`·`answer`·`answered_at`+감사 2) | `V1__init.sql:141-155` |
| `status` 에 CHECK 가 걸려 있나 | **걸려 있다** — `CHECK (status IN ('WAITING','ANSWERED'))`. **이름이 없다**(시스템 생성) | `V1__init.sql:149` |
| 상품 문의 목록이 오염되나 | **아니다** — `productId.eq(...)` 라 NULL 행은 구조적으로 안 잡힌다 | `InquiryRepositoryImpl.findByProduct` |
| 관리자 목록이 NULL 을 견디나 | **견딘다** — 어제 `filter(Objects::nonNull)` + `productId == null ? null : ...` 로 **미리 짜 뒀다** | `InquiryQueryService.findForAdmin:71,77` |
| 다음 마이그레이션 번호 | 최신이 `V41__add_review_hidden.sql` → **다음은 `V42`** | `db/migration/` |
| 일반 문의 작성 API | **없다** — 작성은 `POST /products/{productId}/inquiries` **하나**뿐 | `InquiryControllerImpl.java:37` |
| 내 문의 목록 API | **없다** — `findByAuthorId` 는 `List` 반환에 페이징이 없고 **탈퇴 정리(F-1) 전용**이다 | `InquiryRepository.java` |

**결론: 어제 문서의 계획이 지금도 맞다.** 그리고 어제 관리자 목록을 짤 때 **NULL 을 이미 감안해 둬서**
2단계가 백엔드 조회 쪽을 다시 건드릴 일은 없다.

### 2-2. 🔴 문서에 없던 것 — **일반 문의는 알림이 갈 데가 없다**

```java
// InquiryNotificationHandler.java:36
String link = "/products/" + event.productId() + "#inquiries";
```

B-15 답변 알림은 **상품 페이지의 문의 섹션 앵커로만** 간다. 문의는 **자기 URL 이 없어서**
그렇게 짠 것이고, 그 판단은 그때 옳았다(주석에 이유가 적혀 있다).

⚠ **2단계에서 `product_id` 가 null 이 되면 이 링크는 `/products/null#inquiries` 가 된다.**
답변은 멀쩡히 달리고 알림도 오는데 **누르면 깨진 페이지로 간다** — 그리고 **서버 로그엔 아무것도 안 남는다**
(잘못된 건 링크 **문자열**이지 코드 경로가 아니다). 어제 두 번 나온 「멀쩡해 보이는데 틀린 것」과 같은 종류다.

→ **그래서 3단계가 2단계에 딸려 온다.** BACKLOG·8/06 은 *"2단계를 넣으면 **볼 데**가 필요해진다"* 고
적었는데, 실제 이유는 그보다 강하다 — **알림이 착지할 URL** 이 필요하다. 「내 문의 목록」은
편의 기능이 아니라 **2단계가 성립하기 위한 조건**이다.

### 2-3. 디스크 — 원인은 우리 프로젝트가 아니었다

| 자리 | 크기 | 정체 |
|---|---|---|
| `/var/cache/PackageKit` | **2.3G** | 🔴 그중 **1.0G 짜리 `linux-firmware` RPM 하나**가 최근 2일 안에 받아졌다 — GNOME 이 업데이트를 **미리 내려받아 둔 것** |
| `/var/cache/dnf` | 276M | 리포 메타데이터 |
| `~/.npm/_cacache` | 535M | ⚠ 우리는 **pnpm 만 쓴다**(CLAUDE.md). 사실상 죽은 캐시 |
| `work-goblin/…/backend/build` | 650M | ⚠ `work` 쪽 같은 디렉터리는 **97M** — 여기만 6.7배(테스트 리포트·JaCoCo 누적) |

**즉 «작업하면 계속 준다» 가 아니라 «OS 가 알아서 받아 뒀다» 였다.** F-6 이 *"차오르면"* 이라고
적어 둔 판단이 맞았다 — 우리 쪽 증가분이 아니었다.

→ sudo 없는 둘(`_cacache`·`build`)을 치워 **3.1G → 4.8G (89% → 82%)**. 겹친 하드링크까지 빠져
예상 1.2G 보다 많은 **1.7G** 가 나왔다. 나머지 2.5G 는 sudo 라 **명령어만 넘겼다**(CLAUDE.md 규칙):
`sudo pkcon refresh force -c -1 && sudo dnf clean all`

`/api/inquiries/me` 의 권한 규칙을 **통째로 지웠는데 테스트가 전부 통과했다.**
내가 SecurityConfig 에 *"빠뜨리면 조용히 공개된다"* 고 적어 둔 그 자리다.

원인: 컨트롤러가 `@LoginUser AuthUser`(required=true)로 받고, `LoginUserArgumentResolver` 가
**같은 `UNAUTHENTICATED` 401** 을 던진다. `CustomAuthenticationEntryPoint` 도 같은 ErrorCode 를 쓴다 —
즉 **두 방어선이 HTTP 로 구분되지 않는다.** 관찰 가능한 차이가 없으므로 이건 **동치 변형**이다.

→ 위 「매처가 없으면 남의 쿠폰이 열린다」(쿠폰·찜·적립금) 주석과 **성격이 다르다**. 저기는 소유자를
경로/쿼리에서 받거나 서비스가 찾아 주므로 **정말로 열린다.**

→ **규칙은 남겼다.** 이유를 «없으면 뚫린다» 에서 둘로 바꿔 적었다:
① 인가는 **컨트롤러 앞**에서 끝나야 한다(앞에 필터가 붙는 순간 리졸버 방어의 전제가 깨진다),
② `@LoginUser` 를 빼거나 `required=false` 로 바꾸는 **한 줄 수정**이 이 경로를 조용히 공개로 만든다.

→ 테스트 주석도 고쳤다. 그 401 은 «규칙이 있다» 가 아니라 **«비로그인에게 남의 문의가 안 나간다»**
라는 결과를 못 박는 것이다 — 어느 방어선이 잡든 참이어야 하는 것.

14:24:56  [문의답변] inquiry=019fdaae-…1fbd2 author=019f6919-…

| `by=019f6450` ≠ `author=019f6919` | 답변자와 작성자가 **다른 계정**이다 — 자기 문의엔 답변이 막혀 있다(`INQUIRY-403S`, 8/06) |

### 10-1. «이전» 이 아니라 «확장» 인 이유

새 VM 이전을 검토했으나 **확장이 압도적으로 싸다**: Oracle 19c 를 손대지 않고, SELinux 를 겪어서 얻은
systemd 설정(`EnvironmentFile` 을 못 쓰는 이유가 주석에 있다)·인증서·워크트리 3개가 전부 그대로다.

⚠ **`du` 합계(18.3G)가 `df`(23G)와 4.7G 어긋나 확인했다** — `/opt/oracle/oradata` 가
`oracle:oinstall drwxr-x---` 라 **읽지 못해 0 으로 셌다.** 그 4.7G 는 **지울 수 없는 DB 데이터**다.
차이를 «반올림이겠지» 로 넘겼으면 «지울 게 더 있다» 는 틀린 결론이 나왔을 자리다.

### 10-2. 🔴 스냅샷 — **내가 준 순서가 틀렸다**

확장 순서에 *"파티션을 건드리기 전에 스냅샷을 뜨세요"* 를 넣었다. **그게 확장을 막았다.**

VirtualBox 는 스냅샷이 있으면 VM 이 **차등 디스크(differencing image)** 위에서 돈다.
그 상태로 base 를 `--resize` 하면 **명령은 성공하고 게스트는 그대로다**:

```
TestVm.vdi                 51200 MB   base          ← 늘어났다
  └─ {93119613-...}.vdi    30720 MB   differencing  ← VM 이 실제로 쓰는 것
```

⚠ **차등 디스크는 `--resize` 가 안 된다.** 길은 스냅샷 병합 하나뿐이었다.

**게스트에서 원인을 좁힌 방법** — 커널이 낡은 값을 보는 것과 구분해야 했다:
- `uptime -s` = 17:26 · 부팅 로그가 **커널 새로 올라옴**(재개가 아니다)
- 그 부팅의 `dmesg`: `[sda] 62914560 512-byte logical blocks: (30.0 GiB)`
→ **부팅 시점에 붙어 있던 디스크가 실제로 30G** 였다. 즉 게스트 문제가 아니다.
- `lsblk -o SERIAL` = `VB62d58522-...` → **VirtualBox 는 VDI UUID 로 시리얼을 만든다.**
  호스트 `list hdds` 에서 그 UUID 를 찾아 **어느 파일이 진짜 붙어 있는지** 지목할 수 있었다.

→ **안전망은 스냅샷이 아니라 VM 폴더 복사**여야 했다. 스냅샷은 「되돌리기」 수단이면서
동시에 **디스크 구조를 바꾸는 조작**이라, 디스크 자체를 만지는 작업에는 쓸 수 없다.

### 10-3. 지금 상태 — **절반 끝났다**

```
sda        50G   ← 도달 (스냅샷 병합 후)
└─sda2     29G   ← 아직 (뒤에 21G 가 놀고 있다)
   └─rl-root 26G ← 그래서 / 도 그대로
```

`df -h /` = **26G · 22G 사용 · 4.7G 남음 · 83%**.

**남은 것**: `sudo parted /dev/sda resizepart 2 100%` → 재부팅 → `pvresize` → `lvextend` → `xfs_growfs /`.
⚠ parted 의 *"/etc/fstab 을 업데이트해야 합니다"* 는 **정형 안내라 무시한다** — UUID 도 파티션 번호도
안 바뀌므로 `fstab` 은 그대로 맞다.
⚠ `growpart` 는 없지만 **`parted` 가 이미 있어 아무것도 설치하지 않는다**(CLAUDE.md 버전 고정 규칙).

  3. 주문 상세 → 「주문 취소」 → 🔴 폼에 **"사용한 적립금 ○○원은 …돌려드립니다"** 가 뜬다
  4. 취소 후 → 🔴 **잔액이 1번 값으로 복귀** · 적립금 이력에 **「주문 취소 환불」** 줄
  ⚠ 대조군: **적립금을 안 쓴 주문**의 취소 폼에는 그 줄이 **없어야** 맞다(«0P 환불» 을 안 만든다).
  ⚠ 적립금 잔액이 0 이면 2번을 못 한다 — 적립은 **배송완료**에만 붙는다.
  ⚠ 검증 잔재가 생긴다 — 주문이므로 조건부 잔여 7번에 합류한다. **`ZZ` 를 붙일 것.**

  (아래 9번). 이월에서는 빠진다 — 결정이 끝났으므로 매일 따라 내려올 항목이 아니다.

  **보이지만** 그 시점 화면을 보지 않았다. 단위 테스트는 덮고 있다.

    **끄는 방법은 아직 안 찾았다** — 시스템 동작을 바꾸는 일이라 확인받고 해야 한다.
  ⚠ **`~/.npm/_cacache` 가 왜 되살아나는지 모른다**(§10). 109M 이라 급하지 않지만 **추측으로 적지 않는다.**

## 8. 🔴 후보를 뽑다가 나온 것 — **취소하면 적립금이 사라지고 있었다** (커밋 `c724ae6`)

G-3 를 닫고 «다음은 무엇인가» 를 **BACKLOG 문장을 옮기지 않고 코드에서 다시 뽑다가**(WA §1-3)
후보 목록에 없던 것이 나왔다. 백로그가 «만들 것» 을 적는 문서라 **이미 있는 기능의 구멍**은 거기 없다.

### 8-1. 실측 — 코드 경로로 뽑고, 그다음 **실제로 잃는지** 확인했다

| 실측 | 자리 |
|---|---|
| 적립금은 **주문 시점에 즉시 차감** | `OrderService:137` `pointService.use(...)` |
| 취소는 `ORDERED`·`PAID` = **차감 이후** | `Order.isCancellable()` |
| `cancel()` 은 **재고 복원 + 알림만** | `OrderService:292-303` |
| `PointService` 에 취소용 환불 **없음** | `use`·`earnOnDelivery`·`refundReturnedOrder` 뿐 |
| `OrderCancelledEvent` 구독자 = **판매량·알림** | 적립금 경로 없음 |
| 취소와 적립금을 함께 보는 테스트 | **0건** |

⚠ **여기서 멈추지 않았다.** 위는 전부 «없다» 의 나열이라, 그것만으로는 *"내가 못 찾은 것"* 과
구분되지 않는다(WA §3-3). 그래서 **재현 테스트를 먼저 써서 빨간 것을 봤다**:

```
🔴 주문을 취소하면 쓴 적립금이 돌아온다
   JSON path "$.data.balance" expected:<500> but was:<0>
```

500P 를 쓰고 취소했더니 **잔액이 0 으로 남는다.** 그리고 그때 다른 10건은 전부 통과했다 —
재현 조건이 정확하다는 뜻이다.

🔴 **화면은 «취소됨» 으로 멀쩡하고 알림도 정상이다.** 고객이 잔액을 들여다보기 전까지 아무도 모른다.
오늘 오전 §2-2 의 지뢰(`/products/null#inquiries`)와 **같은 종류** — 틀린 것이 코드 경로가 아니라 **값**이다.

### 8-2. 이건 «안 만든 기능» 이 아니라 **비대칭**이다

반품 승인은 **처음부터 환불했다**(`refundReturnedOrder`). 문서 어디에도 *"취소는 환불하지 않는다"* 는
결정이 없다. B-17(2026-08-04)이 고친 *"반품엔 사유가 있는데 취소엔 없다"* 와 **같은 모양의 구멍**이다.

→ 짝이 있는 두 흐름 중 **한쪽만 손댈 때** 생긴다. 그때 다른 쪽을 나란히 놓고 보지 않으면
«없는 것» 은 눈에 안 띈다 — 있는 것은 보이지만 **없는 것은 안 보인다**.

### 8-3. 설계 — **반품 메서드를 재사용하지 않았다**

`refundCancelledOrder(memberId, usedPoint, orderId)` 를 새로 만들었다. 취소에는 **되돌릴 것이 하나뿐**이다:

| 반품이 하는 것 | 취소는? | 왜 |
|---|---|---|
| 결제금액 환불 | ❌ | 취소는 **쓴 적립금**만 돌려준다(결제가 확정된 적이 없다) |
| 적립 회수 | ❌ **없음** | 적립은 배송완료에만 붙는다 — **줄 일이 없었으니 뺄 것도 없다** |
| 등급·누적 되돌림 | ❌ **없음** | 누적 구매액도 배송완료에만 오른다 — 부르면 **안 더한 것을 뺀다** |

→ 재사용했다면 인자 셋 중 둘이 늘 `0` 인 호출이 된다. 그건 읽는 사람에게 *"취소도 적립을 회수하는구나"*
라는 **틀린 인상**을 준다. **M3 이 이걸 실제로 증명했다**(§8-4).

⚠ **`PointType` 에 `CANCEL` 을 안 만들었다.** 값을 늘리면 Oracle CHECK 제약 마이그레이션이 따라오는데,
**취소인지 반품인지는 `order_id` 로 이미 되짚어진다**(주문 상태가 답을 갖고 있다).
같은 정보를 두 번 적지 않는다 — 재고 이력에 취소 사유를 복사하지 않은 것(V39)과 같은 판단이다.
→ **그래서 이 작업엔 마이그레이션이 없다.** 빈 DB 검증(WA §2-2)도 해당 없음.

⚠ **이벤트로 빼지 않았다.** `@Async` 는 best-effort 라 유실되면 **고객 돈이 사라진다** —
재고 복원을 이벤트로 안 뺀 것, 배송완료 적립을 동기로 둔 것과 같은 판단이다.
순서도 반품 승인과 맞췄다: **재고 → 환불 → 이벤트(알림)**.

### 8-4. 변형 주입 (WA §3) — **5건 전부 잡힘**

| # | 무엇을 망가뜨렸나 | 결과 |
|---|---|---|
| M1 | 환불 호출 자체를 삭제(고치기 전 코드) | **2건 빨감** |
| M2 | `usedPoint <= 0` 가드 제거 | **1건 빨감** — 0원 이력이 생겼다 |
| M3 | **반품 메서드를 재사용**(`refundReturnedOrder`) | **2건 빨감** — 🔴 `totalPurchase` **50,000 → 500** |
| M4 | 잔액만 올리고 **이력을 안 남김** | **2건 빨감** — 원장 불변식(`SUM == balance`)이 실제로 돈다 |
| M5 | `usedPoint` 대신 `refundableAmount` 환불 | **3건 빨감** — 🔴 잔액 **50,000** (취소로 돈을 버는 구멍) |

⚠ **M2·M3 은 새로 쓴 테스트 둘이 잡았다.** 처음 재현 테스트 하나만 있었다면 **둘 다 통과했을 것**이다 —
잔액도 맞고 이력 합도 맞기 때문이다. 「고친 것을 지키는 테스트」와 「고치면서 새로 생긴 틀릴 자리를
지키는 테스트」는 다르다.

### 8-5. 화면 — 반품은 말하고 있었는데 취소는 아무 말이 없었다

취소 폼에 *"사용한 적립금 500원은 취소와 함께 돌려드립니다"* 를 붙였다(**적립금을 쓴 주문에만**).
