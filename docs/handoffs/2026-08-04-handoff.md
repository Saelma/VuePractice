## 2. B-19 재고 변경 이력 — **착수**

### 2-1. 착수 전 실측 — 백로그 항목이 놓친 것이 하나 있다

> WA §1-3 · 8/03 교훈(*"백로그 문장은 착수 시 코드로 다시 확인해야 한다 — 오늘도 두 번 걸렸다"*).

**맞았던 것**: `stock_history` 는 실제로 **없다**(`grep -ril stock_history src/` → 0건).
재고를 바꾸는 지점은 **정확히 다섯 곳**이고, 벌크 UPDATE 두 개(`decreaseStock`·`increaseStock`)에
주문·취소·반품이 전부 모여 있어 **기록 지점이 좁다**:

| # | 경로 | 위치 | 사유 |
|---|---|---|---|
| 1 | 주문 생성 | `OrderService.checkout:85` → `decreaseStock` | `ORDER` |
| 2 | 주문 취소 | `OrderService.cancel:280` → `increaseStock` | `CANCEL` |
| 3 | 반품 승인 | `OrderService.approveReturn:315` → `increaseStock` | `RETURN` |
| 4 | 상품 생성 | `ProductCommandService.create` → `saveVariants` | 초기 재고 |
| 5 | 상품 편집 | `ProductCommandService.update` → `saveVariants` | 관리자 편집 |

**🔴 틀렸던 것 — `variant_id` 는 안정적인 키가 아니다.**

백로그는 *"적립금 이력(`point_history`)이 원장 역할을 하는 선례를 그대로 따르면 된다"* 고 적었는데,
**그대로는 안 된다**. `point_history.member_id` 는 안 바뀌지만 `variant_id` 는 바뀐다:

- `ProductCommandService.update()` 는 옵션을 **통째로 교체**한다
  (`variantRepository.deleteAll(...)` + `saveVariants(...)`, `ProductCommandService.java:82-84`).
- `ProductVariant.of()` 는 **새 엔티티**를 만드므로 PK(UUIDv7)가 새로 발급된다.
- → 관리자가 상품을 **한 번만 저장해도 모든 옵션의 id 가 바뀐다.**

`stock_history.variant_id` 만으로 조회하면 **관리자 편집 한 번에 이력이 통째로 끊긴다** —
원장으로 쓰려고 만든 것이 정작 *"어제 10개였는데"* 를 못 잇는다.

**대응 (결정)**: `order_item` 이 **이미 같은 문제를 스냅샷으로 풀었다** — 옵션이 지워져도 과거 주문
표시가 멀쩡하도록 `variant_name` 을 실어 둔다(`ProductCommandService.java:80` 주석이 그 근거를 적고 있다).
같은 방식으로 간다:

- `stock_history` 에 **`product_id` + `variant_name` 스냅샷**을 함께 남긴다.
- **조회 기준은 `product_id`** 다(`variant_id` 는 느슨한 참조로만 남긴다).

**버린 안**: 옵션 교체를 부분 갱신(id 매칭·삭제 판정)으로 바꾸는 방법. `variant_id` 가 안정되면
스냅샷이 필요 없지만, 그 자리는 **주문·장바구니가 얹혀 있어** B-19 범위를 훨씬 넘는다. 그리고
`ProductCommandService.java:78-79` 가 통째 교체를 고른 이유를 이미 적어 뒀다(*"부분 갱신보다 단순하고
어긋날 여지가 없다"*) — 그 결정을 B-19 때문에 뒤집지 않는다.

### 2-3. 구현 — 커밋 `e75a161`

기록 지점은 §2-1 에서 센 다섯 곳 그대로이고, **전부 `ProductCommandService` 를 지난다**(주문·취소·반품은

곁따라 바뀐 것 셋 — **셋 다 "이력이 근거를 갖게" 하려고 생긴 변경**이다:

| 바뀐 것 | 왜 |

| `OrderService.checkout` 의 재고 차감을 `orderRepository.save()` **뒤로** 옮겼다 | 이력에 `order_id` 를 실어야 하는데 먼저 차감하면 넣을 값이 없다. **적립금 차감이 이미 뒤에 있던 것과 같은 이유**라, 새 규칙이 아니라 있던 규칙에 맞춘 것이다 |

앱이 떴다는 것이 곧 **`ddl-auto=validate` 통과**(= 엔티티와 스키마 일치)다.

떠 있는 동안 `stock_history` 를 실측했다:

| 본 것 | 결과 |
|---|---|
| `VARCHAR2` 의 semantics (WA §2-2-1) | `variant_name`·`reason`·`actor_name` **전부 `char_used='C'`** |
| 감사 컬럼 타입 | `created_at`·`updated_at` **`TIMESTAMP(9) WITH TIME ZONE`** (V26 사고 회피) |
| CHECK 제약 | `reason IN ('ORDER','CANCEL','RETURN','ADMIN_CREATE','ADMIN_EDIT')` |
| FK | `fk_stock_history_product` (R) — 옵션에는 안 걸었다(의도대로) |
| 인덱스 | `idx_stock_history_product` = `PRODUCT_ID` + `SYS_EXTRACT_UTC("CREATED_AT")` |

마지막 줄이 처음엔 낯설어 보인다(2번째 열이 `SYS_NC00013$`). **Oracle 은 `TIMESTAMP WITH TIME ZONE`
컬럼을 색인하면 함수 기반 인덱스로 만든다** — 전수로 확인해 보니 `point_history`(이 설계가 따라온 선례) ·
`orders` · `admin_audit_log` · `member_coupon` 이 **전부 같은 모양**이다. 새로 생긴 문제가 아니다.

## 3. B-17 주문 취소 사유 — **착수** (B-19 를 닫고 이어서)

### 3-1. 착수 전 실측 — **백로그 전제가 오늘만 두 번째로 뒤집혔다**

> WA §1-3. 오늘 §2-1 에서 한 번 겪고도 또 나왔다 — 이 절차를 건너뛰면 안 되는 이유가 하루에 두 번 실증됐다.

**맞았던 것**: 비대칭은 실재한다 — `requestReturn(id, memberId, reason)` 인데 `cancel(id, memberId)` 다.

**🔴 틀렸던 것 — *"취소는 고객도 관리자도 한다"*.** **관리자는 취소를 할 수 없다**:

- `AdminOrderControllerImpl` 전수 = **GET 3개뿐**(`list` · `counts` · `by-member`).
- 취소는 `POST /api/orders/{id}/cancel` 하나이고 `findByIdAndMemberId` 라 **본인 주문만**.

→ 그래서 백로그의 *"누가 취소했는지도 함께 남길지 착수 시 결정"* 은 **지금 답이 정해져 있다** —
취소자는 **항상 주문자 본인**이라 행위자 컬럼을 두면 늘 같은 값이 들어간다. **두지 않았다.**

**⚠ 하나 더 — 백로그가 적은 자리도 정확하지 않았다.** *"관리자 주문 목록에서 왜 취소됐는지 알 방법이
없다"* 고 했는데, `AdminOrderResponse` 에는 **반품 사유조차 없다.** 관리자도 사유는 **주문 상세**에서
본다. 그래서 취소 사유도 상세(`OrderResponse`)에 실었다 — 목록에 넣는 건 반품과의 대칭을 깨는 별개 결정이다.

**선례(그대로 따랐다)**: `return_reason VARCHAR2(500 CHAR)`(V24) · 자유 입력 · 주문 상세 표시.
`cancelled_at` 은 V10 에 이미 있어 **V40 은 `cancel_reason` 한 컬럼**이다.

### 3-2. 착수 시 결정 (사용자)

| 물은 것 | 정한 것 | 근거 |
|---|---|---|
| 사유는 필수인가 | **선택** | 취소는 **돈이 오가기 전** 단계라 입력을 강제하면 마찰이 값보다 크다. 반품이 필수인 건 환불·적립 회수가 얽히기 때문이다 |
| 입력 방식 | **자유 입력만**(선택지 없음) | 반품과 같게 맞춰야 두 화면이 안 갈리고, 선택지를 만들면 그 목록을 관리해야 한다(B-20 에서 같은 판단) |
| 관리자 취소도 만드나 | **안 만든다** | 백로그 전제가 틀렸다고 범위를 늘리지 않는다. 관리자 취소엔 *발송 후에도 되는가·환불까지 따라오는가* 가 얹혀 **크기가 소 → 중**이 된다. BACKLOG 에 별도 항목으로 남겼다 |

**안 덮인 것은 그 사이의 Vue 폼 배선 한 칸**이고, 이 프로젝트는 컴포넌트 렌더링 테스트가 없어
구조적으로 못 덮는 자리다(WA §3). **조건부 잔여로 남긴다.**

**⚠ 5번이 어제 남긴 미확인을 덤으로 닫았다.** 반품 승인이 재고를 복원하면서 `stock_history` 에
**`RETURN +1`(15:30:06)** 이 처음으로 기록됐다 — 어제는 `RETURN` 경로를 브라우저로 안 밟아
통합 테스트로만 덮여 있었다.

**잔재**: 주문 **3건**(`2125`·`2126` CANCELLED, `2127` RETURNED). 상품은 새로 만들지 않고
기존 것을 썼다 → `ZZ` 상품·회원 **0**. 주문 삭제 API 가 없어 7/31 규칙대로 남긴다.

### 3-7. 곁가지 — **끊긴 클라이언트 예외가 배포 확인을 오염시키고 있었다**

브라우저 검증 중 로그를 보다 발견했다. **B-17 때문이 아니라 기존 문제**다(같은 예외가 오늘
배포 **전** 구 jar 에서도 2번 났다):

```
AsyncRequestNotUsableException: Servlet container error notification for disconnected client
  Caused by: java.io.IOException: 파이프가 깨어짐
→ GlobalExceptionHandler#handleUnexpected 가 2차 실패:
  HttpMessageNotWritableException: No converter for ApiResponse with preset Content-Type 'text/event-stream'
```

알림 SSE 는 오래 열려 있는 응답이라 브라우저 이동·서버 재시작에 끊긴다. 포괄 `Exception` 핸들러가
그걸 받아 **①`ERROR "Unhandled exception"` 을 남기고 ②받을 사람이 없는데 답을 쓰려다 또 실패**했다.

**①이 진짜 문제다** — 배포 확인에서 *"ERROR 0건"* 을 근거로 쓰는데, **브라우저를 몇 번 움직이기만
해도 오염된다.** 확인 수단이 조용히 못 쓰게 되는 종류라 지금 고쳤다(커밋 `d08fc94`).
전용 핸들러로 먼저 잡아 `debug` 로만 남기고 `void` 를 돌려준다(본문을 안 만들면 ②도 사라진다).

테스트는 **통합이 아니라 `ExceptionHandlerMethodResolver` 에 직접 물었다** — 끊긴 클라이언트를
MockMvc 로 재현할 수 없고, 포괄 핸들러가 있는 곳에서는 *"실제로 먼저 잡히는가"* 가 곧 규칙이다.
변형 2건(애노테이션 제거 → **2**, `void` 대신 본문 반환 → **1**) 다 잡혔다. 백엔드 **595 tests**(+3).

**🔴 여기서 사고를 하나 냈다 — WA §3(2026-07-31 G-2)의 재발이다.**
SSE 수정을 **커밋하기 전에** 변형을 얹고 `git checkout -- src/main` 으로 되돌렸다. 규약이
*"커밋 전이면 기능도 함께 날아간다"* 고 **명시해 둔 바로 그 함정**인데 그대로 밟았다.
새 파일(테스트)은 추적 대상이 아니라 살아남았고 **수정한 기존 파일만 사라져서**, 증상이
*"테스트는 그대로인데 갑자기 빨개짐"* 으로 보였다.
→ 대화 기록으로 복구한 뒤 **커밋을 먼저 하고** 나머지 변형을 넣었다(그다음부터는 원복이 안전했다).
→ **규약을 읽은 것과 그 순간 지키는 것은 다르다.** G-2 때도 같은 결론이 났는데 또 났다 —
   WA 에 「변형 주입 전 체크」를 한 줄 더 박아 둔다(§3-8).

### 3-8. WA 보강 — 변형 주입 전에 `git status` 를 본다

위 사고를 규약으로 옮겼다. *"커밋 뒤에 한다"* 는 문장만으로는 안 걸러진다는 게 **두 번째로**
증명됐으므로, **확인 동작**을 규약에 넣는다: 변형을 넣기 전에 `git status --short` 가
**비어 있는지** 본다(비어 있지 않으면 그 파일은 되돌릴 때 날아간다).

### 3-9. SSE 수정 배포 — ⚠ **배포는 됐지만 «고쳐졌다» 는 아직 못 적는다**

배포 증거: jar **16:03:47** · 서비스 **16:04:17** · health `UP` · 배포 후 `ERROR` **0건**.

**그런데 `ERROR 0건` 이 여기서는 증명이 아니다.** 이 수정이 사는 자리는 *"SSE 가 붙어 있다가 끊길 때"*
인데, 배포 후 nginx 로그를 보니 **연결이 아예 안 맺어지고 있다** — `/api/notifications/stream` 이
**31초마다 401** 로 되돌아온다(만료된 토큰을 든 탭이 재시도 중). 붙지 않으면 끊길 일도 없고,
끊기지 않으면 그 예외도 안 난다. 즉 **경로를 한 번도 안 밟은 채로 0건**이다.

→ 그래서 §3-7 은 **「배포됨」까지만 참**이고, *"이제 로그가 깨끗하다"* 는 **다음에 SSE 가 실제로
붙었다 끊길 때** 확인해야 한다(조건부 잔여에 적었다).
→ ⚠ 이건 WA §5 의 *"확인 수단은 매번 이 변경의 성질에서 찾는다"* 가 걸리는 자리다. 「ERROR 0건」은
**평소엔 좋은 신호지만 이번엔 정확히 반대**다 — 0 이 나올 이유가 두 개(고쳐졌다 / 안 밟았다)인데
구분이 안 된다. **0 이 정상인 화면을 볼 때와 같은 함정**이고(§2-8 에서 한 번 겪었다), 그때처럼
**기대값을 먼저 뽑았어야** 했다.

**곁다리로 드러난 것**: 오늘 `/api/notifications/stream` 은 **200 이 7건, 401 이 108건**이다.
만료된 토큰을 든 탭이 **31초마다 영원히 재시도**한다 — 사용자에게 보이는 고장은 아니지만
서버는 계속 두드려 맞는다. **조건부 잔여로 남긴다**(B-17 과 무관하고, 고치려면 재연결 정책·토큰
갱신을 함께 봐야 한다).

### 5-3. 구현 — 커밋 `349893e`

🔴 **이 기능의 위험은 전부 «같은 컬럼을 세 곳이 다르게 다룬다» 에 있다.**

| 자리 | 숨긴 리뷰를 | 안 하면 |
|---|---|---|
| 상품 리뷰 목록 | **뺀다**(작성자 본인에게도) | 숨김이 안 먹는다 |
| 평균 별점·리뷰 수 | **뺀다** | ⚠ **보이지도 않는 리뷰가 별점을 끌어내린다** — 화면은 멀쩡해서 제일 안 보인다 |
| 상품당 1회 제한 | 🔴 **그대로 센다** | 숨기자마자 작성자가 새로 써서 **숨김이 무의미**해진다 |

셋 중 마지막만 반대라 헷갈리기 쉽다 — **규칙마다 테스트를 따로** 뒀다.

관리자 목록은 **리포지토리 메서드부터 나눴다**(`findForAdmin`). 고객 목록은 *"숨긴 것을 빼는"* 게

「누구에게 보이나」 플래그를 더하면 그 규칙이 호출부마다 갈린다.

상품명은 catalog 의 `ProductQueryService.findByIds` 로 **한 번에 모아** 가져온다 — 엔티티를 조인하면
도메인 경계를 깨고(CLAUDE.md), 리뷰마다 조회하면 N+1 이다.

⚠ `hidden` 은 **세 가지 상태**다(`null`=전체 / `false`=보이는 것만 / `true`=숨긴 것만).
`apiGet` 이 `null`·`''`·`undefined` 만 거르고 **`false` 는 보내는** 성질에 기댄다 — 그 성질을
프론트 테스트로 못박았다. falsy 로 걸러 버리면 **「보이는 것만」이 조용히 「전체」가 된다.**

8. **취소 폼에 공백만 넣고 누르는 경로를 화면에서 안 봤다**(2026-08-04, §3-6).
   서버 쪽 공백→NULL 은 통합 테스트가, 프론트 `'' → {reason: null}` 은 단위 테스트가 덮는다.
   **안 덮인 것은 그 사이의 Vue 폼 배선 한 칸**이고, 이 프로젝트엔 컴포넌트 렌더링 테스트가 없어
   **구조적으로 못 덮는 자리**다(WA §3).
   - 남은 일: 다음에 주문 취소 화면을 열 일이 있으면 **스페이스만 넣고 눌러 본다**(사유 줄이 안 뜨면 정상).
     ⚠ 취소 가능한 주문이 하나 필요하다 — 그것 때문에 따로 주문을 만들 만한 항목은 아니다.

9. **끊긴 클라이언트 수정이 실제로 도는지 못 봤다**(2026-08-04, §3-9).
   배포는 됐고 `ERROR` 도 0건인데, **SSE 가 안 붙고 있어서 끊길 일도 없었다** — 경로를 한 번도
   안 밟은 채 0건이다. *"이제 로그가 깨끗하다"* 는 **아직 못 적는 말**이다.
   - 남은 일: SSE 가 **붙었다 끊기는** 상황을 한 번 만들고(로그인한 탭에서 페이지 이동)
     `journalctl … | grep -c AsyncRequestNotUsableException` 이 **0** 인지 본다.

10. **만료 토큰 탭이 SSE 를 31초마다 무한 재시도한다**(2026-08-04, §3-9).
    오늘 `/api/notifications/stream` 이 **200 7건 · 401 108건**이었다. 사용자에게 보이는 고장은
    아니지만 서버는 계속 두드려 맞는다.
    - ⚠ 고치려면 **재연결 정책과 토큰 갱신을 같이** 봐야 한다(401 이면 재시도를 멈출지, 갱신 후
      다시 붙을지). 그래서 한 줄 수정이 아니다 — 필요해지면 백로그 항목으로 올린다.
