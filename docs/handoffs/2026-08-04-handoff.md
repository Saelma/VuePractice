## 2. B-19 재고 변경 이력 — **착수**

### 2-1. 착수 전 실측 — 백로그 항목이 놓친 것이 하나 있다

> WA §1-3 · 8/03 교훈(*"백로그 문장은 착수 시 코드로 다시 확인해야 한다 — 오늘도 두 번 걸렸다"*).

**맞았던 것**: `stock_history` 는 실제로 **없다**(`grep -ril stock_history src/` → 0건).
재고를 바꾸는 지점은 **정확히 다섯 곳**이고, 벌크 UPDATE 두 개(`decreaseStock`·`increaseStock`)에
주문·취소·반품이 전부 모여 있어 **기록 지점이 좁다**:

| # | 경로 | 위치 | 사유 |
|---|---|---|---|
| 1 | 주문 생성 | `OrderService.checkout:85` → `decreaseStock` | `ORDER` |
| 2 | 주문 취소 | `OrderService.cancel:280` → `increaseStock` | `CANCEL` |
| 3 | 반품 승인 | `OrderService.approveReturn:315` → `increaseStock` | `RETURN` |
| 4 | 상품 생성 | `ProductCommandService.create` → `saveVariants` | 초기 재고 |
| 5 | 상품 편집 | `ProductCommandService.update` → `saveVariants` | 관리자 편집 |

**🔴 틀렸던 것 — `variant_id` 는 안정적인 키가 아니다.**

백로그는 *"적립금 이력(`point_history`)이 원장 역할을 하는 선례를 그대로 따르면 된다"* 고 적었는데,
**그대로는 안 된다**. `point_history.member_id` 는 안 바뀌지만 `variant_id` 는 바뀐다:

- `ProductCommandService.update()` 는 옵션을 **통째로 교체**한다
  (`variantRepository.deleteAll(...)` + `saveVariants(...)`, `ProductCommandService.java:82-84`).
- `ProductVariant.of()` 는 **새 엔티티**를 만드므로 PK(UUIDv7)가 새로 발급된다.
- → 관리자가 상품을 **한 번만 저장해도 모든 옵션의 id 가 바뀐다.**

`stock_history.variant_id` 만으로 조회하면 **관리자 편집 한 번에 이력이 통째로 끊긴다** —
원장으로 쓰려고 만든 것이 정작 *"어제 10개였는데"* 를 못 잇는다.

**대응 (결정)**: `order_item` 이 **이미 같은 문제를 스냅샷으로 풀었다** — 옵션이 지워져도 과거 주문
표시가 멀쩡하도록 `variant_name` 을 실어 둔다(`ProductCommandService.java:80` 주석이 그 근거를 적고 있다).
같은 방식으로 간다:

- `stock_history` 에 **`product_id` + `variant_name` 스냅샷**을 함께 남긴다.
- **조회 기준은 `product_id`** 다(`variant_id` 는 느슨한 참조로만 남긴다).

**버린 안**: 옵션 교체를 부분 갱신(id 매칭·삭제 판정)으로 바꾸는 방법. `variant_id` 가 안정되면
스냅샷이 필요 없지만, 그 자리는 **주문·장바구니가 얹혀 있어** B-19 범위를 훨씬 넘는다. 그리고
`ProductCommandService.java:78-79` 가 통째 교체를 고른 이유를 이미 적어 뒀다(*"부분 갱신보다 단순하고
어긋날 여지가 없다"*) — 그 결정을 B-19 때문에 뒤집지 않는다.

### 2-3. 구현 — 커밋 `e75a161`

기록 지점은 §2-1 에서 센 다섯 곳 그대로이고, **전부 `ProductCommandService` 를 지난다**(주문·취소·반품은
`decreaseStock`/`increaseStock` 으로, 관리자 등록·편집은 `create`/`update` 로). 그래서 기록을 그 한 클래스에
모을 수 있었다.

곁따라 바뀐 것 셋 — **셋 다 "이력이 근거를 갖게" 하려고 생긴 변경**이다:

| 바뀐 것 | 왜 |
|---|---|
| `OrderService.checkout` 의 재고 차감을 `orderRepository.save()` **뒤로** 옮겼다 | 이력에 `order_id` 를 실어야 하는데 먼저 차감하면 넣을 값이 없다. **적립금 차감이 이미 뒤에 있던 것과 같은 이유**라, 새 규칙이 아니라 있던 규칙에 맞춘 것이다 |
| `decreaseStock` 이 차감 후 스냅샷을 **한 번만** 읽는다 | 이력과 재고부족 이벤트가 **같은 스냅샷**을 쓰므로 둘이 갈릴 수 없다(전에는 이벤트만 읽었다) |
| `@LoginUser AuthUser` 를 `create()`·`update()` 까지 전달 | §2-2 의 「누가」 결정. 컨트롤러 인터페이스엔 `@Parameter(hidden = true)` 로 감춘다 |

⚠ **주문번호 시퀀스에 구멍이 날 수 있다**는 대가가 첫 변경에 붙는다(롤백돼도 시퀀스는 안 돌아간다).
다만 **이미 있던 성질**이다 — 적립금 부족으로 실패하는 경로가 원래 `save()` 뒤에 있었다. 늘어난 것은
*"동시에 마지막 재고를 집는 경합"* 하나뿐이고, 장바구니 단계의 `available()` 이 먼저 거른다.

### 2-6. V39 빈 DB 검증 (WA §2-2) — **통과** · 조건부 잔여 8번도 여기서 닫았다

`esptest` 스키마를 비우고(`tables_left=0` · `seqs_left=0`) 8083 으로 기동했다.

```
Successfully validated 39 migrations
Current version of schema "ESPTEST": << Empty Schema >>
Migrating schema "ESPTEST" to version "1 - init"
  … (39건, 번호 순서대로)
Migrating schema "ESPTEST" to version "39 - add stock history"

```

앱이 떴다는 것이 곧 **`ddl-auto=validate` 통과**(= 엔티티와 스키마 일치)다.

떠 있는 동안 `stock_history` 를 실측했다:

| 본 것 | 결과 |
|---|---|
| `VARCHAR2` 의 semantics (WA §2-2-1) | `variant_name`·`reason`·`actor_name` **전부 `char_used='C'`** |
| 감사 컬럼 타입 | `created_at`·`updated_at` **`TIMESTAMP(9) WITH TIME ZONE`** (V26 사고 회피) |
| CHECK 제약 | `reason IN ('ORDER','CANCEL','RETURN','ADMIN_CREATE','ADMIN_EDIT')` |
| FK | `fk_stock_history_product` (R) — 옵션에는 안 걸었다(의도대로) |
| 인덱스 | `idx_stock_history_product` = `PRODUCT_ID` + `SYS_EXTRACT_UTC("CREATED_AT")` |

마지막 줄이 처음엔 낯설어 보인다(2번째 열이 `SYS_NC00013$`). **Oracle 은 `TIMESTAMP WITH TIME ZONE`
컬럼을 색인하면 함수 기반 인덱스로 만든다** — 전수로 확인해 보니 `point_history`(이 설계가 따라온 선례) ·
`orders` · `admin_audit_log` · `member_coupon` 이 **전부 같은 모양**이다. 새로 생긴 문제가 아니다.

**조건부 잔여 8번(빈 DB 검증 절차의 비밀번호 노출) — 닫는다.**
8/03 이 남긴 남은 일 두 가지를 여기서 처리했다:

- ① **확인**: 자격증명을 `SPRING_DATASOURCE_USERNAME`/`SPRING_DATASOURCE_PASSWORD` 로 넘기고
  **앱이 떠 있는 동안** 확인했다(8/03 에는 이미 내려가 있어서 못 봤다).
  `/proc/<pid>/cmdline` 의 인자는 **`--server.port=8083` 과 `--spring.profiles.active=dev` 둘뿐**이었고,
  `ps -ef` 전수에서 비밀번호 값 **0건**.
- ② **문서 반영**: `db/migration/README.md` 의 절차를 환경변수 방식으로 고치고, 확인 명령(2-1 단계)을
  절차 안에 넣었다 — *"떠 있는 동안 봐야 한다"* 는 것이 이번에 걸린 부분이라 순서까지 적어 뒀다.
- ⚠ **정직하게 적어 둔 한계**: 값이 사라진 게 아니라 **옮겨간 것**이다. 환경변수는 `/proc/<pid>/environ`
  에 남고, 그건 **프로세스 소유자만** 읽는다 — `cmdline`(누구나 읽힘)보다 낫지만 같은 계정에는 보인다.
