### 2-3. 통합이 못 보던 자리 — 여기가 이 작업의 값이다

통합테스트는 마지막에 `SUM(amount) == balance` 로 대조한다. 강력하지만 **못 보는 게 있다**:

1. **부호 오류를 못 잡는다.** `PointHistory.used()` 가 음수를 붙이는데, 양수로 적어도
   *잔액 캐시와 합계가 함께 틀리면* 대조는 통과한다. 이력의 `type`·부호를 **직접 보는 건 단위뿐**이다.
2. **승급 직후 요율.** 누적 99,000 인 회원이 10,000 원을 확정하면 SILVER 로 올라 **200P**(BRONZE 면 100P).
   *"적립률은 누적 반영 **후** 등급으로"* 라는 한 줄이 지켜지는지는 **이 한 케이스에서만** 갈린다.
3. **실패 경로에 이력이 남지 않는가.** 잔액 부족으로 예외가 났는데 원장에 줄이 생기면 합계가 갈라진다.
   행복 경로만 지나는 통합은 이 경로에 들어가지도 않는다.
4. **`Math.max` 가 두 군데** 걸린 반품 순변동 — 잔액 쪽과 이력 쪽. 한쪽만 지워도 정상 케이스는 멀쩡하다.

| 값의 전달 | 링크를 **메일로** | 아이디를 **메일로** | 화면에 띄우면 주소만 넣어 보며 계정을 수집할 수 있다 |
| 요청 제한 | 아이디 3 / IP 10 · 10분 | **주소 3 / IP 10 · 10분** | 성공 하나가 **메일 한 통**이라 비용이 성공에 붙는다 |
| 카운트 시점 | **조회 전** | **조회 전** | 조회 뒤에 세면 429 가 "그 계정은 있다" 를 알려준다 |

**⚠ 한 가지는 일부러 다르게 했다** — 재설정은 dev 에서 토큰을 응답에 실어 화면에 보여준다
(`auth.password-reset.expose-token`). 아이디 찾기엔 **그 갈래를 만들지 않았다**:
**저건 링크지만 이건 신원**이다. dev 확인은 Mailpit 로 한다.

### 3-3. ⚠ 가드를 재설정 것과 공유하지 않은 이유

처음엔 `PasswordResetRequestGuard` 를 그대로 쓰려 했는데 **못 쓴다** — 저쪽은 **아이디**를 세고
여기는 **이메일**을 센다. 억지로 합치면 더 나쁘다: **아이디 찾기를 세 번 하면 비밀번호 재설정
예산까지 소진**돼, 아이디를 되찾은 사람이 곧바로 비밀번호를 못 바꾼다.
→ 공유하는 것은 **카운터 구현**(`AttemptCounter`)이고 **정책(키·임계값)은 각자** 갖는다.
7/30 에 `AttemptCounter` 를 뺀 판단이 바로 여기서 값을 했다(새 가드는 키 2개 + 임계값 3줄이 전부다).

## 5. B-15 문의 답변 알림 — **완료 · 배포·검증 종결**

### 5-1. 왜 이걸 골랐나

오늘 아침 「다음 기능 후보」 표에서 1순위로 적어 둔 그대로다 — **인프라가 이미 전부 있어서**
가장 싸게 닫히는 구멍이었다. 착수 전 실측(WA §1-3)도 백로그 문장과 일치했다:

- 알림 타입은 `ORDER`·`STOCK`·`RESTOCK` **셋뿐**.
- `InquiryCommandService.answer()` 는 `log.info` 한 줄로 끝나고 `ApplicationEventPublisher`
  **주입조차 없었다**.
- 즉 **답변을 달아도 물어본 사람은 모른다.** 문의 화면에 다시 들어와 봐야 안다 —
  이커머스에서 문의는 "물었으면 답을 받는" 왕복인데, 그 왕복의 절반이 없었다.

### 5-2. ⚠ 착수하고 나서 갈린 것 — "이벤트 발행 한 줄"이 아니었다

백로그는 *"`INQUIRY` 타입 하나와 이벤트 발행 한 줄이면 붙는다"* 고 적었다. 붙이는 **양**은 맞았는데,
**어디에 붙이느냐**가 이 작업의 전부였다.

`answer()` 는 **등록·수정 겸용 API** 다(같은 엔드포인트를 다시 호출하면 답변이 갱신된다).
그래서 무조건 발행하면 관리자가 **오타를 고칠 때마다 알림이 간다.** → 첫 답변에서만 발행해야 한다:

```java
boolean firstAnswer = !inquiry.isAnswered();   // ⚠ 이 줄이 answer() 앞
inquiry.answer(req.answer());
if (firstAnswer) { eventPublisher.publishEvent(new InquiryAnsweredEvent(...)); }
```

⚠ **두 줄의 순서가 기능의 유무를 가른다.** `inquiry.answer()` 가 상태를 `ANSWERED` 로 올리므로,
판정을 한 줄 **뒤**에서 하면 `firstAnswer` 가 **영영 `false`** 가 되어 알림이 **아예 안 나간다.**
둘 다 컴파일되고 답변 기능 자체는 멀쩡하다 — **테스트 없이는 배포 후에야 드러나는** 종류다.

### 5-3. 만든 것

| 층 | 파일 | 내용 |
|---|---|---|
| 이벤트 | `domain/inquiry/event/InquiryAnsweredEvent` | `record(inquiryId, productId, authorId, inquiryTitle) implements DomainEvent` |
| 발행 | `InquiryCommandService.answer()` | `ApplicationEventPublisher` 주입 + **첫 답변에서만** 발행 |
| 리스너 | `domain/notification/InquiryEventListener` | `@Async` + `@TransactionalEventListener(AFTER_COMMIT)`, **위임만** |
| 핸들러 | `domain/notification/InquiryNotificationHandler` | `NotificationCommandService.create(authorId, INQUIRY, …)` |
| 타입 | `NotificationType.INQUIRY` | `"문의 답변 알림"` |
| 화면 | `ProductDetailView.vue` | `route.hash === '#inquiries'` 면 문의 섹션까지 스크롤 |

**설계에서 짚은 것 셋:**

1. **알림 대상은 발행자가 아니라 이벤트에 실린 작성자다.** 지금까지의 이벤트(주문·재고·재입고)는
   "행위자 = 대상" 이거나 구독자가 대상을 따로 들고 있었는데, 여기선 **답변한 관리자가 아니라
   물어본 사람**에게 가야 한다. 그래서 `authorId`·`productId`·`inquiryTitle` 을 **페이로드에 싣는다** —
   `inquiryId` 만 보내면 notification 이 inquiry 를 되물어야 하고, 그러면 **역방향 의존**이 생긴다
   (`ReviewRatingChangedEvent` 때와 같은 판단).
2. ⚠ **문의는 자기 URL 이 없다.** 상품 상세 안에 붙어 있어서 링크를 `/products/{id}` 로만 주면
   상품 맨 위로 떨어지고, 사용자가 문의를 **다시 찾아 내려가야 한다** → `#inquiries` 앵커를 붙였다.
   앵커 처리는 **라우터 `scrollBehavior` 가 아니라 `ProductDetailView` 안에서** 한다 —
   라우팅 시점엔 상품 데이터를 아직 못 받아 **문의 섹션이 렌더되기 전**이라 앵커 요소 자체가 없다.
   데이터가 온 뒤인 `onMounted` 끝자리가 맞는 자리다(탭 클릭과 같은 `scrollTo` 를 쓴다).
3. **opt-out 은 공짜로 따라왔다.** 알림 생성은 `NotificationCommandService.create` **한 곳**뿐이라
   타입별 on/off 가 그 안에서 존중되고, 설정 화면은 서버가 `NotificationType.values()` 를 통째로
   내려주므로 **토글이 저절로 생긴다**(프론트 설정 화면 변경 **0**).

**① 스켈레톤 때문에 `ref` 가 `null` 이었다 — 진짜 원인.**

```
const loading = ref(true)          // 초기 true
<div v-if="loading"> 스켈레톤 </div>
<template v-else-if="product">  … <section ref="inquirySec">  ← 여기 안에 있다
```

`onMounted` 는 `loading.value = false` 를 **`finally` 에서** 내렸다. 그래서 `await nextTick()` 을
지나도 화면은 **여전히 스켈레톤**이고 세 섹션 ref 가 전부 `null` 이다 → `scrollTo(null)` 은
`el?.` 옵셔널 체이닝이라 **에러 없이 조용히 아무 일도 안 한다.** 콘솔에 아무것도 안 남는다.

⚠ **같은 줄에 더 오래된 버그가 붙어 있었다** — `setupSpy()` 도 바로 그 자리에서 돌아
`map` 의 키가 전부 `null` 이고 `el && observer.observe(el)` 가 전부 건너뛴다. 즉 **상세 페이지의
탭 밑줄이 스크롤을 따라간 적이 없다**(내가 만든 게 아니라 원래 그랬다). 탭을 *클릭*하는 건
그때는 ref 가 채워져 있어 정상이라 **증상이 반쪽만 보였고, 그래서 아무도 못 봤다.**
→ `loading` 을 `nextTick` **앞**으로 옮겨 둘 다 고쳤다(실패 경로용 `finally` 는 남긴다).

**② 고쳐도 한 번의 스크롤로는 못 선다 — 위쪽이 나중에 자란다.**
`ProductReviews` 는 자기 데이터를 따로 받아 나중에 렌더된다. 스크롤은 **시작할 때 계산한 위치**로
가므로, 그 사이 리뷰 목록이 늘어나면 문의 섹션이 아래로 밀려 **리뷰 중간에 선다.**
→ `scrollToAnchor()`: `ResizeObserver(document.body)` 로 본문 높이가 변할 때마다 다시 맞추고
**2초 뒤 또는 사용자가 직접 움직이면**(`wheel`·`touchstart`·`keydown`) 즉시 손을 뗀다
(스크롤 하이재킹 방지). 화면을 벗어나면 `onBeforeUnmount` 에서 정리한다.

> **여기서 배운 것 — 옵셔널 체이닝은 실패를 삼킨다.**
> `el?.scrollIntoView(...)` 는 "요소가 없으면 넘어간다" 는 뜻인데, **없으면 안 되는 자리**에

**가장 큰 발견은 첫 줄이다.** `domain.notification` 패키지 평균은 26% 인데, 그 안에서
**리스너 100% / 핸들러 4%** 로 갈렸다 — 3층 컨벤션의 **가장 중요한 층만 정확히 비어 있다.**

**H-1(감사)·H-2(적립금)과 같은 종류의 사각**이 또 나온 셈이다.

### 6-5. ⚠ 이 도구의 한계 — 같은 날 실증됐다

B-15 의 가장 위험한 버그(발행 조건을 상태 변경 **뒤**에서 읽은 것)는 **그 줄이 실행되므로

### 10-2. 만든 것 — 3층 이벤트 + **광고해도 되는지 서버가 답하는** 구조

| 층/자리 | 내용 |
|---|---|
| 이벤트 | `MemberSignedUpEvent(memberId, loginId)` — member 도메인이 소유 |
| 발행 | `AuthService.signup()` (저장·적립금 계정 뒤) |
| 리스너 | `WelcomeCouponListener` — `@Async` + `AFTER_COMMIT`, 위임만 |
| 핸들러 | `WelcomeCouponHandler` — 설정된 쿠폰을 그 회원에게 발급 |
| 설정 | `coupon.welcome-coupon-id` ← `.env` 의 `WELCOME_COUPON_ID`. **비우면 기능 꺼짐**(운영 기본값) |
| 공개 API | `GET /api/coupons/welcome` — 없으면 `data:null` |
| 화면 | 홈 혜택 스트립 + 회원가입 화면 안내(둘 다 `null` 이면 **감춘다**) |

**설계에서 짚은 것 셋:**

1. ⚠ **탈퇴 이벤트와 처리 방식이 반대다.** `MemberWithdrawnEvent` 는 발행측 트랜잭션에 합류한다
   (정리에 실패하면 회원 삭제도 롤백돼야 하므로). 가입은 **`@Async` + `AFTER_COMMIT`** 이다 —
   **쿠폰 발급이 실패해도 가입은 유효해야** 하기 때문이다. 쿠폰은 관리자가 다시 줄 수 있지만
   **가입 실패는 사용자가 다시 겪어야 하는 일**이다. 같은 이유로 **적립금 계정 생성은 이벤트로 빼지
   않았다**(계정이 없으면 적립·사용이 통째로 막힌다 — 배송완료 적립을 동기로 둔 것과 같은 판단).
2. ⚠ **화면이 문구를 띄울지는 서버가 정한다.** 자동 발급은 설정으로 켜고 끄는 기능이라,
   화면에 혜택을 적어 두면 **설정을 끈 뒤에도 광고가 남는다.** 그래서 공개 엔드포인트가 **실제 DB 의
   쿠폰**을 돌려줄 때만 문구가 나온다 — 기존 스트립이 지키던 원칙(*"정책을 화면에 적으면 설정만
   바꿨을 때 안내가 거짓말이 된다"*)을 그대로 이었다.
3. ⚠ **보안 예외를 뚫으면서 옆칸까지 열지 않았다.** `/api/coupons/**` 는 인증 필요인데 안내만
   공개라 **그 위에** `GET /api/coupons/welcome` permitAll 을 넣었다(순서가 곧 효력이다).
   `/api/coupons/me` 가 **여전히 401** 인지도 테스트로 고정했다.

**설정 타입도 판단이 필요했다**: `UUID` 로 받으면 값을 안 넣었을 때(빈 문자열) **기동이 깨진다.**
"가입 쿠폰을 안 쓴다"는 정상 상태라 `String` 으로 받고 못 읽으면 비어 있는 값으로 답한다.
E-3(흔한 비밀번호 목록)은 반대로 **못 읽으면 기동 실패**로 뒀는데, 그건 조용히 약해지기 때문이다.
여기는 설정이 틀리면 **광고도 같이 사라져** 거짓말이 안 생긴다.

### 10-6. ⚠ 배포 직후 사용자 지적 → **설정에서 데이터로** (V36, 같은 날)

배포하고 `.env` 에 쿠폰 id 를 넣어 켠 직후 사용자가 물었다 — *"슈퍼 관리자에서 쿠폰 관리할 수 없나?
꼭 env 에서 추가해야 해? 좀 불편하잖아"*. **맞는 지적이라 그날 바로 바꿨다.**

`.env` 방식이 백로그의 최소안이긴 했지만, 불편함보다 이쪽이 더 컸다:

1. **바꿀 때마다 재시작**해야 한다(운영이면 못 할 짓이다).
2. **무엇이 가입 쿠폰인지 화면에서 안 보인다** — `.env` 를 열어 봐야 안다.
3. **죽은 설정이 남는다** — 쿠폰을 지워도 id 는 남고, 안내 API 는 조용히 꺼져 원인을 모른다.

→ **쿠폰이 데이터니 지정도 데이터다.** `coupon.welcome` 플래그(V36)로 옮기고 관리자 화면에서 토글한다.

| 자리 | 내용 |
|---|---|
| **V36** | `coupon.welcome NUMBER(1) DEFAULT 0 NOT NULL` — `member.suspended`(V30)와 같은 boolean 판단(enum CHECK 트랩 회피) |
| **유니크 인덱스** | `ux_coupon_welcome`(함수기반) — `CASE WHEN welcome=1 THEN 1 END` |
| API | `POST`/`DELETE /api/admin/coupons/{id}/welcome` (ADMIN) — 정지/해제와 같은 결 |
| 화면 | 쿠폰 목록에 **「가입 쿠폰」 배지** + 지정/해제 버튼 |
| 제거 | `CouponProperties` · `application.yml` 의 `coupon` 블록 · `.env` 의 `WELCOME_COUPON_ID` |

⚠ **앱이 막는데 왜 DB 제약까지 거는가**: 서비스가 *"기존 해제 → 새로 지정"* 을 한 트랜잭션에서 하지만,
**두 관리자가 동시에 지정하면 서로의 미커밋 변경을 못 봐 둘 다 1 이 될 수 있다.** 그러면 가입 쿠폰이
둘이 되어 **어느 쪽이 나갈지 조회 순서에 달린다.** 그래서 DB 가 최종 보장하고, 그 보장이 진짜인지도
**리포지토리로 앱 방어를 우회해** 테스트했다(`DataIntegrityViolationException`).

⚠ **설정을 지우면서 두 군데를 남기지 않았다** — 설정과 데이터가 공존하면 *"어느 쪽이 이겼는지"* 를
아무도 모른다. `.env` 항목까지 함께 지웠다.

**검증**: 516 → **517** 테스트(`skipped 0`). 변형 주입 3종 전부 잡힘 —
①지정 시 기존 해제 생략(단위 2 + 통합 1) ②핸들러 지정 가드 제거(1) ③해제가 지정으로(통합 1).

**V36 적용 실측**(espdb): `WELCOME NUMBER(1) NOT NULL` · `UX_COUPON_WELCOME UNIQUE FUNCTION-BASED` ·
기존 쿠폰은 **전부 비지정(0)** · `flyway_schema_history` 36 성공.

### 11-1. 오늘 되풀이된 것

- **백로그 문장은 착수 시 코드로 다시 확인해야 한다.** 오늘 세 번 걸렸다 — H-2 의 "소스 16개"(→17개),
  "통합 하나로 덮여 있다"(→안 돌았다), B-15 의 "이벤트 발행 한 줄"(→**한 줄이 어디 놓이냐**가 전부였다).
  WA §1-3 이 하루 종일 값을 했다.
- **"테스트가 있다" ≠ "그 코드가 돈다".** 파일 개수는 거친 지표다 → **WA §3 로 올렸다.**
- **내가 쓴 테스트를 내가 평가하지 않는다** — 운영 코드를 망가뜨려 빨개지는지로 잰다.
  세 항목 모두에 적용했다(H-2 5건 · G-1 3건 · B-15 5건, **전부 잡힘**) → **WA §3 로 올렸다.**
  ⚠ B-15 에서는 **원복 확인 규칙 자체가 값을 했다**(§5-5) — 주입된 변형이 남아 있던 걸 걷어냈다.
- **규율(문서)로 막은 것은 다시 뚫린다.** 게스트/호스트 구분을 7/30 에 겪고 `infra/README` 에 적어
  뒀는데 **오늘 안내에서 그 규칙을 내가 안 썼다**(§3-8). 7/30 의 IP 사고와 같은 모양이다.
- **enum 값 추가는 매번 DDL 을 직접 본다.** B-15 는 제약이 없어 그냥 끝났지만, 그 판정을
  **다른 문서의 주석이 아니라 V26 실물**로 했다(§5-4).
- ⚠ **테스트가 다 통과해도 화면은 틀릴 수 있다.** B-15 는 백엔드 변형 주입 5종을 전부 통과하고도
  **앵커가 안 먹었다**(§5-7) — 원인은 화면 쪽 `ref` 가 `null` 인 것이었고, `?.` 가 그 실패를
  **에러 없이 삼켰다**. 브라우저 5스텝이 아니었으면 못 봤다.
- **내가 코드를 끼워 넣는 자리는 그 줄만 보지 말고 주변 전제를 확인한다.** 앵커 한 줄을
  `setupSpy()` 옆에 넣으면서 **그 `setupSpy()` 가 이미 죽어 있다는 걸 못 봤다**(§5-7 ①) —
  같은 원인이었는데 내 코드가 실패한 뒤에야 드러났다.
- ⚠ **"덮은 줄 알았는데 그 층이 안 돌던" 사각이 오늘만 두 번, 통산 네 번**(H-1 감사 · H-2 적립금 ·
  §5-7 스크롤스파이 · §7 알림 핸들러). 매번 **증상이 반쪽만 보이는** 게 공통점이다 —
  리스너는 돌고 핸들러만 안 돌거나, 탭 클릭은 되고 스크롤 추적만 안 되거나.

  같은 날 데이터로 옮겼다(§10-6). → **"쓰는 사람이 어떻게 켜고 끄나"** 를 착수 시점에 한 번 묻는다.
- ⚠ **늘 하던 명령이 상황이 달라지면 반대로 동작한다.** `git checkout -- src/main` 은 H-6~H-8 에선
