## 2. ⚠ 진짜 사건 — 서버 IP가 `.36` → `.14`로 바뀌어 있었다

### 2-1. 증상은 "테스트 61건 실패"였다

첫 `gradle test`가 173건 중 **61건 실패**. 전부 같은 모양이었다.

```
java.lang.IllegalStateException at DefaultCacheAwareContextLoaderDelegate.java:157
```

이건 **ApplicationContext 로딩 실패**다. 개별 테스트 실패가 아니라 앱이 안 뜬 것이다.
XML의 `Caused by` 최하단까지 내려가니 진짜 원인이 있었다.

```
ORA-12170: TCP connect 시간 초과(30000ms) — host 192.168.50.36 port 3306
```

### 2-2. 내가 두 번 헛짚었다 (기록해 두는 이유)

| # | 가설 | 왜 틀렸나 |
|---|---|---|
| 1 | **로컬 Oracle이 안 떴다** | `oracledb_ESPDB-19c.service`가 inactive·부팅 disabled고 오늘 15:18에 재부팅한 흔적이 있어 그럴듯했다. 사용자가 Oracle을 올렸는데도 **증상이 그대로**였다 |
| 2 | **방화벽이 3306을 막는다** | `127.0.0.1:3306`은 붙고 `192.168.50.36:3306`은 타임아웃 → firewalld 런타임 규칙이 재부팅에 날아간 것으로 보였다. **그럴듯했지만 틀렸다** |

정답은 사용자가 알려줬다 — **DB 호스트가 `192.168.50.14`로 바뀌었다.**
확인해 보니 `.14`는 **이 서버 자신의 새 IP**였다.

```
enp0s3: inet 192.168.50.14/24 ... dynamic
```

`dynamic` — DHCP다. **재부팅하며 리스가 `.36`에서 `.14`로 갈렸다.**
`.36`은 이제 이 서버가 아니므로 타임아웃이 난 것이고, "방화벽이 막는다"와 증상이 **구분되지 않았다**.

> **교훈**: 접속 실패를 방화벽으로 결론짓기 전에 **그 IP가 아직 내 것인지** 확인한다.
> `ip -4 addr` 한 줄이면 됐다. WORKING-AGREEMENTS §5에 사고로 남겼다.

### 2-3. 왜 이게 "운영 다운"이었나

`.env`의 `DB_HOST`가 `.36`을 가리킨 채였고, systemd 유닛이 `ExecStart`에서 그 `.env`를 소싱한다.
→ 백엔드가 DB를 못 잡아 **기동 실패 → 무한 재시작**. 서비스가 `activating`에 붙박여 `:8080`이 죽어 있었다.
nginx(:443)·redis는 살아 있어서 **화면은 뜨는데 API만 죽은** 상태였다.

즉 **오늘 아침부터 운영이 내려가 있었고**, 그 사실을 "테스트가 깨졌다"는 형태로 발견한 셈이다.

### 2-4. DB는 이전된 게 아니라 **같은 DB**였다

새 호스트의 이력을 조회해 확인했다 — 새 DB에 붙은 게 아니라 같은 DB의 IP가 바뀐 것이다.

```
V1(07-16 16:21) … V11·V12(07-21 17:53)  전부 success=1
member 4 · orders 22 · product 5 · image 5
```

어제 espdb에 이미 적용된 V11·V12(7/21 §19-4)도 그대로 있다. **데이터 유실 없음.**

## 3. IP 고정 + 인증서 재발급 — IP에 묶인 것 전수 정리

IP가 바뀌면 **한 곳만 고치고 끝나지 않는다.** 전수 확인한 결과:

| 대상 | 결과 |
|---|---|
| `.env` `DB_HOST` | `.14`로 수정 (gitignore라 커밋 대상 아님 — **다음 세션이 모르면 안 되는 값**) |
| **TLS 인증서 SAN** | `IP:192.168.50.36`뿐이라 **불일치** → 재발급 |
| nginx 설정 | **무관** — `server_name _` (catch-all) |
| 프론트 코드 | **무관** — `/api` 상대경로 |
| `WORKING-AGREEMENTS` §5 | 접속 주소 `.14`로 수정 + 사고 기록 |
| `ARCHITECTURE.md` HTTPS | SAN 현행화 |
| **날짜별 핸드오프(7/14~7/21)** | **일부러 안 고쳤다** — 그 시점의 사실이라 고치면 기록이 아니게 된다 |

### 3-1. IP 정적 고정

```bash
sudo nmcli con mod enp0s3 ipv4.method manual \
  ipv4.addresses 192.168.50.14/24 ipv4.gateway 192.168.50.1 \
  ipv4.dns "96.45.45.45 96.45.46.46"
sudo nmcli con up enp0s3
```

실측: `dynamic` 표기 사라짐 / `ipv4.method: manual` / 기본 라우트 `proto static` /
게이트웨이 ping·DNS·백엔드 health·DB·nginx 전부 정상.

> **남는 위험**: `.14`가 공유기 DHCP 풀 안이면, VM이 꺼진 사이 공유기가 다른 기기에 `.14`를 내줘
> **충돌**할 수 있다. 공유기 예약(MAC `08:00:27:df:8e:fd`)은 **하지 않았다** — 겪으면 그때 걸기로 했다.

### 3-2. 인증서 재발급

기존 파라미터 유지(RSA2048·10년·`CN=glassvue.local`), 루프백 검증용 `127.0.0.1` 추가.

```
SAN: IP:192.168.50.14, IP:127.0.0.1, DNS:localhost, DNS:glassvue.local
원본 /home/ecstel/nginx-tls/2026-07-22/ · 이전 것은 /etc/nginx/ssl/*.bak
```

검증은 `-k`를 **빼고** 했다 — `curl --cacert <새 인증서> https://192.168.50.14/api/products` → **200**.
`-k`로는 SAN이 맞는지 아닌지 알 수 없으므로 의미가 없다.

> **함정**: nginx가 소스 빌드라 바이너리가 `/usr/local/sbin/nginx`인데 sudo의 `secure_path`에
> `/usr/local/sbin`이 없다 → `sudo nginx -t`가 **"명령이 없습니다"**. 전체 경로로 실행해야 한다.
> (`systemctl reload nginx`는 유닛에 전체 경로가 박혀 있어 정상 동작한다.)

## 4. `infra/` 신설 — 재현 근거가 서버에만 있었다

오늘 인증서·systemd·IP를 만지다 드러난 문제다. **저장소를 새로 clone 해도 서버를 세울 수 없었다.**
nginx 설정과 systemd 유닛이 서버에만 있었기 때문이다.

그 설정에는 **사고를 통해 얻은 지식**이 들어 있다는 게 핵심이다 —
`index.html`만 `no-cache`(7/21에 캐시된 옛 번들로 오진), `location`에 `add_header`가 있으면
**server 레벨 헤더가 통째로 무시**되는 nginx 규칙(그래서 업로드·정적 경로마다 보안헤더를 재선언).
서버가 날아가면 이걸 **전부 다시 알아내야 한다.**

```
infra/
├── README.md                        반영 명령(sudo) · 인증서 재발급 · 재구축 체크리스트 6가지
├── env.example                      키·형식만
├── nginx/{nginx.conf, conf.d/glassvue.conf}
└── systemd/glassvue-backend.service
scripts/check-infra-drift.sh         라이브 ↔ 저장소 diff
scripts/deploy-{backend,frontend}.sh 시작 시 위 검사를 자동 실행(경고만)
```

- 파일은 **손으로 옮기지 않고 `cp` 후 `diff`로 일치 확인**했다. 전사 오타가 제일 위험하다.
- **안 올린 것**: `.env` 실값, TLS 개인키. 커밋 전 `grep`으로 유출 점검했다(걸린 건 주석의 계정명뿐).
- **이 방식의 유일한 위험은 사본이 낡는 것**이다. 서버에서 급히 고치고 반영을 잊으면
  `infra/`는 "맞는 것처럼 보이는 틀린 문서"가 되어 **없느니만 못하다.**
  → `scripts/check-infra-drift.sh`(sudo 불필요, 다르면 diff 출력) + WORKING-AGREEMENTS §5에
  "`infra/`가 원본, 서버는 사본" 원칙을 근거와 함께 박아뒀다.
- **문서 규칙만으론 아무것도 강제되지 않아** 배포 스크립트(백엔드·프론트) 시작 시 위 검사를
  자동으로 한 번 돌리게 했다. 배포는 어차피 매번 거치는 관문이라 그 자리에서 알린다.
  **경고만 하고 배포는 계속 진행한다** — 드리프트가 배포를 막으면 급할 때 스크립트를
  우회하게 되어 오히려 나빠지기 때문이다. (`set -euo pipefail`에서도 안 멈추는 것 실측 확인)
- **설정 파일만으론 복구 안 되는 것 6가지**를 README에 명시했다 — Oracle 설치·PDB 생성,
  인증서 배치, `/var/www/glassvue-uploads/` 생성(없으면 `ReadWritePaths` 때문에 기동 실패),
  IP 정적 고정, Oracle 자동시작 enable, `.env` 실값.

   > **정정**: 이 항목을 처음엔 *"systemd 유닛의 낡은 전제(주석이 틀렸다)"* 로 적었는데 **틀린 진단이었다.**
   > `ora_pmon_ESPCDB`·`tnslsnr`이 이 호스트에서 돌고 `127.0.0.1:3306`이 열려 있다 —
   > **"Oracle은 같은 호스트에서 동작하므로"라는 주석은 정확하다.** 바뀐 건 DB 위치가 아니라 이 머신의 IP였는데,
   > 그걸 "DB가 다른 장비로 옮겨졌다"로 잘못 읽었다.

   진짜 문제는 따로 있다. `glassvue-backend.service`의 `After=oracledb_ESPDB-19c.service`가 **효력이 없다** —
   `After=`는 그 유닛이 **같은 부팅 트랜잭션에서 시작될 때만** 순서를 정하는데, 이 유닛은 `disabled`라
   **애초에 시작되지 않는다.** 그래서 오늘 재부팅 때 ①Oracle이 안 뜸 ②백엔드는 기다리지 않고 시작 → 실패
   ③수동으로 Oracle 기동, 순서로 흘렀다.

   **오늘 장애는 원인이 둘이었고 IP만 고쳤다.** Oracle 자동시작은 오늘 `enable`만 해두고
   **검증(재부팅)은 안 했다.**

   - 필요한 건 `sudo systemctl enable oracledb_ESPDB-19c` **하나뿐**이다. (오늘 실행함)
     등록 실측: `is-enabled=enabled` / chkconfig 런레벨 2·3·4·5 활성 / `/etc/rc{3,5}.d/S80oracledb_ESPDB-19c`.
     systemd 관점에서도 `WantedBy=multi-user.target graphical.target`이 붙어 **부팅 트랜잭션에 포함**됐고,
     `glassvue-backend`의 `After=`가 이제 **가리킬 대상이 생겼다**(전엔 disabled라 순서 제약이 무의미했다).
   - ⚠ `/etc/oratab`의 `N`→`Y`는 **불필요**하다. 그 플래그는 Oracle 자체 `dbstart`/`dbshut`이 보는 것인데,
     이 SysV 스크립트의 `start()`는 oratab을 **존재 확인용으로만 grep**하고 `lsnrctl start` +
     `startup; alter pluggable database all open`을 직접 실행한다. (스크립트를 읽고 확인함)
   - **내일 재부팅해서 확인할 것**: Oracle이 자동으로 뜨는가 → 백엔드가 손 안 대고 `active`가 되는가.
     `enable`만으로 SysV 스크립트가 실제로 뜬다는 보장은 없다.
