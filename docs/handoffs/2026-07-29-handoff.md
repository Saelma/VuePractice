## 2. 인프라·관측 도구 재검토 (사용자 제안 — LGTM · MaxGauge · Dynatrace · Jennifer · Kafka · k8s · MQTT)

사용자가 이후 도입 후보로 위 도구들을 제안했다. **코드 작업이 아니라 로드맵 판단**이라 자리는
`ARCHITECTURE.md §6`(미래 인프라 로드맵)이다 — BACKLOG 는 *제품 기능*, ARCHITECTURE 는 *설계·인프라*.

### 2-1. ⚠ 대조 결과 — 대부분 **이미 결정이 있었다**

| 제안 | 문서의 기존 상태 | 갱신 |
|---|---|---|
| **LGTM** | §6 관측 스택이 이미 **Alloy+Loki+Prometheus+Grafana(+Tempo)** | **새 도입이 아니라 같은 것의 다른 이름**임을 명시. 차이는 **M(Mimir) 하나** — Mimir 는 Prometheus 의 *장기보존·수평확장* 백엔드라 단일 VM 엔 비용만 는다 → **Prometheus 유지**, 보존기간·다중 인스턴스 시 remote_write 로 승격 |
| **Jennifer** | §7 에 이미 "상용/유료 ❌" | 유지 |
| **Dynatrace·MaxGauge** | **언급 없었음** | 신규 판단 추가. 둘 다 유료. ⚠ **MaxGauge 는 결이 다르다** — 앱 APM 이 아니라 **Oracle DB 전문**. 무료 대체는 P6SPY(완료)·`v$` 뷰·**Statspack**·`oracledb_exporter`. ⚠ **AWR/ASH 는 무료가 아니다**(Diagnostic Pack 유료 옵션) — 습관적으로 쓰기 전에 확인할 것 |
| **Kafka** | CLAUDE.md·§6 에 **"RabbitMQ 확정, Kafka 아님"**(2차 목표) | 유지 + **왜**를 보강. 우리 이벤트는 *주문완료→알림·적립* 같은 **작업 지시(task queue)** = RabbitMQ 결. Kafka 는 **replay·이벤트소싱·CDC·고스루풋**에서 값이 나는데 지금 셋 다 없다. **순서를 지키면 둘의 차이를 몸으로 알게 된다** |
| **Kubernetes** | §7 에 "단일 VM 엔 오버 ❌" | 유지하되 **학습 목적 예외 조건**을 명시 — 운영 VM 이 아니라 **별도 환경 + k3s/kind**, **Docker 화 이후**(이미지가 없으면 올릴 게 없다) |
| **MQTT** | **언급 없었음** | ❌ 도입 안 함. IoT 디바이스용 경량 pub/sub 이라 **이 도메인에 대응 문제가 없다**. 닮은 자리 둘은 이미 답이 있다 — 실시간 푸시=**SSE 완료**, 서비스 간=**RabbitMQ**. 뒤집히는 조건: 실제 디바이스(키오스크·POS·배송단말) |

### 2-2. 관통하는 판단 근거

- **볼 게 없는 상태에서 도구부터 깔지 않는다** — Sentry 를 보류한 것과 같은 판단(§1 "미리 만들지 않는다").
  관측 도구의 값은 **트래픽·서비스 수**에서 나오는데 지금은 단일 VM·단일 모놀리스·주문 수십 건이다.
- 도입 순서에 의미가 있다: **RabbitMQ → (필요하면) Kafka**, **Docker → (학습이면) k8s**,
  **Prometheus → (모자라면) Mimir**. 뒤에 것부터 깔면 앞의 것이 왜 부족했는지를 영영 모른다.

### 2-3. ⚠ 앞선 판단을 바꿈 — "유료라서 제외" 는 틀린 근거였다 (사용자 전제 확인)

**이 프로젝트는 학습용이고 운영으로 쓰지 않으므로 비용은 제약이 아니다.** 나중에 도입할 수도 있으니
문서에 그렇게 남겨 달라는 요청. WA §1-2 대로 **"앞선 판단을 바꿉니다"** 를 밝히고 바꿨다.

**바꾼 것 / 안 바꾼 것을 갈라 적는다** — 비용은 제외 사유 **중 하나**였을 뿐이다.

### 2-4. 새 절 — ARCHITECTURE §6 「학습 트랙」

**더 근본적인 구멍이 드러났다.** 이 문서의 판단은 그동안 **"운영에 필요한가"** 한 축뿐이었는데,

## 5. 이메일 수집 (B-13) — 구현 완료, **배포 대기**

BACKLOG D 의 「SMTP 실발송」에서 **수집만 떼어낸** 조각(§1-3에서 B-13으로 승격한 그것).
`member.email` 은 V29(7/28)로 컬럼만 있고 **채우는 경로가 없어 전 회원 NULL** 이었다.

### 5-1. 착수 전 결정 (사용자 확정)

| 질문 | 결정 | 이유 |
|---|---|---|
| 가입 시 필수인가 | **신규 가입만 필수** | 신규는 100% 확보되고, 기존 회원은 백필할 출처가 없다. ⚠ **DB 는 nullable 그대로** — "필수"는 **API 계층 규칙**(`SignupRequest @NotBlank`)이지 스키마 제약이 아니다 |
| 기존 회원 유도 | **설정 화면만** | 배너 유도는 노출 조건·닫기 상태 관리가 붙어 범위가 커진다. 필요해지면 그때 |

> ⚠ 백로그엔 *"선택 입력으로 둔다"* 고 적어 뒀었다. **스키마 제약(NOT NULL 불가)이 곧 API 규칙이라고
> 여긴 것**이 어림의 오류였다 — 둘을 갈라 보면 "컬럼은 nullable, 신규 가입만 필수"가 가능하다.

### 5-2. ⚠ 정규화 — 이게 이 작업의 핵심 판단

저장값을 **trim + 소문자**(`Member.normalizeEmail`, `Locale.ROOT`)로 정규화한다.

- **왜**: Oracle `UNIQUE` 는 **대소문자를 구분**한다. 정규화가 없으면 `A@b.com` 과 `a@b.com` 이
  **둘 다 들어간다** — 같은 사람에게 메일이 두 번 가거나, 재설정 링크가 엉뚱한 계정으로 간다.
  `uk_member_email` 이 있으니 안전하다고 믿기 쉬운데 **제약만으로는 안 막힌다.**
- **규칙을 한 곳에 둔 이유**: 가입(AuthService)과 변경(MemberService) 이 각자 정규화하면 언젠가 어긋난다.
- **검사와 저장이 같은 값을 써야 한다** — `existsByEmail` 에 원본을 넣고 저장은 정규화값으로 하면
  중복 검사가 통과해 버린다. 그래서 리포지토리 메서드에 "정규화된 값이 온다"를 주석으로 못박았다
  (여기서 `lower()` 를 또 걸면 인덱스를 못 탄다).
- ⚠ `Locale.ROOT` 명시: 기본 로케일이 터키어면 `"I".toLowerCase()` 가 `ı` 가 된다(터키 I 문제).

### 5-3. 구현

- **백엔드**: `SignupRequest.email`(@NotBlank @Email @Size 255) · `AuthService.signup` 중복검사 +
  저장 · `MemberService.changeEmail` · `EmailUpdateRequest` · `PATCH /api/members/me/email` ·
  `ErrorCode.DUPLICATE_EMAIL(MEMBER-409E)` · `MemberRepository.existsByEmail/existsByEmailAndIdNot` ·
  **`MemberResponse` 에 `email` 추가**(기존 회원은 null = "등록 안 함").
- **프론트**: `SignupView` 이메일 입력(느슨한 형식 검사 — 서버보다 엄격하면 정상 주소가 막힌다) ·
  `MyPageView`(/settings) 「이메일」 카드(미등록이면 안내 문구 + 버튼 라벨이 "등록"/"변경") ·
  `api/member.changeEmail`. ⚠ **화면은 입력값이 아니라 응답값을 되비춘다**(서버가 소문자로 바꾸므로).
- **마이그레이션 없음** — V29 컬럼 재사용, 엔티티 매핑도 무변경(`@Column(unique, length=255)` 그대로).
  그래서 빈 DB(esptest) 검증도 대상이 아니다.
- ⚠ **확인 메일이 없다 → 저장된 주소는 미검증이다.** SMTP 가 붙으면 "확인 메일 → 확인 전 pending"
  을 얹어야 한다(BACKLOG D 에 적어 뒀다).

### 5-4. ⚠ 컴파일러가 못 잡는 호출부 (WA §3 이 경고한 자리)

`SignupRequest` 에 필드를 더하자 **컴파일러가 Java 호출부 3곳을 즉시 잡아냈다**(AuthServiceTest).
그런데 **`mockMvc.perform(post("/api/auth/signup"))` 의 JSON 본문 3곳은 컴파일러가 모른다** —
`AuthFlowIntegrationTest` 2곳 · `PointFlowIntegrationTest` 1곳. 문자열이라 grep 으로 찾아 고쳤다.
규약이 예고한 함정에 실제로 걸릴 뻔한 자리라 기록해 둔다.

### 5-6. ⚠ 배포 순서 주의 — 이번엔 "백엔드 먼저" 에 대가가 있다

태그라인)는 `product` 컬럼 추가(마이그레이션)가 붙어 성격이 다르므로 뺐다.

### 7-1. 리뷰 많은순 정렬 — 화이트리스트 한 줄

- `ProductRepositoryImpl.SORTABLE` 에 `reviewCount` 추가 + 프론트 `SORT_OPTIONS` 한 줄.
  **새로 계산하는 게 없다** — `review_count` 는 `ReviewRatingChangedEvent`(7/20)가 이미 갱신 중이다.
- ⚠ **평점순 바로 뒤에 둔 게 의도다.** 평점만 열려 있으면 **"리뷰 1건에 별 5개"가 최상단**에 온다.
  리뷰 수 정렬은 그 반대편(많이 검증된 것)을 보여줘 왜곡을 보완한다 — 둘은 짝이다.
- 테스트는 **순서까지** 본다(기존 `avgRating` 테스트는 값이 전부 0이라 "거부되지 않음"만 봤다).
  같은 데이터에서 **평점순 1위의 리뷰가 1건**임을 함께 단언해 두 정렬이 실제로 다름을 고정했다.
  ⚠ 벌크 UPDATE 후 `entityManager.clear()` — 1차 캐시 때문에 옛 값을 읽는 함정(ARCHITECTURE §3).

### 7-2. 비로그인 홈 혜택 안내 — ⚠ 디자인이 아니라 **노출의 구멍**이었다

착수해 보니 이건 UI 취향 문제가 아니었다. **무료배송·적립금을 다 만들어 놓고 비로그인에게 한 번도
알리지 않고 있었다**:

- 혜택 허브(`/benefits`)는 **로그인 후에만** 보인다.
- 무료배송 안내는 **장바구니에 담아야** 나온다(`amountUntilFree`) — 즉 **담기 전엔 이유를 모른다.**

→ 홈 히어로 아래에 비로그인 전용 스트립. 로그인 회원은 이미 적립금·등급 카드가 그 자리를 써서 제외.

**⚠ 숫자를 화면에 적지 않았다 — 공개 정책 API 두 개를 새로 열었다.**

| 엔드포인트 | 주는 것 | 소유 |
|---|---|---|
| `GET /api/policy/shipping` | `fee`, `freeThreshold` | `global/policy`(배송비 정책이 global 에 있는 이유와 같다 — cart·order 공유, order↔cart 순환 회피) |
| `GET /api/policy/grades` | 등급별 `minPurchase`·`earnPercent` | **point 도메인**(등급은 point 소유. 경로만 공개 구역) |

이 프로젝트 규약이 **"화면이 임계값을 몰라도 된다 — 서버가 계산해 준다"**(PointPanel·쿠폰
`discountPreview` 주석)라서 그대로 따랐다. `application.yml` 이나 `MemberGrade` 를 고쳤을 때
**안내 문구만 조용히 거짓말**이 되는 걸 막는다.

**⚠ 쿠폰은 광고하지 않는다.** 8fter 는 가입 쿠폰을 내걸지만, **우리 쿠폰은 관리자
지정 발급만** 있고 자가·자동 발급이 없다 — **가입해도 쿠폰이 안 생긴다.** 없는 혜택을 문구로 적을 수는
없어서 뺐다. 자동 발급을 만들면 그때 한 줄 붙인다(BACKLOG 「선착순 발급」과 같은 자리).

### 7-3. ⚠ 테스트가 잡은 것 — 등급표를 어디에 두느냐

처음엔 `GET /api/points/grades` 로 뒀는데 **테스트가 401 을 잡아냈다.** `/api/points/**` 는
SecurityConfig 가 **한 줄로 `authenticated`** 로 막는 구역이다(기본이 permitAll 이라 매처를 빠뜨리면
남의 적립금이 열리는 자리).

**거기에 "이것만 공개" 예외를 넣는 건 보호 구역에 구멍을 뚫는 것**이라 경로를 옮겼다.

> 감사 로그(`/api/admin/audit/**` 를 `/api/admin/**` 위에 얹은 것)와 **방향이 반대**라는 게 핵심이다 —
> 그건 **좁히는** 예외(ADMIN → SUPER_ADMIN)라 실수해도 **더 잠기지만**, 이건 **넓히는** 예외라
> 실수하면 **열린다.** 그래서 공개 정책은 **처음부터 공개인 네임스페이스**(`/api/policy/**`)로 모았다 —
> 여기엔 회원별 정보가 절대 들어오지 않는다는 규칙과 함께.

## 8. 상품 한 줄 태그라인 (V33) — 8fter ② · **배포 대기**

8fter 후보의 마지막 하나. 앞의 둘과 달리 **스키마가 붙는다**.

### 8-1. ⚠ `description` 을 잘라 쓰지 않고 컬럼을 새로 판 이유

가장 싼 길은 "설명 앞 60자를 카드에 보여주기"였다. 안 했다 — **설명은 문단이라 앞에서 자르면 문장이
중간에 끊긴다.** 그리고 더 근본적으로 **카드용 한 줄과 상세 설명은 목적이 다른 글**이다(전자는 사게
만드는 카피, 후자는 정보). 같은 데이터로 둘 다 하려 들면 둘 다 어정쩡해진다.

- `VARCHAR2(100 CHAR)` — ⚠ **CHAR semantics**(WA §2-2-1). 실측 확인: `char_used=C, char_length=100`.
- 100자로 잡은 건 **길이로 용도를 알리려는 것**이다. 상품명(200)보다 짧게 둬서 "여기에 설명을 쓰지 말라"를
  스키마가 말하게 했다.
- 엔티티에 **`length = 100` 명시** — 안 주면 기본 255 로 검증돼 `ddl-auto=validate` 가 DDL(100)과
  어긋난다며 **부팅을 막는다**(V12·admin_audit_log 에서 겪은 자리).
- **nullable · 백필 없음** — 사람이 쓰는 카피이지 파생 데이터가 아니라 채울 값이 없다. 기존 상품은 전부 null.

### 8-2. ⚠ 캐시 포맷이 바뀌었다 (WA §2-7)

**`ProductResponse` 는 Redis 캐시(`products:list`) 직렬화 대상**이다. 필드를 하나 더한 것이
곧 **캐시 포맷 변경**이라, 이미 쌓인 값과의 호환을 **추측하지 않고 바이트로** 확인했다.

- 신 코드 ← **옛 캐시값**(tagline 키 없음): 직렬화 후 그 키를 지운 JSON 을 만들어 실제로 역직렬화해 봤다.
  → `tagline=null`, 나머지 필드 정상. **테스트로 고정**(`tagline이_없던_옛_캐시값도_읽힌다`).
- 반대 방향(구 jar ← 신 캐시값)은 **롤백할 때만** 생긴다 — 배포는 구 jar 를 내리고 신 jar 를 올리므로
  둘이 동시에 뜨지 않는다. ⚠ **되돌릴 일이 생기면 캐시를 flush** 해야 한다(아래 배포 절).

### 8-3. 화면 규칙 — 없으면 줄 자체를 없앤다

- 카드: 상품명 **아래**, 가격 **위**(무엇이 좋은지는 이름 다음에 읽혀야 한다). `v-if` + `line-clamp-1`.
  ⚠ 빈 줄을 남기면 **태그라인 있는 카드와 없는 카드의 높이가 달라져** 그리드가 들쭉날쭉해진다.
- 관리 폼: 빈 입력을 **`null` 로 보낸다**(빈 문자열이면 카드의 `v-if` 가 통과해 아무것도 없는 줄이 생긴다).
  **"없음"은 null 하나로만 표현**한다.

## 9. ⚠ 레퍼런스 인용 방침 정정 — 남의 카피를 원문으로 옮기지 않는다

사용자가 **저장소 public 전환**을 검토하며 물었다: *"8fter 벤치마킹이 깃허브 로그에 있어도 되나?"*

**출처를 밝히는 쪽이 좋은 문서**다. 우리가 한 것도 자산 복제가 아니라 패턴 참고다(이미지·폰트·코드·문구 전부 우리 것).

**⚠ 다만 하나가 잘못돼 있었다 — 8fter 의 마케팅 문구를 원문 그대로 옮겨 적었다.**
사용자가 이걸 짚었고(2026-07-29), 고쳤다.

| 자리 | 있던 것 | 바꾼 것 |

| DESIGN.md §2 ①·§2 인용 | 8fter 의 가입 혜택 배너 문구 원문 | "가입 혜택(쿠폰·무료배송)을 헤더/히어로에 상시 노출" |

## 11. 비밀번호 재설정 링크 **메일 발송** (B-10 완성) — 배포 대기

D 의 마지막 반쪽. 토큰 발급·검증은 7/28 에 끝났고, **오늘 B-13 이 「보낼 주소」를 만들어 조건이 풀렸다.**

### 11-1. ⚠ "실발송"이 아니다 — 로컬 캐처

사용자 질문: *"진짜 그 이메일로 보내는 거냐, 테스트가 불편할 텐데"*. 정당한 우려였고, 그래서 셋 중 골랐다.

| 방식 | 판단 |
|---|---|
| 라이브러리만(+GreenMail 테스트) | 자동 검증은 되지만 **눈으로 볼 화면이 없다** — 브라우저 검증 선호와 안 맞는다 |
| **로컬 메일 캐처 (Mailpit)** ⭐ | 받은 메일을 붙잡고 **밖으로 안 보낸다**. 웹 UI 로 즉시 확인 — 오히려 **테스트가 편해진다**(`redis-cli` 로 토큰 캐던 절차가 사라진다) |
| 외부 SMTP(Gmail 등) | 진짜 발송 + 외부 전송 → **우리 원칙과 충돌**. 사용자가 걱정한 불편도 여기서 생긴다 |

- 설치: `~/tools/mailpit` 에 **단일 바이너리**(v1.30.6). `sudo` 없음, 시스템 스택 무변경, 지울 땐 폴더만 삭제.
- `127.0.0.1` 바인딩이라 LAN 에서도 안 보인다. **코드는 어느 방식이든 동일** — `spring.mail.*` 두 줄만 다르다.

### 11-2. 구현

- **`global/mail/Mailer` + `MailProperties`** — 발송은 업무가 아니라 인프라라 global(주문 확인·배송 알림도 같은 통로를 쓰게 된다).
- **`AuthService.requestPasswordReset`** 에서 발송. ⚠ **열거 방지가 걸린 자리**라 세 갈래를 조용히 넘긴다:
  ①이메일 없는 기존 회원 ②채널 없는 환경 ③발송 실패. **예외가 올라가면 500 이 나가면서 "그 아이디는
  존재한다"가 드러난다**(없는 아이디는 애초에 여기까지 안 온다).
- **링크 base-url 은 설정에서** 온다 — 요청 `Host` 헤더로 만들면 **헤더를 조작해 공격자 서버로 가는
  재설정 링크를 남에게 보내게** 할 수 있다(host header injection).
- **본문·수신자를 로그에 남기지 않는다** — 재설정 링크는 **그 자체가 자격증명**이라, 찍히면 로그를 읽는
  사람이 남의 비밀번호를 바꿀 수 있다.

### 11-3. ⚠ 헛디딘 것 둘 — 둘 다 "적어둔 것"이 "확인한 것"이 아니었다

**(1) 이름 충돌로 컨텍스트가 통째로 안 떴다.** 클래스를 `MailSender` 로 두니 빈 이름이 `mailSender` 가 되어
스프링 부트가 자동 등록하는 `JavaMailSenderImpl`(같은 이름)과 **`BeanDefinitionOverrideException`** 충돌.
테스트 **154건이 무더기로 실패**했다. → `Mailer` 로 개명. **스프링이 이미 쓰는 이름은 피한다.**

> 무더기 실패를 보고 WA §5 대로 **`Caused by` 최하단**부터 봤다 — 첫 번째는 YAML 중복 키
> (`glassvue:` 블록이 이미 있는데 하나 더 만들었다), 그다음이 이 빈 충돌이었다. 증상이 아니라 근본 원인.

**(2) ⚠ 더 중요한 것 — 내가 문서에 적은 안전장치가 실제로는 작동하지 않았다.**

`application.yml` 에 `host: ${MAIL_HOST:}` 를 두고 *"값이 비었으니 운영은 발송이 꺼진다"* 고 **주석까지
달았다. 틀렸다.** 값이 비어도 **프로퍼티는 존재**해서 자동설정 조건이 통과하고, 빈 host 가 localhost 로
폴백해 **`:1025` 에 실제로 붙었다.**

**어떻게 알았나** — 로컬 캐처를 열어 보니 **기본 프로파일로 도는 통합 테스트가 보낸 메일**이 쌓여 있었다.
캐처가 없었으면 **영영 몰랐을 것**이다(운영에선 그 포트에 아무것도 없어 조용히 실패했을 테니).

→ `application.yml` 에서 **`spring.mail` 키 자체를 제거**했다. **"기본값을 비워 둔다"와 "키를 두지 않는다"는
다르다.** 그리고 이번엔 주석이 아니라 **테스트로 고정**했다(`MailerAutoConfigOffTest` — 기본 프로파일에서
`Mailer.isEnabled()` 가 false). 누가 `spring.mail` 을 되살리면 그 테스트가 깨진다.

> 오늘 §7-3(등급표 401)에 이어 **테스트가 내 설계를 두 번 반증했다.** 공통점: 둘 다 *"이렇게 되겠지"* 를
> 적어두고 확인하지 않은 자리였다.

## 12. ⚠ 상품 카드 높이 — 내 판단이 틀렸던 자리 (사용자 지적)

§8 에서 태그라인을 넣으며 이렇게 적었다: *"빈 줄을 남기면 카드 높이가 달라지니 `v-if` 로 줄 자체를 없앤다."*
**틀렸다.** 줄을 빼는 것 **역시** 높이를 바꾼다 — 조건부 렌더링을 어느 쪽으로 하든 해결되지 않는 문제였다.

사용자가 목록을 눈으로 보고 알려 줬다: *"반팔티 < 몽쉘10개 < 몽쉘 순으로 세로가 길어진다."*
그 순서가 원인을 그대로 드러냈다.

| 상품 | 높이를 늘린 것 |
|---|---|
| 반팔티 | 없음(제일 짧음) |
| 몽쉘 10개 | **품절 배지** |
| 몽쉘 | **태그라인** |

⚠ **원인이 셋이었고 둘은 오늘 이전부터 있었다** — 태그라인(오늘) · 품절 배지 · 정가 취소선.
즉 **태그라인이 없었어도 품절 상품이 섞인 목록은 이미 어긋나 있었다.** 새로 만든 게 아니라
**원래 있던 흠을 하나 더 눈에 띄게 만든 것**이었다.

### 12-1. 고친 방식 — 조건부가 아니라 구조

1. 카드를 **`h-full flex-col`** — 그리드 자식은 기본이 stretch 인데, 카드가 `h-full` 이 아니라
   **내용만큼만 커지고 있었다.** 이걸 받도록 바꾼다.
2. 가격·별점 줄에 **`mt-auto`** — 위 내용이 몇 줄이든 **항상 카드 바닥**에 붙는다.
3. 품절/판매중지 배지를 **이미지 오버레이**로 이동 — 텍스트 흐름에서 아예 뺀다
   (할인 배지가 이미 오버레이라 방식도 일관된다).

### 12-2. 검증

## 13. 이메일 소유 인증 (B-14) — 배포 대기

§11(발송 채널)이 조건을 풀자마자 이어서. **B-13 이 남긴 구멍**을 메운다 — 지금까지 저장된 주소는
미검증이라 **오타가 있으면 재설정 링크가 남의 주소로 갔다.**

### 13-1. 착수 전 결정 (사용자 확정)

| 질문 | 결정 | 이유 |
|---|---|---|
| 인증 방식 | **6자리 인증번호** | 설정 화면에서 바로 입력 — 페이지를 떠났다 돌아오지 않는다. 「설정에서 내 이메일 인증」 흐름에 자연스럽다 |
| 미인증 주소로 재설정 링크를 보낼까 | **보낸다**(현행 유지) | 안 보내면 안전하지만 **오타 낸 사람은 계정을 영영 못 찾는다**(관리자 개입 외 경로 없음). 대신 「미인증」 배지로 드러낸다 |

> ⚠ 사용자가 *"Mailpit 했다며, 그걸로 하면 되는 거 아니야?"* 라고 물었고 **맞다** — 발송 인프라는
> §11 에서 끝나 손댈 게 없었다. B-14 가 새로 만든 건 **토큰 저장소·컬럼·확인 엔드포인트·화면**뿐이다.

### 13-2. ⚠ 두 가지 보안 판단

**(1) 이메일을 바꾸면 인증이 풀린다** (`Member.updateEmail`). **인증은 "그 주소"에 대한 것이지 회원에
대한 게 아니다.** 안 그러면 인증된 주소를 미인증 주소로 갈아끼워 **"인증됨" 딱지만 물려받을 수 있다.**
같은 값을 재저장할 때도 푼다 — 예외를 두면 "언제 유지되는지"가 규칙이 되어 나중에 어긋난다.

**(2) 무차별 대입 차단.** 6자리는 **100만 가지뿐**이다. 남의 주소를 넣고 코드를 찍어 맞히면
**소유하지도 않은 주소가 인증된다.** 그래서 셋을 함께 걸었다:

| 장치 | 값 | 근거 |
|---|---|---|
| 시도 횟수 제한 | **5회 → 코드 폐기** | 100만 중 5번만 볼 수 있어 성공 확률이 사실상 0. ⚠ 폐기 후엔 **정답도 안 통한다**(재발송 필요) |
| TTL | **10분** | 재설정 토큰(30분)보다 짧다. 메일 열고 바로 넣는 것이라 길 이유가 없고, 짧을수록 시도 시간도 준다 |
| 난수 | `SecureRandom` | 예측 가능하면 위 제한이 무의미하다 |

⚠ **실패 사유를 구분하지 않는다**(`MEMBER-400V` 하나) — 만료/횟수초과/불일치를 나눠 주면
**남은 시도 횟수를 세어** 재발송 타이밍을 맞출 수 있다.

> 키 방향도 재설정 토큰과 **반대**다. 저쪽은 토큰이 키(링크로 오므로 토큰만으로 대상을 찾아야 한다),
> 여기는 **memberId 가 키**다 — 로그인한 본인이 자기 주소를 인증하는 흐름이라 대상을 이미 알고,
> 오히려 회원별로 묶여 있어야 남의 코드를 맞혀 볼 수 없다.

## 14. Mailpit systemd 유닛 — 부팅 자동기동 (사용자 제안)

*"터미널 닫으면 죽는 것보다 DB처럼 자동으로 켜지는 게 낫지 않나"* (사용자). 맞는 판단이라 유닛으로 올렸다.

### 14-1. ⚠ 두 번 실패했고, 둘 다 규약에 이미 있던 함정이었다

**(1) `203/EXEC` — SELinux** (WA §6-2 의 그 신호)

바이너리를 `~/tools/mailpit/` 에 두고 유닛을 올리니 **"Failed to locate executable … Permission denied"**.
파일 권한은 `-rwxr-xr-x`, 소유자도 맞고, **셸에서는 잘 실행됐다.** 진단은 `ls -lZ` 한 줄이었다:

| | |
|---|---|
| 바이너리 | `user_home_t` ← **`init_t`(systemd) 가 실행 못 하는 타입** |
| SELinux | `Enforcing` |
| 정상 동작하는 백엔드 jar | `/opt/...` 의 `usr_t` |

→ **`/opt/mailpit` 으로 옮겼다**(운영 jar 자리와 일관). `restorecon` 으로 라벨 확정 —
`chcon` 은 재라벨링 때 날아간다. 규약은 **WA §6-2-1** 로 신설했다.
⚠ `203/EXEC` 는 "실행조차 못 했다"라 **앱 로그가 아예 없다** — 프로그램 문제로 착각하기 쉽다.

**(2) `status=1/FAILURE` — 포트 충돌**

라벨을 고쳤는데도 죽었다. 원인은 **아까 손으로 띄워 둔 Mailpit(1시간 52분째)** 이 `:1025` 를 쥐고 있던 것.

> ⚠ **그때 `curl :8025` 는 200 이었다.** 옛 프로세스가 응답한 것인데 "떠 있으니 됐다"로 오해하기 딱 좋다 —
> WA §6-1(*"지금 떠 있다"는 자동기동 성공의 증거가 아니다*)이 말하는 어긋난 상태 그대로다.
> 판별은 **`ss -lntp` 로 누가 쥐고 있는지**를 봐야 갈린다. `infra/README` 에 주의로 적었다.

## 15. 플래키 테스트 정리 — ⚠ 원인이 이월 메모와 달랐다

7/24부터 **6일째** 내려온 항목. 이월엔 이렇게 적혀 있었다:

> **플래키 테스트** `NoticeQueryServiceIntegrationTest`(Redis 조회수 격리) — 테스트마다 Redis 키 clear 로 고칠 수 있다.

**그 처방은 틀렸다.** 열어 보니 그 테스트엔 **이미 `@AfterEach` 정리가 있었다.**

### 15-1. 실측으로 찾은 진짜 원인

가설로 고치지 않고 실험했다 — 손으로 `notice:view:<uuid>` 키를 만들고 지켜봤다:

```
[t=0]   생성 = 7
[t=10s] 값 유지: 7
[t=20s] ❌ 사라짐
```

**아무도 안 지웠는데 사라졌다.** 범인은 **운영(:8080)의 `NoticeViewCountFlusher`** 다 —
30초마다 `notice:view:*` 를 **SCAN + GETDEL** 하는데, 테스트와 운영이 **같은 Redis db0** 를 쓴다.
즉 **운영이 테스트 키를 가져가고 있었다.**

> ⚠ **`@AfterEach` 로는 원리적으로 못 막는다** — 지우는 게 테스트가 아니라 **다른 프로세스**다.
> 이월 메모가 "정리하면 된다"고 적은 건, 증상만 보고 **원인을 짐작해 적은 것**이었다.

### 15-2. 고친 방식 — 정리가 아니라 격리

`build.gradle` 의 test 태스크에 시스템 프로퍼티 둘:

| 프로퍼티 | 값 | 무엇을 막나 |
|---|---|---|
| `spring.data.redis.database` | `1` | **운영 플러셔**가 테스트 키에 닿는 것 |
| `notice.view-count.flush-interval-ms` | `86400000` | **테스트 컨텍스트 자신의** `@Scheduled` 가 db1 을 비우는 것 |

⚠ **`src/test/resources/application.yml` 은 쓰지 않았다** — main 의 것을 **통째로 가려서**
datasource 설정까지 날아간다. 새 프로파일도 안 만들었다: 기본 프로파일 동작을 검증하는
테스트(`MailerAutoConfigOffTest`)의 전제가 바뀐다. 시스템 프로퍼티는 둘 다 피한다.

**부수효과 — 반대 방향 오염도 사라졌다.** 오늘 `auth:reset:`·`auth:email-verify:` 키를 손으로
치운 게 그 때문이었는데, 이제 테스트는 운영 Redis 를 아예 건드리지 않는다.

| 게이트 | 결과 |
|---|---|
| **전체 테스트** | **359 pass · skipped 0 · fail 0** (`--rerun-tasks` 강제 재실행) |

> 격리는 **남이 건드리는 것**도 막는다.
