## 2. 인프라·관측 도구 재검토 (사용자 제안 — LGTM · MaxGauge · Dynatrace · Jennifer · Kafka · k8s · MQTT)

사용자가 이후 도입 후보로 위 도구들을 제안했다. **코드 작업이 아니라 로드맵 판단**이라 자리는
`ARCHITECTURE.md §6`(미래 인프라 로드맵)이다 — BACKLOG 는 *제품 기능*, ARCHITECTURE 는 *설계·인프라*.

### 2-1. ⚠ 대조 결과 — 대부분 **이미 결정이 있었다**

| 제안 | 문서의 기존 상태 | 갱신 |
|---|---|---|
| **LGTM** | §6 관측 스택이 이미 **Alloy+Loki+Prometheus+Grafana(+Tempo)** | **새 도입이 아니라 같은 것의 다른 이름**임을 명시. 차이는 **M(Mimir) 하나** — Mimir 는 Prometheus 의 *장기보존·수평확장* 백엔드라 단일 VM 엔 비용만 는다 → **Prometheus 유지**, 보존기간·다중 인스턴스 시 remote_write 로 승격 |
| **Jennifer** | §7 에 이미 "상용/유료 ❌" | 유지 |
| **Dynatrace·MaxGauge** | **언급 없었음** | 신규 판단 추가. 둘 다 유료. ⚠ **MaxGauge 는 결이 다르다** — 앱 APM 이 아니라 **Oracle DB 전문**. 무료 대체는 P6SPY(완료)·`v$` 뷰·**Statspack**·`oracledb_exporter`. ⚠ **AWR/ASH 는 무료가 아니다**(Diagnostic Pack 유료 옵션) — 습관적으로 쓰기 전에 확인할 것 |
| **Kafka** | CLAUDE.md·§6 에 **"RabbitMQ 확정, Kafka 아님"**(2차 목표) | 유지 + **왜**를 보강. 우리 이벤트는 *주문완료→알림·적립* 같은 **작업 지시(task queue)** = RabbitMQ 결. Kafka 는 **replay·이벤트소싱·CDC·고스루풋**에서 값이 나는데 지금 셋 다 없다. **순서를 지키면 둘의 차이를 몸으로 알게 된다** |
| **Kubernetes** | §7 에 "단일 VM 엔 오버 ❌" | 유지하되 **학습 목적 예외 조건**을 명시 — 운영 VM 이 아니라 **별도 환경 + k3s/kind**, **Docker 화 이후**(이미지가 없으면 올릴 게 없다) |
| **MQTT** | **언급 없었음** | ❌ 도입 안 함. IoT 디바이스용 경량 pub/sub 이라 **이 도메인에 대응 문제가 없다**. 닮은 자리 둘은 이미 답이 있다 — 실시간 푸시=**SSE 완료**, 서비스 간=**RabbitMQ**. 뒤집히는 조건: 실제 디바이스(키오스크·POS·배송단말) |

### 2-2. 관통하는 판단 근거

- **볼 게 없는 상태에서 도구부터 깔지 않는다** — Sentry 를 보류한 것과 같은 판단(§1 "미리 만들지 않는다").
  관측 도구의 값은 **트래픽·서비스 수**에서 나오는데 지금은 단일 VM·단일 모놀리스·주문 수십 건이다.
- 도입 순서에 의미가 있다: **RabbitMQ → (필요하면) Kafka**, **Docker → (학습이면) k8s**,
  **Prometheus → (모자라면) Mimir**. 뒤에 것부터 깔면 앞의 것이 왜 부족했는지를 영영 모른다.

### 2-3. ⚠ 앞선 판단을 바꿈 — "유료라서 제외" 는 틀린 근거였다 (사용자 전제 확인)

위 2-1 을 적을 때 상용 APM 3종을 **"상용/유료 → ❌ 제외"** 로 닫았다. 사용자가 전제를 정정했다:
**이 프로젝트는 학습용이고 운영으로 쓰지 않으므로 비용은 제약이 아니다.** 나중에 도입할 수도 있으니
문서에 그렇게 남겨 달라는 요청. WA §1-2 대로 **"앞선 판단을 바꿉니다"** 를 밝히고 바꿨다.

**바꾼 것 / 안 바꾼 것을 갈라 적는다** — 비용은 제외 사유 **중 하나**였을 뿐이다.

| | 처음 판단 | 지금 |
|---|---|---|
| 비용·라이선스 | 제외 사유 | ❌ **철회** — 학습용이라 제약 아님 |

### 2-4. 새 절 — ARCHITECTURE §6 「학습 트랙」

**더 근본적인 구멍이 드러났다.** 이 문서의 판단은 그동안 **"운영에 필요한가"** 한 축뿐이었는데,
**이 프로젝트는 운영하지 않는다.** 그 축만 쓰면 §1 "미리 만들지 않는다"가 **배우려고 넣는 것까지 전부 막는다** —
실제로 C-8(상품 옵션)은 그 예외를 의식적으로 선택하고 근거를 남긴 사례였다. 축이 하나 빠져 있었던 것이다.

그래서 **트랙을 둘로 나눠 명문화**했다(ARCHITECTURE §6 「학습 트랙」, §1 에도 연결).

| | 운영 트랙 | 학습 트랙 |
|---|---|---|
| 질문 | "지금 없어서 아픈가?" | "넣으면 **무엇을 겪게 되는가?**" |
| 통과 조건 | 실제 문제·요구 | **겪을 거리가 실재할 것** |
| 실패 모드 | 오버엔지니어링 | **no-op 설치**(깔았는데 화면이 비어 아무것도 안 배움) |

**3원칙**: ①**운영 VM 을 실험대로 쓰지 않는다**(별도 VM/포트/프로파일 — `esptest`·Redis 별도 db 와 같은 이유)
②**볼 게 먼저, 도구는 나중**(k6 가 관측·APM 의 선행) ③**"무엇을 배웠나"를 핸드오프에 남긴다**
(안 그러면 "깔았다"만 남고 지식은 안 남는다).

**권장 순서**: `k6 부하 → OSS 관측(LGTM) → 상용 평가판 비교 → Docker/compose → k3s·kind → RabbitMQ → Kafka`.
뒤엣것부터 하면 **앞의 것이 왜 부족했는지를 영영 모른다.**

> ⚠ **MQTT 만 이 순서에서 빠진다.** 나머지는 "지금은 실효가 없다"지만 MQTT 는 **대응 문제 자체가

## 5. 이메일 수집 (B-13) — 구현 완료, **배포 대기**

BACKLOG D 의 「SMTP 실발송」에서 **수집만 떼어낸** 조각(§1-3에서 B-13으로 승격한 그것).
`member.email` 은 V29(7/28)로 컬럼만 있고 **채우는 경로가 없어 전 회원 NULL** 이었다.

### 5-1. 착수 전 결정 (사용자 확정)

| 질문 | 결정 | 이유 |
|---|---|---|
| 가입 시 필수인가 | **신규 가입만 필수** | 신규는 100% 확보되고, 기존 회원은 백필할 출처가 없다. ⚠ **DB 는 nullable 그대로** — "필수"는 **API 계층 규칙**(`SignupRequest @NotBlank`)이지 스키마 제약이 아니다 |
| 기존 회원 유도 | **설정 화면만** | 배너 유도는 노출 조건·닫기 상태 관리가 붙어 범위가 커진다. 필요해지면 그때 |

> ⚠ 백로그엔 *"선택 입력으로 둔다"* 고 적어 뒀었다. **스키마 제약(NOT NULL 불가)이 곧 API 규칙이라고
> 여긴 것**이 어림의 오류였다 — 둘을 갈라 보면 "컬럼은 nullable, 신규 가입만 필수"가 가능하다.

### 5-2. ⚠ 정규화 — 이게 이 작업의 핵심 판단

저장값을 **trim + 소문자**(`Member.normalizeEmail`, `Locale.ROOT`)로 정규화한다.

- **왜**: Oracle `UNIQUE` 는 **대소문자를 구분**한다. 정규화가 없으면 `A@b.com` 과 `a@b.com` 이
  **둘 다 들어간다** — 같은 사람에게 메일이 두 번 가거나, 재설정 링크가 엉뚱한 계정으로 간다.
  `uk_member_email` 이 있으니 안전하다고 믿기 쉬운데 **제약만으로는 안 막힌다.**
- **규칙을 한 곳에 둔 이유**: 가입(AuthService)과 변경(MemberService) 이 각자 정규화하면 언젠가 어긋난다.
- **검사와 저장이 같은 값을 써야 한다** — `existsByEmail` 에 원본을 넣고 저장은 정규화값으로 하면
  중복 검사가 통과해 버린다. 그래서 리포지토리 메서드에 "정규화된 값이 온다"를 주석으로 못박았다
  (여기서 `lower()` 를 또 걸면 인덱스를 못 탄다).
- ⚠ `Locale.ROOT` 명시: 기본 로케일이 터키어면 `"I".toLowerCase()` 가 `ı` 가 된다(터키 I 문제).

### 5-3. 구현

- **백엔드**: `SignupRequest.email`(@NotBlank @Email @Size 255) · `AuthService.signup` 중복검사 +
  저장 · `MemberService.changeEmail` · `EmailUpdateRequest` · `PATCH /api/members/me/email` ·
  `ErrorCode.DUPLICATE_EMAIL(MEMBER-409E)` · `MemberRepository.existsByEmail/existsByEmailAndIdNot` ·
  **`MemberResponse` 에 `email` 추가**(기존 회원은 null = "등록 안 함").
- **프론트**: `SignupView` 이메일 입력(느슨한 형식 검사 — 서버보다 엄격하면 정상 주소가 막힌다) ·
  `MyPageView`(/settings) 「이메일」 카드(미등록이면 안내 문구 + 버튼 라벨이 "등록"/"변경") ·
  `api/member.changeEmail`. ⚠ **화면은 입력값이 아니라 응답값을 되비춘다**(서버가 소문자로 바꾸므로).
- **마이그레이션 없음** — V29 컬럼 재사용, 엔티티 매핑도 무변경(`@Column(unique, length=255)` 그대로).
  그래서 빈 DB(esptest) 검증도 대상이 아니다.
- ⚠ **확인 메일이 없다 → 저장된 주소는 미검증이다.** SMTP 가 붙으면 "확인 메일 → 확인 전 pending"
  을 얹어야 한다(BACKLOG D 에 적어 뒀다).

### 5-4. ⚠ 컴파일러가 못 잡는 호출부 (WA §3 이 경고한 자리)

`SignupRequest` 에 필드를 더하자 **컴파일러가 Java 호출부 3곳을 즉시 잡아냈다**(AuthServiceTest).
그런데 **`mockMvc.perform(post("/api/auth/signup"))` 의 JSON 본문 3곳은 컴파일러가 모른다** —
`AuthFlowIntegrationTest` 2곳 · `PointFlowIntegrationTest` 1곳. 문자열이라 grep 으로 찾아 고쳤다.
규약이 예고한 함정에 실제로 걸릴 뻔한 자리라 기록해 둔다.

## 7. 리뷰 많은순 정렬 + 비로그인 홈 혜택 안내 (8fter 발) — **완료** (배포·검증 종결)

### 7-2. 비로그인 홈 혜택 안내 — ⚠ 디자인이 아니라 **노출의 구멍**이었다

착수해 보니 이건 UI 취향 문제가 아니었다. **무료배송·적립금을 다 만들어 놓고 비로그인에게 한 번도
알리지 않고 있었다**:

- 무료배송 안내는 **장바구니에 담아야** 나온다(`amountUntilFree`) — 즉 **담기 전엔 이유를 모른다.**

→ 홈 히어로 아래에 비로그인 전용 스트립. 로그인 회원은 이미 적립금·등급 카드가 그 자리를 써서 제외.

**⚠ 숫자를 화면에 적지 않았다 — 공개 정책 API 두 개를 새로 열었다.**

| 엔드포인트 | 주는 것 | 소유 |

`discountPreview` 주석)라서 그대로 따랐다. `application.yml` 이나 `MemberGrade` 를 고쳤을 때
**안내 문구만 조용히 거짓말**이 되는 걸 막는다.

**⚠ 쿠폰은 광고하지 않는다.** 8fter 는 가입 쿠폰을 내걸지만, **우리 쿠폰은 관리자
지정 발급만** 있고 자가·자동 발급이 없다 — **가입해도 쿠폰이 안 생긴다.** 없는 혜택을 문구로 적을 수는
없어서 뺐다. 자동 발급을 만들면 그때 한 줄 붙인다(BACKLOG 「선착순 발급」과 같은 자리).

### 7-3. ⚠ 테스트가 잡은 것 — 등급표를 어디에 두느냐

처음엔 `GET /api/points/grades` 로 뒀는데 **테스트가 401 을 잡아냈다.** `/api/points/**` 는
SecurityConfig 가 **한 줄로 `authenticated`** 로 막는 구역이다(기본이 permitAll 이라 매처를 빠뜨리면
남의 적립금이 열리는 자리).

**거기에 "이것만 공개" 예외를 넣는 건 보호 구역에 구멍을 뚫는 것**이라 경로를 옮겼다.

> 감사 로그(`/api/admin/audit/**` 를 `/api/admin/**` 위에 얹은 것)와 **방향이 반대**라는 게 핵심이다 —
> 그건 **좁히는** 예외(ADMIN → SUPER_ADMIN)라 실수해도 **더 잠기지만**, 이건 **넓히는** 예외라
> 실수하면 **열린다.** 그래서 공개 정책은 **처음부터 공개인 네임스페이스**(`/api/policy/**`)로 모았다 —
> 여기엔 회원별 정보가 절대 들어오지 않는다는 규칙과 함께.

## 8. 상품 한 줄 태그라인 (V33) — 8fter ② · **배포 대기**

8fter 후보의 마지막 하나. 앞의 둘과 달리 **스키마가 붙는다**.

### 8-1. ⚠ `description` 을 잘라 쓰지 않고 컬럼을 새로 판 이유

가장 싼 길은 "설명 앞 60자를 카드에 보여주기"였다. 안 했다 — **설명은 문단이라 앞에서 자르면 문장이
중간에 끊긴다.** 그리고 더 근본적으로 **카드용 한 줄과 상세 설명은 목적이 다른 글**이다(전자는 사게
만드는 카피, 후자는 정보). 같은 데이터로 둘 다 하려 들면 둘 다 어정쩡해진다.

- `VARCHAR2(100 CHAR)` — ⚠ **CHAR semantics**(WA §2-2-1). 실측 확인: `char_used=C, char_length=100`.
- 100자로 잡은 건 **길이로 용도를 알리려는 것**이다. 상품명(200)보다 짧게 둬서 "여기에 설명을 쓰지 말라"를
  스키마가 말하게 했다.
- 엔티티에 **`length = 100` 명시** — 안 주면 기본 255 로 검증돼 `ddl-auto=validate` 가 DDL(100)과
  어긋난다며 **부팅을 막는다**(V12·admin_audit_log 에서 겪은 자리).
- **nullable · 백필 없음** — 사람이 쓰는 카피이지 파생 데이터가 아니라 채울 값이 없다. 기존 상품은 전부 null.

### 8-2. ⚠ 캐시 포맷이 바뀌었다 (WA §2-7)

**`ProductResponse` 는 Redis 캐시(`products:list`) 직렬화 대상**이다. 필드를 하나 더한 것이
곧 **캐시 포맷 변경**이라, 이미 쌓인 값과의 호환을 **추측하지 않고 바이트로** 확인했다.

- 신 코드 ← **옛 캐시값**(tagline 키 없음): 직렬화 후 그 키를 지운 JSON 을 만들어 실제로 역직렬화해 봤다.
  → `tagline=null`, 나머지 필드 정상. **테스트로 고정**(`tagline이_없던_옛_캐시값도_읽힌다`).
- 반대 방향(구 jar ← 신 캐시값)은 **롤백할 때만** 생긴다 — 배포는 구 jar 를 내리고 신 jar 를 올리므로
  둘이 동시에 뜨지 않는다. ⚠ **되돌릴 일이 생기면 캐시를 flush** 해야 한다(아래 배포 절).

### 8-3. 화면 규칙 — 없으면 줄 자체를 없앤다

- 카드: 상품명 **아래**, 가격 **위**(무엇이 좋은지는 이름 다음에 읽혀야 한다). `v-if` + `line-clamp-1`.
  ⚠ 빈 줄을 남기면 **태그라인 있는 카드와 없는 카드의 높이가 달라져** 그리드가 들쭉날쭉해진다.
- 관리 폼: 빈 입력을 **`null` 로 보낸다**(빈 문자열이면 카드의 `v-if` 가 통과해 아무것도 없는 줄이 생긴다).
  **"없음"은 null 하나로만 표현**한다.
