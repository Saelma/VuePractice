### 2-4. 이 API 의 판단 셋

**① 기준값(`threshold`)을 응답에 실어 준다.**
화면이 *"5개 이하"* 를 스스로 적으면 `catalog.low-stock-threshold` 를 바꾼 순간 **문구가 거짓말이 된다.**
G-2 에서 *"혜택 문구는 서버가 값을 줄 때만 노출한다"* 고 정한 것과 같은 자리다(DESIGN §7).
게다가 그 값은 **재고 부족 알림과 같은 것**이라, 알림은 "3개 남았다"는데 대시보드는 안 세는 식으로
갈리지 않는다.

**② `HIDDEN` 제외 · `SOLD_OUT` 포함.**
숨긴 상품은 팔지 않으니 채울 이유가 없다 — 넣으면 「할 일」 목록에 **아무도 손댈 필요 없는 줄**이 낀다.
반대로 `SOLD_OUT` 은 관리자가 손으로 붙이는 표시일 뿐 **재입고가 필요한 건 그대로**라 남긴다.
> ⚠ 실측: `ProductStatus` 에는 **자동 전이가 없다** — 재고가 0이 돼도 `SOLD_OUT` 으로 바뀌지 않는다.
> 코드 어디에도 `status` 를 **쓰는(write)** 경로가 상품 생성·수정 요청 말고는 없고, 읽는 쪽은
> 전부 `!= SELLING`(`ProductResponse.soldOut` · `CartService.available`) 이라 **`SOLD_OUT` 과
> `HIDDEN` 을 구분해서 보는 코드가 없다.** 즉 둘은 관리자가 손으로 고르는 표시일 뿐이고,
> "품절인가"의 진짜 근거는 상태가 아니라 **재고**다 — 그래서 재고 부족 판정도 재고로 한다.

**③ `count`(전체)와 `items`(상위 8줄)를 나눈다.**
`items.size()` 를 숫자로 쓰면 **"10건 넘게 있는데 10으로 보이는"** 거짓말이 된다.
목록의 줄마다 `productId` 를 실어 **고치러 갈 길**을 준다 — 숫자만 주고 끝내면 관리자가 결국
상품을 다시 찾아야 한다.

## 2-10. B-21 가입 약관 동의 — **완료** (배포는 §2-10-7)

### 2-10-1. 왜 이걸 골랐나 — 후보 셋 중 G-3 을 빼고 나서

B-16 을 닫고 다음 후보(G-3 · B-21 · 소형 3건)를 실측했는데, **G-3 의 크기 판정이 백로그와 달랐다**(§2-10-2).
남은 둘 중 B-21 을 골랐다(사용자 확정) — **개인정보를 수집·저장하면서 동의를 안 받는 것**이
이커머스 형태에서 가장 눈에 띄는 빈자리이고, 마이그레이션이 있어 **배포~빈 DB 검증까지 전체 흐름**을
한 번 더 밟는다.

### 2-10-2. ⚠ 착수 전 실측 — **G-3 은 백로그보다 크다** (그래서 뺐다)

백로그 G-3 은 *"`product_id` 를 nullable 로 열면 관리자 답변·알림·목록이 **전부 재사용**된다"*
(크기 소~중)고 적었는데, 실측하니 **재사용되는 건 답변 API 와 알림뿐**이었다.

| 항목이 적은 것 | 실측 |
|---|---|
| "⚠ 상품 문의 쿼리에 `product_id is not null` 이 필요하다" | ❌ **불필요하다.** `InquiryRepositoryImpl` 이 `productId.eq(productId)` 라 **NULL 행은 애초에 안 잡힌다** — 경고가 헛짚었다 |
| "목록이 전부 재사용된다" | ❌ 문의 API 가 **`/products/{productId}/inquiries` 뿐**이다. ①일반 문의 **작성 API 없음** ②**내 문의 목록 API·화면 없음**(`findByAuthorId` 는 리포지토리에만 있고 **탈퇴 정리에서만** 쓰인다) ③**관리자 문의 목록 API·화면 없음** |

가장 큰 건 ③이다 — **관리자는 상품 상세 화면에 들어가야만 문의에 답한다.** 상품이 없는 일반 문의는
**관리자가 찾아갈 경로가 아예 없다.** 즉 G-3 을 제대로 하려면 **B-18(리뷰·문의 관리)의 관리자 목록
화면이 사실상 선행**이다. → **G-3 은 크기 「중」이고 B-18 과 한 묶음**으로 다시 적었다(BACKLOG 갱신).

> **오늘만 백로그 주장이 세 번 틀렸다**(B-16 에서 둘, G-3 에서 하나). WA §1-3 이 하루 종일 값을 했다.

### 2-10-3. 착수 시 정한 것 (사용자 확정)

| 결정 | 고른 것 | 근거 |
|---|---|---|
| 약관 **본문** | **연습용 예시 문안 + 화면 배지로 고지** | ⚠ 법률 문서라 임의로 정하지 않고 물었다. 그럴듯한 약관을 지어내면 **나중에 그대로 쓰일 위험**이 있어서, 경고를 주석이 아니라 **화면 맨 위 배지**로 못 박았다 |
| 마케팅 수신 동의 | **넣는다 (선택 동의)** | 아래 ⚠ 참조 — 제안한 방식이 안 돼서 **수단을 바꿨다** |
| 동의 이력 | **컬럼 둘**(테이블 아님) | 백로그 권장(최소안)을 따랐다. 약관 버전 관리는 약관이 바뀔 일 없는 연습 프로젝트에 과하다 |

> ⚠ **내가 제시한 선택지 하나가 실제로는 안 됐다.** 마케팅 동의를 *"기존 알림 설정에 그대로 반영
> (새 컬럼 없이)"* 하겠다고 적었는데, 알림 설정의 단위는 `NotificationType` enum 이고 서버가
> `values()` 를 통째로 내려줘 **설정 화면에 토글이 저절로 생긴다**(B-15 때 확인한 성질).
> 그런데 **마케팅 알림을 보내는 코드가 없으니 아무 일도 안 하는 토글**이 된다 — 이 프로젝트가
> 피해 온 no-op 배선이다.
> → **`member.marketing_agreed_at` 컬럼**으로 바꿨다. **동의 기록은 배선이 아니라 근거**라 성격이
> 다르다: 지금 안 받으면 **나중에 소급해서 받을 수 없고**, 발송 채널이 생겼을 때 반드시 필요하다.
> 넣기로 한 결정은 그대로 이행하고 **수단만 바꾼 것**이다.

### 2-10-4. 만든 것

**V37 — `member.terms_agreed_at` · `marketing_agreed_at`** (둘 다 nullable, **백필 없음**)

이 마이그레이션의 핵심은 **백필을 안 한 것**이다. V34(`email_verified`)는 `DEFAULT 0` 으로 백필했는데
**거기선 그게 사실과 맞았다**("지금까지 아무도 인증한 적이 없다" = 0). 여기는 반대다 —
기존 회원에게 `sysdate` 를 넣으면 **동의한 적 없는 사람에게 동의 시각이 생긴다.**
하필 이 컬럼은 "동의를 받았다"는 **근거**로 쓸 값이라 **거짓이 가장 비싼 자리**다.
→ `NULL` = 「동의 기록 없음」. 그게 지금의 사실이다.

⚠ 그래서 **소급 적용도 없다** — 기존 회원은 재동의 없이 계속 로그인된다(E-3 비밀번호 정책과 같은 판단).
이걸 테스트로 고정해 뒀다 — 안 그러면 나중에 "동의 안 한 회원 차단"을 무심코 넣어 **기존 회원 전부를
잠글** 수 있다.

⚠ **약관과 개인정보 처리방침을 한 컬럼으로 합쳤다.** 둘 다 필수라 항상 같이 참/거짓이고, 나누면
*"약관만 동의한 회원"* 이라는 **일어날 수 없는 상태**가 표현 가능해진다.

**검증은 DTO 가 아니라 서비스 + 전용 ErrorCode(`AUTH-400T`)**

`@AssertTrue` 를 쓰면 `COMMON-400` 에 `agreeTerms: ...` 형태로 나가는데 그건 **형식 오류의 문구**다.
동의 누락은 형식이 아니라 **정책**이고(비밀번호 정책 E-3 을 DTO 가 아니라 서비스에 둔 것과 같은 판단),
프론트가 **코드로 어느 체크박스를 붉힐지** 고를 수 있어야 한다.
⚠ **`null` 과 `false` 를 함께 막는다** — 필드를 아예 안 보내는 것도 "동의 안 함"이다.
⚠ **동의 시각은 서버가 찍는다.** 요청에 시각을 받지 않는다 — 근거로 쓸 값이라 클라이언트가 정하면
조작 가능해진다.

**화면** — `/terms` · `/privacy`(둘 다 **공개**. 가입 전에 읽는 문서라 로그인 뒤에 두면 안 된다) +
가입 체크박스. 두 문서는 **컴포넌트 하나**가 라우트 이름으로 갈린다(골격이 같아 파일을 나누면
한쪽만 고쳐져 생김새가 갈린다 — 인증 화면 셋을 같은 골격으로 유지한 것과 같은 판단).
⚠ 「전체 동의」는 **필수 ∧ 선택**이다. 필수만으로 켜지게 하면 **선택 동의를 한 적 없는 사람에게
동의 표시가 뜬다.**

⚠ **관리자 회원 상세에 동의 시각을 실었다**(`AdminMemberResponse`) — **조회할 수 없는 동의 기록은
근거 구실을 못 한다.** 화면은 `null` 을 「미동의」가 아니라 **「기록 없음」** 으로 읽어야 한다:
그 사람들은 거부한 게 아니라 **물어본 적이 없는** 것이다.

## 2-11. 마케팅 알림 발송 — **완료** (B-21 후속, 배포는 §2-11-5)

### 2-11-1. 왜 했나 — **사용자 지적에서 나왔다**

B-21 을 닫고 설명하던 중 사용자가 물었다: *"마케팅 동의한 사람한테만 알림을 전송하는 로직을 하면
조회나 컬럼의 쓸모도 다 생겨서 괜찮아지는 거 아니야?"*

**맞는 지적이었다.** B-21 은 동의를 **받기만** 하고 쓰는 곳이 없었다 — 의도된 상태였지만
(동의는 소급해서 못 받으니 먼저 받아 둔다) **고리가 안 닫혀 있었다.** 발송까지 만들면:
①컬럼이 실제로 쓰이고 ②알림 토글이 죽은 게 아니게 되고 ③**수신 거부 경로가 생긴다**
(개인정보 처리방침에 *"동의를 철회할 수 있다"* 고 적어 놓고 방법이 없던 자리다).

### 2-11-2. ⚠ 이 작업의 전부는 「동의와 토글을 합칠 것인가」였다 (사용자 확정)

내가 처음 추천한 것은 **「스위치 하나」**(설정 토글이 `marketing_agreed_at` 을 직접 읽고 쓴다)였는데,
**그 추천이 틀렸다.** 사용자가 되물어 다시 따져 보고 뒤집었다(WA §1-2).

| | 스위치 하나 (내 처음 추천) | **따로** (채택) |
|---|---|---|
| 토글을 끄면 동의 기록 | 🔴 **지워진다**(`= null`) | ✅ 남는다 |
| "언제 동의했었나" | **답 못 함** | 답 가능 |
| `NotificationQueryService` | 🔴 `MARKETING` 만 다른 저장소 → 분기 | ✅ 다른 타입과 동일 |

> **내가 앞뒤가 안 맞았다.** 백필을 안 한 이유가 *"동의 기록에 거짓을 쓰면 안 된다"* 였는데,
> **철회로 기록을 지우는** 설계를 추천했다. 동의 이력은 지우는 게 아니라 **쌓는** 쪽이다.

**두 값은 같은 것을 말하지 않는다** — 그래서 합치면 오히려 서로 다른 둘을 한 칸에 욱여넣는 게 된다:

| 값 | 뜻 | 성질 | 저장소 |
|---|---|---|---|
| `member.marketing_agreed_at` | **동의했나** | 일어난 사건, 안 변함 (근거) | member 컬럼 |
| `NotificationType.MARKETING` 토글 | **지금 받고 싶나** | 자유롭게 바뀜 (선호) | `member_notification_pref` |

⚠ G-2 의 *"설정과 데이터가 갈린다"* 문제와 **다르다** — 저건 **같은 것**을 두 군데가 말해서 생긴 문제였다.

### 2-11-3. 만든 것 — **마이그레이션 0건**

## 2-14. ⚠ 장바구니에 담은 뒤 재고가 빠지면? — **사용자 지적으로 메운 테스트 공백**

배포 후 브라우저 검증 중 사용자가 물었다: *"재고가 있어서 장바구니에 담았고, 지금은 재고가 없는데,
`/checkout` 으로 가니까 주문이 되는 거지?"*

**재현해 보니 코드는 정상이었다.** 방어가 **두 겹**이다:
1. 결제 시작에 `getCart` 로 **`available` 을 다시 계산**한다 — 장바구니(Redis)는 `variantId → 수량`
   만 들고 있어 **담은 시점의 재고를 저장하지 않는다.** 판정은 늘 조회 시점이다.
2. 그다음 원자적 `decreaseStock`(`where v.stock >= :qty`) — 0행이면 `OUT_OF_STOCK`.

| 시나리오 | 결과 |
|---|---|
| 담을 땐 재고 5 → 결제 시점 **0** | ✅ `400 ORDER-400U`, 재고 음수 안 됨 |
| 3개 담았는데 재고가 **2** 로 감소 | ✅ 막힘, **부분 차감도 안 일어남** |
| 담은 뒤 상품이 **판매중지(HIDDEN)** | ✅ 막힘, 재고 그대로 |
| 재고 == 주문 수량 (경계) | ✅ 주문되고 재고 0 |

> **그런데 테스트 공백은 진짜였다.** 기존 테스트
> (`ProductVariantFlowIntegrationTest.soldOutVariantBlocksCheckout`)는 **담을 때 이미 재고가 0** 인
> 경우만 봤다. **담은 뒤 빠지는** 경로는 한 줄도 없었는데, **실사용에선 그쪽이 훨씬 흔하다**
> (장바구니에 며칠 담아 두는 게 정상이고 그 사이 재고는 바뀐다).
> → `StaleCartStockIntegrationTest` **4건**으로 고정했다. 지적이 없었으면 안 열어 봤을 자리다.

⚠ **만들면서 가짜 실패를 한 번 겪었다.** 「재고 == 수량」 케이스에서 *"재고가 안 줄었다"* 고 나왔는데,
`decreaseStock` 이 **벌크 UPDATE 라 1차 캐시를 갱신하지 않는** 것이 원인이었다 — 결제 과정의
`getCart` 가 그 옵션을 이미 로딩해 둬서 **차감 전 값**을 읽었다.
`ProductVariantRepository` javadoc 이 정확히 경고해 둔 자리다(*"벌크 UPDATE라 1차 캐시를 갱신하지
않는다 — 그래서 차감 후 값은 스칼라 프로젝션으로 읽는다"*).
→ `currentStock()` 에 `flush()`+`clear()` 를 넣고 **왜 필요한지 주석으로** 남겼다.
⚠ **운영 코드가 아니라 테스트가 틀린 경우**라, 변형 주입과 반대 방향의 착시다 —
빨간불이 곧 버그는 아니다.

  실패를 0으로 그리면 **"할 일이 없다"로 읽힌다.** `—` 로 표시하고 무엇을 못 읽었는지 위에 알린다.
  → **DESIGN §7 에 올렸다.**
- ⚠ **0이 정상인 화면은 「기대값」을 먼저 뽑아 놓고 검증한다**(§2-8). 대시보드는 반품 요청 0건·
  부연 문구 없음이 **전부 정상**이라, 기대값 없이 보면 *"안 나온다"* 와 *"0이라 안 나온다"* 를
  구분할 수 없다. 브라우저 스텝을 주기 전에 DB 에서 숫자를 뽑아 함께 건넸고, 실제로 그게 없었으면
  "부연 문구가 안 뜬다"를 버그로 의심했을 자리다.
- ⚠ **백로그 주장이 오늘만 세 번 틀렸다** — B-16 에서 둘(§2-1), G-3 에서 하나(§2-10-2).
  특히 G-3 은 *"목록이 전부 재사용된다"* 가 틀려서 **크기 판정 자체가 바뀌었다**(소~중 → 중, B-18 과 한 묶음).
  → **착수 전 실측이 "확인"이 아니라 "우선순위를 다시 정하는" 단계**로 쓰인 첫 사례다.

  알림 설정에 반영"* 하겠다고 물어 놓고, 만들려니 **아무 일도 안 하는 토글**이 되는 구조였다.
  → 선택지를 줄 때도 **그 수단이 실제로 되는지 먼저 실측**한다. 이번엔 결정(넣는다)은 지키고
