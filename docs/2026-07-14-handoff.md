## 4. 시작 전에 알아야 할 것 (중요)

### 4-1. `ddl-auto=update` — **적용 완료** (2026-07-14)

`spring.jpa.hibernate.ddl-auto=update`로 변경하고 재빌드·배포·재기동까지 마쳤다. 이제 **`@Entity`를 만들고 앱을 재기동하면 Hibernate가 Oracle에 실제로 `CREATE TABLE`을 날린다.**

확인한 사실:
- `ESP` 계정 권한: `CREATE TABLE`, `CREATE SEQUENCE`, `CREATE VIEW`, `UNLIMITED TABLESPACE` **보유**
- 현재 스키마: **테이블 0개** (엔티티가 없으니 정상)
- 기본 테이블스페이스: `USERS`

엔티티를 만든 뒤 테이블이 실제로 생겼는지 확인하는 방법:

```sql
-- sqlplus로 접속 후
select table_name from user_tables;
```

> 운영에서는 `update`를 쓰지 않는다(컬럼 삭제·타입 변경을 반영하지 못하고, 예기치 않은 DDL이 나간다). 연습이 끝나고 스키마가 안정되면 `validate` + Flyway/Liquibase로 옮기는 게 정석.

### 4-2. Lombok vs JPA 어노테이션 — 누가 무슨 일을 하나

어노테이션이 한 클래스에 몰려 있어 헷갈리기 쉬운데, **출신이 다르고 하는 일도 다르다.**

| 어노테이션 | 출신 | 하는 일 |
|---|---|---|
| `@Entity` `@Id` `@Column` `@GeneratedValue` | **JPA** (`jakarta.persistence`) | 이 클래스가 **DB 테이블**임을 선언. 컬럼·PK 매핑 |
| `@Getter` `@Setter` `@Builder` `@NoArgsConstructor` | **Lombok** | 게터·세터·생성자 **자바 코드를 컴파일 시점에 자동 생성**. DB와 무관 |

실제로 컬럼을 추가하는 흐름은 이렇다:

1. `@Entity` 클래스에 필드 추가 → `private String phone;`
2. Hibernate가 `ddl-auto=update` 설정에 따라 `ALTER TABLE ... ADD phone` 실행
3. Lombok은 그 필드의 `getPhone()`을 자동으로 만들어줄 뿐

즉 **"필드 추가 → 컬럼 자동 반영"의 주체는 JPA/Hibernate이고, Lombok은 게터·세터 타이핑을 줄여주는 보조 도구**다. 빠르게 개발되는 느낌의 실체는 JPA 쪽이다. (Lombok을 빼도 DB는 똑같이 동작한다. 대신 게터·세터를 손으로 다 써야 한다.)

### 4-3. Redis를 어디에 쓸지 정해야 한다

지금 Redis는 `maxmemory 512mb` + **`allkeys-lru`**(메모리 차면 오래된 키 자동 삭제)로 설정돼 있다. **캐시·세션용 설정**이다.

→ 절대 지워지면 안 되는 데이터(예: 작업 큐, 분산 락)를 같은 인스턴스에 넣으면 축출될 수 있다. 연습 범위에서는 **캐시/세션/카운터**로만 쓰는 게 맞다.

## 6. 모노레포 → MSA 전환 대비

지금은 `esp-backend`(단일) + `esp-frontend` 구조다. 나중에 MSA로 갈 수 있게 **지금부터 지켜두면 좋은 것**들:

**A. 패키지를 계층이 아니라 도메인 기준으로 나눈다**

```
kr.co.ecstel.esp
├─ notice/          ← 나중에 이 폴더째로 떼어내면 서비스 하나
│   ├─ NoticeController, NoticeService, Notice, NoticeRepository
├─ comment/
└─ common/
```

계층별(`controller/`, `service/`, `entity/`)로 나누면 나중에 도메인을 떼어낼 때 파일이 사방에 흩어져 있어 고생한다.

**B. 도메인 간 직접 참조를 피한다**

`Notice` 엔티티가 `Comment` 엔티티를 JPA 연관관계로 직접 물면, 나중에 서비스를 분리할 때 **테이블 조인이 서비스 경계를 넘어버려** 못 쪼갠다. 도메인 경계를 넘을 때는 **ID로만 참조**하고 필요하면 서비스 계층에서 조회하는 습관을 들이면 전환이 쉽다. (연습 단계에서 과하게 지킬 필요는 없지만, "여기가 나중에 경계가 되겠구나"는 의식할 것)

**C. API 우선 (Swagger가 여기서 값을 한다)**

각 도메인의 API를 Swagger로 문서화해두면, 나중에 서비스를 분리할 때 그 문서가 **그대로 서비스 간 계약**이 된다.

**D. 중간 단계로 Gradle 멀티모듈을 거치는 게 안전하다**

```
esp-backend/
├─ settings.gradle        (include 'notice-service', 'common')
├─ common/
└─ notice-service/
```

한 프로세스로 돌지만 모듈 경계가 강제되므로, 도메인 간 의존이 새는 걸 컴파일 단계에서 잡아준다. 여기까지 정리되면 **각 모듈을 별도 프로세스로 띄우는 건 설정 문제**로 줄어든다.

**E. 인프라는 이미 MSA 친화적이다**

- **Nginx** — 지금은 정적+프록시지만, 그대로 **API 게이트웨이** 역할로 확장 가능 (`/api/notice/*` → 8080, `/api/order/*` → 8081)
- **Redis** — 서비스 간 공유 캐시/세션 저장소로 쓸 수 있음
- **`.env` + 환경변수 주입** — 서비스가 늘어도 설정 방식은 동일

> 다만 **처음부터 MSA로 시작하지는 말 것.** 도메인 경계가 뭔지 모르는 상태에서 쪼개면 분산 트랜잭션·네트워크 지연·디버깅 난이도만 얻고 얻는 게 없다. 모노리스로 만들고 경계가 보일 때 쪼개는 게 정석이다.

## 7. 오늘 걸렸던 함정 (같은 데서 두 번 넘어지지 않기)

기록으로 남긴다. 전부 실제로 겪고 해결한 것들.

| 함정 | 증상 | 원인 / 해결 |
|---|---|---|
| **깊은 경로에서 Redis 빌드** | 테스트 대량 실패 | 유닉스 소켓 경로 상한 108자 초과. `/usr/local/src`처럼 짧은 경로에서 빌드 |
| **Redis `Type=notify`** | 90초 타임아웃 후 기동 실패 | `USE_SYSTEMD=yes` 없이 빌드해 libsystemd 미링크. `Type=exec`로 해결 |
| **systemd `EnvironmentFile`로 `.env` 읽기** | Permission denied | **SELinux**가 `init_t`(PID 1)의 홈 디렉터리 파일 읽기를 차단. root라도 못 지나감. 앱 프로세스(ecstel)가 직접 읽도록 변경 |
| **Nginx가 홈 디렉터리 서빙 불가** | 접근 실패 | `/home/ecstel`이 700이라 `nginx` 유저가 통과 못 함. `/var/www`로 배포 |
| **nvm이 root에만 설치됨** | ecstel에서 `node: command not found` | `/root`는 다른 유저가 못 읽음. ecstel 계정에 별도 설치 |
