## 2. 헛짚은 가설 4개 (기록해 두는 이유)

| # | 가설 | 왜 틀렸나 |
|---|---|---|
| 1 | **호스트명이 IPv6 링크로컬로 해석돼 리스너 바인드 실패** | `listener.ora` 가 `(HOST = ecstel)` 인데 `/etc/hosts` 에 핀이 없어 `getent hosts ecstel` 이 `fe80::…` 를 먼저 보여줬다. 그럴듯했지만 **프로그램이 실제로 쓰는 `getaddrinfo`(`getent ahosts`)는 `192.168.50.14` 하나만** 돌려준다. 해석은 원래 정상이었다 |
| 2 | **부팅 시 네트워크 미준비** | sysv-generator 유닛에 네트워크 의존성이 없어 부팅 13초 만에 실행되는 건 사실이었다. override 로 **13초 → 39초**까지 밀었는데 **똑같이 실패**했다 → 타이밍 문제가 아니다 |
| 3 | **sqlplus `startup` 실패** | 수동 실행하면 정상 기동한다. 게다가 `sqlplus -s` 는 내부 SQL 이 실패해도 `exit` 이 **0 을 반환**한다(`WHENEVER SQLERROR EXIT` 없음) → `RETVAL1` 은 사실상 항상 0이라 애초에 범인이 될 수 없었다 |
| 4 | **`su` 로 환경변수가 전파되지 않음** | 스크립트는 root 셸에서 `export ORACLE_HOME/ORACLE_SID` 후 `su` 로 넘긴다. 직접 확인: `SID=[ESPCDB] HOME=[/opt/oracle/product/19c/dbhome_1]` — **정상 전파** |

1·2 는 `627813c` 로 커밋까지 하고 재부팅했다가 **09:21:38 재부팅에서 동일하게 실패**하며 탈락했다.
이때 백엔드가 DB 를 못 잡아 `activating` 무한 재시작 — **운영이 다시 내려갔다.**

> **여기서 방향을 틀었어야 했다.** "고쳤는데 그대로 실패"는 **가설이 틀렸다는 신호**인데,
> 처음엔 "override 가 안 먹었나" 쪽을 의심했다. 실제로는 override 는 **잘 먹었고**(13→39초가 증거),
> 그 사실이 오히려 2번 가설을 반증하고 있었다.

## 3. 진짜 원인 — SELinux 가 `init_t` 의 `/bin/su` 실행을 거부한다

### 3-1. 왜 아무 에러도 안 보였나

부팅 로그를 성공 케이스와 나란히 놓자 결정적 차이가 보였다.

```
[실패, 08:15/09:22]                        [성공, 09:53]
Starting Oracle Net Listener.              Starting Oracle Net Listener.
                                           Oracle Net Listener started.        ← 이 줄이 없다
Starting Oracle Database instance ESPCDB.  Starting Oracle Database instance ESPCDB.
                                           Oracle Database instance ESPCDB started.  ← 이 줄도 없다
Failed to start ...                        Started SYSV: ...
```

**둘 다** 실패했고, 전부 **같은 1초 안**에 끝났다. 두 명령의 유일한 공통점은 **`su`** 다.

원인 추적이 어려웠던 이유가 세 겹이다:

1. 스크립트가 두 명령의 출력을 **`> /dev/null 2>&1` 로 통째로 버린다**(70·83행).
   그래서 `"Failed to start ..."` 한 줄만 남는다.
2. **Oracle 이 아예 실행되지 않았으므로** TNS/ORA 에러도, 리스너 로그도 **어디에도 없다.**
   "리스너 로그를 보자"가 계속 헛돌았다.
3. 셸에서 수동 실행하면 `unconfined_t` 라 **항상 성공**한다 → "수동은 되는데 부팅만 실패"로 보인다.

### 3-2. 증거

`journalctl | grep avc` 는 **빈손이었다.** AVC 거부는 저널이 아니라 **`/var/log/audit/audit.log`** 로만 간다.
(단서는 있었다 — 실패 다음 초에 `Starting SETroubleshoot daemon for processing new SELinux denial logs...`)

```
$ sudo ausearch -ts 09:22:10 -te 09:22:25

type=AVC msg=audit(...:64): avc: denied { execute } for pid=1077 comm="oracledb_ESPDB-" name="su"
  scontext=system_u:system_r:init_t:s0
  tcontext=system_u:object_r:su_exec_t:s0  tclass=file permissive=0
type=AVC msg=audit(...:66): avc: denied { execute } for pid=1087 ... (동일)
type=SYSCALL ... success=no exit=-13
type=SERVICE_START ... unit=oracledb_ESPDB-19c ... res=failed
```

**거부가 PID 1077·1087 두 개** — 리스너용 `su` 와 sqlplus 용 `su`, 정확히 두 번이다.
`exit=-13`(EACCES). SELinux 는 `Enforcing`.

### 3-3. 수정 — 원본 스크립트를 건드리지 않는다

```
/bin/su           → su_exec_t   (init_t 에서 거부)
/usr/sbin/runuser → bin_t       (init_t 가 실행 가능)
```

`runuser` 는 util-linux 가 **init 스크립트용으로 제공하는 `su` 대체품**이고 옵션(`-s`/`-c`)이 같다.
그리고 스크립트 47행에 훅이 있다:

```bash
if [ -z "$SU" ];then SU=/bin/su; fi
```

→ **환경변수 `SU` 만 넣으면 원본 스크립트 수정 없이 교체된다.** drop-in 에 한 줄:

```ini
[Service]
Environment=SU=/usr/sbin/runuser
```

원본(`/etc/init.d/oracledb_ESPDB-19c`)은 설치 프로그램 소유라 손대지 않는 방침을 지켰다
(`infra/README` 의 "여기 없는 것" 항목).

### 3-4. 검증 — **재부팅 없이** 부팅 조건을 재현했다

`systemctl start` 는 ExecStart 를 **`init_t` 컨텍스트로 실행**한다. 즉 SELinux 조건이 부팅과 같다.
DB 를 내린 뒤 `systemctl start` 가 성공하면 부팅에서도 성공한다.

```
$ sudo bash /tmp/ora-debug.sh stop          # cold 상태로
$ sudo systemctl start oracledb_ESPDB-19c   # ← init_t 로 실행됨
$ systemctl is-active oracledb_ESPDB-19c glassvue-backend
active
active
```

|---|---|
| 기동 소요 | **30초** (09:53:02 → 09:53:32) — 실패할 땐 1초였다 |
| 유닛 로그 | `runuser[27272]: pam_unix(runuser:session): session opened for user oracle` ← `su` 아님 |
| | `Oracle Net Listener started.` · `Oracle Database instance ESPCDB started.` **둘 다 출력** |

## 4. 진단 중 발견한 별건 — 스크립트가 PDB 를 못 연다

디버그 실행(리다이렉트를 벗긴 사본)에서 드러났다.

```
bash: 경고: here-document가 줄 1에서 파일의 끝으로 구분됨 (`EOF'를 예상함)
ORA-00933: SQL 명령어가 올바르게 종료되지 않았습니다
SP2-0042: 알 수 없는 명령어 "EOF" - 무시됨
```

스크립트 78~83행이 두 군데 깨져 있다:

1. heredoc 종료자 `EOF` 가 **들여쓰기**돼 있다 — `<<` 는 들여쓴 종료자를 인식하지 않는다(`<<-` 가 아님).
2. `alter pluggable database all open` 에 **세미콜론이 없어** 다음 줄 `exit` 이 붙어버린다 → `ORA-00933`.

즉 **스크립트는 PDB 를 여는 데 매번 실패하고 있다.** 그런데도 `espdb` 는 열려 있다 — 확인해 보니
Oracle 19c 의 PDB **saved state** 가 대신 열고 있었다.

```
select name, open_mode from v$pdbs;               → ESPDB  READ WRITE
select con_name, state from dba_pdb_saved_states; → ESPDB  OPEN
```

**오늘 재부팅이 그대로 실증한다** — 10:08 부팅에서 스크립트의 `alter ...` 는 `ORA-00933` 으로 실패했는데
`ESPDB` 는 `READ WRITE` 로 올라왔다. saved state 가 실제로 동작한 것이다.

> **처음엔 "saved state 가 없어지면 터진다"고 적었는데 표현이 과했다.** saved state 는 CDB 에
> **영구 저장되는 정식 메커니즘**이라 저절로 사라지지 않는다(`discard state` 를 명시적으로 하거나
> PDB 를 재생성해야 없어진다). **현 서버에는 추가 조치가 필요 없다.**

→ 다만 **재구축 시에는 이 상태가 없다.** 새로 만든 PDB 는 saved state 가 비어 있어 부팅 후
`MOUNTED` 로 남는다. `infra/README` 재구축 절차에 "PDB 를 연 뒤 `save state` 한 번" 을 명시했다.

## 5. `/tmp` WebP 바이너리 누수 — 전용 tmpdir 로 해결 (7/21 부터 이월)

scrimage-webp 는 JVM 이 시작할 때 `cwebp`(4.6MB)·`dwebp`(1.9MB)를 `java.io.tmpdir` 에 추출하고
**종료할 때 정리하지 않는다.** 파일명이 JVM 마다 고유해서(`cwebp<난수>binary`) **덮어쓰지도 않는다.**
→ `gradle test`·`bootRun` 을 돌릴 때마다 `/tmp` 에 6.5MB 씩 쌓였다.

### 5-1. ⚠ 착수 전 판단이 틀렸다 — "무한히 커진다"가 아니었다

이 항목을 "시간이 지날수록 나빠지는 **유일한** 항목"이라며 1순위로 추천했는데, **근거가 틀렸다.**
착수해서 실측해 보니:

| 확인 | 결과 |
|---|---|
| `/usr/lib/tmpfiles.d/tmp.conf` | **`q /tmp 1777 root root 10d`** — 10일 경과분 자동 삭제 |
| `systemd-tmpfiles-clean.timer` | **active** (하루 1회, 실측 당시 33분 전 실행됨) |
| 그래서 | **무한 증가가 아니라 10일치에서 상한이 걸린다** |
| 규모 | 37MB = 디스크의 **0.14%**. `/tmp` 전체가 58MB |
| 루트 81% 의 실제 원인 | `/opt/oracle` 11G + `/usr` 5.3G + `/home` 3G (7/21 점검) — `/tmp` 와 무관 |
| 운영 서비스 | **누수 없음.** 유닛이 `PrivateTmp=yes` 라 격리 — private tmp 13개 총 **0바이트**, webp 바이너리 **0개** |

→ **디스크 압박의 원인이 아니고, 운영과도 무관하며, 자동 상한도 있다. 위험이 아니라 위생 문제였다.**
그래도 대응이 싸서(설정 몇 줄) 그대로 진행했다. **다만 "1순위"라는 판단은 철회한다.**

> **교훈**: "계속 커진다"고 단정하기 전에 **이미 걸려 있는 자동 정리부터 확인**한다.
> `tmpfiles.d` 규칙 한 줄이 전제를 통째로 바꿨다.

### 5-2. 선택한 안과 버린 안

**① 앱 전용 `java.io.tmpdir`** 을 골랐다 — `build/apptmp` 로 돌려 **`gradle clean` 이 함께 치우게** 한다.

- **버린 ②(`systemd-tmpfiles` 주기 정리)**: 이미 10일 규칙이 있어 중복이고, 기간을 줄이면
  **실행 중 JVM 이 쓰는 바이너리를 지울 위험**이 있다. scrimage 는 변환할 때마다 그 바이너리를
  `exec` 하므로, 지워지면 그 뒤 변환이 깨진다.
- **버린 ③(현행 유지)**: 자동 상한이 있으니 방치해도 되긴 하지만, 개발할 때마다 6.5MB 씩
  시스템 `/tmp` 에 남기는 건 정리 대상이 불분명하다. 프로젝트 `build/` 안이면 **경계가 명확하다.**

## 6. `ItemThumb` 컴포넌트 테스트 (7/21 부터 이월)

순수 컴포넌트 중 **유일하게 테스트가 없던 것**. 이걸로 DevExtreme 을 안 쓰는 컴포넌트는 전부 커버됐다.

### 무엇을 고정했나 — "로드 실패가 정상 흐름"이라는 계약

이후 상품이 삭제되면 파일이 정리돼 **404 가 된다**(V9, 7/21 §12). 이름·가격이라는 본질 기록은 남으므로
화면은 깨지지 않고 대체 표시로 넘어가야 한다.

6건을 넣었고, 그중 **둘이 핵심**이다:

- **로드 실패 시 대체 표시로 넘어간다** — `img` 에 `error` 를 발생시키면 `img` 가 사라지고 `🖼️` 가 뜬다.
- **`src` 가 바뀌면 실패 상태를 초기화하고 다시 시도한다** — 목록에서 컴포넌트가 **재사용**되므로,
  실패 상태가 남아 있으면 **다음 품목까지 계속 대체 표시로 뜬다.** `watch(() => props.src)` 가 그걸 막는데,
  이건 없어도 화면이 "그럴싸하게" 동작해서 조용히 회귀하기 쉬운 종류다 — 그래서 테스트로 못박았다.

나머지 4건: `src` 있으면 이미지 / 없으면 대체 표시(배송지 도입 이전 주문처럼 스냅샷이 없는 경우) /
`size` 클래스 반영(목록과 상세의 썸네일 크기가 다르다) / 대체 표시는 `aria-hidden`(장식).

## 7. 문의 목록 이미지 N+1 실측 (7/21 부터 이월) — **N+1 없음**

`findByGroups` 배치로 회피했다고 적어만 뒀고 **실제 쿼리 수를 센 적이 없던** 항목.
P6SPY 는 이미 깔려 있었으므로(`application-dev.yml` 이 URL 에 `p6spy:` 접두사만 붙인다) 띄워서 셌다.

### 7-1. 측정 방법

- dev 인스턴스를 **8081** 에 띄우고 **Redis 는 db3 으로 격리**했다.
  격리한 이유가 둘이다 — ①운영 캐시(db0)를 안 건드리려고 ②`products:list` 가 캐시되므로
  **캐시 히트가 나면 쿼리가 0 이 되어 측정이 무의미**해진다.
- 요청 직전 로그 줄 수를 기록하고, 요청 후 **그 뒤에 붙은 줄만** 잘라 세는 방식(다른 요청과 섞이지 않게).
- 데이터를 만들지 않고 **읽기만** 했다 — 검증 잔여물 없음(§3).

### 7-2. 결과

**문의 목록** (`/api/products/{지바}/inquiries`, 문의 4건·이미지 그룹 1개) — **총 2회**

```
1  select ... from inquiry i1_0 where ...        ← 목록
2  select ... from image i1_0 where image_group_id in (...) order by sort_order
```

**상품 목록** (`/api/products?size=20`, 이미지 그룹 2개) — **총 3회**

```
1  select ... from product p1_0 ... fetch first 20 rows only
2  select ... from image i1_0 where i1_0.image_group_id in ('019F82DA…','019F64BA…') order by sort_order
3  select ... from category c1_0 where c1_0.id in ('019F647B…','019F647B…',NULL × 98)
```

### 7-3. 판정

- **이미지 N+1 없음.** 상품 목록에서 **그룹이 2개인데 이미지 쿼리는 1회**다 — N+1 이었다면 3회여야 한다.
- `ImageService.findByGroups` 의 `i.getImageGroup().getId()` 가 **LAZY 프록시를 초기화하지 않는다**는 것도
  같은 결과로 실증됐다(초기화됐다면 그룹 수만큼 `image_group` 조회가 붙는다).
- **문의 목록도 같은 `findByGroups` 를 호출**하므로 그 성질이 그대로 적용된다.

> ⚠ **측정의 한계를 정확히 적는다**: 문의 쪽은 **이미지 그룹이 1개뿐**이라, 그 요청만으로는
> 배치와 N+1 이 **구분되지 않는다**(둘 다 1회). 판별은 그룹이 2개인 **상품 목록이 해줬고**,
> 문의는 동일 코드를 호출한다는 근거로 이어 붙인 것이다. 그룹이 3개 이상인 문의 데이터를 만들면
> 문의 경로만으로도 직접 판별할 수 있으나, 그러려면 ZZ 검증 데이터(상품·이미지·문의) 생성이 필요해
> 오늘은 하지 않았다.

### 7-4. 부수로 확인한 것

- **카테고리 `IN` 에 붙은 `NULL` 98개는 버그가 아니다.** `application.yml` 의
  `hibernate.default_batch_fetch_size: 100` 이 동작한 결과다(주석에 *"지연로딩 연관(예: product.category)을
  페이지 단위로 일괄 로딩해 N+1 완화"* 라고 이미 적혀 있다). 즉 **카테고리도 N+1 이 아니라 배치**다.
  바인드 슬롯을 100개로 패딩하는 건 실행계획 재사용을 위한 Hibernate 동작이다.
- **문의 목록에 count 쿼리가 없다.** 첫 페이지이고 결과 수(4)가 페이지 크기(50)보다 작아
  Spring Data 가 count 를 생략한 것(`PageableExecutionUtils`). 정상이다.

### 7-5. 정리 확인

dev 종료 후 실측: 8081 응답 없음 · 운영 `active`/health `UP` · **운영 캐시 db0 253키 무손상** · dev db3 0키.

## 8. 기능 추가 — 주문 배송 추적 (V13)

이월을 다 털고 **이커머스 기준 기능 갭**을 뽑아 그중 하나를 구현했다. 후보를 A(주문 흐름의 구멍)·
B(커머스 표준)·C(규모 확장)로 나눴고, **A-1 배송 추적**을 골랐다 — 새 기능이라서가 아니라
**이미 만든 것이 미완이라서**다. 배송지(V11)·진행 스텝 UI·관리자 발송 처리를 다 만들어 놓고
"보냈고 어떻게 가고 있는지"만 비어 있었다.

> 참고로 뽑은 갭 목록: **A**-1 배송추적 / A-2 배송비 / A-3 사람이 읽는 주문번호,
> **B**-4 쿠폰 / B-5 배송지 주소록 / B-6 위시리스트 / B-7 정가·할인가,
> **C** 상품 옵션(사이즈·색상) · 반품/교환 · 적립금·등급 · 매출 통계.
> **A-2(배송비)는 A-1 다음으로 값어치가 크다** — 금액 계산의 토대라 쿠폰(B-4)보다 먼저 와야 한다.
> 배송비 없이 쿠폰을 넣으면 계산 로직을 다시 짜게 된다.

### 8-1. 만든 것

상태 흐름이 `ORDERED → PAID → SHIPPED → **DELIVERED**` 로 늘었다.

| 계층 | 내용 |
|---|---|
| DB | **V13** — `orders`에 `ship_carrier`·`ship_tracking_no`·`delivered_at`(전부 nullable, CHAR semantics) + `status` CHECK 교체 |
| enum | `DeliveryCarrier`(CJ·우체국·한진·롯데·로젠·기타) — 택배사별 **조회 URL 형식을 서버가 갖는다** |
| 엔티티 | `Order.ship(carrier, trackingNo)` · `deliver()` · `isDeliverable()` |
| DTO | `OrderShipRequest`(둘 다 `@NotNull`/`@NotBlank`) · `OrderResponse`에 `shipCarrier`·`shipCarrierName`·`shipTrackingNo`·`trackingUrl`·`deliveredAt` |
| API | `POST /api/orders/{id}/ship`이 **본문을 받게 변경** · `POST /api/orders/{id}/deliver` 신설(둘 다 ADMIN) |
| 프론트 | 주문 상세에 **배송 추적 카드**(조회 링크) + 진행 스텝 4단계, 관리자 화면·상세에 **운송장 입력 폼**, 배송완료 버튼, 상태 탭에 배송완료 |

### 8-2. 판단 근거 (버린 안 포함)

- **운송장을 필수로 했다.** 선택으로 두면 "발송됐는데 추적 정보가 없는" 주문이 생기는데,
  나중에 채워 넣을 경로가 없어 그 주문은 **영영 추적 불가**가 된다. 그래서 발송 전이와
  운송장 등록을 한 트랜잭션으로 묶었다("발송 처리 = 운송장 등록").
- **조회 URL을 서버가 만든다.** 택배사별 URL 형식을 프론트에 두면 화면마다 중복되고 서버는
  검증할 근거가 없다. 응답에 완성된 `trackingUrl`을 실어 주면 화면은 링크만 걸면 된다.
  링크가 없으면(null) 화면이 감추고 송장번호만 보여준다.
  > ⚠ **처음엔 실제 택배사 URL을 enum에 박았다가 되돌렸다 — §8-7 참고.**
- **`ship_carrier`에는 CHECK를 안 걸었다.** 택배사는 앞으로 늘어날 값이라 CHECK를 걸면
  하나 추가할 때마다 아래 §8-3의 제약 교체 작업을 반복해야 한다. 검증은 enum이 역직렬화 단계에서 한다.
  반대로 `status`는 상태 전이 규칙이라 **DB 레벨 보호를 유지**했다 — 둘의 성격이 다르다.
- **`isCancellable()`은 손대지 않았다.** `<> CANCELLED`가 아니라 **명시적 열거**(ORDERED·PAID)로
  돼 있어서 DELIVERED가 늘어도 자동으로 포함되지 않았다. 7/16에 상태를 확장하며 리뷰 구매인증
  범위가 조용히 어긋났던 사고(ARCHITECTURE §5)의 대비책이 실제로 작동한 사례다.

### 8-3. ⚠ Oracle CHECK 제약 교체 — 이름이 DB마다 다르다

`V1__init.sql`이 `status`를 **인라인 CHECK**로 선언해서 제약 이름이 자동 생성(`SYS_Cnnnnnn`)이고,
그 이름이 **espdb와 esptest에서 서로 다르다.** 이름을 하드코딩하면 한쪽에서만 동작하고
빈 DB 검증(§2-2)에서 깨진다. → PL/SQL로 **조건으로 찾아 드롭**한 뒤 `ck_orders_status`로
**이름을 붙여** 다시 만들었다. 다음 상태 추가부터는 `migration/README`의 예시대로 DROP/ADD 두 줄이면 된다.

- 못 찾아도 실패시키지 않게 했다(루프). **대신 그게 위험 지점이다** — 드롭이 조용히 실패하면
  옛 제약(4값)과 새 제약(5값)이 **공존**해 `DELIVERED` 저장이 ORA-02290으로 터진다.
  그래서 검증에서 **제약이 1개인지**를 직접 확인했다(§8-4).
- 구 jar 영향 없음: **넓히는 방향**이라 구 jar는 DELIVERED를 쓰지 않고 쓰던 4개 값은 그대로 허용된다.
  §5가 경계하는 건 좁히는 경우다. 사용자 확인 후 적용했다.

### 8-5. ⚠ HTTP 호출부 — 컴파일러가 안 잡아주는 자리

- 컴파일러가 잡아준 것: `Order.ship()`·`OrderService.ship()` 호출 **5곳**(테스트).
- **컴파일러가 못 잡는 것**: `mockMvc.perform(post(".../ship"))` 2곳, 프론트 `shipOrder()` 2곳.

### 8-6. ⚠ 배포 사고 — 옛 코드가 조용히 배포됐다

배포 스크립트를 돌렸는데 **백·프론트 둘 다 옛 코드가 나갔다.** 원인은 하나다:

> **배포 스크립트는 작업 브랜치가 아니라 `main` 워크트리(`/home/ecstel/work`)에서 빌드한다.**
> 그때 `main`은 배송 추적 커밋 2건을 아직 못 받은 상태였다.

**가장 나쁜 점은 조용했다는 것이다.** 스크립트는 정상 종료했고 jar 파일 시각(13:45)도 갱신돼서
겉보기엔 배포에 성공한 것 같았다. 실제로 나간 건 그 전 커밋이었다.

**게다가 내 확인 방법이 그 사실을 한 번 가렸다.** 신규 `/deliver` 가 있는지 보려고 미인증 요청을
날려 **401이 나오니 "엔드포인트 있음"으로 판단**했는데, `/api/orders/**` 는 인증이 필요해서
**없는 경로도 401**이다. 존재 여부를 상태코드로 가리려 한 게 잘못이었다.

→ 확실한 신호로 다시 확인했다:

| 신호 | 배포 전(옛 코드) | 배포 후 |
|---|---|---|
| OpenAPI 경로 | `/ship` 만 | **`/ship` + `/deliver`** |
| `/ship` requestBody | 없음 | **`OrderShipRequest`(`carrier`·`trackingNo` 둘 다 required)** |
| carrier enum | — | `CJ·KOREA_POST·HANJIN·LOTTE·LOGEN·ETC` |
| 프론트 번들 | `index.437a53f0.js` | **`index.2160b31c.js`**(로컬 빌드와 일치) |

**두 교훈 모두 WORKING-AGREEMENTS §5로 옮겼다** — ①배포 전 `main` ff 머지 ②배포 확인은
OpenAPI·번들 해시 같은 "코드가 실제로 바뀐 증거"로.

### 8-7. ⚠ 되돌린 결정 — 실제 택배사 URL을 코드에 박았다가 뺐다

처음 구현에서 `DeliveryCarrier` enum에 **실제 택배사 조회 URL**(CJ대한통운·우체국·한진·롯데·로젠)을
박았다. 그리고 그게 동작하는지 확인한다고 **그 사이트들에 curl GET을 보냈다.**
사용자가 *"실제 택배사 사이트에 보내면 어떡하냐, 돈 나가는 거 아니냐"* 며 중단시켰다.

**과금은 실제로 없었다** — 계약도 API 키도 없는 공개 조회 페이지에 대한 단순 GET 5건이고,
브라우저로 그 주소를 여는 것과 같다. 하지만 **지적 자체는 타당했고, 두 가지가 잘못이었다:**

1. **외부로 나가는 호출을 확인 없이 했다.** 결과가 무해했다는 건 사후 판단이고, 보내기 전에 물었어야 한다.
2. **더 근본적으로, 연습 단계에서 실제 택배사를 가리키는 설계 자체가 틀렸다.**
   - 주문이 전부 가짜라 송장번호도 가짜 → 링크를 눌러도 **"조회 결과 없음"** 만 나온다. 쓸모가 없다.
   - **통제할 수 없는 외부 의존**이 생긴다. 실제로 확인 중 CJ만 응답하지 않았는데(`000`),
     봇 차단인지 URL 변경인지 **알 방법이 없다는 게 문제의 핵심**이다 — 우리 화면의 링크가
     조용히 깨져 있어도 알 수 없다.
   - ARCHITECTURE §1 "미리 만들지 않는다"에도 어긋난다.

**고친 방식** — URL을 **설정으로 빼고 기본값은 앱 안의 예시 페이지**로:

| 계층 | 변경 |
|---|---|
| `DeliveryCarrier` | URL 제거, `displayName` + `isTrackable()`만 남김(ETC는 조회할 곳이 없다) |
| `DeliveryProperties` | `glassvue.delivery` 설정. 택배사별 URL 맵 + 기본 형식. 자리표시자 `{trackingNo}`·`{carrier}` |
| `application.yml` | 기본값 `/mock-tracking?carrier={carrier}&no={trackingNo}` |
| 프론트 | `MockTrackingView.vue` + `/mock-tracking` 라우트 — **"예시 페이지입니다"를 화면 맨 위에 명시**하고, 배송 단계의 시각은 **비워 둔다**(지어낸 값을 넣지 않는다) |

- **실서비스 전환은 설정만 채우면 된다** — 코드 변경 없음. PG를 seam으로 남겨둔 것과 같은 방식.
- `default-tracking-url`을 빈 문자열로 두면 **링크 자체를 안 만든다**(송장번호만 표시).
- 이 전환 경로가 실제로 되는지 `DeliveryPropertiesTest`로 고정했다(택배사별 설정이 기본값을 이긴다).

> **교훈**: 연습 단계 프로젝트에서 **외부 서비스로 실제 요청을 보내거나 링크를 걸지 않는다.**
> 필요하면 **앱 안에 예시 페이지를 만들어** 거기로 보내고, 외부 호출이 필요하면 **먼저 묻는다.**

**배포 확인(실측)**: jar에 `DeliveryProperties.class` 존재(14:28) · `DeliveryCarrier.class`가
2794→**1984바이트**로 줄어듦(URL이 빠진 부수 증거) · 프론트 번들 **`index.5c2faeef.js`**(로컬과 일치) ·
번들에 `/mock-tracking` 포함 · health `UP`.

> ⚠ **`/mock-tracking`에 HTTP 200이 온다는 건 배포 증거가 아니다** — SPA라 nginx가 모든 경로에
> `index.html`을 돌려준다. 실제로 이 신호에 한 번 속을 뻔했다. 번들 해시로 확인해야 한다.
> (§8-6의 "401이면 엔드포인트 있음"과 같은 종류의 착각이다.)

**⚠ 그리고 여기서 `main` ff 머지를 또 빠뜨려 옛 코드가 한 번 더 배포됐다 — 오늘 두 번째다.**
§8-6에서 규약(§5)으로 올려놨는데도 재발했다. **규약만으로는 안 걸러진다.**
→ 대응: ①앞으로 배포를 요청하기 **전에 내가 먼저 `main`을 ff 머지**한다(사람이 기억할 단계를 줄인다)
②배포 스크립트가 시작할 때 `main`이 뒤처졌으면 **경고**하도록 하는 게 구조적 해법이다
(이미 `check-infra-drift.sh`를 그 자리에서 돌리고 있으니 같은 방식 — 막지 않고 경고만).

### 8-8. 배포 후 브라우저 확인 순서

> `ZZ` 규약(§3-1): **실상품이 아니라 `ZZP-` 상품을 만들어서** 하고, 수령인에 `ZZ`를 남긴다.
> 실상품으로 하면 재고가 실제로 깎이고, `ZZ`가 없으면 나중에 정리 대상을 못 찾는다.
> 발송·배송완료는 **되돌릴 수 없으니**(취소 불가) 반드시 `ZZP-` 상품으로 할 것.

1. 관리자로 **`ZZP-` 상품 등록** → 일반 계정으로 장바구니 담기 → 주문서에서 **수령인 `ZZ수령인`** 으로 결제.
2. 주문 상세 → 진행 스텝이 **4단계**로 보이고 "배송 완료"가 마지막에 있는지(아직 미점등).
3. 구매자로 **결제하기** → `PAID`.
4. 관리자 주문 화면 → 그 주문의 **[발송]** → **운송장 입력 폼**이 뜨는지.
   **송장번호를 비운 채 [발송 처리]** → "송장번호를 입력해 주세요"로 **화면에서 먼저 막히는지**(서버 400 아니라).
5. 택배사 `CJ대한통운` + 송장번호 입력 → 발송 처리 → 목록에서 상태 `발송완료`, **[배송완료] 버튼**이 생기는지.
6. 주문 상세 → **배송 추적 카드**에 택배사·송장번호가 보이고 **[배송 조회 ↗]** 링크가 CJ 조회 페이지로 가는지.
   (⚠ 운영 서버는 LAN 내부지만 이 링크는 **브라우저가 여는 것**이라 클라이언트에 인터넷이 있으면 열린다.)
7. 택배사를 **기타**로 한 주문도 하나 만들어 → 송장번호는 보이는데 **조회 링크는 없어야** 한다.
8. 관리자 **[배송완료]** → 상태 `배송완료`, 진행 스텝 4단계 **전부 점등** + 수령 일시 표시.
9. **배송 추적 도입 이전 주문**을 열어 → 배송 추적 카드가 **아예 안 보여야** 한다(빈 칸이 아니라).
   진행 스텝도 깨지지 않아야 한다.
10. 주문 목록 상태 탭에 **배송완료**가 있고 건수가 맞는지. 관리자 화면 상태별 건수도 마찬가지.
11. **정리**: `ZZP-` 상품 삭제. 발송된 주문은 취소가 안 되므로 **주문 레코드는 남는다** —
    남는 주문을 사용자에게 보고한다(§3).
