## 2. 무엇을 할 것인가 — B-9 재입고 알림

이월의 「그다음 작업 후보」이자 BACKLOG 다음 추천이었다. 인앱 알림 인프라(전달·설정·SSE·토스트)가 §11 로
이미 깔려 있어 **producer 하나만 얹으면 되는** 자리라고 적혀 있었다. 실제로도 그랬지만, 착수 전 코드를
읽다가 **제품 결정 두 개**가 나왔다(코드가 아니라 사용자가 정할 것이라 물었다).

### 2-1. ⚠ 착수 전 발견 두 가지

1. **`notification.type` 에는 CHECK 제약이 없다**(V26 확인). 그래서 `NotificationType.RESTOCK` 추가에
   **마이그레이션이 필요 없다** — Oracle enum CHECK 트랩(메모리 참조)이 여기엔 해당하지 않는다.
   V26 이 일부러 unconstrained VARCHAR2 로 둔 덕이다. (트랩은 `product.status`·`orders.status`·
   `point_history.type` 등 **CHECK 가 붙은** enum 컬럼에만 해당.)
2. **관리자 상품 편집이 옵션을 delete + 재삽입한다**(`ProductCommandService.update`) → **`variant.id` 가
   편집할 때마다 새로 생긴다.** 이게 두 결정을 다 좌우했다:
   - 관리자 재고 입력(restock 의 **주된** 실제 경로)은 `increaseStock` 을 안 타서 이벤트가 안 나간다.
   - variant_id 로 구독을 걸면 관리자가 편집하는 순간 **구독이 전부 고아**가 된다.

### 2-2. 결정 (사용자 확정)

| 질문 | 결정 | 이유 |
|---|---|---|
| 발송 트리거 | 주문취소·반품복원 **+ 관리자 재고편집** | 실제 이커머스의 주된 재입고는 "관리자가 재고를 채우는 것". 이걸 빼면 기능이 반쪽 |
| 구독 단위 | **상품 단위**(member+product) | variant.id 불안정 회피. 위시리스트와 같은 검증된 패턴. 멀티옵션 상품 false positive 는 감수 |

상품 단위로 정하니 관리자 편집 경로도 깔끔해졌다 — 옵션이 아니라 **상품 총재고 0→양수**만 감지하면 된다.

## 3. 구현

### 3-1. 이벤트 — `StockReplenishedEvent` (catalog 소유, `StockRunningLowEvent` 와 대칭)

재고는 catalog 가 소유하므로 재입고 이벤트도 catalog 가 낸다(주문 경로든 관리자 경로든 같은 이벤트).
페이로드는 `(productId, productName)` — 상품 단위라 옵션 정보를 담지 않는다.

### 3-2. ⚠ 3층 중 **핸들러를 restock 도메인에 뒀다** (재고부족과 다르다)

재고부족(`StockRunningLowEvent`)은 notification 도메인이 받는다 — 받아서 관리자에게 알리면 끝이라
알림이 곧 주체다. **재입고는 다르다** — 구독(신청) 데이터가 있고, 발송 후 그 구독을 **소진**해야 한다.
notify + 소진은 **구독 생명주기**라 restock 관심사다. 그래서:

- `catalog/event/StockReplenishedEvent` (발행: catalog)
- `restock/RestockEventListener` (어댑터, `@Async @TransactionalEventListener(AFTER_COMMIT)`)
- `restock/RestockNotificationHandler` (신청자 조회 → `NotificationCommandService.create(RESTOCK)` → 그 상품 구독 `deleteByProductId`)

의존 방향 `catalog →(event)→ restock → notification`, **순환 없음**. notification 은 restock 을 모른다.
알림 생성은 notification 의 공개 입구(`create`)로만 — 그 안에서 타입별 opt-out("재입고 알림" 끔)도 존중된다.

### 3-3. ⚠ 재입고 판정 — "상품 총재고 0→양수" 를 두 경로에서 (한 번만 발화)

`ProductVariantRepository.sumStockByProduct(productId)` 를 새로 추가해 상품 총재고를 스칼라로 읽는다.

- **`increaseStock(variantId, qty)`**(주문취소 §OrderService:261 · 반품승인 :296): 옵션 증가 후,
  `총재고 − 방금 더한 qty == 0` 이면 증가 직전이 0(=상품 전체 품절)이었다는 뜻 → 지금 양수면 발화.
  한 주문에 같은 상품 옵션이 여러 개여도 **첫 증가에서만** 조건이 참이라 발화는 1회.
- **`update(id, req)`**(관리자 편집): 옵션 통째 교체 **전** 총재고를 재두고(`stockBefore`),
  교체 후 총재고가 양수면서 `stockBefore==0` 이면 발화. `sumStockByProduct` 가 JPQL 이라 재삽입분을
  flush 한 뒤 값을 본다.

`increaseStock` 은 이제 반환행이 0(옵션 삭제됨)이면 조용히 무시하고, 아니면 판정한다.

### 3-4. 구독 도메인 + API (위시리스트 미러)

- `restock_subscription`(RAW(16) PK, member_id·product_id 느슨한 UUID, 감사 컬럼 `TIMESTAMP(9) WITH TIME ZONE`,
  `UNIQUE(member_id, product_id)`) — V28.
- ⚠ **위시리스트와 달리 `product_id` 인덱스를 따로 만들었다.** 조회 경로가 둘(내 신청=member_id / 신청자
  전원=product_id)인데, 후자가 재입고마다 도는 핫 경로인데 UNIQUE 선두가 member_id 라 못 탄다.
- 서비스: CQRS 분리(`RestockSubscriptionCommandService` subscribe/unsubscribe 멱등 · `...QueryService` myProductIds).
- API: `POST/DELETE /api/restock/{productId}`, `GET /api/restock/product-ids`. 전부 본인 것만(토큰).
- `SecurityConfig` 에 `/api/restock/**` authenticated 추가(기본 permitAll 이라 안 넣으면 남의 신청 열림 —
  위시리스트·쿠폰에서 겪은 자리).

### 3-5. 프론트 — 품절 상품에 "재입고되면 알림 받기"

`api/restock.js` · `stores/restock.js`(위시리스트 스토어 미러, 낙관적 토글) · `components/RestockButton.vue`.
`ProductDetailView` 는 **상품 전체 품절**(`totalStock === 0`)일 때만 버튼을 보여준다(부분 품절은 다른 옵션을
살 수 있으니 대상 아님 — 이벤트 기준과 일치). 로그아웃 시 `clearRestock()`(남의 신청 상태 누수 방지).
알림 설정 화면은 `NotificationType.values()` 를 순회하므로 **RESTOCK 토글이 자동 노출**된다(코드 무수정).

> **브라우저 검증**(품절→신청→재입고→알림 관통):
> 1. 상품 하나를 **전체 품절**로 만든다(관리자: 모든 옵션 재고 0, 또는 재고만큼 주문). 상품 상세에

> 2. 그 버튼으로 신청 → 다시 누르면 "신청됨(취소)" 토글. 다른 계정으로도 신청.
> 3. **관리자로 그 상품 재고를 채운다**(옵션 편집에서 재고>0 저장) → 신청한 계정(들)에 **재입고 토스트**가
>    뜨고 벨 뱃지가 오르는지(← 실제 이커머스의 주 경로). 알림 클릭 시 그 상품 상세로 이동.
> 4. **주문취소/반품 경로**로도: 품절 상품의 마지막 재고를 주문했다가 취소 → 재입고 알림이 오는지.
> 5. 발송 후 **재신청이 필요한지**(일회성이라 알림 받으면 구독이 비워짐 — 다시 품절되면 다시 신청).
> 6. 마이페이지 **알림 설정에서 "재입고 알림" 끄고** 재입고 → 안 오는지. 켜면 오는지(opt-out 존중).
> 7. 로그아웃 → 다른 계정에서 이전 신청 버튼 상태가 **안 새는지**.
