## 1. 묶음4-1 — 캐시 직렬화 Jackson3 이전 (`a55e795`)

### "deprecated 한 줄 교체"가 아니라 **Jackson2→3 마이그레이션**이었다
7/20 §10-A는 이걸 "생성자 `[removal]` 경고 정리"로 봤다. 실제로 파보니:

- `GenericJackson2JsonRedisSerializer`는 **생성자만이 아니라 클래스 전체**가 `@Deprecated(since=4.0, forRemoval)`.
  빌더(`.builder().objectMapper(mapper).build()`)로 바꿔도 **클래스 자체가 deprecated라 경고가 안 사라진다.**
- 원인: Spring Data Redis 4.1이 **Jackson 2 → Jackson 3(`tools.jackson`)** 로 이동. 대체품은
  `GenericJacksonJsonRedisSerializer`(Jackson3 기반). classpath에 Jackson2(2.21)·Jackson3(3.1.4)가 **둘 다** 있다.

→ 스코프가 커져 사용자에게 확인받고 **Jackson3 이전 + 배포 시 캐시 flush**로 결정.

### ⚠ 와이어 포맷이 바뀐다 — 실측으로 잡았다 (중요)
처음엔 Jackson2 빌더의 `defaultTyping(true)`로 바꿨는데, **바이트 동일성 테스트를 돌리자 실패**했다.

| 대상 | Jackson2(기존) `activateDefaultTyping(EVERYTHING, As.PROPERTY)` | Jackson3 / 빌더 defaultTyping |
|---|---|---|
| 객체 | `{"@class":"…", …}` | 같음 |
| **스칼라**(UUID/Instant/enum) | `["java.util.UUID","019f…"]` (WRAPPER_ARRAY 폴백) | `"019f…"` (타입 안 감쌈) |

두 포맷은 **양방향 역직렬화가 다 실패**(`MismatchedInputException`). 7/20 §10-A가 경고한
"기존 캐시와 포맷이 달라지면 배포 직후 역직렬화 실패"가 정확히 이거다.

→ Jackson3는 더 깔끔한 포맷(스칼라 비래핑)을 쓰되, **기존 캐시와 호환 안 되니 배포 시 flush**한다(TTL 60초).
`enableDefaultTyping(BasicPolymorphicTypeValidator.allowIfBaseType(Object))` — 기존과 같은 신뢰 모델(내부 캐시).

### 검증 (실측)
- **단위**: `CacheSerializationTest`(왕복) — `PageResponse<ProductResponse>`가 record/enum/Instant/UUID까지
  타입 잃지 않고 복원. 전체 백엔드 **139개 통과**(0 실패).
- **라이브**(dev :8081, **격리 Redis db3** — 운영 db0 무영향): `products:list`·`notices:list` 둘 다
  miss→hit **200**, 저장값이 신 포맷(`{"@class":"…PageResponse","content":["…List12",[…]]}`, 스칼라 비래핑) 확인.
  운영 :8080 health 200 유지, 운영 캐시 무손상.
- **왜 격리 db인가**: 공유 Redis라 신 포맷 dev가 구 포맷 키를 만지면 운영(구 jar)이 500날 수 있다.
  실제 배포는 "구 jar 중지→flush→신 jar"라 공존이 없지만, dev 검증은 공존을 만들어서 격리했다.

## 2. 묶음4-2 — 닉네임 유니크 + 빈 카테고리 삭제 (`339efc2`, **V6**)

정책 결정이 필요해 사용자에게 확인: **닉네임 유니크 강제** / **빈 카테고리만 삭제 허용**.

### 2-1. 닉네임 유니크
- **왜**: 닉네임이 `review.author`·`orders.buyer_nickname`에 **스냅샷**되는데(7/20 §8-2), 중복 허용이면
  동명이인이 생겨 관리자 화면에서 누구 주문/리뷰인지 못 가린다.
- 앱: 가입(`AuthService.signup`)·변경(`MemberService.changeNickname`)에 `existsByNickname` 검사.
  변경은 `existsByNicknameAndIdNot`로 **본인 제외**(같은 값 재저장 허용).
- DB: **V6** `ALTER TABLE member ADD CONSTRAINT uk_member_nickname UNIQUE`. 앱 검사와 별개로,
  존재검사-저장 사이의 경합(TOCTOU) **최종 방어선**. `DUPLICATE_NICKNAME("MEMBER-409")` 신설.
- **사전 확인**(WORKING-AGREEMENTS §2-5): 제약 추가 전 기존 중복 조회 → **0건**(회원 4명 전부 고유). 안전.
- **빈 DB 검증**(§2-2): `esptest` 스키마를 비우고 앱 기동 → V1→V6 **순차 적용, validate 통과**,
  `UK_MEMBER_NICKNAME`(NICKNAME)·기존 login_id 유니크(LOGIN_ID) 각각 다른 컬럼 확인(중복 제약 아님).

### 2-2. 빈 카테고리 삭제
- **왜**: 기존엔 카테고리 삭제 기능이 **아예 없었다**(`CategoryService`에 delete 없음). `product.category_id`는
  `nullable=false` FK라 소속 상품이 있으면 삭제 불가여야 한다.
- `DELETE /api/categories/{id}`(ADMIN) 신설. 서비스에서 `existsByCategoryId`로 먼저 걸러
  **`CATEGORY_IN_USE(409)`** — FK 위반 500 대신 의미 있는 에러. 없으면 삭제.
- 보안: 기존 상품 매처와 같은 명시적 패턴으로 `DELETE /api/categories/*` → `hasRole("ADMIN")`.
  **권한 통합테스트**(401/403/200 + 사용중 409) — 권한 규칙은 단위 테스트로 안 잡힌다(7/20 §7-2 계열).
- 프론트: 카테고리 관리 화면에 삭제 버튼(사용중이면 서버 메시지 그대로 노출).

### 2-3. ⚠ V6는 공유 espdb에 이미 적용됨
통합 테스트를 돌리는 순간 Flyway가 공유 espdb에 V6를 적용한다. **UNIQUE 제약은 순수 추가와 달라**
운영(구 jar)에서도 즉시 중복 닉네임 가입/변경이 막힌다(기존 중복 0건이라 데이터는 안 깨지고, 구 jar는
깔끔한 409 대신 500을 냄, 되돌릴 수 있음). 사용자 승인 후 적용. **배포하면 신 jar가 409로 정리된다.**

## 4. 묶음4-3 — HSTS / mkcert (코드 변경 없음, **제안만**)

sudo/nginx(git 밖)라 실행은 사용자 몫. 조사 결과 + 결정:
- **HSTS는 IP 접속(192.168.50.36)엔 무효** — RFC 6797 §2.3상 브라우저는 **IP 리터럴에 HSTS를 저장하지 않는다.**
  지금 넣어도 실효 없음 → **도메인+Let's Encrypt 도입 시점**에 켠다(그때 `max-age` 짧게 시작).
- **mkcert도 미룸** — 경고를 없애려면 **접속하는 각 클라이언트 신뢰 저장소에 루트 CA를 설치**해야 한다
  (서버에만 깔면 소용없음). 연습 단계에서 self-signed 1회 클릭 대비 CA 배포 부담이 커서 도메인 때 공인 인증서로.
- **대신 지금 넣을 것**: IP에서도 유효한 보안 헤더 3종(`X-Content-Type-Options: nosniff`,
  `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`).
  적용 준비된 제안·명령을 `scratchpad/nginx-security-headers-proposal.md`에 둠(사용자가 nginx reload).
  ⚠ nginx `add_header` 상속 함정: location에 자체 add_header가 있으면(`/uploads/`·`/static/`) server 레벨이 무시됨.

## 5. 배포 주의사항 (다음에 배포할 때 반드시)

1. **캐시 flush 필수**(묶음4-1). 신·구 포맷 비호환 → 배포 절차:
   ```bash
   # 신 jar 배포 직후(또는 직전 구 jar 중지 후):
   redis-cli DEL "$(redis-cli KEYS 'products:list*')" "$(redis-cli KEYS 'notices:list*')" 2>/dev/null
   # 또는 두 키 패턴만 지우기. 안 하면 배포 직후 최대 60초간 구 포맷 값이 500.
   ```
2. **V6는 espdb에 이미 적용됨**(§2-3). 배포는 스키마가 앞서 있으니 안전. 신 jar가 중복 닉네임을 409로 정리.
3. **응답 계약 변경**(`OrderResponse.buyerNickname`): 백·프론트 **함께 배포**(§WORKING-AGREEMENTS 5). 백엔드 먼저.
4. 배포 후 운영(https://192.168.50.36)에서 상품 목록·주문 상세·카테고리 삭제·닉네임 중복 실제 확인.
